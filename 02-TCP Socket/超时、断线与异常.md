# 超时、断线与异常

## 学习目标

学完本章后，你应该能够：

- 区分“暂时没有数据”“等待超时”“对端正常关闭”和“连接发生错误”。
- 在 Linux 和 Windows 上为接收、发送设置超时，并正确判断超时返回值。
- 理解为什么拔网线后连接不一定马上报错，以及如何用心跳发现“无声断线”。
- 正确处理 `recv()` 返回 `0`、连接复位、发送失败和系统调用被打断。
- 设计不会快速重试、不会复用坏 Socket、不会泄漏资源的重连流程。
- 用统一的清理路径关闭连接，并区分 `shutdown()` 与 `close()`/`closesocket()`。

## 1. 先建立一个判断模型

网络程序等待数据时，结果通常属于下面四类之一：

| 结果     | 典型表现                                                    | 说明                  | 是否应该立刻重连        |
| ------ | ------------------------------------------------------- | ------------------- | --------------- |
| 收到数据   | `recv()` 返回正数                                           | 本次得到若干字节，可能只是半条消息   | 否               |
| 对端有序关闭 | `recv()` 返回 `0`                                         | 对端发送了 FIN，不会再发送字节   | 通常是，取决于业务       |
| 等待超时   | Linux 为 `EAGAIN/EWOULDBLOCK`，Windows 常见为 `WSAETIMEDOUT` | 在规定时间内没有等到结果；连接未必已断 | 不要立即连续重连，先按协议处理 |
| 发生错误   | `ECONNRESET`、`EPIPE` 等                                  | 当前操作失败，连接通常不能继续使用   | 关闭旧连接后再决定是否重连   |

可以把一次读操作画成：

~~~text
调用 recv()
    |
    +-- 返回 > 0：处理收到的字节
    +-- 返回 0：对端正常关闭
    +-- 返回“超时”：本轮没有等到数据
    +-- 返回其他错误：记录错误并结束当前连接
~~~

最重要的初学者原则是：**超时不等于断线，`recv() == 0` 也不等于收到空字符串。** 超时只描述“这次等待没有在规定时间内完成”；而 `0` 是 TCP 明确告诉你的“对端发送方向已经结束”。

## 2. 超时到底解决什么问题

默认 Socket 通常是阻塞模式。下面的调用可能一直等下去：

~~~c
int n = recv(sock, buffer, sizeof buffer, 0);
~~~

如果对端既不发送数据，也不关闭连接，线程就会一直睡在 `recv()`。这不一定是 CPU 空转，但会带来两个问题：

1. 一个线程可能长时间无法处理其他任务。
2. 网络路径已经失效时，程序没有机会进入重连或告警逻辑。

超时给等待设置了上限：例如“最多等 5 秒”。时间到了以后，程序可以记录日志、发送心跳、取消请求或关闭连接。

超时需要和协议一起设计。HTTP 请求、登录认证、文件传输和心跳不应机械地使用同一个值：

| 场景 | 常见思路 |
| --- | --- |
| 建立连接 | 几秒到几十秒，取决于网络环境 |
| 普通请求响应 | 比业务正常响应时间稍长，例如 5～30 秒 |
| 心跳响应 | 通常较短，并允许少量连续丢失 |
| 大文件发送 | 不宜只靠一个很短的总超时，可按进度和空闲时间判断 |

## 3. 接收和发送超时

### 3.1 Linux/POSIX：`SO_RCVTIMEO` 和 `SO_SNDTIMEO`

Linux 使用 `struct timeval` 表示超时：

~~~c
#include <sys/socket.h>
#include <sys/time.h>

struct timeval timeout;
timeout.tv_sec = 5;
timeout.tv_usec = 0;

setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO,
           &timeout, sizeof timeout);  // recv 最多等 5 秒
setsockopt(fd, SOL_SOCKET, SO_SNDTIMEO,
           &timeout, sizeof timeout);  // send 阻塞最多等 5 秒
~~~

如果接收超时，阻塞式 `recv()` 通常返回 `-1`，并把 `errno` 设为 `EAGAIN` 或 `EWOULDBLOCK`。这两个值在许多 Linux 系统上数值相同，但代码最好都判断：

~~~c
ssize_t n = recv(fd, buffer, sizeof buffer, 0);
if (n > 0) {
    // 处理 n 个字节
} else if (n == 0) {
    // 对端正常关闭
} else if (errno == EAGAIN || errno == EWOULDBLOCK) {
    // 本次等待超时；不要把它当成断线
} else if (errno == EINTR) {
    // 被信号打断，可以重新调用 recv()
} else {
    // 其他错误，当前连接通常应结束
}
~~~

注意：`SO_RCVTIMEO` 是 Socket 选项，不是“整个请求的总耗时”。如果程序先读三次，每次最多 5 秒，那么总等待时间可能接近 15 秒。需要总超时时，应使用 `clock_gettime()` 记录截止时间，或用 `select()`/`poll()` 统一管理事件。

### 3.2 Windows Winsock：超时单位是毫秒

Windows 用 `DWORD` 表示毫秒：

~~~c
#include <winsock2.h>

DWORD timeout_ms = 5000;
setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO,
           (const char *)&timeout_ms, sizeof timeout_ms);
setsockopt(sock, SOL_SOCKET, SO_SNDTIMEO,
           (const char *)&timeout_ms, sizeof timeout_ms);
~~~

超时时，`recv()` 或 `send()` 返回 `SOCKET_ERROR`。常见错误码是 `WSAETIMEDOUT`；在非阻塞模式或配合事件循环时，也可能看到 `WSAEWOULDBLOCK`。因此应先取一次错误码再判断：

~~~c
int n = recv(sock, buffer, (int)sizeof buffer, 0);
if (n > 0) {
    // 处理 n 个字节
} else if (n == 0) {
    // 对端正常关闭
} else {
    int error = WSAGetLastError();
    if (error == WSAETIMEDOUT || error == WSAEWOULDBLOCK) {
        // 本次等待没有及时完成
    } else if (error == WSAEINTR) {
        // 被系统事件打断，可以重试
    } else {
        // 其他错误，当前连接通常应结束
    }
}
~~~

Windows 的超时参数和 Linux 不同：Linux 是秒与微秒组成的结构体，Windows 是毫秒整数；不要把一个平台的写法直接复制到另一个平台。

## 4. 连接超时：为什么不能只设置 `SO_SNDTIMEO`

`connect()` 是建立连接的操作。很多初学者会以为设置 `SO_SNDTIMEO` 就能限制 `connect()`，但在不同系统和场景下并不可靠。更可控的做法是：

1. 把 Socket 临时设为非阻塞。
2. 调用 `connect()`。
3. 如果返回“正在进行”（Linux 的 `EINPROGRESS`、Windows 的 `WSAEWOULDBLOCK`），用 `select()` 等待可写或异常事件。
4. 等待结束后用 `getsockopt(..., SO_ERROR, ...)` 检查连接最终是否成功。
5. 恢复阻塞模式，或者继续按非阻塞方式使用。

“可写”不一定代表连接成功；它只表示连接状态已经有结果，必须再检查 `SO_ERROR`。

### 4.1 Linux：带截止时间的 `connect()` 核心代码

~~~c
#include <errno.h>
#include <fcntl.h>
#include <sys/select.h>
#include <sys/socket.h>

static int connect_with_timeout(int fd,
                                const struct sockaddr *address,
                                socklen_t address_len,
                                int timeout_seconds) {
    int old_flags = fcntl(fd, F_GETFL, 0);
    if (old_flags == -1 || fcntl(fd, F_SETFL,
                                  old_flags | O_NONBLOCK) == -1) {
        return -1;
    }

    int result = connect(fd, address, address_len);
    if (result == 0) {
        fcntl(fd, F_SETFL, old_flags);
        return 0;
    }
    if (errno != EINPROGRESS) {
        fcntl(fd, F_SETFL, old_flags);
        return -1;
    }

    fd_set writable;
    FD_ZERO(&writable);
    FD_SET(fd, &writable);
    struct timeval timeout = { timeout_seconds, 0 };
    result = select(fd + 1, NULL, &writable, NULL, &timeout);
    if (result <= 0) {
        fcntl(fd, F_SETFL, old_flags);
        if (result == 0) errno = ETIMEDOUT;
        return -1;
    }

    int socket_error = 0;
    socklen_t error_len = sizeof socket_error;
    if (getsockopt(fd, SOL_SOCKET, SO_ERROR,
                   &socket_error, &error_len) == -1) {
        fcntl(fd, F_SETFL, old_flags);
        return -1;
    }
    fcntl(fd, F_SETFL, old_flags);
    if (socket_error != 0) {
        errno = socket_error;
        return -1;
    }
    return 0;
}
~~~

这段代码只展示连接控制逻辑。失败时调用者应关闭这个 fd；不要把连接失败的 fd 放回重连循环继续使用。

### 4.2 Windows：带截止时间的 `connect()` 核心代码

~~~c
#include <winsock2.h>

static int connect_with_timeout(SOCKET sock,
                                const struct sockaddr *address,
                                int address_len,
                                long timeout_seconds) {
    u_long nonblocking = 1;
    if (ioctlsocket(sock, FIONBIO, &nonblocking) == SOCKET_ERROR) {
        return -1;
    }

    int result = connect(sock, address, address_len);
    if (result == 0) {
        nonblocking = 0;
        ioctlsocket(sock, FIONBIO, &nonblocking);
        return 0;
    }

    int error = WSAGetLastError();
    if (error != WSAEWOULDBLOCK && error != WSAEINPROGRESS) {
        nonblocking = 0;
        ioctlsocket(sock, FIONBIO, &nonblocking);
        WSASetLastError(error);
        return -1;
    }

    fd_set writable;
    fd_set excepted;
    FD_ZERO(&writable);
    FD_ZERO(&excepted);
    FD_SET(sock, &writable);
    FD_SET(sock, &excepted);
    struct timeval timeout = { timeout_seconds, 0 };
    result = select(0, NULL, &writable, &excepted, &timeout);
    if (result <= 0) {
        nonblocking = 0;
        ioctlsocket(sock, FIONBIO, &nonblocking);
        if (result == 0) WSASetLastError(WSAETIMEDOUT);
        return -1;
    }

    int socket_error = 0;
    int error_len = sizeof socket_error;
    if (getsockopt(sock, SOL_SOCKET, SO_ERROR,
                   (char *)&socket_error, &error_len) == SOCKET_ERROR) {
        nonblocking = 0;
        ioctlsocket(sock, FIONBIO, &nonblocking);
        return -1;
    }
    nonblocking = 0;
    ioctlsocket(sock, FIONBIO, &nonblocking);
    if (socket_error != 0) {
        WSASetLastError(socket_error);
        return -1;
    }
    return 0;
}
~~~

Windows 的 `select()` 第一个参数被忽略，所以传 `0`；Linux 则需要传“最大文件描述符加一”。这正是平台接口差异之一。

### 4.3 用“打电话”理解连接超时

如果上面的代码暂时看不懂，可以先把 `connect()` 想象成打电话：

- **阻塞式 `connect()`**：拨号后一直拿着电话等，直到接通或失败。
- **非阻塞式 `connect()`**：开始拨号后立即返回，程序可以自己决定最多等几秒。
- **`select()`**：等待“拨号结果”。
- **`SO_ERROR`**：确认到底是接通了，还是对方拒接或网络失败。

#### 为什么 `SO_SNDTIMEO` 不可靠？

`SO_SNDTIMEO` 主要控制 `send()`：

~~~c
send(sock, data, length, 0);
~~~

它表示发送缓冲区满时，`send()` 最多等待多长时间。

但 `connect()` 不是普通的 `send()`。它需要完成 TCP 三次握手，还可能等待地址解析、ARP、路由以及防火墙丢包后的 TCP 重试。不同系统对 `SO_SNDTIMEO` 是否影响 `connect()` 的行为并不完全一致，所以不能依赖它实现可靠的连接超时。

#### 这 5 步到底在做什么？

**第一步：设置非阻塞。**

~~~text
普通模式：
connect() ──────────────── 一直等待

非阻塞模式：
connect() ── 立即返回“还在连接”
~~~

Linux 使用 `fcntl()` 设置 `O_NONBLOCK`；Windows 使用 `ioctlsocket()` 设置 `FIONBIO`。设置成功后，`connect()` 不会因为等待握手而长时间卡住。

**第二步：调用 `connect()`。**

非阻塞模式下，连接可能还没有完成：

- Linux 可能返回 `-1`，并且 `errno == EINPROGRESS`。
- Windows 可能返回 `SOCKET_ERROR`，并且 `WSAGetLastError() == WSAEWOULDBLOCK`。

这通常不是最终失败，而是“连接还在进行，请稍后检查结果”。

**第三步：用 `select()` 等待。**

~~~text
最多等待 5 秒
    |
    +-- 连接完成
    +-- 连接失败
    +-- 5 秒内没有结果：超时
~~~

Linux 的 `select()` 第一个参数传最大文件描述符加一；Windows 会忽略第一个参数，所以通常传 `0`。如果 `select()` 返回 `0`，说明规定时间内没有连接结果，应关闭这个 Socket，并在需要时重新创建 Socket。

**第四步：为什么“可写”不一定是成功？**

`select()` 把连接 Socket 放进“可写集合”，只表示连接过程已经有结果：

~~~text
服务器端口存在：connect 完成 → Socket 可写
服务器端口拒绝：connect 失败 → Socket 也可能显示可写
~~~

因此，“可写”只能说明“现在可以查询连接结果”，不能直接说明连接成功。

**第五步：用 `SO_ERROR` 查询最终结果。**

~~~c
int error = 0;
socklen_t length = sizeof(error);

getsockopt(fd, SOL_SOCKET, SO_ERROR,
           &error, &length);

if (error == 0) {
    // 连接成功
} else {
    // 连接失败；error 是具体原因
}
~~~

常见结果可以这样理解：

~~~text
error == 0              连接成功
error == ECONNREFUSED   服务器拒绝连接
error == ETIMEDOUT      连接超时
~~~

Windows 也使用 `getsockopt(..., SO_ERROR, ...)`，只是 Socket 类型、错误码类型和错误获取函数不同。

#### 把整个流程串起来

~~~text
创建 Socket
    ↓
设置为非阻塞
    ↓
调用 connect()
    ↓
连接立即成功？ ── 是 ──→ 连接完成
    ↓ 否
得到 EINPROGRESS / WSAEWOULDBLOCK
    ↓
select() 最多等待 5 秒
    ↓
select() 返回 0？ ── 是 ──→ 超时，关闭 Socket
    ↓ 否
getsockopt(SO_ERROR)
    ↓
SO_ERROR == 0？ ── 是 ──→ 连接成功
    ↓ 否
连接失败，关闭 Socket
~~~

可以把本节先记成一句话：**不要让 `connect()` 自己无限等待。先把 Socket 设置为非阻塞，让 `connect()` 尽快返回；如果连接还在进行，就用 `select()` 等待一段时间；`select()` 返回后，必须用 `SO_ERROR` 判断究竟是成功还是失败。**

### 4.4 Windows 关键函数逐项拆解

这一小节集中解释 `connect_with_timeout()` 中最容易看不懂的三组代码。先记住它们的分工：

~~~text
ioctlsocket()   改变 Socket 的阻塞/非阻塞模式
fd_set          告诉 select() 要观察哪些 Socket
select()        在限定时间内等待 Socket 状态发生变化
getsockopt()    查询 connect() 最终成功还是失败
~~~

#### 4.4.1 `ioctlsocket(sock, FIONBIO, &nonblocking)`

`ioctlsocket()` 是 Windows Winsock 用来修改 Socket 工作方式的函数：

~~~c
u_long nonblocking = 1;
int result = ioctlsocket(sock, FIONBIO, &nonblocking);
~~~

三个参数分别表示：

| 参数 | 含义 |
| --- | --- |
| `sock` | 要设置的 Socket |
| `FIONBIO` | 设置是否使用非阻塞 I/O |
| `&nonblocking` | 指向设置值的指针，函数从这里读取 `0` 或非零值 |

设置值的含义：

~~~c
u_long nonblocking = 1;
ioctlsocket(sock, FIONBIO, &nonblocking); // 开启非阻塞

nonblocking = 0;
ioctlsocket(sock, FIONBIO, &nonblocking); // 恢复阻塞
~~~

阻塞和非阻塞的区别可以这样理解：

~~~text
阻塞模式：
recv() 当前没有数据 → 等到数据到达、对端关闭或发生错误

非阻塞模式：
recv() 当前没有数据 → 立即返回 SOCKET_ERROR，
                        WSAGetLastError() 通常为 WSAEWOULDBLOCK
~~~

同样，非阻塞 `connect()` 如果不能立即完成，也会先返回 `SOCKET_ERROR`。此时若错误码为 `WSAEWOULDBLOCK` 或 `WSAEINPROGRESS`，通常表示“连接仍在进行”，而不是最终失败。

`ioctlsocket()` 的返回值必须检查：

~~~c
if (ioctlsocket(sock, FIONBIO, &nonblocking) == SOCKET_ERROR) {
    printf("ioctlsocket failed: %d\n", WSAGetLastError());
}
~~~

返回 `0` 表示设置成功；返回 `SOCKET_ERROR` 表示设置失败。

#### 4.4.2 `fd_set`、`FD_ZERO()` 和 `FD_SET()`

`fd_set` 可以先理解为一个“Socket 集合”。下面的代码创建两个集合：

~~~c
fd_set writable;
fd_set excepted;

FD_ZERO(&writable);
FD_ZERO(&excepted);

FD_SET(sock, &writable);
FD_SET(sock, &excepted);
~~~

每一行的作用是：

| 代码 | 作用 |
| --- | --- |
| `fd_set writable` | 创建一个集合，用来观察哪些 Socket 变得可写 |
| `fd_set excepted` | 创建一个集合，用来观察哪些 Socket 出现异常状态 |
| `FD_ZERO(&writable)` | 清空可写集合，避免其中存在未初始化内容 |
| `FD_ZERO(&excepted)` | 清空异常集合 |
| `FD_SET(sock, &writable)` | 把 `sock` 加入可写观察集合 |
| `FD_SET(sock, &excepted)` | 把 `sock` 加入异常观察集合 |

执行完成后，可以把集合想象成：

~~~text
writable = { sock }
excepted = { sock }
~~~

也就是告诉 `select()`：“请观察这个 `sock` 的可写状态和异常状态。”

注意，`select()` 会修改这些集合，只留下本次真正就绪的 Socket。调用返回后可用 `FD_ISSET()` 检查：

~~~c
if (FD_ISSET(sock, &writable)) {
    // sock 出现在本次可写结果中
}

if (FD_ISSET(sock, &excepted)) {
    // sock 出现在本次异常结果中
}
~~~

如果还要再次调用 `select()`，通常要重新执行 `FD_ZERO()` 和 `FD_SET()`，不能假设上一次传入的集合保持不变。

#### 4.4.3 `select()` 到底等待什么

Windows 示例中的调用是：

~~~c
result = select(0, NULL, &writable, &excepted, &timeout);
~~~

参数含义如下：

| 参数 | 含义 |
| --- | --- |
| `0` | Windows 忽略第一个参数；Linux 则要求传最大文件描述符加一 |
| `NULL` | 不观察可读事件 |
| `&writable` | 观察集合中的 Socket 是否可写 |
| `&excepted` | 观察集合中的 Socket 是否出现异常状态 |
| `&timeout` | 最多等待多长时间 |

在非阻塞连接场景中，`select()` 的作用是：

> 最多等待指定时间，直到连接过程产生结果。

它的返回值有三类：

| 返回值 | 含义 |
| --- | --- |
| `result > 0` | 至少有一个 Socket 状态就绪；连接过程已有结果 |
| `result == 0` | 等待时间耗尽，发生连接超时 |
| `result == SOCKET_ERROR` | `select()` 调用本身失败，使用 `WSAGetLastError()` 获取原因 |

在 Windows 的非阻塞连接流程中，成功通常体现在可写集合，失败可能体现在异常集合；但不能只根据这两个集合断定最终结果。最稳妥的做法仍然是继续查询 `SO_ERROR`。

这里的“可写”并不等于“连接一定成功”，而是“连接过程已经有结果，可以查询了”：

~~~text
连接成功 ──→ select() 返回
连接失败 ──→ select() 也可能返回
                    ↓
          都要查询 SO_ERROR
~~~

#### 4.4.4 `getsockopt(..., SO_ERROR, ...)`

代码如下：

~~~c
int socket_error = 0;
int error_len = sizeof socket_error;

if (getsockopt(sock, SOL_SOCKET, SO_ERROR,
               (char *)&socket_error,
               &error_len) == SOCKET_ERROR) {
    // getsockopt() 查询操作本身失败
}
~~~

这次查询的完整意思是：“读取 `sock` 在 Socket 层保存的待处理错误，并写入 `socket_error`。”

| 参数 | 含义 |
| --- | --- |
| `sock` | 要查询的 Socket |
| `SOL_SOCKET` | 查询 Socket 层的通用选项 |
| `SO_ERROR` | 查询 Socket 当前保存的错误结果 |
| `(char *)&socket_error` | 用来接收错误码的内存地址；强制转换是为了匹配 Winsock 参数类型 |
| `&error_len` | 调用前表示接收空间大小，调用后表示实际返回长度 |

这里存在两层完全不同的错误，必须区分：

~~~text
第一层：getsockopt() 是否查询成功
    返回 SOCKET_ERROR → 查询操作本身失败
    使用 WSAGetLastError() 查看原因

第二层：connect() 的最终结果是什么
    socket_error == 0  → 连接成功
    socket_error != 0  → 连接失败，该值就是失败原因
~~~

推荐写成清楚的分支：

~~~c
int socket_error = 0;
int error_len = sizeof socket_error;

if (getsockopt(sock, SOL_SOCKET, SO_ERROR,
               (char *)&socket_error,
               &error_len) == SOCKET_ERROR) {
    printf("getsockopt failed: %d\n", WSAGetLastError());
    // 查询操作失败
} else if (socket_error != 0) {
    printf("connect failed: %d\n", socket_error);
    // 查询成功，但 connect() 失败
} else {
    printf("connect success\n");
    // 查询成功，并且 connect() 成功
}
~~~

#### 4.4.5 把四个概念连起来

~~~text
ioctlsocket(FIONBIO, 1)
    把 Socket 设置为非阻塞
        ↓
connect()
    立即成功，或返回“仍在连接”
        ↓
FD_ZERO() + FD_SET()
    准备要观察的 Socket 集合
        ↓
select()
    在超时时间内等待连接过程产生结果
        ↓
getsockopt(SO_ERROR)
    查询最终是连接成功还是连接失败
        ↓
ioctlsocket(FIONBIO, 0)
    按本例需要恢复阻塞模式
~~~

最后再记住一项资源规则：`connect_with_timeout()` 返回失败时，旧 Socket 通常不应继续使用。这个辅助函数没有调用 `closesocket()`，因此调用者负责关闭失败的 Socket，并在重连时重新调用 `socket()` 创建新 Socket。

## 5. 断线：有序关闭、复位和半关闭

### 5.1 对端正常关闭：`recv() == 0`

当对端调用 `close()`，或调用 `shutdown(..., SHUT_WR/SD_SEND)` 结束发送方向，本端最终会看到：

~~~c
int n = recv(sock, buffer, sizeof buffer, 0);
if (n == 0) {
    // 对端不会再发送新字节
}
~~~

这不是错误，也不是“收到长度为 0 的消息”。本端应完成当前协议允许的收尾工作，然后关闭自己的 Socket。若业务需要自动恢复，可以在关闭旧 Socket 后发起一次新的连接。

### 5.2 异常断开：RST 和发送错误

如果对端进程崩溃、强制终止或连接状态不再匹配，内核可能发送 TCP RST（复位）。本端常见表现是：

| 操作 | Linux 常见错误 | Windows 常见错误 |
| --- | --- | --- |
| `recv()` | `ECONNRESET`、`ETIMEDOUT` | `WSAECONNRESET`、`WSAETIMEDOUT` |
| `send()` | `EPIPE`、`ECONNRESET`、`ENOTCONN` | `WSAECONNRESET`、`WSAENOTCONN` |
| `connect()` | `ECONNREFUSED`、`ETIMEDOUT` | `WSAECONNREFUSED`、`WSAETIMEDOUT` |

错误码只对“刚刚失败的那一次 API 调用”有效。Windows 要在失败后马上保存 `WSAGetLastError()` 的结果；Linux 也应尽快读取 `errno`，不要先调用可能覆盖错误状态的函数。

### 5.3 Linux 的 `SIGPIPE`

Linux 向已经关闭的连接发送时，除了 `send()` 返回 `EPIPE`，进程还可能收到 `SIGPIPE`，默认行为是直接结束进程。学习程序可以在启动时忽略它：

~~~c
#include <signal.h>

signal(SIGPIPE, SIG_IGN);
~~~

然后仍然检查 `send()` 返回值。忽略信号并不会修复网络，只是让程序能够记录错误、关闭当前连接，而不是整个进程退出。Windows 没有这个 Linux 默认行为，但也必须检查 `send()` 是否返回 `SOCKET_ERROR`。

### 5.4 `shutdown()` 和关闭函数的职责

~~~text
shutdown()                  close()/closesocket()
改变发送/接收方向             释放本地 Socket 句柄
可用于半关闭                   最终应调用
不是资源释放函数               不能省略
~~~

Linux：

~~~c
shutdown(fd, SHUT_WR);   // 只结束发送方向，还可以 recv()
shutdown(fd, SHUT_RDWR); // 两个方向都结束
close(fd);               // 释放文件描述符
~~~

Windows：

~~~c
shutdown(sock, SD_SEND);
shutdown(sock, SD_BOTH);
closesocket(sock);
~~~

Windows 程序最后还要调用与 `WSAStartup()` 配对的 `WSACleanup()`。`closesocket()` 关闭一个 Socket，`WSACleanup()` 清理 Winsock 库；两者不能互相替代。

### 5.5 C 语言里的“异常”如何处理

本章示例使用 C 语言。C 没有像 Java 或 Python 那样的内置 `try/catch` 网络异常机制；Socket API 通常通过返回值报告结果：

~~~text
先检查返回值
    ↓
失败时立刻保存 errno/WSAGetLastError()
    ↓
根据错误类型决定：重试、等待、关闭连接或报告配置错误
~~~

不要用“忽略错误”代替异常处理。例如 `send()` 失败后仍然继续解析“发送成功”的状态，往往会让后面的业务数据建立在错误连接之上。把 API 错误转换成程序自己的状态（如 `CONNECTED`、`TIMED_OUT`、`CLOSED`、`FAILED`），主循环会更容易读懂。

## 6. “拔网线”为什么不一定马上报错

TCP 只有在收到报文、发送数据失败，或 TCP/应用层探测得到结果时，才能确认路径出了问题。如果双方都没有发送任何数据，连接可能暂时仍显示为 `ESTABLISHED`：

~~~text
连接已建立
    ↓ 拔网线/路由器断电
没有 FIN，也没有 RST 到达
    ↓
双方暂时没有可观察的事件
    ↓
下一次发送、心跳或 keepalive 才发现问题
~~~

因此，“本地 Socket 还存在”不等于“对端在线”。常用的存活检测有两种：

1. **应用层心跳**：定期发送 `PING`，要求对端在期限内回复 `PONG`。可以携带连接编号和时间戳，能同时确认应用程序仍然工作。
2. **TCP keepalive**：由内核发送探测报文。适合兜底，但默认间隔在不同系统上可能很长，不能直接当作实时心跳。

简单心跳状态机：

~~~text
每隔 heartbeat_interval 发送 PING
        ↓
等待 PONG，记录 last_pong_time
        ↓
超过 failure_threshold 个周期没有 PONG
        ↓
停止使用旧 Socket → 关闭 → 按退避策略重连
~~~

心跳本身也要遵守消息边界，例如每行一条 `PING\n`。不要在一个线程写心跳、另一个线程随意写业务数据，却没有规定并发发送的顺序；否则字节可能交错，应该使用发送锁或单独的发送队列。

## 7. Linux 示例：带接收超时的客户端

下面的客户端连接本机 `127.0.0.1:8080`，设置 5 秒接收超时，发送一行文本并等待回显。它故意把“超时”和“断线”分开打印。请先运行仓库中的回显服务器，或使用 [[发送与接收数据]] 中的 Linux 服务端。

保存为 `timeout_client_linux.c`：

~~~c
#include <arpa/inet.h>
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/time.h>
#include <unistd.h>

static int send_all(int fd, const char *data, size_t length) {
    size_t sent = 0;
    while (sent < length) {
        ssize_t n = send(fd, data + sent, length - sent, 0);
        if (n > 0) {
            sent += (size_t)n;
        } else if (n < 0 && errno == EINTR) {
            continue;
        } else {
            perror("send");
            return -1;
        }
    }
    return 0;
}

int main(void) {
    signal(SIGPIPE, SIG_IGN);

    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd == -1) {
        perror("socket");
        return 1;
    }

    struct timeval timeout = {5, 0};
    if (setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO,
                   &timeout, sizeof timeout) == -1) {
        perror("setsockopt(SO_RCVTIMEO)");
        close(fd);
        return 1;
    }

    struct sockaddr_in server = {0};
    server.sin_family = AF_INET;
    server.sin_port = htons(8080);
    if (inet_pton(AF_INET, "127.0.0.1", &server.sin_addr) != 1) {
        fprintf(stderr, "invalid server address\n");
        close(fd);
        return 1;
    }

    if (connect(fd, (struct sockaddr *)&server, sizeof server) == -1) {
        perror("connect");
        close(fd);
        return 1;
    }

    const char message[] = "hello with timeout\n";
    if (send_all(fd, message, strlen(message)) == -1) {
        close(fd);
        return 1;
    }

    char buffer[1024];
    ssize_t n = recv(fd, buffer, sizeof buffer - 1, 0);
    int receive_error = errno; // recv 失败后立刻保存 errno
    if (n > 0) {
        buffer[n] = '\0';
        printf("received: %s", buffer);
    } else if (n == 0) {
        printf("peer closed normally (recv == 0)\n");
    } else if (receive_error == EAGAIN || receive_error == EWOULDBLOCK) {
        printf("receive timeout: no data within 5 seconds\n");
    } else if (receive_error == EINTR) {
        printf("recv interrupted; retry according to the protocol\n");
    } else {
        errno = receive_error;
        perror("recv");
    }

    shutdown(fd, SHUT_RDWR);
    close(fd);
    return n < 0 && receive_error != EAGAIN &&
           receive_error != EWOULDBLOCK ? 1 : 0;
}
~~~

编译和运行：

~~~bash
gcc -Wall -Wextra -Wpedantic -std=c11 timeout_client_linux.c -o timeout_client_linux
./timeout_client_linux
~~~

如果服务端收到请求后故意等待超过 5 秒，客户端会打印超时；如果服务端先关闭连接，客户端会打印 `recv == 0`。这两种现象的处理路径不同。

## 8. Windows 示例：Winsock 接收超时客户端

保存为 `timeout_client_windows.c`：

~~~c
#include <winsock2.h>
#include <stdio.h>
#include <string.h>

#pragma comment(lib, "Ws2_32.lib")

static int send_all(SOCKET sock, const char *data, int length) {
    int sent = 0;
    while (sent < length) {
        int n = send(sock, data + sent, length - sent, 0);
        if (n > 0) {
            sent += n;
        } else {
            printf("send failed: %d\n", WSAGetLastError());
            return -1;
        }
    }
    return 0;
}

int main(void) {
    WSADATA wsa_data;
    int result = WSAStartup(MAKEWORD(2, 2), &wsa_data);
    if (result != 0) {
        printf("WSAStartup failed: %d\n", result);
        return 1;
    }

    SOCKET sock = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (sock == INVALID_SOCKET) {
        printf("socket failed: %d\n", WSAGetLastError());
        WSACleanup();
        return 1;
    }

    DWORD timeout_ms = 5000;
    if (setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO,
                   (const char *)&timeout_ms,
                   sizeof timeout_ms) == SOCKET_ERROR) {
        printf("setsockopt failed: %d\n", WSAGetLastError());
        closesocket(sock);
        WSACleanup();
        return 1;
    }

    struct sockaddr_in server = {0};
    server.sin_family = AF_INET;
    server.sin_port = htons(8080);
    server.sin_addr.s_addr = htonl(INADDR_LOOPBACK);

    if (connect(sock, (const struct sockaddr *)&server,
                sizeof server) == SOCKET_ERROR) {
        printf("connect failed: %d\n", WSAGetLastError());
        closesocket(sock);
        WSACleanup();
        return 1;
    }

    const char message[] = "hello with timeout\n";
    if (send_all(sock, message, (int)strlen(message)) == -1) {
        closesocket(sock);
        WSACleanup();
        return 1;
    }

    char buffer[1024];
    int n = recv(sock, buffer, (int)sizeof buffer - 1, 0);
    int receive_error = WSAGetLastError();
    if (n > 0) {
        buffer[n] = '\0';
        printf("received: %s", buffer);
    } else if (n == 0) {
        printf("peer closed normally (recv == 0)\n");
    } else if (receive_error == WSAETIMEDOUT ||
               receive_error == WSAEWOULDBLOCK) {
        printf("receive timeout: no data within 5 seconds\n");
    } else if (receive_error == WSAEINTR) {
        printf("recv interrupted; retry according to the protocol\n");
    } else {
        printf("recv failed: %d\n", receive_error);
    }

    shutdown(sock, SD_BOTH);
    closesocket(sock);
    WSACleanup();
    return n == SOCKET_ERROR &&
           receive_error != WSAETIMEDOUT &&
           receive_error != WSAEWOULDBLOCK ? 1 : 0;
}
~~~

## 9. 可靠的收发错误处理模板

### 9.1 Linux `recv()` 模板

~~~c
for (;;) {
    ssize_t n = recv(fd, buffer, sizeof buffer, 0);
    if (n > 0) {
        handle_bytes(buffer, (size_t)n);
        continue;
    }
    if (n == 0) {
        log_info("peer closed");
        break;
    }
    if (errno == EINTR) {
        continue;                 // 系统调用被信号打断
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        log_info("receive timeout");
        break;                    // 也可以发心跳后继续
    }
    log_error("recv failed", errno);
    break;
}
~~~

### 9.2 Windows `recv()` 模板

~~~c
for (;;) {
    int n = recv(sock, buffer, (int)sizeof buffer, 0);
    if (n > 0) {
        handle_bytes(buffer, n);
        continue;
    }
    if (n == 0) {
        printf("peer closed\n");
        break;
    }

    int error = WSAGetLastError();
    if (error == WSAEINTR) {
        continue;
    }
    if (error == WSAETIMEDOUT || error == WSAEWOULDBLOCK) {
        printf("receive timeout\n");
        break;
    }
    printf("recv failed: %d\n", error);
    break;
}
~~~

`send()` 也应循环处理部分发送；一旦遇到不可恢复错误，应停止使用当前 Socket。不要在错误发生后继续调用 `send()`，也不要把同一个坏 Socket 交给“下一次重连”。

## 10. 重连策略：关闭旧连接，再创建新连接

### 10.1 最小流程

~~~text
发现超时/断线/不可恢复错误
        ↓
停止读写旧 Socket
        ↓
shutdown（可选）→ close/closesocket
        ↓
等待一段时间
        ↓
重新 socket() → connect()
        ↓
成功：重新认证/恢复会话
失败：继续退避，直到达到上限
~~~

必须先关闭旧 Socket。连接失败后继续拿旧句柄尝试，容易让状态混乱；而且一个 Socket 的本地地址、非阻塞状态和错误状态可能已经不适合下一次连接。

### 10.2 指数退避和抖动

不要写成“失败后立即 `while` 循环重连”。服务器不可用时，这会造成：

- 客户端消耗 CPU 和临时端口；
- 大量客户端同时冲击服务器，形成重连风暴；
- 日志刷屏，真正的问题反而难以发现。

可使用指数退避：

~~~text
第 1 次失败：等待 1 秒
第 2 次失败：等待 2 秒
第 3 次失败：等待 4 秒
第 4 次失败：等待 8 秒
后续：最多等待 30 秒
~~~

实际应用通常再加入随机抖动，例如在 `[0, 当前等待时间]` 中随机取一个值，让大量客户端不要在同一时刻再次连接。连接成功后把失败计数清零。

### 10.3 重试前先判断错误是否值得重试

| 错误/情况 | 是否通常重试 | 说明 |
| --- | --- | --- |
| 临时超时 | 可以 | 先按协议重试或发送心跳 |
| `ECONNREFUSED`/`WSAECONNREFUSED` | 可以退避重试 | 服务端可能尚未启动 |
| 名称解析失败、地址格式错误 | 不应盲目重试 | 先修配置 |
| 认证失败、协议版本不兼容 | 通常不应立即重试 | 重试也不会改变原因 |
| 对端正常关闭 | 视业务 | 长连接可重连，单次请求可能直接结束 |

重连成功后不要假设服务器还记得旧会话。通常需要重新登录、重新订阅、重新发送未完成请求。若请求可能已经在服务器执行，再次发送前必须考虑幂等性和请求编号，否则可能造成重复写入等业务问题。

## 11. 资源清理：让每条错误路径都能退出

初学者常见的问题是：成功路径能 `close()`，错误路径却直接 `return`，久而久之出现文件描述符或 Socket 泄漏。建议采用“创建一个资源，就明确谁负责清理”的结构。

Linux 伪代码：

~~~c
int fd = socket(...);
if (fd == -1) return 1;

if (connect(fd, ...) == -1) {
    int saved_errno = errno;  // 需要时先保存
    close(fd);
    errno = saved_errno;
    return 1;
}

// ... 使用 fd ...
shutdown(fd, SHUT_RDWR);      // 可选
close(fd);                     // 必须
~~~

Windows 伪代码：

~~~c
SOCKET sock = socket(...);
if (sock == INVALID_SOCKET) {
    WSACleanup();
    return 1;
}

if (connect(sock, ...) == SOCKET_ERROR) {
    int error = WSAGetLastError();
    closesocket(sock);
    WSACleanup();
    printf("connect failed: %d\n", error);
    return 1;
}

// ... 使用 sock ...
shutdown(sock, SD_BOTH);      // 可选
closesocket(sock);            // 必须
WSACleanup();
~~~

服务器还要区分监听 Socket 和连接 Socket：客户端断线时只关闭 `client_fd`/`client_sock`，不能误关监听 Socket，否则服务器就无法接受下一位客户端。

## 12. 常见错误与排查顺序

遇到“卡住”或“连接断了”，按下面顺序检查，比盲目修改代码有效：

1. **确认卡在哪个 API**：是 `connect()`、`accept()`、`recv()` 还是 `send()`？在调用前后打印日志。
2. **记录返回值和错误码**：Linux 记录 `errno`，Windows 记录 `WSAGetLastError()`；不要只打印“失败”。
3. **判断是不是超时**：超时表示本轮等待未完成，不一定是连接已坏。
4. **检查对端是否有序关闭**：`recv() == 0` 时，结束当前会话，不要继续等数据。
5. **检查地址和端口**：确认服务端已经 `listen()`，客户端连接的是正确的 IP 与端口。
6. **检查防火墙和监听地址**：`127.0.0.1` 只允许本机；局域网访问还需要正确的绑定地址和防火墙规则。
7. **确认旧 Socket 已关闭**：重连前不要复用失败的 Socket。

Linux：

~~~bash
ss -ltnp | grep 8080
~~~

Windows PowerShell：

~~~powershell
Get-NetTCPConnection -LocalPort 8080 -ErrorAction SilentlyContinue
netstat -ano | Select-String ":8080"
~~~

如果 `recv()` 长时间没有返回，而你没有设置超时，这可能只是阻塞模式的正常行为。若两端都在等待对方先发送，就会形成应用层死锁：协议必须明确“谁先发请求、谁再回复”。

## 13. 实践

### 实践一：观察真正的超时

修改回显服务器：收到客户端连接后先 `sleep(10)`，再读取或回复数据。客户端把接收超时设为 5 秒，观察它打印“超时”，而不是“对端关闭”。Linux 可用 `sleep(10)`；Windows 可用 `Sleep(10000)`（需要包含 `<windows.h>`）。

### 实践二：观察正常断线

服务端启动后，客户端连接但不发送数据，随后直接退出。服务端的 `recv()` 最终应返回 `0`。记录这一点：这是 FIN 导致的正常关闭，不是超时。

### 实践三：观察重连退避

让客户端连接一个没有服务的端口，打印每次失败时间和等待时间。实现最大 30 秒的指数退避，并在连接成功后将计数归零。

### 实践四：实现简单心跳

约定每 5 秒发送 `PING\n`，服务端回复 `PONG\n`。连续 3 个周期未收到 `PONG` 就关闭旧连接并重连。为发送数据加锁，确保心跳和业务消息不会互相交错。

### 实践五：检查每条错误路径

故意让 `socket()`、`connect()`、`setsockopt()` 或 `recv()` 失败，确认 Linux 使用 `close()`，Windows 使用 `closesocket()`，且 Windows 程序最后调用 `WSACleanup()`。可以配合任务管理器或 Linux 的 `/proc/<pid>/fd` 观察是否不断产生未释放句柄。

## 检查

- [ ] 我能说明超时与断线不是同一个概念。
- [ ] 我知道 `recv() > 0`、`recv() == 0`、超时和其他错误分别表示什么。
- [ ] 我能在 Linux 中识别 `EAGAIN/EWOULDBLOCK`，在 Windows 中识别 `WSAETIMEDOUT/WSAEWOULDBLOCK`。
- [ ] 我知道 Linux 的 `SO_RCVTIMEO` 使用 `timeval`，Windows 使用毫秒 `DWORD`。
- [ ] 我知道连接超时应使用非阻塞 `connect()` + `select()`，并检查 `SO_ERROR`。
- [ ] 我知道 Linux 发送到断线连接可能触发 `SIGPIPE`，并会检查 `send()` 返回值。
- [ ] 我不会在错误发生后继续使用旧 Socket。
- [ ] 我能画出“关闭旧连接 → 退避等待 → 创建新连接”的重连流程。
- [ ] 我知道重连可能需要重新认证，并会考虑请求幂等性。
- [ ] 我能区分 `shutdown()` 与 `close()`/`closesocket()` 的职责。
- [ ] 我能保证成功和失败路径都释放资源。
