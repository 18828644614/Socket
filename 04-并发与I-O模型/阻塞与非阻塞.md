# 阻塞与非阻塞

> 本章面向完全新手。你不需要提前理解“内核”“线程”“就绪事件”等术语，下面会逐个解释。代码沿用本知识库的 C 语言路线，并提供 Windows 原生与 Linux/WSL 的运行方法。
>
> 这一章要解决的问题是：**网络数据还没到时，一次 Socket 调用会怎样？程序接下来应该做什么？**

## 0. 先规划：这一章学什么，按什么顺序学

### 0.1 学完以后，你应该能做什么

- 看懂程序为什么停在 `accept()`、`connect()`、`recv()` 或 `send()`。
- 区分阻塞、非阻塞、超时，并知道它们解决的问题。
- 根据调用结果区分“收到字节”“暂时不能操作”“对端结束发送”“真正出错”。
- 在 Linux 和 Windows 上设置 Socket 的非阻塞模式。
- 运行同一组实验，观察三种等待方式的差异。
- 解释为什么非阻塞代码需要保存进度，以及为什么无限重试会浪费 CPU。
- 带着明确的问题进入 [[线程与进程模型]]、[[I-O多路复用]] 和 [[事件循环]]。

## 1. 前置知识：从零看懂网络程序

### 1.1 最少需要哪些 C 语言知识

先不要求你会写复杂 C 程序，但需要理解这些写法：

| 写法 | 通俗解释 | 示例 |
| --- | --- | --- |
| 变量 | 存放某个值的名字 | `int n = 0;` |
| 函数调用 | 请某段已有代码做事，再拿到返回结果 | `n = recv(...);` |
| 条件分支 | 根据结果决定接下来走哪条路 | `if (n > 0) ...` |
| 循环 | 重复一段操作 | `for (;;) ...` 表示一直循环 |
| 字符数组 | 一块连续内存，可以存放多个字节 | `char buf[128];` |
| 指针 | 指向一块内存的位置 | 把 `buf` 传给 `recv()`，让它把字节写进去 |
| `sizeof` | 求某个对象占多少字节 | `sizeof buf` 在此处是 128 |
| `return` / `break` / `continue` | 退出函数 / 退出循环 / 开始下一轮循环 | 错误后 `break`，暂时没数据则安排稍后重试 |
| 头文件 | 提供函数和类型的声明 | `#include <stdio.h>` |
| 宏和条件编译 | 编译时选择代码，不是在运行时做判断 | `#ifdef _WIN32` 选择 Windows 版本 |

如果这张表仍然陌生，先看 [[C语言网络编程基础]] 和 [[Socket编程环境]]。本章完整示例中的平台辅助函数可以先理解用途，再逐行研究。

### 1.2 IP、端口、TCP 和 Socket 是什么

- **IP 地址**：帮助找到一台网络设备。本章使用 `127.0.0.1`，表示“当前这台电脑自己”，也叫回环地址。
- **端口**：帮助找到这台设备上的某个网络服务。本章使用 `19090`。
- **TCP**：提供可靠、按顺序传输字节的协议。它不替你划分应用消息，也不保证每次网络操作马上完成。
- **Socket**：程序使用操作系统网络能力的入口。可以把它暂时理解为“一个可以发送、接收数据的通信端点”。
- **服务器**：先在固定地址等待连接的一方。
- **客户端**：主动向服务器发起连接的一方。连接建立后，双方都能发送和接收。

如果这些概念不熟悉，按顺序看 [[IP地址与端口]] → [[TCP与UDP概念]] → [[Socket基础]]。

### 1.3 一个 TCP 服务器的基本顺序

```text
服务器：socket → bind → listen → accept → recv/send → close
客户端：socket → connect             → send/recv → close
```

| 函数 | 做什么 | 本章重点 |
| --- | --- | --- |
| `socket()` | 创建通信入口 | 新建 Socket 默认通常是阻塞模式 |
| `bind()` | 绑定本地地址与端口 | 端口占用会失败 |
| `listen()` | 把 Socket 变成监听入口 | 此调用本身不是“停在那里等待一个客户端” |
| `accept()` | 从待接受的连接中取出一个，返回新的 Socket | 没有待接受的连接时可能等待 |
| `connect()` | 发起连接 | 建立连接需要时间，可能等待或返回正在进行 |
| `recv()` | 从本机接收缓冲区取字节 | 没有字节可取时怎么办 |
| `send()` | 把字节交给本机发送机制 | 本机暂时没有空间接收字节时怎么办 |
| `close()` / `closesocket()` | 释放 Socket | Linux 和 Windows 使用不同函数 |

注意服务器有两类 Socket：

```text
监听 Socket：负责接新连接
    │ accept()
    ├── 已连接 Socket A：与客户端 A 收发
    └── 已连接 Socket B：与客户端 B 收发
```

**监听 Socket 和已连接 Socket 是不同对象。** 想让某个连接上的 `recv()` 非阻塞，就要为那个已连接 Socket 设置模式。不要假设 `accept()` 返回的新 Socket 在所有平台上都会继承监听 Socket 的模式。

### 1.4 必须先接受的事实：TCP 传的是字节流

“字节”是计算机存储数据的基本单位。英文 `hello` 在本章使用的编码中是 5 字节；中文的字符数通常不等于字节数。

客户端两次发送 `he` 和 `llo\n`，服务器可能分多次读到，也可能一次读到 `hello\n`。**一次 `send()` 不对应一次 `recv()`。**

本章只观察读到的字节，不尝试解析完整业务消息。需要“读到一整行”时，还要累积数据并寻找换行符，见 [[字节、编码与数据边界]] 和 [[消息边界与拆包]]。

## 2. 等待发生在哪里：程序、线程和缓冲区

### 2.1 程序、进程、线程、CPU

- **程序**：你编译出来的可执行文件，包含“要做什么”的指令。
- **进程**：程序启动后的一次运行实例，有自己的资源。服务器和客户端通常是两个进程。
- **线程**：进程中执行代码的一条路线。先把本章服务器看作只有一条执行路线。
- **CPU**：执行代码的硬件。同一时刻，某条线程可能正在运行，也可能在等。
- **调度**：操作系统决定让哪条线程使用 CPU。

所以，“这个线程卡在 `recv()`”不代表整台电脑停了，也不代表所有线程都停了。同一线程在调用返回前不能执行后面的语句；其他线程和进程仍然可以运行。

### 2.2 操作系统和内核

操作系统管理 CPU、内存、文件与网络。**内核**是负责这些底层工作的重要部分。

应用程序通常不能直接操作网卡和 TCP 的内部状态，而是通过接口请操作系统帮忙。在 Linux 中，`recv()` 等操作最终涉及系统调用；Windows 通过 Winsock 提供网络接口。初学阶段理解“应用代码与操作系统之间有边界”即可。

### 2.3 缓冲区：先暂存，后取走

**缓冲区**就是临时存放数据的地方。这里至少要区分三处：

```text
客户端的应用内存 "hello\n"
        │ send()
        ▼
客户端的操作系统发送缓冲区
        │ TCP 通过网络传输
        ▼
服务器的操作系统接收缓冲区
        │ recv()
        ▼
服务器的应用内存 char buf[128]
```

`send()` 成功通常表示本机接受了若干字节供发送，**不代表对方程序已经处理了这些字节**。要确认业务处理完成，需要对方返回应用层响应。

`recv()` 读取本机已经收到的字节。如果当前没有数据，操作系统必须按 Socket 的模式决定：让这条线程等，还是立即告诉它“现在取不到”。

### 2.4 用取快递理解，但不要把比喻当成定义

- 阻塞：来到柜台，包裹没到，于是在那里等到能取或出现其他结果。
- 非阻塞：来到柜台，包裹没到，柜台马上告诉你“现在没有”；何时再来由你安排。
- 带超时的等待：最多等一段时间，到点还没有就返回。

包裹已经在柜台时，三种方式都可能立即拿到。**阻塞模式允许等待，不是每次都必须等待。**

## 3. 阻塞：条件不满足时，让当前线程等待

### 3.1 最小例子

以下片段假定 `s` 已经是一个连接成功的 TCP Socket；它不是可以独立运行的完整程序。

```c
char buf[128];
puts("before recv");
int n = (int)recv(s, buf, sizeof buf, 0);
puts("after recv");
```

如果 `s` 是阻塞模式，对方一直不发送也不结束发送，通常只看到 `before recv`。程序正在等接收结果，还没运行到第二个 `puts()`。

当有字节可读、对端结束发送、发生错误或设置的超时到期时，调用可能返回。这里的 `(int)` 只用于本章的 128 字节小缓冲区：Linux 的正式返回类型是 `ssize_t`，Windows 是 `int`，写大数据程序时应保留正确类型。

### 3.2 四个调用分别在等什么

| 调用 | 阻塞模式下可能等待的条件 | 可以怎样观察 |
| --- | --- | --- |
| `accept()` | 有一个可以接受的连接 | 只启动服务器，不启动客户端 |
| `connect()` | 连接建立成功或失败 | 连接受网络和对端状态影响，本机连接通常很快 |
| `recv()` | 有可读字节、收到结束发送通知，或出现错误 | 客户端连接后暂停发送 |
| `send()` | 本机能接受待发送字节，或出现错误 | 对方不读且持续大量发送时可能出现；小消息不易观察 |

`recv()` 不要求你指定的缓冲区装满。例如最多读 128 字节，当前只有 3 字节可读时，普通 TCP 接收可以返回 3。这里默认标志参数为 `0`；特殊标志如 `MSG_WAITALL` 会改变等待行为，本章不用它。

`listen(backlog)` 的队列长度也不是应用层并发处理能力。服务器即使允许其他连接排队，也可能一次只服务一个客户端。

### 3.3 阻塞是否浪费 CPU

通常等待网络时，操作系统会让这条线程休眠，等条件变化再唤醒。它不会为了“等数据”一直高速执行你的 C 循环。

但是它仍然占用线程等资源，而且这条执行路线无法同时做后续工作。一个单线程服务器如果正在等客户端 A 发数据，就不能继续执行代码去服务客户端 B。

因此，阻塞很适合流程简单、连接少的入门程序；连接多时，要考虑 [[线程与进程模型]] 或事件驱动的组织方式。

### 3.4 阻塞与同步不是同一个问题

**阻塞/非阻塞**主要问：条件暂时不满足时，这次调用会不会让当前线程等？

**同步/异步**主要问：操作的完成结果是怎样交付给程序的？在本章直接使用 `recv()` 的方式中，程序在调用返回时拿到读到的字节数或失败结果；某些异步接口则先提交操作，稍后通过完成通知拿到结果。

因此，把 Socket 设成非阻塞，并不会自动获得“后台替你读完，再通知你”的功能。你仍要主动调用、检查结果、保存进度。这些词在不同语言框架中可能有不同约定，阅读文档时要看具体接口的语义。

## 4. 非阻塞：现在不能做，就马上告诉你

### 4.1 它改变的是调用行为，不是网络速度

非阻塞模式下，当某次操作暂时无法进行，调用会立即返回一个“暂时不能完成”的结果。它不会让数据凭空出现，也不会让连接自动建立得更快。

“立即”是指不为了等待这项 I/O 条件而停住线程，不是承诺任何函数都花零时间。执行函数、复制字节和系统调度仍然需要时间。

```text
调用非阻塞 recv()
  ├─ 有字节：返回本次读到的字节数
  ├─ 对端结束发送且已无剩余字节：返回 0
  ├─ 当前没有字节、连接也没结束：返回失败形式 + 暂时不可读错误码
  └─ 真正的错误：返回失败形式 + 对应错误码
```

### 4.2 TCP `recv()` 的判断表

以下讨论读取长度大于 0 的 TCP Socket。UDP 不使用“`recv() == 0` 表示对端结束发送”这条规则，零长度 UDP 数据报也可以是合法数据。

| 情况 | Linux/POSIX | Windows Winsock | 下一步 |
| --- | --- | --- | --- |
| 读到字节 | `n > 0` | `n > 0` | 处理前 `n` 字节，按协议累积 |
| 对端有序结束发送 | `n == 0` | `n == 0` | 结束读取；是否继续发送由协议决定 |
| 非阻塞下暂时无数据 | `n == -1` 且 `errno` 为 `EAGAIN` 或 `EWOULDBLOCK` | `n == SOCKET_ERROR` 且错误为 `WSAEWOULDBLOCK` | 保留连接，安排稍后再读 |
| 被可处理的中断打断 | `EINTR` | 不是直接照搬 Linux 的信号处理模型 | 按程序退出/取消策略决定是否重试 |
| 真正失败 | 如 `ECONNRESET` | 如 `WSAECONNRESET` | 记录错误并处理连接 |

`EAGAIN` 可以理解为“稍后再试”；`EWOULDBLOCK` 可以理解为“这一步本来需要等待”。它们是错误码的名字。在 Linux 上常常数值相同，但可移植代码仍应判断两者。

**不要只看返回值为负数就认定断线。也不要把 `recv() == 0` 当成“再等一会儿”。**

补充一个容易漏掉的顺序：对端先发送数据再正常结束发送时，你通常先读完剩余字节，然后才读到 `0`。收到 FIN 不代表本机缓冲区里的数据被丢掉。TCP 还允许“发送方向结束、接收方向继续”，见 [[连接生命周期]]。

### 4.3 正确的处理形状

Linux 片段，`s` 是已设为非阻塞的连接：

```c
char buf[128];
ssize_t n = recv(s, buf, sizeof buf, 0);
if (n > 0) {
    /* 处理 buf 中的前 n 字节 */
} else if (n == 0) {
    /* 对端已结束发送，退出读取流程 */
} else {
    int err = errno;  /* 失败后立即保存，不要先调用别的函数 */
    if (err == EAGAIN || err == EWOULDBLOCK) {
        /* 保留连接，交回调度流程，稍后再读 */
    } else if (err == EINTR) {
        /* 检查退出/取消要求；本章简单示例会重试 */
    } else {
        /* 真正的读取错误，记录并结束连接 */
    }
}
```

Windows 的对应错误获取函数是 `WSAGetLastError()`，不是 `errno`，也不应直接用 `GetLastError()` 代替。**错误码只在调用报告失败之后读取**；成功调用后读到的旧错误码不能拿来判断本次结果。

### 4.4 最大陷阱：把等待变成忙等

错误示范：

```c
/* 不要照着写：没有数据也不断调用，可能耗掉一个 CPU 核心。 */
for (;;) {
    if (recv(s, buf, sizeof buf, 0) < 0) {
        continue;
    }
}
```

**忙等**就是在条件没变化时，仍快速重复检查。线程看似“不阻塞”，却用大量 CPU 做没有进展的工作。这个例子还把所有错误混在一起，连断线等情况都没有正确退出。

三种改进方式：

| 方式 | 思路 | 适用范围 |
| --- | --- | --- |
| 间隔轮询 | 每次没数据就睡一小会儿再试 | 本章教学对照；简单但有延迟，连接多时效率差 |
| 等待就绪 | 请操作系统等到“可以尝试读/写”，再调用 | `select/poll/epoll` 等，后续重点 |
| 重新安排任务 | 本连接没进展时先处理其他连接或任务 | 需要事件循环或其他调度结构 |

“轮询”就是重复询问状态。睡 500 毫秒轮询会减少空转，却可能让刚到的数据再等接近 500 毫秒才被处理，另外还受调度影响。不要把这个教学做法当成高性能服务器方案。

### 阶段 D 检查（一）

- [ ] 能分别处理正数、零、暂时不可读和真正错误。
- [ ] 能解释为什么 `EAGAIN` 一般不应立即关闭连接。
- [ ] 知道只在失败后取错误码，并立即保存。
- [ ] 能解释忙等的 CPU 开销，以及睡眠轮询的延迟。

## 5. 怎样设置模式：Linux 与 Windows

### 5.1 Linux：保留原有标志，再设置 `O_NONBLOCK`

**文件描述符**是 Linux 用来标识已打开资源的整数，Socket 也使用它。例如变量 `fd` 可能是 3、4、5；这些数字不是端口号。深入内容见 [[文件描述符]]。

`fcntl()` 可以查询或修改描述符的属性。“标志位”是一组用整数中的不同二进制位记录的开关。

```c
#include <fcntl.h>

int set_nonblocking(int fd, int enabled) {
    int flags = fcntl(fd, F_GETFL, 0);  /* 先读取现有开关 */
    if (flags == -1) return -1;
    if (enabled) {
        flags |= O_NONBLOCK;           /* 打开非阻塞开关 */
    } else {
        flags &= ~O_NONBLOCK;          /* 只关闭非阻塞开关 */
    }
    return fcntl(fd, F_SETFL, flags);   /* 成功返回 0，失败返回 -1 */
}
```

`|=` 表示保留原有位并加上指定开关；`&= ~` 表示保留其他位，只清除指定开关。不要直接用 `F_SETFL, O_NONBLOCK` 覆盖所有已有状态标志。

调用后必须检查结果：

```c
if (set_nonblocking(fd, 1) == -1) {
    perror("set_nonblocking");
    /* 结束或走清理路径，不要假装已经切换成功 */
}
```

这些是 Linux/POSIX 接口，不能直接复制到 Windows 原生 Winsock 程序中。在 Linux，多处共享同一底层打开对象时，修改模式还可能影响其他使用者；入门时让一个连接只有一个明确的管理者。

### 5.2 Windows：`ioctlsocket()` 与 `FIONBIO`

Windows 的 Socket 类型是 `SOCKET`，不应强行存进 `int`，尤其在 64 位程序中。

```c
#include <winsock2.h>

int set_nonblocking(SOCKET s, int enabled) {
    u_long mode = enabled ? 1UL : 0UL;
    return ioctlsocket(s, FIONBIO, &mode);
    /* 成功为 0，失败为 SOCKET_ERROR，之后读取 WSAGetLastError() */
}
```

- `mode = 1`：设为非阻塞。
- `mode = 0`：恢复阻塞。本章仅使用普通 Winsock Socket；高级事件接口可能还有额外模式约束。
- `&mode`：把变量的地址传给函数。

完整程序还需要先 `WSAStartup()` 初始化，最后 `WSACleanup()` 清理。关闭 Socket 用 `closesocket()`。

### 5.3 两个平台快速对照

| 项目 | Linux | Windows |
| --- | --- | --- |
| Socket 类型 | `int` | `SOCKET` |
| 创建/接受失败 | `-1` | `INVALID_SOCKET` |
| 普通收发失败 | `-1` | `SOCKET_ERROR` |
| 取错误码 | `errno`，包含 `<errno.h>` | `WSAGetLastError()` |
| 暂时不可操作 | `EAGAIN/EWOULDBLOCK` | `WSAEWOULDBLOCK` |
| 切换模式 | `fcntl()` | `ioctlsocket()` |
| 关闭 | `close()` | `closesocket()` |
| 初始化网络库 | 普通例子不需专门初始化 | `WSAStartup()` |
| 编译链接 | 普通 Socket 示例通常无需额外网络库 | GCC/MinGW 加 `-lws2_32` |

- [ ] 能解释为什么 Linux 要先 `F_GETFL` 再 `F_SETFL`。
- [ ] 不把 Windows 的 `SOCKET` 当普通 `int`。
- [ ] 会检查设置模式是否成功。
- [ ] 会对 `accept()` 得到的新连接明确设置模式。

## 6. 超时：这次等待最多持续多久

### 6.1 三种行为放在一起比较

假定连接有效，对方不发数据也不关闭：

| 做法 | 当前无数据时 | 线程的表现 | 程序何时重新获得控制 |
| --- | --- | --- | --- |
| 阻塞 `recv()`，未设超时 | 等接收结果 | 通常休眠 | 数据、结束发送或错误到来；可能等很久 |
| 非阻塞 `recv()` | 返回暂时不可读 | 很快回到调用方 | 本次调用返回后 |
| 有期限地等可读 | 等可读状态或期限 | 等待期间通常休眠 | 就绪、超时或错误 |

**超时是一条等待策略，不是所有平台共有的第三种 Socket 模式。** 可以给某些阻塞操作设置超时，也可以在非阻塞 Socket 外面管理等待期限。

### 6.2 方法一：设置收发超时选项

以下片段都假定 `s` 是已建立的阻塞连接。

Linux 的接收超时：

```c
#include <sys/time.h>
struct timeval limit = {0};
limit.tv_sec = 2;
if (setsockopt(s, SOL_SOCKET, SO_RCVTIMEO,
               &limit, sizeof limit) == -1) {
    perror("SO_RCVTIMEO");
}
```

Windows 的接收超时：

```c
DWORD limit_ms = 2000;
if (setsockopt(s, SOL_SOCKET, SO_RCVTIMEO,
               (const char *)&limit_ms, sizeof limit_ms) == SOCKET_ERROR) {
    printf("SO_RCVTIMEO failed: %d\n", WSAGetLastError());
}
```

Linux 参数是 `timeval`（秒与微秒），Windows 参数是毫秒数。发送超时选项叫 `SO_SNDTIMEO`。两者都要检查设置结果。

需要记住的边界：

- Linux 阻塞 `recv()` 在超时且没有读到字节时，通常返回 `-1` 和 `EAGAIN/EWOULDBLOCK`；这个错误码也用于非阻塞的“暂时没数据”，必须结合当前模式解释。
- Windows 阻塞接收超时常见错误为 `WSAETIMEDOUT`。Winsock 文档指出阻塞接收超时后连接状态不确定，应该关闭 Socket。不要把 Linux 上的超时恢复方式原样搬过去。
- 这类选项针对支持它的 Socket 操作，不是“整段程序两秒后强行停止”。`SO_RCVTIMEO` 不是控制 `select()` 等待时间的办法。
- 把这些选项设置成零通常表示禁用该超时，不是“零秒后报超时”。
- 本章只把它们用于已连接 Socket 的收发。连接超时、监听接受超时的支持与行为有平台差异，不能简单照搬。
- 非阻塞 Socket 没数据时本来就立即返回，设一个接收超时不会让它自动等两秒。

更多平台错误和恢复策略见 [[超时、断线与异常]]。下面实验选择“非阻塞 + 等待可读”，让两平台的对照更清楚。

### 6.3 方法二：先 `select()` 等可读，再 `recv()`

**就绪**表示“现在值得尝试某项操作”。可读可能表示有字节，也可能表示对端结束发送或错误，需要调用 `recv()` 才知道结果。

`select()` 让操作系统观察一组 Socket，并等待可读、可写或其他指定状态。本章只观察一个 Socket 的可读状态。

```text
把连接设为非阻塞
       │
       ▼
select：最多等两秒，看连接是否可读
       ├─ 超时：本轮无可读事件，应用决定继续等还是结束
       ├─ 失败：检查错误
       └─ 可读：调用 recv，再判断字节 / EOF / 暂时不可读 / 错误
```

`select()` **可以阻塞等待**。它与“非阻塞 Socket”组合完全合理：等待事件时让线程休息，实际读写时避免意外长时间等待。

就绪通知不是数据本身，也不是永远有效的保证。其他线程可能读走数据，状态也可能改变。所以即使 `select()` 说可读，仍然保留 `recv()` 的暂时不可读分支。

#### 6.3.1 先纠正一个容易形成的理解：谁实现了非阻塞？

“用 `select()` 实现非阻塞”是一个常见但容易误导新手的说法。实际要把下面三个部分分开：

| 部分 | 它负责什么 | 它不负责什么 |
| --- | --- | --- |
| `fcntl(..., O_NONBLOCK)` / `ioctlsocket(..., FIONBIO, ...)` | 改变某个 Socket 的操作模式，让暂时无法完成的收发立即返回 | 不告诉你什么时候再试比较合适 |
| `select()` | 等待一组 Socket 的就绪状态，告诉你哪些可以尝试操作 | 不修改 Socket 模式，也不替你读取数据 |
| 你的循环与连接状态 | 根据就绪结果调用收发、保存未完成数据、安排下一轮 | 不会因为用了某个 API 就自动写好 |

可以把三者的合作说成：

> 非阻塞模式保证“这次读不到，就把控制权还给我”；`select()` 帮我选择“什么时候、对哪个连接再试”；循环负责持续推进这些连接。

**仅仅调用一次 `select()`，不会让后面的阻塞 `recv()` 永久变成非阻塞。** `select()` 也不会新建线程或后台替你接收消息。

#### 6.3.2 为什么允许 `select()` 等待，却要避免 `recv()` 长时间等待？

假设只有一条服务器线程，要处理客户端 A、B、C。

如果直接顺序调用阻塞接收：

```text
recv(A) → recv(B) → recv(C)
   ↑
   A 一直不发送，线程停在这里。
   即使 B 已有数据，也还没有机会运行到 recv(B)。
```

改为一起观察：

```text
select 同时观察 A、B、C
   │
   ├─ 都没事件：让线程休息，等待其中任意一个发生变化
   │
   └─ B 可读：返回，处理 B
                   │
                   └─ 做完有限工作，重新观察 A、B、C
```

区别在于：前一种是在等**指定的 A**，后一种是在等**这一组里任何可处理的连接**。

线程在 `select()` 等待期间，同样不能执行后面的代码。但是当这组连接都暂时无事可做时，休眠能避免浪费 CPU；某个连接就绪后，又能让程序获得处理它的机会。

如果服务器还要每隔一秒检查定时任务，可以让本次 `select()` 最多等到最近的任务期限，再在返回后处理定时任务。若其他线程需要立即唤醒事件循环，还需额外的唤醒机制；`select()` 不会自动知道应用内存里的任务已经变化。

#### 6.3.3 一次调用从进入到返回，究竟发生了什么？

从应用程序的视角，可以按下面的顺序理解：

1. 程序准备一个集合，写入“我关心 A、B、C 是否可读”。
2. 程序调用 `select()`，并指定最长等待时间。
3. 操作系统检查这些 Socket 当前是否满足所请求的就绪条件。
4. 如果已有 Socket 就绪，通常可以直接返回，不必等满时间。
5. 如果没有就绪且允许等待，当前线程进入等待；这时应用代码不再自行高速询问每个 Socket。
6. 数据到达、连接结束等事件使相关状态变化时，系统可以唤醒等待线程，再检查就绪条件。超时或错误也可以使调用返回。
7. 成功返回时，传入的集合被改成“这次实际就绪的对象”，程序逐个检查并处理。

这是一条理解接口的主线，不是所有操作系统内部代码的逐行实现。

在 Linux 中，可以进一步想象：内核检查描述符对应资源的就绪条件，并借助等待队列等机制安排休眠和唤醒。这里的**等待队列**记录谁在等待某种状态变化，不是保存聊天消息的队列。系统会协调检查状态与登记等待，避免简单的“检查之后刚好来数据”造成遗漏唤醒。

这里还要区分两件事：

- `select()` 的等待通常不是在内核里不停高速扫描来消耗 CPU。
- 但它在调用和返回过程中仍有集合处理、状态检查与扫描成本；程序也要找出哪些对象就绪。传统 `select()` 不会因此变成处理海量连接的零成本接口。

当连接很多时，集合容量、扫描和复制等成本就需要关注，这也是后续学习 `poll/epoll` 的原因之一。本章先理解休眠、唤醒与就绪通知即可。

#### 6.3.4 可读、可写，具体表示什么？

就绪条件和“业务完成”不是一回事：

| 被观察的对象与条件 | 为什么可能就绪 | 返回后怎么确认 |
| --- | --- | --- |
| 监听 Socket 可读 | 有待接受的连接 | 调用 `accept()`，处理成功、暂时无连接或错误 |
| 已连接 TCP Socket 可读 | 有接收字节 | 调用 `recv()`，可能只读到半条消息 |
| 已连接 TCP Socket 可读 | 对端结束发送且输入已到末尾 | 调用 `recv()` 得到 `0` |
| 已连接 TCP Socket 的相关就绪状态 | 某些连接错误使操作可以返回 | 实际操作或错误查询确认，不能只看集合 |
| 已连接 TCP Socket 可写 | 当前可以尝试发送 | 调用 `send()`，仍要检查部分发送和错误 |

可写不是“保证任意长度都能一次发完”。例如当前能接受少量字节，你却提交几兆字节；阻塞发送仍可能等待更多空间，非阻塞发送则可能只接受一部分。

异常集合 `exceptfds` 也不是“所有 Socket 错误的统一通知箱”。它监视特定异常条件，具体含义与平台、操作有关；例如 Windows 的非阻塞连接失败需要注意异常集合。普通收发仍须检查返回值和错误码。

#### 6.3.5 看懂五个参数与四个集合操作

Linux/POSIX 的调用形式：

```c
int ready = select(nfds, &reads, &writes, &exceptions, &limit);
```

| 参数 | 初学者理解 | 只观察一个连接可读时 |
| --- | --- | --- |
| `nfds` | POSIX 下，需要检查的最大描述符编号加一 | `s + 1`；不是连接数量 |
| `readfds` | 关心哪些 Socket 可以尝试读/接受连接 | `&reads` |
| `writefds` | 关心哪些 Socket 可以尝试写 | 不关心就传 `NULL` |
| `exceptfds` | 关心哪些 Socket 的特定异常条件 | 本章接收实验传 `NULL` |
| `timeout` | 最多等多久 | 指向 `timeval`，或按需要传 `NULL` |

例如 POSIX 下观察描述符 4 和 9，`nfds` 应为 10，不是 2。Winsock 忽略第一个参数，所以本章 Windows 分支传 `0`。

`NULL` 表示这里没有提供相应对象。没有监视写事件，就把写集合的位置传 `NULL`，不需要造一个空集合凑数。

集合的使用顺序：

```c
/* 概念片段：a、b 已连接、已设为非阻塞，并符合平台集合容量限制。 */
fd_set reads;
FD_ZERO(&reads);       /* 清空：本轮暂时没放任何 Socket */
FD_SET(a, &reads);     /* 放入 a */
FD_SET(b, &reads);     /* 放入 b */
/* 下一步：准备超时，调用 select；成功返回后逐个用 FD_ISSET 检查。 */
```

四个常用操作：

- `FD_ZERO`：清空一个集合。
- `FD_SET`：加入一个对象。
- `FD_CLR`：从集合中移除一个对象。
- `FD_ISSET`：判断某个对象是否在集合里；通常用于判断返回后的就绪对象。

`fd_set` 不应假定是两平台布局相同的普通数组。POSIX 的常见实现使用位集合，描述符编号必须在允许范围内；Winsock 使用自己的集合表示和数量限制。容量与可移植细节留到 [[I-O多路复用]] 深入。

#### 6.3.6 为什么每轮要重新准备集合？

传入集合表达的是“我想看谁”，返回集合表达的是“这轮谁就绪”，所以它同时承担输入和输出。

```text
调用前 reads = {A, B, C}
这轮只有 B 可读
调用后 reads = {B}
```

如果下一轮直接把这个返回集合再次传进去，实际上就只观察 B，A、C 可能被漏掉。

通常维护两份信息：

1. **长期管理的连接集合**：当前还需要观察的所有对象。
2. **本轮传给 `select()` 的副本**：每轮从长期集合重新复制，允许调用修改它。

本章 `wait_readable()` 只有一个对象，每次都重新 `FD_ZERO`、`FD_SET`，所以没有额外维护长期集合。多个连接时，关闭连接还必须从长期管理结构中移除它，避免下一轮继续观察无效对象。

#### 6.3.7 `select()` 的返回值不是 Socket 编号，也不是字节数

| 返回结果 | 含义 | 下一步 |
| --- | --- | --- |
| `> 0` | 请求的集合中出现了就绪项 | 用 `FD_ISSET()` 检查对象，再执行相应操作 |
| `== 0` | 本次等待超时，没有所请求的就绪事件 | 执行超时/定时任务策略 |
| 失败：POSIX `-1`，Winsock `SOCKET_ERROR` | 这次等待调用失败 | 立即保存错误码，处理错误或允许的中断 |

只用一个读集合时，正数可理解为这个集合中有多少 Socket 就绪。若同一个对象同时出现在多个返回集合中，不能把返回值简单当成“互不重复的连接数”。

第 7 节仅观察一个 Socket，所以 `ready > 0` 后直接尝试读它。多个 Socket 时，即使 `ready == 1`，也不能把它解释成“编号为 1 的 Socket 可读”，必须检查各个对象的集合成员关系。

#### 6.3.8 三种等待参数，决定 `select()` 自己是否等待

| 超时参数 | 行为 | 适用理解 |
| --- | --- | --- |
| `NULL` | 没有就绪时可以一直等待，直到就绪或错误/中断等结果 | 本次没有设置超时上限 |
| `timeval` 为正数 | 没有就绪时最多等待所给时长 | 本章每轮最多两秒 |
| `timeval` 的秒和微秒都为零 | 只检查当前状态，不为就绪而等待 | 本次非阻塞查询 |

容易混淆的两个“零”：

- **超时值为零**：调用者要求这次立刻检查。
- **返回值为零**：这次没有等到或查到所请求的就绪事件。

零超时可以让这一次 `select()` 不等待，**仍不会改变 Socket 模式**。如果调用后直接对一个没有就绪的阻塞 Socket 执行 `recv()`，依然可能被卡住。

同样，不要把零超时查询写成无间隔无限循环：

```text
不断 select(零超时) → 没就绪 → 立即再 select(零超时) → ……
```

这样仍是忙等。若当前没有其他有用任务，通常应该允许 `select()` 等待到事件或最近的定时任务期限。

#### 6.3.9 已经通知可读，为什么 `recv()` 还要非阻塞？

可以用时间顺序看一个典型情况：

```text
时刻 1：Socket 接收缓冲区里有 5 字节
时刻 2：线程甲的 select 返回，报告可读
时刻 3：线程乙先把这 5 字节读走
时刻 4：线程甲调用 recv，此时又没有数据了
```

- 如果 Socket 是阻塞模式，线程甲可能再次进入等待。
- 如果 Socket 是非阻塞模式，线程甲取得暂时不可读结果，能把控制权交回事件循环。

这说明就绪是状态观察，不是“这段数据已经专门留给你”的预约。即使没有第二个线程，也应考虑平台允许的就绪状态变化或偶发虚假就绪等边界。

还有更常见的情形：第一次 `recv()` 已经读走当前数据，你为了读取剩余消息又调用第二次 `recv()`。**第一次就绪不保证第二次仍然有数据。** 阻塞第二次读取会把事件循环卡在这一条连接上。

因此，事件循环中的常用组合是：

```text
非阻塞 Socket
      +
select 等待整组连接的就绪状态
      +
就绪后执行有限工作，暂时不可操作时保留状态并返回循环
```

并不是说 `select()` 绝对不能观察阻塞 Socket；它可以。只是“先就绪、后使用阻塞调用”并不能保证后续任何操作都不会等待，尤其是反复读取、特殊接收标志或大块发送时。

#### 6.3.10 把这段解释对应到本章实验代码

按顺序找到第 7 节中的这些位置：

1. `set_nonblocking(peer, use_nonblocking)`：`wait` 模式在这里真正开启非阻塞，`select()` 还没有参与。
2. `wait_readable(peer, 2000)`：这里允许当前线程等待可读或两秒超时。
3. `FD_ZERO/FD_SET`：在辅助函数里准备“本轮只观察 peer”。
4. `select(...)`：等待并返回就绪结果，函数没有把数据写入应用接收数组。
5. `recv(peer, buf, sizeof buf, 0)`：这里才把字节读到 `buf`。
6. `would_block(err)`：即使刚得到可读通知，也保留“现在又读不到”的处理路径。
7. 下一轮循环：再次准备集合、等待、处理，而不是在一个连接上无限阻塞读取。

可以做两个小实验来检验理解：

- 保持 `wait` 模式的 Socket 为非阻塞，只把等待参数改成 5000 毫秒，搭配 `idle` 并观察日志：它仍可能等在 `select()`，因为“Socket 非阻塞”不等于“所有函数都不等待”。客户端同样在约五秒关闭，超时与 EOF 的先后存在时序竞争，出现任一结果都应能解释。
- 若想更稳定地区分等待与查询，把客户端静默时长改为 8000 毫秒：`wait_readable(peer, 2000)` 应在约两秒返回超时；`wait_readable(peer, 0)` 则通常立即返回零，服务器按本例策略结束。测试后恢复参数。

不建议通过去掉所有等待来证明“程序非阻塞”，那只会制造忙等。更有用的目标是：**有工作时及时处理；无工作时合理休息；任何一个连接都不无限占住处理其他连接的机会。**

**第四步：只抓住三段核心代码**

第一段，真正设置非阻塞模式：

```c
u_long enabled = 1;
ioctlsocket(clients[i], FIONBIO, &enabled);
```

这改变的是 `clients[i]` 的模式。以后 `recv()` 暂时读不到时，可以立即返回 `SOCKET_ERROR` 和 `WSAEWOULDBLOCK`。完整代码会检查设置是否成功。

第二段，一起观察两个连接：

```c
FD_ZERO(&reads);
FD_SET(clients[0], &reads);  /* A */
FD_SET(clients[1], &reads);  /* B */
select(0, &reads, NULL, NULL, &timeout);
```

这是为了讲解而抽出的片段，假定 A、B 都还有效；完整代码通过循环跳过已关闭的连接。Windows 的第一个参数被忽略，不是说只检查零个 Socket。

第三段，跳过本轮没就绪的连接：

```c
if (!FD_ISSET(clients[i], &reads)) {
    continue;  /* 本轮不对这个连接调用 recv */
}
int n = recv(clients[i], buffer, sizeof buffer, 0);
```

`FD_ISSET()` 是“这个连接在返回后的集合里吗？”前面的 `!` 表示取反，所以这段的意思是：**不在集合里，就跳过；在集合里，才尝试读取。**

这三段解决三个不同问题：设置模式 → 等谁就绪 → 读取就绪者。它们不能互相替代。

**完整服务器：`win_select_server.c`**

下面代码与已保存的源码一致，可以直接编译：

```c
#include <winsock2.h>
#include <stdio.h>

int main(void) {
    WSADATA wsa;
    SOCKET listener = INVALID_SOCKET;
    SOCKET clients[2] = {INVALID_SOCKET, INVALID_SOCKET};
    const char *names[2] = {"A", "B"};
    int result = 1;
    int alive = 2;
    setvbuf(stdout, NULL, _IONBF, 0);

    int startup = WSAStartup(MAKEWORD(2, 2), &wsa);
    if (startup != 0) {
        printf("WSAStartup failed: %d\n", startup);
        return 1;
    }
    listener = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listener == INVALID_SOCKET) {
        printf("socket failed: %d\n", WSAGetLastError());
        goto cleanup;
    }
    struct sockaddr_in address = {0};
    address.sin_family = AF_INET;
    address.sin_port = htons(19100);
    address.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (bind(listener, (const struct sockaddr *)&address,
             sizeof address) == SOCKET_ERROR) {
        printf("bind failed: %d\n", WSAGetLastError());
        goto cleanup;
    }
    if (listen(listener, 2) == SOCKET_ERROR) {
        printf("listen failed: %d\n", WSAGetLastError());
        goto cleanup;
    }
    puts("Listening on 127.0.0.1:19100");

    /* 教学简化：先阻塞地接受两个连接，再一起观察它们。 */
    for (int i = 0; i < 2; ++i) {
        printf("Waiting for client %s...\n", names[i]);
        clients[i] = accept(listener, NULL, NULL);
        if (clients[i] == INVALID_SOCKET) {
            printf("accept failed: %d\n", WSAGetLastError());
            goto cleanup;
        }
        /* 第一步：真正开启这个连接的非阻塞模式。 */
        u_long enabled = 1;
        if (ioctlsocket(clients[i], FIONBIO, &enabled) == SOCKET_ERROR) {
            printf("ioctlsocket failed: %d\n", WSAGetLastError());
            goto cleanup;
        }
        printf("Client %s connected; nonblocking enabled\n", names[i]);
    }
    closesocket(listener);
    listener = INVALID_SOCKET;
    puts("Both connected. Now watch A and B together.");

    while (alive > 0) {
        /* 每轮重新放入所有尚未关闭的连接。 */
        fd_set reads;
        FD_ZERO(&reads);
        for (int i = 0; i < 2; ++i) {
            if (clients[i] != INVALID_SOCKET) FD_SET(clients[i], &reads);
        }
        struct timeval timeout = {2, 0};

        /* 第二步：等任意连接可读，最多两秒；Winsock 忽略参数 0。 */
        puts("select: waiting for any readable client...");
        int ready = select(0, &reads, NULL, NULL, &timeout);
        if (ready == SOCKET_ERROR) {
            printf("select failed: %d\n", WSAGetLastError());
            goto cleanup;
        }
        if (ready == 0) {
            printf("timeout: no readable client; keep %d remaining connection(s)\n", alive);
            continue;
        }

        for (int i = 0; i < 2; ++i) {
            if (clients[i] == INVALID_SOCKET) continue;
            /* 第三步：只对本轮就绪的连接尝试接收。 */
            if (!FD_ISSET(clients[i], &reads)) {
                printf("[%s] not readable: skip recv\n", names[i]);
                continue;
            }
            char buffer[128];
            int n = recv(clients[i], buffer, sizeof buffer, 0);
            if (n > 0) {
                printf("[%s] received %d bytes: ", names[i], n);
                fwrite(buffer, 1, (size_t)n, stdout);
                putchar('\n');
            } else if (n == 0) {
                printf("[%s] EOF: close this client\n", names[i]);
                closesocket(clients[i]);
                clients[i] = INVALID_SOCKET;
                --alive;
            } else {
                int err = WSAGetLastError();
                if (err == WSAEWOULDBLOCK) {
                    printf("[%s] temporarily unreadable: retry later\n", names[i]);
                    continue;
                }
                printf("[%s] recv failed: %d\n", names[i], err);
                goto cleanup;
            }
        }
    }
    result = 0;

cleanup:
    for (int i = 0; i < 2; ++i) {
        if (clients[i] != INVALID_SOCKET) closesocket(clients[i]);
    }
    if (listener != INVALID_SOCKET) closesocket(listener);
    WSACleanup();
    puts("server finished");
    return result;
}
```

本例每轮对每个就绪连接最多调用一次 `recv()`，避免在 A 上无限读取。超过 128 字节的数据可以留到下一轮：如果仍有未读数据，下一轮 `select()` 通常仍会报告可读。日志打印的是字节片段，没有实现完整消息解析，也没有回显响应。

`recv() == 0` 时把该连接关闭并标记 `INVALID_SOCKET`，下一轮不再加入集合。否则，已结束的输入可能一直被报告可读，导致循环空转。

**完整客户端：`run_client.ps1`**

```powershell
param(
    [Parameter(Mandatory = $true)]
    [ValidateSet('A', 'B')]
    [string]$Name,

    [ValidateRange(-1, 120)]
    [int]$DelaySeconds = -1
)

if ($DelaySeconds -eq -1) {
    if ($Name -eq 'A') { $DelaySeconds = 20 }
    else { $DelaySeconds = 0 }
}

$client = [System.Net.Sockets.TcpClient]::new()
try {
    $client.Connect('127.0.0.1', 19100)
    Write-Output "$Name connected; wait $DelaySeconds seconds before sending"
    if ($DelaySeconds -gt 0) { Start-Sleep -Seconds $DelaySeconds }
    $bytes = [System.Text.Encoding]::ASCII.GetBytes("hello from $Name")
    $stream = $client.GetStream()
    $stream.Write($bytes, 0, $bytes.Length)
    Write-Output "$Name submitted $($bytes.Length) bytes locally"
}
finally {
    $client.Dispose()
    Write-Output "$Name closed"
}
```

客户端使用阻塞连接和小消息发送即可，实验关注的是服务器如何安排 A、B。脚本中的 `Start-Sleep` 发生在独立的客户端进程中，不会让服务器线程休眠。客户端发送成功仍只代表交给本机发送机制。

**最后按时间线复述一次**

| 时间阶段 | A 在做什么 | B 在做什么 | 服务器在做什么 |
| --- | --- | --- | --- |
| A 刚连接 | 等 20 秒 | 尚未启动 | 等待第二个连接，暂未进入事件循环 |
| B 也连上 | 继续等，不发消息 | 立即发送 | `select()` 同时观察 A、B |
| B 的数据可读 | 继续等 | 发送后关闭 | 跳过未就绪的 A，读取 B 的字节 |
| B 已处理，A 还静默 | 继续等 | 已退出 | 等在 `select()`；每两秒超时后再等 |
| A 的延迟结束 | 发送并关闭 | 已退出 | 读取 A，确认 EOF，最后退出 |

假如使用“对 A 做阻塞读取，返回后才读 B”的顺序代码，A 的等待就会拖住 B。本例通过就绪集合跳过未就绪的 A，并用非阻塞接收保留状态变化时立即返回的能力。

注意：本例通常不会真的在 A 上触发 `WSAEWOULDBLOCK`，因为 `FD_ISSET()` 已经让它跳过了 A。非阻塞错误分支保留在那里，是为了处理“通知可读之后，真正读取时状态又变了”等情况。**不用看到暂时不可读日志，才能证明已经设置了非阻塞。**

核验记录（2026-10-13）：Windows MinGW GCC 15.2.0 使用 `-Wall -Wextra -Werror` 编译通过；实际启动本节 PowerShell 客户端，以 A 延迟五秒、B 立即发送验证：服务器约 0.35 秒读取 B，约 5.22 秒读取 A，中间两次等待超时均保留 A，最终两个连接均正常 EOF 并退出。默认 20 秒可用于手动操作，五秒是本次自动验证参数。

完成后回答三个问题：

1. 哪一行真正打开非阻塞模式？答案：`ioctlsocket(..., FIONBIO, ...)`。
2. 哪一行让服务器知道这轮 A 可以跳过？答案：检查返回集合的 `FD_ISSET()`。
3. 两个连接都没有事件时，服务器停在哪里？答案：通常等待在 `select()`；两秒超时后继续下一轮，而不是高速空转。

#### 6.3.12 对照一次真实运行：逐段读懂日志

下面按你实际运行的顺序解释。你的结果符合预期：B 先发送并被处理；B 正常结束后，服务器等待 A；A 随后发送并结束，服务器退出。

**一、准备接收两个连接**

```text
Listening on 127.0.0.1:19100
Waiting for client A...
Client A connected; nonblocking enabled
Waiting for client B...
Client B connected; nonblocking enabled
Both connected. Now watch A and B together.
```

- `Listening`：创建、绑定、监听成功，操作系统可以接收连接请求。
- `Waiting for client A`：服务器调用第一个阻塞 `accept()`；没有客户端时会等在这里。
- `Client A connected`：第一个 `accept()` 返回，取得 A 的已连接 Socket，并用 `ioctlsocket()` 开启非阻塞。
- `Waiting for client B`：调用第二个阻塞 `accept()`，等待第二个连接；A 的非阻塞模式不会影响监听 Socket 的模式。
- `Client B connected`：第二个连接也接受并配置好了。
- `Both connected`：此后才进入 `select()` 循环。此时活动连接数 `alive` 为 2。

本例为了讲解固定接收两个连接，不能用这段初始化流程判断它是一个完整的生产服务器。

**二、第一轮：跳过 A，处理 B**

```text
select: waiting for any readable client...
[A] not readable: skip recv
[B] received 12 bytes: hello from B
```

调用前，本轮读集合中放入了 `{A, B}`。`select()` 等待或检查后发现 B 可读，成功返回。`waiting` 只是调用前打印的日志，不表示它必然等满两秒；B 的数据可能在调用前已到，也可能在等待期间到达。

这次返回后的读集合包含 B，不包含 A。循环先检查 A：`FD_ISSET(A, &reads)` 为假，因此只打印提示，**没有调用 `recv(A)`**。接着检查 B，为真，才调用 `recv(B)`，读到 12 字节。

`hello from B` 的字节数是 `5 + 1 + 4 + 1 + 1 = 12`。脚本使用 ASCII 编码，未发送换行符和 C 字符串结尾的 `\0`；服务器自己加的输出换行不属于收到的数据。

这一轮直接展示了 `select()` 的作用：服务器知道可以跳过当前未就绪的 A，去处理 B。

**三、第二轮：B 已结束发送，也会被报告可读**

```text
select: waiting for any readable client...
[A] not readable: skip recv
[B] EOF: close this client
```

PowerShell 客户端发送后，在 `finally` 中执行 `Dispose()`，正常关闭连接。服务器上一次已经读走 B 的测试字节；再次接收时，剩余输入已结束，`recv(B)` 返回 `0`。

**结束输入也是一种可读结果**：这里可以立即得到“没有后续字节了”的结果，而不必一直等待新数据。所以，“可读”不等于“必有新的文本消息”。

服务器此时关闭自己的 B Socket，将 `clients[1]` 标记为 `INVALID_SOCKET`，并把 `alive` 从 2 减为 1。下一轮只观察 A。

B 关闭的通知可能在服务器第一次读 B 之前就已到达；只要仍有已接收字节，服务器先读字节，之后才得到 EOF。你这次分为两轮，是正常现象。

**四、中间六次超时：每次只结束本轮等待**

你的旧版日志重复了六次：

```text
select: waiting for any readable client...
timeout: no readable client; keep both connections
```

这一阶段只剩 A。每轮都会把 A 加入新的读集合，重设两秒等待时间；如果没有出现所请求的就绪事件，`select()` 返回 `0`，程序打印超时日志，然后 `continue` 进入下一轮。

服务器在这两秒等待期间通常休眠，其他进程和线程可以继续运行。它没有对 A 不停执行 `recv()`，也没有把一次等待超时视为断线。

旧提示 `keep both connections` 是示例日志写得不准确，**不是 B 复活或关闭失败**。它原来是一句写死的文字；本次已改为根据 `alive` 输出：

```text
timeout: no readable client; keep 1 remaining connection(s)
```

这表示“保留 1 个尚未关闭的连接”。修改源码后必须重新编译，旧 `.exe` 不会自动更新。

六次两秒超时大约覆盖十二秒的等待，另有最后一轮不足两秒的等待及执行/调度耗时。不能由此推出 A 的延迟设成了十二秒：A 的 20 秒从它自己连接成功后开始计时，而服务器在 B 也连接成功后才进入这个循环。手动启动 B 所用的时间已经消耗了 A 的一部分延迟。没有时间戳，不能从这份日志精确反推各阶段时长。

**五、A 终于发送，然后结束输入**

```text
select: waiting for any readable client...
[A] received 12 bytes: hello from A
select: waiting for any readable client...
[A] EOF: close this client
server finished
```

A 的延迟结束，发送 `hello from A` 并关闭。服务器在数据可读时从 `select()` 返回，调用 `recv(A)` 得到正数，处理字节；随后再得到 EOF，关闭 A，`alive` 从 1 变成 0。

`while (alive > 0)` 不再成立，程序退出循环，执行清理并打印 `server finished`。结束原因是两个连接都已处理完并关闭，不是中间累计了若干次超时。

**把每轮实际工作列出来**

| 阶段 | 本轮调用前的读集合 | `select()` 的结果 | 实际接收操作 | 剩余连接数 |
| --- | --- | --- | --- | --- |
| 读取 B 的消息 | A、B | B 可读，返回正数 | `recv(B)` 返回 12；不调用 `recv(A)` | 2 |
| 确认 B 结束 | A、B | B 可读，返回正数 | `recv(B)` 返回 0，关闭 B | 1 |
| 六次超时 | 只有 A | 每次返回 0 | 不调用 `recv()`，继续下一轮 | 1 |
| 读取 A 的消息 | 只有 A | A 可读，返回正数 | `recv(A)` 返回 12 | 1 |
| 确认 A 结束 | 只有 A | A 可读，返回正数 | `recv(A)` 返回 0，关闭 A | 0 |

特别区分两个零：`select()` 返回零是“本次等待超时”，`recv()` 在本例返回零是“该连接的输入已结束”。它们不是同一件事。

这次日志也没有出现 `WSAEWOULDBLOCK`，原因是程序先检查就绪集合，通常已经避开了当前读不到的对象；非阻塞接收是后续实际操作的保障，不需要每轮都触发暂时不可读错误才能证明它生效。

### 6.4 三种“超时”别混淆

| 名称 | 问的是什么 | 例子 |
| --- | --- | --- |
| 单次调用/等待超时 | 这一次最多等多久 | 一次 `select()` 最多两秒 |
| 空闲超时 | 已经多久没有任何新进展 | 收到字节后重新计算两秒无数据期限 |
| 整个请求总期限 | 从请求开始到完整响应最多多久 | 不管分几次收，总共只能十秒 |

如果你每次 `recv()` 都允许等两秒，对方每 1.5 秒发一个字节，这条连接可能持续很久。**每次都没有超时，不代表整个请求及时完成。**

总期限的一般计算方式：

```text
开始时间 = 单调时钟的当前时间
截止时间 = 开始时间 + 允许的总时长
每次等待前：剩余时间 = 截止时间 - 当前时间
剩余时间 <= 0：结束请求
否则：用剩余时间作为本次等待上限
```

“单调时钟”用于测经过了多久，不因用户校准日期时间而往回跳。Linux 可以使用 `clock_gettime(CLOCK_MONOTONIC, ...)`，Windows 可以使用 `GetTickCount64()` 或合适的性能计时接口。

本章实验的 `wait` 模式每轮最多等待两秒，超时就结束连接；它不是实现完整消息的总期限，也不是完整的心跳协议。

- [ ] 知道不同平台的超时参数和失败结果不完全相同。

## 7. 完整实验：同一服务器，三种等待方式

### 7.1 实验设计与限制

本节包含三个文件。请分别保存代码块里的内容，不要把三个文件拼成一个文件：

```text
io_model_demo/
├── net_demo.h       平台差异和等待函数
├── mode_server.c    接受一个连接，按指定模式接收字节
└── probe_client.c   立即发送、延迟发送、静默、关闭或分段发送
```

服务器只服务**一个连接**，连接结束后退出，下一次实验必须重新启动。监听地址为 `127.0.0.1:19090`，客户端和服务器必须在同一个系统环境运行：都在 Windows 原生，或都在同一个 WSL/Linux 环境。暂不混用 Windows 和 WSL 的地址转发机制。

三种服务器模式：

| 命令参数 | 已连接 Socket 的模式 | 没有数据时怎么做 |
| --- | --- | --- |
| `blocking` | 阻塞 | 停在 `recv()` 等待 |
| `nonblocking` | 非阻塞 | 返回后睡 500 毫秒，再尝试 |
| `wait` | 非阻塞 | 先用 `select()` 等可读，最多两秒；超时就关闭连接 |

**三种模式的监听 `accept()` 都使用阻塞方式。** 这里故意只改变接收阶段，便于做单变量对照。非阻塞监听、多个连接以及完整事件循环留给后续章节。

客户端只发送，服务器只接收和打印，**没有回显响应**。客户端显示发送完成只代表交给本机发送机制，不是服务器业务确认。

### 7.2 文件一：`net_demo.h`

头文件中集中处理平台差异。`static inline` 表示这些小辅助函数在包含它的源码中使用；先不用研究编译器是否真的把函数展开。

```c
#ifndef NET_DEMO_H
#define NET_DEMO_H

/* 在 POSIX 系统头文件之前声明要使用的接口版本。 */
#ifndef _WIN32
#ifndef _POSIX_C_SOURCE
#define _POSIX_C_SOURCE 200809L
#endif
#endif

#include <stdio.h>
#include <string.h>
#include <errno.h>

#ifdef _WIN32
#include <winsock2.h>  /* 必须在 windows.h 之前 */
#include <ws2tcpip.h>
#include <windows.h>
typedef SOCKET socket_t;
typedef int io_count_t;
#define BAD_SOCKET INVALID_SOCKET
#define SEND_END SD_SEND
#else
#include <sys/types.h>
#include <sys/socket.h>
#include <sys/select.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <fcntl.h>
#include <signal.h>
#include <time.h>
typedef int socket_t;
typedef ssize_t io_count_t;
#define BAD_SOCKET (-1)
#define SEND_END SHUT_WR
#endif

#define DEMO_PORT 19090

static inline int net_init(void) {
#ifdef _WIN32
    WSADATA data;
    int err = WSAStartup(MAKEWORD(2, 2), &data);
    if (err != 0) {
        printf("WSAStartup failed: %d\n", err);
        return -1;
    }
#else
    /* 对方关闭后再发送时，让程序取得错误，而不是被 SIGPIPE 终止。 */
    if (signal(SIGPIPE, SIG_IGN) == SIG_ERR) {
        perror("signal");
        return -1;
    }
#endif
    return 0;
}

static inline void net_cleanup(void) {
#ifdef _WIN32
    WSACleanup();
#endif
}

static inline void socket_close(socket_t s) {
#ifdef _WIN32
    closesocket(s);
#else
    close(s);
#endif
}

static inline int socket_error(void) {
#ifdef _WIN32
    return WSAGetLastError();
#else
    return errno;
#endif
}

static inline void report_error(const char *where, int err) {
#ifdef _WIN32
    printf("%s failed: Winsock error %d\n", where, err);
#else
    printf("%s failed: %s (errno=%d)\n", where, strerror(err), err);
#endif
}

static inline int would_block(int err) {
#ifdef _WIN32
    return err == WSAEWOULDBLOCK;
#else
    return err == EAGAIN || err == EWOULDBLOCK;
#endif
}

static inline int interrupted(int err) {
#ifdef _WIN32
    /* 本章不用 Winsock 取消接口，不把它当 POSIX 信号重试。 */
    (void)err;
    return 0;
#else
    return err == EINTR;
#endif
}

static inline int set_nonblocking(socket_t s, int enabled) {
#ifdef _WIN32
    u_long mode = enabled ? 1UL : 0UL;
    return ioctlsocket(s, FIONBIO, &mode);
#else
    int flags = fcntl(s, F_GETFL, 0);
    if (flags == -1) return -1;
    if (enabled) flags |= O_NONBLOCK;
    else flags &= ~O_NONBLOCK;
    return fcntl(s, F_SETFL, flags);
#endif
}

static inline void sleep_ms(unsigned int ms) {
#ifdef _WIN32
    Sleep(ms);
#else
    struct timespec remaining;
    remaining.tv_sec = ms / 1000;
    remaining.tv_nsec = (long)(ms % 1000) * 1000000L;
    while (nanosleep(&remaining, &remaining) == -1 && errno == EINTR) {
        /* 被信号打断后继续睡剩余时间。 */
    }
#endif
}

/* 返回 >0：可读；0：超时；<0：失败。失败后马上取错误码。 */
static inline int wait_readable(socket_t s, int timeout_ms) {
    fd_set reads;
    struct timeval limit;
#ifndef _WIN32
    /* POSIX fd_set 不能容纳超出范围的描述符。 */
    if (s < 0 || s >= FD_SETSIZE) {
        errno = EINVAL;
        return -1;
    }
#endif
    FD_ZERO(&reads);
    FD_SET(s, &reads);
    limit.tv_sec = timeout_ms / 1000;
    limit.tv_usec = (timeout_ms % 1000) * 1000;
#ifdef _WIN32
    /* Winsock 忽略第一个参数。 */
    return select(0, &reads, NULL, NULL, &limit);
#else
    /* POSIX 要传监视的最大描述符 + 1。此处只有 s。 */
    return select(s + 1, &reads, NULL, NULL, &limit);
#endif
}

#endif
```

其中 `fd_set` 是“这一轮要观察哪些 Socket”的集合，`FD_ZERO` 清空集合，`FD_SET` 把一个 Socket 放入集合。由于本函数只观察一个 Socket，返回正数就表示它可读；多个 Socket 时还要用 `FD_ISSET()` 逐个检查。

**每次调用 `select()` 都重建集合与超时值。** `select()` 会修改集合，有些平台也会修改超时结构，不能把一次调用后的内容不加重置地重复使用。

### 7.3 文件二：`mode_server.c`

```c
#include "net_demo.h"

int main(int argc, char **argv) {
    /* 输出不缓冲，确保你能立即看到停在调用之前的日志。 */
    setvbuf(stdout, NULL, _IONBF, 0);
    if (argc != 2 ||
        (strcmp(argv[1], "blocking") != 0 &&
         strcmp(argv[1], "nonblocking") != 0 &&
         strcmp(argv[1], "wait") != 0)) {
        puts("usage: mode_server blocking|nonblocking|wait");
        return 1;
    }
    int use_nonblocking = strcmp(argv[1], "blocking") != 0;
    int use_wait = strcmp(argv[1], "wait") == 0;
    if (net_init() != 0) return 1;

    socket_t listener = BAD_SOCKET;
    socket_t peer = BAD_SOCKET;
    int result = 1;
    listener = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listener == BAD_SOCKET) {
        report_error("socket", socket_error());
        goto cleanup;
    }
#ifndef _WIN32
    /* Linux 重启监听时复用本地地址；Windows 不照搬此选项语义。 */
    int reuse = 1;
    if (setsockopt(listener, SOL_SOCKET, SO_REUSEADDR,
                   &reuse, sizeof reuse) == -1) {
        report_error("setsockopt", socket_error());
        goto cleanup;
    }
#endif
    struct sockaddr_in address = {0};
    address.sin_family = AF_INET;
    address.sin_port = htons(DEMO_PORT);
    address.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (bind(listener, (const struct sockaddr *)&address,
             sizeof address) != 0) {
        report_error("bind", socket_error());
        goto cleanup;
    }
    if (listen(listener, 8) != 0) {
        report_error("listen", socket_error());
        goto cleanup;
    }
    printf("listening on 127.0.0.1:%d; mode=%s\n", DEMO_PORT, argv[1]);
    puts("accept begin (blocking in all three modes)");
    for (;;) {
        peer = accept(listener, NULL, NULL);
        if (peer != BAD_SOCKET) break;
        int err = socket_error();
        if (interrupted(err)) continue;
        report_error("accept", err);
        goto cleanup;
    }
    puts("accepted one client");
    if (set_nonblocking(peer, use_nonblocking) != 0) {
        report_error("set_nonblocking", socket_error());
        goto cleanup;
    }

    result = 0;
    for (;;) {
        if (use_wait) {
            puts("select begin: up to 2000 ms");
            int ready = wait_readable(peer, 2000);
            if (ready == 0) {
                puts("timeout: no readable event; demo closes this connection");
                break;
            }
            if (ready < 0) {
                int err = socket_error();
                if (interrupted(err)) continue;
                report_error("select", err);
                result = 1;
                break;
            }
            puts("readable: try recv");
        }
        char buf[128];
        puts("recv begin");
        io_count_t n = recv(peer, buf, sizeof buf, 0);
        if (n > 0) {
            printf("recv returned %ld bytes: ", (long)n);
            fwrite(buf, 1, (size_t)n, stdout);
            putchar('\n');
        } else if (n == 0) {
            puts("recv returned 0: peer ended its sending direction");
            break;
        } else {
            int err = socket_error();
            if (interrupted(err)) continue;
            if (use_nonblocking && would_block(err)) {
                puts("would block: keep connection and retry later");
                if (!use_wait) sleep_ms(500);
                continue;
            }
            report_error("recv", err);
            result = 1;
            break;
        }
    }

cleanup:
    if (peer != BAD_SOCKET) socket_close(peer);
    if (listener != BAD_SOCKET) socket_close(listener);
    net_cleanup();
    puts("server finished");
    return result;
}
```

读代码时抓住四件事：

1. `accept()` 成功之后得到 `peer`，为 `peer` 明确设置模式。
2. `wait` 分支先等待可读，`nonblocking` 分支直接尝试读取。
3. `recv()` 分别处理正数、零、暂时不可读、其他错误。
4. 不管从哪个错误分支退出，最后都走 `cleanup` 释放资源。`goto cleanup` 在这里用于集中清理，并不是跳着做正常业务。

`fwrite(buf, 1, n, stdout)` 只打印实际读到的字节，不要求 `buf` 以 `\0` 结尾。不要改成直接 `printf("%s", buf)`，因为 `recv()` 不会自动补字符串终止符。

### 7.4 文件三：`probe_client.c`

```c
#include "net_demo.h"

/* 仅供阻塞客户端使用：循环把小段数据交给本机发送机制。 */
static int send_all_blocking(socket_t s, const char *data, int length) {
    int sent = 0;
    while (sent < length) {
        io_count_t n = send(s, data + sent, length - sent, 0);
        if (n > 0) {
            sent += (int)n;
        } else if (n < 0) {
            int err = socket_error();
            if (interrupted(err)) continue;
            report_error("send", err);
            return -1;
        } else {
            puts("send made no progress");
            return -1;
        }
    }
    return 0;
}

int main(int argc, char **argv) {
    setvbuf(stdout, NULL, _IONBF, 0);
    if (argc != 2 ||
        (strcmp(argv[1], "data") != 0 &&
         strcmp(argv[1], "delay") != 0 &&
         strcmp(argv[1], "idle") != 0 &&
         strcmp(argv[1], "close") != 0 &&
         strcmp(argv[1], "split") != 0)) {
        puts("usage: probe_client data|delay|idle|close|split");
        return 1;
    }
    if (net_init() != 0) return 1;
    int result = 1;
    socket_t s = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (s == BAD_SOCKET) {
        report_error("socket", socket_error());
        net_cleanup();
        return 1;
    }
    struct sockaddr_in address = {0};
    address.sin_family = AF_INET;
    address.sin_port = htons(DEMO_PORT);
    address.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (connect(s, (const struct sockaddr *)&address, sizeof address) != 0) {
        report_error("connect", socket_error());
        goto cleanup;
    }
    puts("client connected");
    if (strcmp(argv[1], "idle") == 0) {
        puts("no sending; keep socket open for 5000 ms");
        sleep_ms(5000);
    } else if (strcmp(argv[1], "close") == 0) {
        puts("close without sending");
    } else {
        if (strcmp(argv[1], "delay") == 0) {
            puts("wait 3000 ms before sending");
            sleep_ms(3000);
        }
        if (strcmp(argv[1], "split") == 0) {
            if (send_all_blocking(s, "he", 2) != 0) goto cleanup;
            puts("submitted he; wait 1000 ms");
            sleep_ms(1000);
            if (send_all_blocking(s, "llo\n", 4) != 0) goto cleanup;
        } else {
            if (send_all_blocking(s, "hello\n", 6) != 0) goto cleanup;
        }
        puts("submitted all test bytes locally");
        if (shutdown(s, SEND_END) != 0) {
            report_error("shutdown", socket_error());
            goto cleanup;
        }
    }
    result = 0;

cleanup:
    socket_close(s);
    net_cleanup();
    puts("client closed");
    return result;
}
```

`data` 立即发送；`delay` 连接后等三秒；`idle` 保持连接五秒但不发任何数据；`close` 连接成功后立即正常关闭；`split` 分两次发送，中间隔一秒。

`shutdown(..., SEND_END)` 表示本端不会再发送字节，不是发送一条“空消息”。本例随后关闭 Socket，因此不会继续接收；更完整的半关闭用法见 [[连接生命周期]]。

本客户端一直使用阻塞模式，所以它的发送循环在这里成立。不要把这个函数原样用到非阻塞 Socket 上，非阻塞发送需要第 9 节的进度保存逻辑。

### 7.6 Linux/WSL：保存、编译、运行

如果用 WSL，先进入 WSL 的 Linux 终端。Windows 的 E 盘在常见 WSL 配置下对应 `/mnt/e`。若挂载路径不同，以自己的配置为准。

## 8. 对照实验：先预测，再运行

下面表格写的是参数。Windows 使用 `.\mode_server.exe 参数` 和 `.\probe_client.exe 参数`；Linux 使用 `./mode_server 参数` 和 `./probe_client 参数`。

### 8.1 实验一：观察阻塞的位置

先运行服务器 `blocking`，先不启动客户端。

预期服务器停在：

```text
listening on 127.0.0.1:19090; mode=blocking
accept begin (blocking in all three modes)
```

再运行客户端 `delay`。服务器会继续打印：

```text
accepted one client
recv begin
```

从客户端连接成功开始，约三秒后收到 `hello\n`。再接收时最终得到 `0`，然后服务器结束。

字节有可能分多次读到，下面只是常见输出，不能要求日志逐行完全相同：

```text
recv returned 6 bytes: hello

recv begin
recv returned 0: peer ended its sending direction
server finished
```

观察问题：等待三秒时，为什么看不到下一条日志？答案是当前线程还没有从 `recv()` 返回，不是程序一定崩溃了。

### 8.2 实验二：观察暂时不可读

重新启动服务器 `nonblocking`，客户端仍运行 `delay`。

延迟期间会多次看到：

```text
recv begin
would block: keep connection and retry later
```

每次失败后程序睡 500 毫秒，再尝试读取。三秒后会读到测试字节，最终读到 `0`。

观察问题：为什么暂时不可读之后没有关闭连接？因为“此刻没有字节”不等于“连接已经结束”。轮询次数取决于调度，不要把次数当成网络协议保证。

### 8.3 实验三：观察等待超时

重新启动服务器 `wait`，客户端运行 `idle`。

客户端连接后保持五秒不发数据；服务器约两秒后打印：

```text
select begin: up to 2000 ms
timeout: no readable event; demo closes this connection
server finished
```

客户端仍可能继续睡到五秒才退出，因为它没有调用接收操作来观察服务器的关闭。

**服务器关闭连接是本示例选择的策略。** `select()` 返回 `0` 本身只表示这次等待期间没有选定的就绪事件，不会替你自动关闭 Socket，也不证明客户端在两秒时已经死亡。

### 8.4 实验四：正常关闭与暂时没数据的区别

分别用三种服务器模式搭配客户端 `close`。连接接受之后，服务器应最终读到 `0`；`wait` 模式也会得到可读事件，然后由 `recv()` 确认结束发送。

如果改用客户端 `idle`：

- `blocking` 在接收处等待，约五秒后才因客户端关闭读到 `0`。
- `nonblocking` 在五秒期间反复看到暂时不可读，客户端关闭后读到 `0`。
- `wait` 大约两秒后按示例策略主动关闭，通常不会等到客户端五秒后的关闭。

本例使用正常关闭。强制终止、连接复位等情况可能产生错误结果，不要认为每种关闭方式都一定返回 `0`。

### 8.5 实验五：等待就绪不一定等到超时

服务器 `wait` 搭配客户端 `data`。有数据或结束发送到来后，等待会提前返回，不会机械地睡满两秒。

再搭配客户端 `split`。通常先读到 `he`，一秒后读到 `llo\n`。但要记住 TCP 分段接收受时序影响，不能承诺必然得到这两次返回。

无论读几次，把所有正数返回对应的字节依次拼起来，应该是 `hello\n`。这是数据顺序和应用累积的问题，不是模式设置能解决的消息边界问题。

### 8.6 建议完成的实验矩阵

每格都是一次独立实验，需要重新启动服务器。时间从接受连接附近算起，受操作系统调度影响，允许合理误差。

| 服务器模式 | 客户端 `data` | 客户端 `delay` | 客户端 `idle` | 客户端 `close` | 客户端 `split` |
| --- | --- | --- | --- | --- | --- |
| `blocking` | 收到字节后最终 EOF | 等约三秒，再收到字节和 EOF | 等约五秒，再 EOF | 最终 EOF | 累积得到完整测试字节 |
| `nonblocking` | 字节和 EOF；也可能短暂不可读 | 多次不可读，后收到字节和 EOF | 多次不可读，约五秒后 EOF | 最终 EOF；可能先短暂不可读 | 不可读与收到字节交替，最终 EOF |
| `wait` | 就绪后收字节，最终 EOF | 约两秒先超时关闭 | 约两秒超时关闭 | 可读后确认 EOF | 一秒间隔小于等待上限，收到字节后 EOF |

EOF 是“输入结束”的常用缩写，这里指 TCP `recv()` 返回 `0`，不是一个名为 EOF 的网络字节。

`wait + delay` 是进阶观察项：服务器两秒时先关闭，客户端三秒时才发送，客户端可能报告错误，也可能首次 `send()` 仍然成功。TCP 关闭和错误传播有时序，不要用“一次发送成功”证明对方仍在处理。最稳定的超时入门实验是 `wait + idle`。

### 8.7 可选观察：CPU 与 Socket 状态

Windows 可以用任务管理器观察服务器 CPU；Linux 用 `top` 或 `ps`。本章程序等待时 CPU 通常很低，但短实验和采样精度可能让读数不稳定。

Linux/WSL 可在第三个终端运行：

```bash

ss -tn '( sport = :19090 or dport = :19090 )'
```

Windows PowerShell：

```powershell

```

`LISTEN` 表示正在监听，`ESTABLISHED` 表示 TCP 连接已建立。**连接状态不能证明应用线程正在运行、消息已经完整收到或业务处理成功。** 更多观察方法见 [[网络观察工具]]。

## 9. 从“能运行”走向“能正确处理连接”

### 9.1 非阻塞接收：保存未完成的消息

假定协议用换行符结束一条消息，第一次只读到 `hel`，第二次读到 `lo\n`。你需要保留第一次的数据，拼起来才得到完整消息。

暂时不可读时，不要清空已经收到的数据，也不要把它当成完整消息交给业务逻辑。

```text
连接的接收状态
  已累积字节：hel
  本次 recv：暂时不可读
  下一步：保留 hel，等待下一次可读
  再次收到：lo\n
  拼接后：hello\n，按协议识别为一条消息
```

这叫“保存状态”：保存以后继续操作时需要的信息。还要限制最大消息长度，避免对方持续发送不带换行的大量数据。具体解析见 [[消息边界与拆包]]、[[安全与输入校验]]。

### 9.2 非阻塞发送：保存剩余字节，等待可写

`send()` 也可能部分完成，阻塞模式同样不能假设一次发送完整。

非阻塞发送尤其要处理三种结果：

| 结果 | 应该做什么 |
| --- | --- |
| 返回正数 `n` | 记住已经接受的 `n` 字节，从剩余位置继续 |
| 暂时不可写 | 保留尚未发送的数据与偏移量，等可写再继续 |
| 真正错误或无进展 | 按连接策略处理，避免无限循环 |

例如总共 1000 字节，第一次发送 400 字节，第二次暂时不可写：之后应从第 400 字节的位置继续剩下的 600 字节，不能从头重发，也不能丢弃尾部。

下面是可配合 `net_demo.h` 理解的**进阶片段**，并非第 7 节服务器的一部分。这里约定 `0 <= sent <= length <= 4096`，Socket 已经是非阻塞模式，缓冲区在发送结束前保持有效且不被修改。

```c
struct pending_send {
    char bytes[4096];
    int length;  /* 总字节数，不是字符串字符数 */
    int sent;    /* 已交给本机发送机制的字节数 */
};

/* 返回 1：全部交出；0：现在不可写，稍后继续；-1：失败。 */
int flush_pending(socket_t s, struct pending_send *p) {
    while (p->sent < p->length) {
        io_count_t n = send(s, p->bytes + p->sent,
                            p->length - p->sent, 0);
        if (n > 0) {
            p->sent += (int)n;
            continue;
        }
        if (n < 0) {
            int err = socket_error();
            if (interrupted(err)) continue;
            if (would_block(err)) return 0;
            report_error("send", err);
        } else {
            puts("send made no progress");
        }
        return -1;
    }
    return 1;
}
```

真正的事件循环拿到 `0` 后，登记对该连接的“可写”关注，再处理其他工作。下一次可写时，拿同一个 `pending_send` 继续调用；拿到 `1` 后取消不再需要的可写关注。

**不要永远监视所有连接的可写事件。** TCP Socket 很多时候都可写，如果没有待发数据还不停处理可写事件，事件循环可能空转。

本片段只说明进度管理。大量数据或多个连接时，还需要每轮工作量限制、发送队列长度限制和公平调度，避免一个连接占住整个循环。

### 9.3 非阻塞 `accept()`：暂时没有连接也不是坏监听

如果把监听 Socket 设成非阻塞，当前没有待接受的连接时，`accept()` 会失败返回：Linux 为 `-1` 和 `EAGAIN/EWOULDBLOCK`，Windows 为 `INVALID_SOCKET` 和 `WSAEWOULDBLOCK`。

正确流程是等待监听 Socket 可读，再尝试接受连接。成功后，对得到的新 Socket 明确配置模式。实际服务器还可能一轮接受多个连接，直到暂时没有更多连接，同时限制每轮工作量。

这一点解释了本章实验的限制：仅仅将 `peer` 改成非阻塞，不会改变 `listener` 上的 `accept()`。

### 9.4 非阻塞 `connect()`：立即返回不代表连接已经成功

`connect()` 与 `recv()` 的判断方式不同，不要把所有暂时状态都只写成一个 `would_block()` 分支。

| 初次连接调用的结果 | Linux TCP | Windows TCP | 含义 |
| --- | --- | --- | --- |
| 立即成功 | 返回 `0` | 返回 `0` | 连接已经建立 |
| 正在进行 | 返回 `-1`，通常为 `EINPROGRESS` | 返回 `SOCKET_ERROR`，通常为 `WSAEWOULDBLOCK` | 已开始建立，但尚未完成 |
| 立即失败 | 其他相关错误 | 其他相关错误 | 本次不能继续按正常连接流程使用 |

`EINPROGRESS` 就是“正在进行”。在连接进行中重复调用 `connect()` 还可能出现 `EALREADY` 等结果；不要靠高速重复连接调用判断完成。

完整流程应是：

```text
创建 Socket，先设置非阻塞
       ↓
调用 connect
  ├─ 立即成功：进入正常收发
  ├─ 立即失败：关闭并记录错误
  └─ 正在进行：保留“连接中”状态与截止时间
                  ↓
          等待连接完成事件或超时
                  ↓
          getsockopt(SO_ERROR) 查询最终结果
             ├─ 查询失败：处理查询错误
             ├─ SO_ERROR 为 0：连接成功
             └─ SO_ERROR 非 0：连接失败，关闭 Socket
```

在常见 Linux TCP `select()` 用法中观察可写状态，再查询 `SO_ERROR`。在 Winsock 的 `select()` 用法中，应同时观察写集合与异常集合：连接成功可能在写集合报告，失败可能在异常集合报告，然后检查最终错误。两平台不能只靠“可写了”断言连接成功。

`getsockopt()` 意思是“查询 Socket 的一个选项”。在上述连接完成通知之后，Linux 查询示意：

```c
int connect_error = 0;
socklen_t length = sizeof connect_error;
if (getsockopt(s, SOL_SOCKET, SO_ERROR,
               &connect_error, &length) == -1) {
    perror("getsockopt");  /* 查询操作自身失败 */
} else if (connect_error != 0) {
    fprintf(stderr, "connect failed: %s\n", strerror(connect_error));
} else {
    puts("connected");
}
```

Windows 查询示意：

```c
int connect_error = 0;
int length = sizeof connect_error;
if (getsockopt(s, SOL_SOCKET, SO_ERROR,
               (char *)&connect_error, &length) == SOCKET_ERROR) {
    printf("getsockopt failed: %d\n", WSAGetLastError());
} else if (connect_error != 0) {
    printf("connect failed: %d\n", connect_error);
} else {
    puts("connected");
}
```

两个片段都假定你已经正确发起连接，并等到相应完成事件，不能在连接还没完成时随便查询一个零值就宣布成功。总期限到期时关闭这次 Socket；之后重试应创建新 Socket，而不是盲目复用失败对象。

这属于本章的进阶衔接，不要求你现在独立写完整客户端。第 7 节客户端仍使用本机的阻塞 `connect()`。

### 9.5 一张连接状态表

**状态机**可以理解为：明确记录“当前处于哪个阶段”，然后根据事件决定下一步。先不用学习数学定义。

| 当前状态 | 遇到的结果 | 下一步 |
| --- | --- | --- |
| 连接中 | 完成通知且 `SO_ERROR == 0` | 改为已连接 |
| 已连接、等待读取 | 暂时不可读 | 保留接收数据，等待下一次可读 |
| 已连接、累积消息 | 又收到若干字节 | 继续累积，尝试解析完整消息 |
| 已连接、等待发送 | 暂时不可写 | 保留发送进度，等待可写 |
| 读取方向已结束 | `recv() == 0` | 不再读取，按协议处理剩余发送与关闭 |
| 任何相关状态 | 真正错误或期限到期 | 按策略结束、清理、必要时重连 |

完整实现见 [[状态机与连接管理]]。入门示例读到 `0` 就直接关闭，属于“本例不需要继续发送”的简化策略。

### 9.6 为什么下一章要学线程和 I/O 多路复用

**并发**指在一段时间内推进多项任务，不要求它们在完全相同的一瞬间执行。**并行**指多项工作确实同时执行，例如不同 CPU 核心上的线程。

服务器要服务 100 个连接，常见路线是：

| 路线 | 怎么组织代码 | 还要解决的问题 |
| --- | --- | --- |
| 阻塞 Socket + 多线程/多进程 | 某个连接等待时，其他执行路线继续处理 | 线程数量、共享数据、同步与资源成本 |
| 非阻塞 Socket + 就绪等待 + 事件循环 | 一条或少量执行路线根据事件推进多个连接 | 连接状态、部分读写、工作量限制、任务调度 |

**把 Socket 设置成非阻塞，不会自动让第 7 节服务器服务多个客户端。** 它仍然只接受一个连接，然后只处理这个连接。

I/O 多路复用就是“同时观察多个通信入口，找出哪些值得处理”。事件循环就是“等待事件 → 分发处理 → 更新状态 → 再等待”的循环。

即使所有 Socket 都非阻塞，在事件处理函数里长时间 `sleep()`、做大量 CPU 运算、等待用户输入或进行其他阻塞操作，也会拖住这一条执行路线。非阻塞网络接口不能自动修复整个程序的阻塞点。

## 10. 常见错误与排查顺序

### 10.1 逻辑错误对照表

| 常见错误 | 会发生什么 | 正确做法 |
| --- | --- | --- |
| 把 `recv() == 0` 当暂时没数据 | 反复读取已结束的输入，可能空转 | 结束读取流程，按协议清理 |
| 所有负数都关闭连接 | 非阻塞正常等待被当成断线 | 读取错误码，区分暂时状态与真正失败 |
| `EAGAIN` 后马上无限重试 | CPU 空转 | 等待就绪或安排之后重试 |
| 设置模式失败仍继续 | 实际还在阻塞，排查时误判 | 检查返回值，失败就走错误路径 |
| 只修改监听 Socket，假定新连接继承 | `recv()` 行为与预期不同 | 对新连接明确配置 |
| 读到几字节就认定是完整消息 | 半条消息被当成业务请求 | 按应用协议累积与解析 |
| `send()` 后不检查字节数 | 丢失未交出的尾部字节 | 保存偏移量，继续剩余部分 |
| 暂时不可写后从头重发 | 对方收到重复字节 | 从未发送位置继续 |
| `printf("%s", buf)` 打印原始接收数组 | 越过有效数据范围读取，输出乱码或崩溃 | 按实际长度输出，或安全补终止符 |
| 把 `select()` 可读当“必有业务消息” | EOF、错误或半条消息被误处理 | 再调用 `recv()` 分类 |
| 重复使用 `select()` 修改后的集合 | 漏监视 Socket、超时异常 | 每轮重建集合和时间参数 |
| 把两秒超时等同于服务器已死亡 | 错误重连、重复请求 | 看协议与恢复策略，区分超时和断线 |
| 一个事件里做大量工作 | 其他连接响应很慢 | 限制每轮工作量，必要时移交其他执行路线 |
| 关闭后仍保存旧 Socket 并继续使用 | 操作失败，甚至误操作后来复用的资源编号 | 取消事件关注、删除状态、标记无效 |

### 10.2 编译和运行错误

| 现象 | 优先检查 |
| --- | --- |
| `gcc` 找不到 | 是否安装编译器，是否在当前终端 PATH 中 |
| `net_demo.h` 找不到 | 三个文件是否在同一目录，文件名是否多了 `.txt` |
| Windows 提示缺少 Winsock 函数的链接符号 | 编译命令末尾是否加了 `-lws2_32` |
| Windows 头文件重复定义等错误 | `winsock2.h` 是否在 `windows.h` 前，是否混入其他旧 Socket 头文件 |
| `bind` 失败，Linux 常见 `EADDRINUSE` / Windows 10048 | 端口是否已经有程序监听，旧服务器是否仍在运行 |
| `connect` 失败，Linux 常见 `ECONNREFUSED` / Windows 10061 | 服务器是否先启动，地址/端口是否一致，是否混用了 Windows 与 WSL |
| 服务器一直停在 `accept begin` | 客户端是否实际运行并连接到了这个服务 |
| 非阻塞模式没看到暂时不可读 | 数据可能已经到达；使用 `delay` 更容易观察 |
| `wait` 模式在 `delay` 客户端发送前结束 | 两秒等待小于三秒发送延迟，这是实验预期 |
| 重跑时仍显示旧行为 | 修改后是否重新编译，运行的是否是当前目录程序 |

错误码数字不必死记，先用错误名称和上下文理解问题。本章 Windows 日志打印数字，必要时根据 Winsock 文档查询。

### 10.3 一个可靠的排查顺序

1. 先确认程序能正确编译，警告内容也要读。
2. 确认运行环境：两个程序是否都在 Windows 原生，或都在同一个 Linux/WSL。
3. 确认服务器启动并监听正确端口。
4. 看最后一条调用前日志：停在 `accept`、`select` 还是 `recv`？
5. 看调用返回值，再看失败后立即保存的错误码。
6. 核对 Socket 的模式、操作对象和超时策略。
7. 核对已收到的数据长度、已发送进度、连接是否已结束。
8. 最后再用状态查看工具、调试器或系统调用观察工具深入排查。

不要一遇到等待就开始改防火墙；先根据日志确认程序正在等什么。本章只测试回环地址，无需向外网开放端口。

## 11. 练习题：从理解到改造

先独立作答，再看下一节提示。代码练习可以新建实验副本，保留第 7 节的原始版本方便比较。

### 11.1 基础理解

1. 一个阻塞 `recv()` 申请最多读取 128 字节，目前有 3 字节可读。一定要等到 128 字节才返回吗？为什么？
2. 服务器等在 `recv()` 时，客户端还能运行吗？这说明“阻塞”的范围是什么？
3. 非阻塞 TCP `recv()` 返回 `-1`，Linux 错误码是 `EAGAIN`。你应该关闭连接，还是保留连接稍后再读？
4. TCP `recv()` 返回 `0`。这与“收到一个长度为零的文本字符串”有什么不同？
5. `select()` 返回 `0` 后，Socket 是否已自动关闭？能否直接认定网络已经断开？
6. 客户端 `send()` 返回 6，能否证明服务器已收到并打印了 `hello\n`？若需要确认，应增加什么？
7. 把 Socket 改成非阻塞，为什么不会自动变成多客户端服务器？

### 11.2 实验与日志

8. 完成 `blocking + idle`、`nonblocking + idle`、`wait + idle`。分别记录连接接受后等待多久、出现哪些返回结果、谁先结束连接。
9. 把客户端 `delay` 的 3000 毫秒改成 1000 毫秒，重新编译，再运行 `wait + delay`。先预测结果，再对照日志解释。
10. 把非阻塞轮询间隔从 500 改成 100 毫秒，对比日志数量和响应延迟。为什么降低间隔不等于高性能？不需要把间隔改成零做忙等测试。
11. 用客户端 `split` 测试三种模式。记录每次收到多少字节，为什么不能把接收次数写死？

### 11.3 代码改造

12. 让 `wait` 模式在连续三次两秒等待超时后才关闭；每次实际收到字节时清零计数。说明这与严格的六秒总期限有何区别。
13. 为服务器增加统计：总接收字节数、暂时不可读次数、等待超时次数。保证 EOF 和错误后都能输出统计，且没有资源泄漏。
14. 增加一个按 `\n` 划分消息的接收缓冲区。客户端分段发送时只在完整消息到达后打印，并设置例如 1024 字节的消息长度上限。如何处理 EOF 时还剩半条消息？
15. 纸上模拟第 9 节的发送状态：总长度 10，第一次 `send()` 返回 4，第二次暂时不可写，第三次返回 3。每一步偏移是多少，最后还剩几字节？
16. 进阶选做：设计一个“从接受连接开始，总共最多十秒”的期限。说明如何用单调时钟更新剩余等待时间，以及为什么收到零散字节不能延长总期限。

## 12. 练习参考与阶段验收

### 12.1 基础题参考

1. 不一定。普通 TCP `recv()` 的长度是上限，已有字节可以让它返回少于 128 的正数。
2. 客户端通常在另一个进程运行，不受这条服务器线程的等待直接阻止。阻塞首先影响当前调用所在的执行路线。
3. 保留连接，安排重试。它说明当前无字节可读，不说明连接结束。
4. 长度大于零的 TCP 接收返回 `0` 表示对端结束发送，且当前已无字节可读，不是一条由 TCP 帮你定义的空消息。

### 12.2 实验与改造提示

- 第 8 题：阻塞通常等约五秒才 EOF；轮询在此期间多次暂时不可读；`wait` 约两秒后由服务器主动关闭。以实际日志为准。
- 第 9 题：一秒小于两秒，通常应在超时前收到数据并最终读到 EOF。
- 第 10 题：间隔变短意味着检查更频繁，CPU/系统调用开销可能增多；处理延迟一般下降，但随连接数增加，轮询成本仍会扩大。
- 第 11 题：字节总内容和顺序需要正确，读取分组由时序决定，不能假定一对一。
- 第 12 题：`ready == 0` 时递增，第三次才结束；`n > 0` 时清零。单轮重试、数据到来和执行耗时使它不是严格总期限；对方持续发字节还会不断重置。
- 第 13 题：计数变量放在接收循环外，只在对应结果分支更新，清理路径统一打印。不要把负数当作字节数累加。
- 第 14 题：保留未解析尾部；一轮接收也可能含多条消息。EOF 时若协议要求换行结束，则未完成尾部应按协议报截断/丢弃，不能默默当成合法消息。
- 第 15 题：偏移依次为 4、4、7，剩余依次为 6、6、3。暂时不可写不增加进度。
- 第 16 题：记录一个固定截止时间，每次等待前重新计算剩余时间；收到字节不改变它。被中断后也应重新计算，避免不断延长期限。
