# 状态机与连接管理

> 面向完全新手，沿用本知识库的 **C 语言 + TCP Socket** 路线。先规划，再解释，再运行。实验同时支持 Windows Winsock 和 Linux/WSL；Python 只用来制作方便观察的测试客户端。
>
> 本章要回答：**一次读不完、一时发不完、客户端突然离开时，服务器怎样记住做到哪里，并把每个连接照顾到结束？**

## 0. 先看学习地图：学什么，按什么顺序学

### 0.1 学完本章的具体目标

你不需要背完全部 TCP 状态名称。先做到以下事情：

1. 解释“状态、事件、条件、动作、状态转换”各是什么意思。
2. 用结构体保存每个连接自己的 Socket、输入、输出、解析进度和时间。
3. 画出连接生命周期和消息解析的两个状态机。
4. 收到半条消息时保留进度；一次收到多条时逐条处理。
5. `send()` 只发送一部分时，从正确位置继续。
6. 客户端结束发送时，分清“发送剩余响应”与“立即清理”。
7. 限制消息大小、队列大小、连接数和等待时间。
8. 运行一个多客户端回显服务器，并通过实验验证上述行为。

**回显**就是收到什么正文，回复什么正文，用来把注意力集中在连接管理而不是业务逻辑上。

## 1. 前置知识：先弄清程序到底在处理什么

### 1.1 最少需要的 C 语言知识

| 写法或词语 | 通俗解释 | 本章用途 |
| --- | --- | --- |
| 变量 | 给一个值取名字 | 保存已收到多少字节 |
| `if`、`switch` | 根据条件或类别选择动作 | 不同状态处理不同事件 |
| `while`、`for` | 重复做一组动作 | 持续处理连接、解析消息 |
| 函数、返回值 | 请一段代码做事并取得结果 | 判断 `recv()` 是否成功 |
| 数组 | 一块连续的存储空间 | 暂存收到和待发送的字节 |
| 指针 | 保存内存位置 | `c->in` 表示通过指针访问连接的输入数组 |
| `struct` | 把相关信息放在一起 | 一个连接拥有一份记录 |
| `enum` | 给有限的几种情况命名 | `OPEN`、`DRAINING` 等 |
| `size_t` | 表示大小和长度的无符号整数类型 | 记录数组用了多少空间 |
| `uint32_t` | 明确为 32 位的无符号整数类型 | 保存 4 字节长度 |
| `uint64_t` | 明确为 64 位的无符号整数类型 | 保存毫秒计时值 |
| `sizeof` | 求对象占多少字节 | 限制一次读取的长度 |
| `memcpy` | 按指定长度复制字节，内存不能重叠 | 把正文复制到输出队列 |
| `memmove` | 按指定长度移动字节，允许重叠 | 把输入剩余部分移到开头 |

`size_t` 不表示负数。所以只有在确认 `recv()` / `send()` 返回正数后，才能把结果转换成 `size_t`。把 `-1` 先转成无符号数，会变成一个很大的数。

### 1.2 Socket、监听、连接

Socket 是程序使用网络通信的端点。可以把句柄理解成“操作系统交给程序的一张资源编号票”。

- 监听 Socket 等待新客户，不直接收发某个客户的业务消息。
- `accept()` 返回已连接 Socket，一个客户端对应一个。
- Linux 常用 `int` 文件描述符；Windows 使用 `SOCKET`，不能随意压缩成 `int`。
- `127.0.0.1` 指本机；端口帮助定位本机上的服务。本章使用 `19100`。

~~~text
服务端：socket → bind → listen → accept → recv/send → close
客户端：socket → connect → send/recv → close
~~~

同一个服务端可以同时有一个监听 Socket 和许多已连接 Socket。

### 1.3 TCP 是有序字节流

TCP 在连接正常工作时，把发送的字节按顺序交给接收方，但不告诉应用“这是一条完整业务消息”。

~~~text
发送端两次发送：   "hello"、"world"
接收端可能读到：   "he"、"llowor"、"ld"
也可能一次读到：   "helloworld"
~~~

拆分和合并是正常行为。所谓“半包”“粘包”，描述的是应用消息与一次读取的结果不一致，不是 TCP 把数据弄坏了。

**协议**就是双方约定的消息格式和处理规则；**解析**就是按约定从字节中辨认一条条消息。

### 1.4 四个缓冲区，不要混在一起

缓冲区是暂存数据的内存。以一次请求和响应为例：

~~~text
客户端程序
  → 客户端内核发送缓冲区
  → 网络
  → 服务端内核接收缓冲区
  → recv()
  → 服务端应用输入缓冲区
  → 解析、处理
  → 服务端应用输出队列
  → send()
  → 服务端内核发送缓冲区
  → 网络 → 客户端程序
~~~

内核是操作系统负责网络、设备和资源管理的核心部分。应用输入和输出缓冲区由我们编写的程序维护。

`send()` 成功只说明相应字节交给了本机网络栈，不能证明对端应用已经读取或处理。需要确认“业务完成”时，必须额外设计确认消息。

### 1.5 非阻塞、就绪、事件循环

- **阻塞调用**：条件不满足时可能在调用内部等待。
- **非阻塞调用**：条件不满足时立即告诉程序“现在做不了”。
- **就绪通知**：提示某个 Socket 现在值得尝试读或写。
- **事件循环**：集中等待通知，再处理事件、更新状态、检查时间，然后继续等待。

`select()` 不会帮你读数据，也不会保存你的解析进度。它只帮助等待。

| 调用结果 | 含义 | 下一步 |
| --- | --- | --- |
| `recv() > 0` | 这次得到一些字节 | 保存并尝试解析 |
| `recv() == 0`，且请求的长度大于 0 | 对方有序结束发送，即 EOF | 停止读，决定收尾策略 |
| `send() > 0` | 这次交出了这些字节 | 推进输出偏移 |
| 返回错误，暂时不可读/写 | 当前没有机会 | 保留状态，回到等待 |
| 返回错误，被信号中断 | 此次调用被打断 | 检查退出标志，之后重试 |
| 其他错误 | 例如连接重置 | 记录原因，回收该连接 |

Linux 用 `errno` 获取错误，暂时做不了通常是 `EAGAIN/EWOULDBLOCK`；Windows 用 `WSAGetLastError()`，对应 `WSAEWOULDBLOCK`。它们都不意味着连接一定坏了。

## 2. 状态机：把“现在做到哪里”说清楚

### 2.1 为什么不能只写一串顺序代码

想象服务端遇到这些事：

1. A 只发来消息头的一半。
2. B 已经发来完整消息，需要回复。
3. 给 B 的回复只发出去一部分。
4. C 结束发送，但仍在等待响应。

如果函数只允许“进来就读完整请求并发完整响应”，等待 A 或 B 就可能拖住其他人。事件循环要求处理函数及时返回，因此必须把进度留在函数外。

**连接上下文**就是属于一个连接的记录，让下一次处理能接着上一次继续。

### 2.2 五个基本词

| 词语 | 通俗解释 | 示例 |
| --- | --- | --- |
| 状态 | 当前处境 | 等消息头、等正文、准备收尾 |
| 事件 | 刚刚发生的事 | 收到字节、发现 EOF、超时 |
| 条件 | 采取动作之前必须成立的判断 | 消息头是否已有 4 字节 |
| 动作 | 具体做什么 | 保存长度、生成响应、关闭 Socket |
| 转换 | 做完后进入什么状态 | 从等头变为等正文 |

可以按一句话描述：**在某状态遇到某事件，如果某条件成立，就做某动作，进入某状态。**

比如：在“等头”状态收到字节，若已经积累 4 字节，则读取长度、检查是否合法，然后进入“等正文”。

### 2.3 最小示意代码

下面是教学片段，不是独立程序；完整代码在第 8 节：

~~~c
enum ParseState { HEADER, BODY };

/* 收到的数据和计数在连接对象中，函数返回后仍保留。 */
if (c->parser == HEADER && c->in_len >= 4) {
    /* 解出正文长度、验证范围、移除消息头。 */
    c->parser = BODY;
}
if (c->parser == BODY && c->in_len >= c->body_need) {
    /* 处理完整正文，把响应排队。 */
    c->parser = HEADER;
}
~~~

关键不是一定要用 `switch` 或某个库，而是每种处境都有明确的保存位置与处理规则。

### 2.4 状态转换表比零散的条件更容易检查

| 当前解析状态 | 输入条件 | 动作 | 下一状态 |
| --- | --- | --- | --- |
| HEADER | 少于 4 字节 | 保留，等待 | HEADER |
| HEADER | 已有 4 字节，长度合法 | 保存长度，消费消息头 | BODY |
| HEADER | 长度为 0 或大于上限 | 记录协议错误，关闭 | 连接结束 |
| BODY | 正文尚不够 | 保留，等待 | BODY |
| BODY | 正文够，但输出队列没空间 | 保留完整正文，等输出减少 | BODY |
| BODY | 正文够，输出有空间 | 生成响应、消费正文 | HEADER |

**消费**在这里指“这些字节已经处理完，从待处理输入中移除”，不是从网络中重新读取。

## 3. 一个连接里，需要记住哪些信息

### 3.1 每个连接一份对象

不能把所有客户端的未完成消息放进同一份全局数组。例如 A 的输入是 `he`，B 的输入是 `OK`，它们必须留在不同记录里。

| 信息 | 为什么保存 |
| --- | --- |
| Socket 句柄 | 知道操作哪个连接 |
| 连接编号 | 日志能区分不同连接 |
| 生命周期状态 | 决定还读不读、何时关闭 |
| 解析状态、正文所需长度 | 记住已经读到消息的哪一步 |
| 输入数组、已用长度 | 保留半条消息和下一条消息 |
| 输出数组、起止偏移 | 保存尚未发送的字节 |
| 暂停读取标志 | 输出积压时限制新输入 |
| 最近进展、消息起始、收尾起始时间 | 限制不同类型的等待 |

句柄只是连接对象的一部分，不能替代整个对象。

### 3.2 两个状态机分别负责两件事

**生命周期状态机**：这个连接是否还能接收、是否正在收尾、是否已经释放。

~~~mermaid
stateDiagram-v2
    [*] --> FREE
    FREE --> OPEN: 接受连接并初始化
    OPEN --> DRAINING: 收到EOF且没有截断消息
    OPEN --> FREE: 致命错误或超时，清理
    DRAINING --> FREE: 输出发空、错误或收尾超时，清理
~~~

本实验里：

- `FREE`：数组槽位空闲，Socket 无效，相关资源已关闭。逻辑上的“已关闭”直接合并到此状态。
- `OPEN`：允许处理完整请求，也允许发送响应。
- `DRAINING`：不再读新请求，只把已有响应交给网络栈，然后关闭。英文可理解为“把积存内容排出去”。

**解析状态机**：当前在等消息头，还是在等正文。

~~~mermaid
stateDiagram-v2
    [*] --> HEADER
    HEADER --> HEADER: 消息头不足4字节
    HEADER --> BODY: 头完整且长度合法
    BODY --> BODY: 正文不足或输出空间不足
    BODY --> HEADER: 完整正文已处理并排队
~~~

网络可读、可写是事件，不应简单等同于一个互斥的“READING/WRITING”状态。一条 TCP 连接可以双向收发，等待输入的同时也可能有响应要发。

### 3.3 应用状态与 TCP 内核状态不同

你可能在网络工具中看到 `ESTABLISHED`、`FIN_WAIT_1`、`CLOSE_WAIT`、`TIME_WAIT`。它们描述 TCP 在操作系统内部的连接过程，详见 [[连接生命周期]]。

本章的 `HEADER`、`BODY`、`DRAINING` 是应用自己定义的状态。两者没有一一对应关系：TCP 连接已建立时，应用可能在等头、等正文、发响应或做业务处理。

### 3.4 状态不变量：无论发生什么都必须成立的规则

“不变量”听起来复杂，实际就是“每次处理后都应保持的规则”。本章规定：

~~~text
0 <= in_len <= 输入容量
0 <= out_begin <= out_end <= 输出容量
待发送长度 = out_end - out_begin
BODY 状态下：1 <= body_need <= 1024
FREE 状态下：Socket 无效，不参与事件集合
DRAINING 状态下：不再读取新请求
只有待发送长度大于 0 时才关注可写
~~~

C 的无符号长度自然不会小于 0，但减法顺序错误仍会产生很大的数，所以必须维持起止偏移的顺序。

## 4. 输入缓冲区：把零散的字节组成消息

### 4.1 本章的协议：4 字节长度 + 正文

前面的 [[事件循环]] 使用换行协议。本章改用长度前缀协议，便于直接观察“等头 → 等正文”的转换。

~~~text
一条消息 = 4 字节正文长度 + 指定长度的正文
hello    = 00 00 00 05 + 68 65 6c 6c 6f
~~~

这里数字用十六进制写，每两位表示一个字节。正文不包含长度头；`hello` 正文长 5 字节，整条消息长 9 字节。

约定如下：

1. 长度是无符号 32 位数，采用大端字节序，即高位字节在前，也称网络字节序。
2. 正文长度范围为 **1～1024 字节**；0 在本协议中是非法值，不表示断开。
3. 正文可以是任意字节，包含换行或 `\0` 也可以；演示客户端默认使用 UTF-8 文本。
4. 同一连接可以连续发送多条消息，服务器按原顺序逐条回显。
5. 响应也采用同样的格式，正文原样返回。
6. EOF 出现在消息之间时正常收尾；消息头或正文中途结束属于截断错误，立即关闭并放弃尚未交出的输出。

**字节序**解决“一个多字节整数按什么顺序放到网络上”的问题。例如数字 5 的 4 字节网络表达为 `00 00 00 05`。

不要直接发送 C `struct` 的内存：结构体可能有填充字节，整数的本机字节序也可能与约定不同。

### 4.2 每次 recv 以后做三件事

~~~text
把新字节追加到输入数组的空闲区域
  → 根据解析状态尽可能取出完整消息
  → 保留尚未处理的尾部，回到事件循环
~~~

追加的位置是 `in + in_len`，可读入的空间是 `sizeof in - in_len`。不能每次都从数组开头覆盖。

### 4.3 手算一次分段到达

假设发送 `hello`，服务端观察到三批字节：

| 批次 | 新字节 | 处理后解析状态 | 尚未处理输入 | 保存的正文长度 |
| --- | --- | --- | --- | --- |
| 1 | `00 00` | HEADER | `00 00` | 未确定 |
| 2 | `00 05 he` | BODY | `he` | 5 |
| 3 | `llo` | HEADER | 空 | 重置为 0 |

第二批到达后，4 字节头已经完整，所以消费头，并把 5 保存到 `body_need`。第三批之后正文完整，才能生成响应。

UTF-8 中文可能在任意字节间拆开。服务端按字节组装和回显，不把半个汉字当字符串解码；客户端拿到完整正文后再解码。

### 4.4 一次读到多条：解析需要循环

~~~text
输入：[长度3][one][长度3][two][下一条头的前2字节]
解析：交付 one → 交付 two → 留下 2 字节头
状态：HEADER
~~~

如果只解析第一条，第二条已经在应用输入缓冲区里，而内核可能没有新字节，不会再提供你期待的新读事件。

因此要持续解析已有输入，直到出现以下情况之一：

- 头不够；
- 正文不够；
- 输出队列暂时容纳不了响应；
- 发现协议错误。

输出空间恢复后，也必须重新处理已有输入，不能只依赖下一次网络读取。

### 4.5 如何安全地解读长度

完整代码采用逐字节组合，避免未对齐指针和类型转换问题：

~~~c
uint32_t len = ((uint32_t)p[0] << 24)
             | ((uint32_t)p[1] << 16)
             | ((uint32_t)p[2] << 8)
             |  (uint32_t)p[3];
~~~

`<<` 表示左移二进制位，`|` 把互不重叠的部分组合起来。先把字节转换成无符号 32 位数，再移位。

另一种常见写法是先 `memcpy()` 到一个 `uint32_t`，再用 `ntohl()` 转成本机整数。不要直接把 `unsigned char *` 强行当作 `uint32_t *` 解引用。

顺序必须是：**先确认头完整 → 解长度 → 验证范围 → 才计算、分配或读取正文。**

### 4.6 最大长度与空消息

从网络收到的长度不能直接信任。比如 `ff ff ff ff` 表示 4294967295，不能据此申请几 GB 内存。

本实验先验证 1～1024，之后 `4 + body_need` 才安全。本协议禁止空正文是一个应用决定，其他协议可以允许空正文，但仍需与 `recv() == 0` 分开。

## 5. 输出缓冲区：从正确位置续发

### 5.1 输出先排队，事件循环以后再发送

业务处理生成响应时，不保证网络立刻能接收它。把它先放进应用输出队列，之后在可写事件里发送。

~~~text
解析完整消息
  → 把响应头与正文加入输出队列
  → 下一轮关注可写
  → send 接受部分或全部
  → 更新偏移
  → 仍有内容就继续关注可写
~~~

这样解析函数不会为了等待一个慢客户端而停住整个服务器。

### 5.2 两个偏移比“已发送/未发送”更精确

本实验使用 `out_begin` 与 `out_end`：

~~~text
数组：[已经交出的区域][尚未发送的区域][空闲区域]
                     ^                ^
                  out_begin        out_end

待发送长度 = out_end - out_begin
下一次从 out + out_begin 开始
~~~

例如队列有 100 字节，第一次成功发送 30：`out_begin` 从 0 变为 30，`out_end` 仍是 100，待发送为 70。

当两者相等，队列为空，将两个偏移都重置为 0。追加响应时，如果数组尾部不够但总空闲足够，就把未发送区域移到开头，这叫压紧。

### 5.3 四类发送结果

| 情况 | 处理 | 常见错误 |
| --- | --- | --- |
| 正数 | 只推进实际返回的长度 | 直接把整个队列清空 |
| 暂时不能发 | 不改偏移，等待下轮可写 | 原地无限重试，CPU 空转 |
| 被中断 | 保存进度，之后重试或退出 | 把可重试事件当致命错误 |
| 致命错误 | 关闭并回收这个连接 | 让整个服务进程退出 |

对本实验这种“请求长度大于 0 的普通 TCP 发送”，若意外返回 0，也视作无法推进并关闭，避免死循环。

一次 `send()` 成功不等于整条响应发完；整个应用队列发空，也不等于对端业务已经确认。

### 5.4 按需关注可写

没有输出时不要把连接放进写集合。TCP Socket 经常处于可写状态，如果一直关注，`select()` 会不断立即返回，CPU 可能很高。

~~~c
if (c->out_end > c->out_begin) {
    FD_SET(c->sock, &writes);
}
~~~

这是示意片段，完整集合构建见第 8 节。

### 5.5 背压：下游慢，先减少新工作

客户端可以一直发请求，却不读取响应。输出若无限增长，最终会耗光内存。

**背压**是当后面的环节处理不过来时，限制前面的环节继续送入工作。本实验设置：

- 输出总容量：4112 字节，相当于 4 条最大响应。
- 高水位：待发达到 2056 字节，暂停网络读取。
- 低水位：待发降到 1028 字节或以下，恢复读取。

水位就是队列长度的阈值。使用不同的高低阈值，避免在一个临界值附近反复暂停、恢复。

暂停读取后，客户端不一定立刻停止：内核仍可能暂存一些字节。积压继续增加时，TCP 流量控制才逐渐影响发送方。

已在输入缓冲区里的完整请求，也可能因输出空间不足暂停解析。**恢复发送后重新解析已有输入**，才能让整个管道继续前进。

### 5.6 公平性：每轮只做有限工作

**公平性**表示其他连接也能得到处理机会。本实验每轮每连接最多一次 `recv()` 和一次 `send()`，每次发送最多 256 字节，输入解析也受固定输入容量约束。

这里的 256 是故意选择的教学预算，不是 TCP 的发送上限。大响应会在多轮中推进，但不能据此声称操作系统一定发生了部分发送。真实部分发送仍以实际返回值为准。

进阶服务器通常会调整字节、消息、时间预算。若改用 epoll 边缘触发，不能简单照搬“每轮只读一次”，详见 [[08-C与Linux深入/epoll深入]]。

## 6. EOF、半关闭、错误与资源回收

### 6.1 EOF：对方结束发送，不等于不能接收

EOF 是 End Of File 的缩写，在 TCP 接收中表示对端有序结束了它的发送方向。

**半关闭**指只结束一个方向。客户端调用 `shutdown(..., SHUT_WR)`，表示“不再发请求”，仍可接收服务器的响应；Windows 对应发送方向的常量是 `SD_SEND`。

正常例子：客户端发完整消息 → 结束发送 → 继续接收 → 服务端把响应发完再关闭。

### 6.2 收到 EOF 后的决策

| 输入情况 | 本实验策略 | 原因 |
| --- | --- | --- |
| HEADER 且输入为空 | OPEN → DRAINING | 请求边界完整，可以收尾 |
| HEADER 且输入有 1～3 字节 | 立即关闭，记录 truncated frame | 消息头被截断 |
| BODY 且正文不够 | 立即关闭，记录 truncated frame | 正文被截断 |

本实验通常不会在“输入有完整消息但输出无空间”时继续读取 EOF，因为背压已经暂停读取。输出恢复后先解析，随后才继续读取并观察 EOF。

进入 DRAINING 后只关注尚未完成的发送，输出为空就关闭。不要继续对 EOF 连接调用 `recv()`，否则它可能每次都返回 0，引起空转。

这里的“发完”指全部交给本机网络栈。示例没有设置中止式 `SO_LINGER`；普通关闭会让网络栈按 TCP 规则处理已接受的数据，但没有对方应用确认就无法保证业务处理成功。

### 6.3 致命错误：立即释放

连接重置、协议长度非法、资源上限或超时都可能要求关闭。连接重置是对方或网络栈中止连接，不一定有正常 EOF。

出错后的标准动作：

1. 记录连接编号和关闭原因。
2. 停止让这个连接参与后续事件分发。
3. 关闭 Socket。
4. 释放或清空输入、输出、业务对象与计时信息。
5. 把槽位标记为空闲。

**资源泄漏**就是“已经不需要的资源仍没归还”。只写 `state = FREE` 却不关闭 Socket，依然会泄漏。

### 6.4 谁负责释放：资源所有权

**所有权**指“谁负责最终把资源归还”。本实验由事件循环统一管理所有连接，所有关闭路径都调用同一个 `close_connection()`。

该函数先检查是否已经 FREE，因而重复调用也不会重复关闭；这种“重复执行不会进一步改变结果”的性质称为幂等。

教学代码使用静态连接数组，没有 `malloc()`，但 Socket 仍必须关闭。改成动态内存以后，还要释放队列和连接对象。

### 6.5 关闭后别再使用：句柄可能被复用

操作系统可以把已关闭的句柄值再次分给新连接。把旧数字当永久身份，可能把旧任务的结果发给新人。

本实验的日志使用递增连接编号，且单线程处理，无跨线程回传。工程中常用“槽位编号 + 代次编号”，代次在槽位复用时变化，用来验证迟到的任务是否仍属于原连接。

清理以后不要继续发送，也不要继续解引用已经释放的对象。完整代码在每个可能关闭的动作后检查状态，并在处理完旧事件以后才接受新连接，减少同一轮复用的混淆。

## 7. 超时与容量：不能无限等待

### 7.1 等待超时不是连接超时

`select()` 等待 1 秒返回 0，仅表示这一秒没有关注的就绪事件，不代表所有连接都坏了。服务器应当借此检查各个连接自己的截止时间。

### 7.2 不同的等待要分开计时

| 类型 | 本实验默认值 | 起算或更新方式 | 防止什么 |
| --- | --- | --- | --- |
| 空闲超时 | 30 秒 | 接受连接、成功读取或成功发送时更新最近进展 | 长期占用而不产生网络进展 |
| 消息组装超时 | 10 秒 | 收到一条消息的首批字节开始，后续零碎字节不续期 | 一点点发送，永远不完成消息 |
| 写入无进展超时 | 10 秒 | 首次排队开始；正数发送成功才更新 | 输出一直有内容却交不出去 |
| 收尾超时 | 5 秒 | 进入 DRAINING 开始，发送进展不续期 | 收尾一直无法完成 |

消息超时的计时范围包含该消息等待输出空间的时间。这是本实验选择的简化规则；工程中可以把网络组装超时与内部排队超时分开。

输入一次读到多条时，示例在转向已有的下一条消息时使用当时的时间，不为每个字节记录精确到达时间。这是适合固定小缓冲区的教学实现。

**慢速占用攻击**的一种形式是不断发送少量字节来拖延完整请求。仅用“最近收到字节”更新的空闲超时防不住它，固定的消息完成期限更有帮助。

### 7.3 使用单调时钟

单调时钟用于计算经过了多长时间，不随手动校时突然前跳或后退。Linux 使用 `clock_gettime(CLOCK_MONOTONIC, ...)`；Windows 使用 `GetTickCount64()`。

~~~text
经过时间 = 当前单调时间 - 开始单调时间
超过对应期限 → 记录原因 → 清理
~~~

`select()` 最多等待 1 秒，所以期限检查可能延迟约一轮，再加处理所需时间。严格的定时系统可把等待时间设为最近截止时间。

### 7.4 容量与内存估算

本实验最多 16 个连接，每个输入 1028 字节，输出 4112 字节，加上状态信息，固定应用缓冲区总量约 80 KiB。

KiB 表示 1024 字节。这只是数组内存，不包括操作系统的 TCP 缓冲区、程序其他数据和栈。

容量要同时限制：连接数量、单条消息长度、每连接输入/输出、总体队列。固定容量满了怎么办，也必须约定：本实验拒绝多余连接，非法长度直接关闭，输出积压用背压。

## 8. 分平台实践：Windows 与 Linux 的状态机回显服务端

### 8.1 两份代码做同一件事

Windows 和 Linux 的网络接口有一些不同，所以这里提供两份**互相独立、各自完整**的 C 服务端源文件，不使用 `#ifdef` 把两套 Socket 调用混在一起：

- `state_server_windows.c`：Windows Winsock 版本，可用 MinGW-w64 GCC 或 Visual Studio 编译。
- `state_server_linux.c`：Linux/POSIX Socket 版本，可用 Linux GCC 编译，也适用于 WSL。

两份程序的协议、端口、状态机、缓冲区上限、超时和日志设计相同；Socket 初始化、错误处理、就绪等待、计时和关闭调用则分别使用各自平台的接口。Windows 代码块只包含 Winsock/Windows 实现，Linux 代码块只包含 POSIX 实现，两者不靠 `#ifdef` 或 `#else` 切换平台。每次只选择与你当前系统匹配的一份代码编译。Python 测试客户端可以共用，但服务端监听地址是 `127.0.0.1`，所以客户端必须在服务端所在的同一台机器、同一个网络运行环境中运行；例如 WSL 服务端应优先在同一个 WSL 发行版里运行客户端。

先认识这些函数，再看 `main()`：

1. `close_connection()`：所有关闭路径统一经过这里。
2. `parse_input()`：HEADER/BODY 状态转换与响应排队。
3. `read_once()`：一次读取，分类处理数据、EOF、错误。
4. `write_once()`：一次发送，保存未发部分，重新解析已有输入。
5. `check_timeouts()`：分开检查四种期限。
6. `main()`：准备集合 → 等待 → 分发旧连接 → 接受新连接。

日志中的 `id` 是连接编号，`fd` 是操作系统句柄。正文可能含二进制字节，因此程序不直接用 `%s` 打印正文。

### 8.2 Windows 完整代码：state_server_windows.c

在 Windows 实验中复制本代码块，保存为 `state_server_windows.c`。这份代码只使用 Winsock/Windows 接口，不含 Linux 分支。

~~~c
#ifndef _WIN32_WINNT
#define _WIN32_WINNT 0x0600
#endif
#include <winsock2.h>
#include <ws2tcpip.h>
#include <windows.h>
typedef SOCKET socket_t;
#define BAD_SOCKET INVALID_SOCKET
#define socket_close closesocket
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <signal.h>
#include <stdlib.h>

#define PORT 19100
#define MAX_CLIENTS 16
#define MAX_BODY 1024u
#define INPUT_CAP (MAX_BODY + 4u)
#define OUTPUT_CAP (4u * INPUT_CAP)
#define HIGH_WATER (2u * INPUT_CAP)
#define LOW_WATER INPUT_CAP
#ifndef SEND_SLICE
#define SEND_SLICE 256u
#endif
#define IDLE_MS 30000u
#define FRAME_MS 10000u
#define WRITE_MS 10000u
#define DRAIN_MS 5000u

enum LifeState { FREE, OPEN, DRAINING };
enum ParseState { HEADER, BODY };
typedef struct Connection {
    socket_t sock;
    unsigned id;
    enum LifeState life;
    enum ParseState parser;
    unsigned char in[INPUT_CAP], out[OUTPUT_CAP];
    size_t in_len, out_begin, out_end;
    uint32_t body_need;
    int read_paused, frame_active;
    uint64_t last_progress, frame_since, write_since, drain_since;
} Connection;

static Connection clients[MAX_CLIENTS];
static volatile sig_atomic_t stopping = 0;
static void on_stop(int sig) { (void)sig; stopping = 1; }

static uint64_t now_ms(void) {
    return (uint64_t)GetTickCount64();
}

static int socket_error(void) {
    return WSAGetLastError();
}

static int retry_later(int err) {
    return err == WSAEWOULDBLOCK || err == WSAEINTR;
}

static int nonblocking(socket_t s) {
    u_long mode = 1;
    return ioctlsocket(s, FIONBIO, &mode);
}

static size_t pending(const Connection *c) {
    return c->out_end - c->out_begin;
}

static void close_connection(Connection *c, const char *reason) {
    if (c->life == FREE) return;
    printf("id=%u close: %s; pending=%zu input=%zu\n",
           c->id, reason, pending(c), c->in_len);
    socket_close(c->sock);
    memset(c, 0, sizeof *c);
    c->sock = BAD_SOCKET;
    c->life = FREE;
}

static void update_backpressure(Connection *c) {
    int old = c->read_paused;
    if (!old && pending(c) >= HIGH_WATER) c->read_paused = 1;
    else if (old && pending(c) <= LOW_WATER) c->read_paused = 0;
    if (old != c->read_paused)
        printf("id=%u read %s; pending=%zu\n", c->id,
               c->read_paused ? "paused" : "resumed", pending(c));
}

static uint32_t decode_length(const unsigned char *p) {

### 8.4 代码与概念对应表

| 概念 | 代码位置 | 观察点 |
| --- | --- | --- |
| 独立上下文 | `Connection clients[]` | 每个槽位有自己的计数 |
| 生命周期 | `life` | FREE → OPEN → DRAINING → FREE |
| 增量解析 | `parse_input()` | HEADER/BODY 不因函数返回而丢失 |
| 不完整输入 | `consume_input()`、`in_len` | 只移除处理过的字节 |
| 输出续发 | `write_once()` | 从 `out_begin` 继续 |
| 背压 | `update_backpressure()` | 高水位暂停、低水位恢复 |
| 已缓存工作继续执行 | 发送后调用 `parse_input()` | 不等新的读事件 |
| 统一回收 | `close_connection()` | 清空、关闭、恢复 FREE |
| 超时 | `check_timeouts()` | 使用单调毫秒值 |
| 避免旧事件作用于新连接 | 先分发旧连接，最后 `accept_one()` | 新连接从下一轮参加等待 |

两份实现的操作系统接口对应关系如下。此表只帮助阅读；运行时选择对应系统的完整代码即可：

| 操作 | Windows 版本 | Linux 版本 |
| --- | --- | --- |
| Socket 句柄 | `SOCKET` | `int` 文件描述符 |
| 设置非阻塞 | `ioctlsocket()` | `fcntl()` |
| 读取错误 | `WSAGetLastError()` | `errno` |
| 等待可读/可写 | `select(0, ...)` | `select(maxfd + 1, ...)` |
| 单调时间 | `GetTickCount64()` | `clock_gettime(CLOCK_MONOTONIC, ...)` |
| 断开时防止进程退出 | Winsock 错误返回 | 忽略 `SIGPIPE` |

完整代码每轮重建 `fd_set` 和等待时间。Linux 检查句柄数值必须小于 `FD_SETSIZE`；Windows 按集合项数限制，这里 16 个客户端加一个监听 Socket 在默认容量内。

### 8.5 这个实验的简化边界

它是单线程、固定小容量的教学服务器：没有认证、TLS、线程池或可靠业务确认。逐次打印日志也会影响性能，不适合作为压测基准。

按 Ctrl+C 会统一释放连接，但会放弃尚未交出的输出；它演示的是明确清理路径。第 14 节再讨论怎样把整台服务器的退出改成有期限的优雅停机。

### 9.5 测试客户端 state_client.py

Python 的角色是发出特定格式的数据并检查响应。你不必先学完整 Python 课程，先认识：`with` 自动归还资源，`bytes` 表示字节，`struct.pack()` 按格式构造整数，`assert` 用来检查结果是否符合预期。

`!I` 表示一个采用网络字节序的无符号 4 字节整数。客户端的 `sendall()` 是阻塞式辅助函数，适合这个单连接测试脚本，**不能把它的等待思路照搬到服务器事件循环里**。

保存完整代码为 `state_client.py`：

~~~python
import argparse
import socket
import struct
import time

HOST, PORT = "127.0.0.1", 19100


def frame(body):
    if not 1 <= len(body) <= 1024:
        raise ValueError("body must contain 1..1024 bytes")
    return struct.pack("!I", len(body)) + body


def recv_exact(sock, count):
    result = bytearray()
    while len(result) < count:
        part = sock.recv(count - len(result))
        if not part:
            raise EOFError("server closed before a full response")
        result.extend(part)
    return bytes(result)


def recv_frame(sock):
    length = struct.unpack("!I", recv_exact(sock, 4))[0]
    if not 1 <= length <= 1024:
        raise ValueError(f"invalid response length: {length}")
    return recv_exact(sock, length)


def expect_closed(sock):
    # An invalid request may be followed by EOF or a reset, depending on the OS.
    try:
        part = sock.recv(1)
    except ConnectionResetError:
        print("server reset the connection")
        return
    if part:
        raise AssertionError(f"unexpected response: {part!r}")
    print("server closed the connection")


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--case", default="echo", choices=[
        "echo", "split", "pipeline", "large", "half-close", "truncated",
        "bad-length", "idle", "slow-header", "slow-reader",
    ])
    parser.add_argument("--text", default="hello")
    args = parser.parse_args()
    body = args.text.encode("utf-8")

    with socket.create_connection((HOST, PORT), timeout=5) as sock:
        sock.settimeout(5)
        if args.case == "bad-length":
            sock.sendall(struct.pack("!I", 1025))
            expect_closed(sock)
            return
        if args.case == "truncated":
            sock.sendall(struct.pack("!I", 5) + b"he")
            sock.shutdown(socket.SHUT_WR)
            expect_closed(sock)
            return
        if args.case == "idle":
            print("connected without sending; wait about 35 seconds")
            sock.settimeout(35)
            expect_closed(sock)
            return
        if args.case == "slow-header":
            sock.sendall(b"\x00\x00")
            print("only 2 header bytes sent; waiting for frame timeout")
            sock.settimeout(15)
            expect_closed(sock)
            return
        if args.case == "slow-reader":
            # Intentionally refuse to receive: this is an abnormal stress client.
            sock.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 1024)
            sock.settimeout(2)
            print("sending many requests without receiving replies")
            try:
                sock.sendall(frame(b"x" * 1024) * 20000)
            except (socket.timeout, ConnectionError) as exc:
                print("sender stopped:", type(exc).__name__)
            print("keep refusing replies for 13 seconds; watch server logs")
            time.sleep(13)
            return
        if args.case == "pipeline":
            bodies = [b"one", b"two", "你好".encode("utf-8")]
            sock.sendall(b"".join(frame(item) for item in bodies))
            for expected in bodies:
                actual = recv_frame(sock)
                assert actual == expected, (actual, expected)
                print("echo:", actual.decode("utf-8"))
            return
        if args.case == "large":
            body = b"x" * 1024
        packet = frame(body)
        if args.case == "split":
            sock.sendall(packet[:2])
            print("sent 2 header bytes; pausing for 0.6 seconds")
            time.sleep(0.6)
            sock.sendall(packet[2:5])  # The rest of the header and one body byte.
            print("sent the rest of the header and 1 body byte; pausing again")
            time.sleep(0.6)
            sock.sendall(packet[5:])
        else:
            sock.sendall(packet)
        if args.case == "half-close":
            sock.shutdown(socket.SHUT_WR)
            print("write side closed; still receiving")
        actual = recv_frame(sock)
        assert actual == body, (actual, body)
        if args.case == "large":
            print("echo verified:", len(actual), "body bytes")
        else:
            print("echo:", actual.decode("utf-8"))
        if args.case == "half-close":
            expect_closed(sock)


if __name__ == "__main__":
    main()
~~~

## 10. 逐步实验：先预测，再运行，再解释

以下用 Windows 命令；Linux 改用 `python3 state_client.py`。始终保持终端 A 的服务端运行。每次实验都记录“预期、实际、解释”。

### 实验 1：消息头与正文分段到达

~~~powershell
python .\state_client.py --case split --text hello
~~~

预期：前两字节不能解出长度；头完整后进入 BODY；收到全部正文才回显。客户端最后打印 `echo: hello`。

暂停只是提高看到分段读取的机会，TCP 不保证特定的 `recv()` 次数。不要把 `sleep()` 当成消息边界方案。

**验收：**画出 HEADER → HEADER → BODY → HEADER，并解释每步 `in_len` 的含义。

### 实验 2：连续三条消息

~~~powershell
python .\state_client.py --case pipeline
~~~

预期依次打印 `one`、`two`、`你好`。一次发送可能对应一次或多次接收，但解析结果必须正好三条，保持顺序。

**验收：**指出解析代码中的循环，并解释为什么处理完第一条不能随意清空整个输入数组。

### 实验 3：大响应在多轮中续发

~~~powershell
python .\state_client.py --case large
~~~

正文为 1024 字节，加 4 字节头共 1028。默认每次最多提交 256 字节，通常可观察到 `pending`：772 → 516 → 260 → 4 → 0。

实际 `send()` 可以返回比请求更小的正数，所以也可能出现更多步骤。客户端依然应收到完整 1024 字节正文。

**验收：**能根据日志算出偏移，知道这些多轮主要来自人为预算，不能声称实验必然触发了操作系统的短写。

进一步可以停掉旧服务端，重编译为更小的发送预算：

~~~powershell
gcc -std=c11 -Wall -Wextra -O0 -g -DSEND_SLICE=7 .\state_server_windows.c -o .\state_server.exe -lws2_32
.\state_server.exe
~~~

Linux/WSL 对应命令是：

~~~bash
gcc -std=c11 -Wall -Wextra -O0 -g -DSEND_SLICE=7 state_server_linux.c -o state_server
./state_server
~~~

预算必须是正数。练习结束后按当前平台的原命令重编译恢复默认值。

### 实验 4：半关闭后仍收到响应

~~~powershell
python .\state_client.py --case half-close --text "reply before close"
~~~

预期：客户端打印结束发送的提示，收到完整响应，然后看到服务器关闭。服务端可能在观察 EOF 之前就已交出响应，所以 `DRAINING` 时队列不一定非空。

**验收：**知道客户端停止发送后仍能接收，知道队列发空的收尾行为。

如果要更清楚地观察 DRAINING 时仍有输出，可使用 `SEND_SLICE=7` 运行此实验，但事件顺序依然受调度影响。

### 实验 5：正文被截断

~~~powershell
python .\state_client.py --case truncated
~~~

声明正文 5 字节，只发 `he` 就半关闭。预期服务端记录 `truncated frame at EOF`，不把 `he` 当完整消息回显。

**验收：**能说明截断输入的策略来自应用协议，而不是 TCP 自动补齐正文。

### 实验 6：长度越界

~~~powershell
python .\state_client.py --case bad-length
~~~

声明 1025，超过本协议上限。预期服务端记录 `invalid body length`，客户端观察到 EOF 或重置。

然后再次运行普通 `hello`：应仍然成功，说明一个错误客户端没有让服务端退出。

**验收：**找到“先校验，后复制”的代码位置。练习把长度改成 0 和 `0xffffffff`，也应拒绝。

### 实验 7：一个沉默连接不拖住另一个

终端 B：

~~~powershell
python .\state_client.py --case idle
~~~

在等待期间，终端 C 进入实验目录执行：

~~~powershell
python .\state_client.py --text "client C works"
~~~

预期 C 很快收到回显；B 约 30～31 秒后看到关闭，服务端原因是 `idle timeout`。

**验收：**知道循环没有在 B 上阻塞等待请求。

### 实验 8：只有半个消息头，不能永久占用

~~~powershell
python .\state_client.py --case slow-header
~~~

只发头的前两字节，不再继续。预期约 10～11 秒后关闭，原因是 `frame timeout`，不是等待 30 秒空闲超时。

**验收：**找到 `frame_since` 的设置位置，并确认收到零碎后续字节不会不断重置同一条消息的期限。

### 实验 9：不接收响应的慢客户端与背压

~~~powershell
python .\state_client.py --case slow-reader
~~~

它发送大量最大消息，却不读响应。程序设置发送超时，避免测试客户端永远卡住；服务端日志可能很多。

观察 `read paused`、`read resumed`，以及待发队列是否始终小于等于 4112。客户端发送也可能超时，这符合下游不读取时整个管道逐渐堵住的预期。

网络栈缓冲容量和调度不同，何时真正堵住不保证一致。有时会出现 `write timeout`，有时先发生 `frame timeout`，有时客户端结束实验时才让服务端观察到错误。**验收重点是有限队列和其他连接仍可工作**，不要求某个固定关闭原因。

在终端 C 同时运行普通回显，确认其他连接能取得进展。这个压力客户端只用于单独的教学服务，不需要扩大消息数量。

### 实验 10：达到连接上限与重复复用

将以下代码保存为独立文件 `limit_probe.py`，在实验目录运行 `python .\limit_probe.py`；Linux 使用 `python3 limit_probe.py`：

~~~python
import socket
import time

connections = []
try:
    for _ in range(17):
        connections.append(socket.create_connection(("127.0.0.1", 19100), timeout=3))
        time.sleep(0.05)
    extra = connections[-1]
    extra.settimeout(3)
    try:
        assert extra.recv(1) == b""
    except ConnectionResetError:
        pass
    print("17th connection rejected by the application")
finally:
    for item in connections:
        item.close()
~~~

开始前确认没有其他测试客户端占位。第 17 个可能 TCP 连接成功，然后被应用关闭；`connect()` 成功不保证服务器应用接纳它。

实验结束后再发普通消息，确认旧连接槽位能回收并用于新连接。观察日志中连接编号递增，而句柄数字可能复用。

## 11. 常见错误：从现象追到原因

### 11.1 环境与协议不一致

| 现象 | 常见原因 | 如何检查或修正 |
| --- | --- | --- |
| 找不到 `gcc`、`cl` 或 Python | 工具未安装或终端路径未配置 | 先看 [[01-基础入门/Socket编程环境]] |
| 找不到 Winsock 函数的链接符号 | Windows GCC 忘记 Socket 库 | 在编译命令末尾加 `-lws2_32` |
| 找不到 `sys/socket.h` | 在 Windows 原生编译 Linux 专用源文件 | Windows 请编译 `state_server_windows.c`；Linux/WSL 才编译 `state_server_linux.c` |
| `bind` 报 Windows 10048 / Linux 地址占用 | 已有程序占用 19100 | 先停止旧的实验服务端，再运行新版本 |
| Windows 提示无法覆盖 `.exe` | 旧程序仍在运行 | 在服务端窗口按 Ctrl+C，再编译 |
| 客户端连接被拒绝 | 服务端没启动或端口不同 | 确认终端 A 有 listening 日志，双方都用 19100 |
| 用 Ncat 输入 hello 后被关闭 | 本章是二进制长度前缀协议，不是行协议 | 使用给出的 Python 客户端 |
| 中文乱码 | 客户端文本编码或终端显示不同 | 按 UTF-8 编码，完整正文后解码 |

Windows 可在 PowerShell 用 `Get-NetTCPConnection -LocalPort 19100` 观察相关连接；Linux 可用 `ss -tnp`。端口探测工具通常只证明 TCP 可连，不能验证本章消息协议。

### 11.2 状态与缓冲区错误

| 错误做法 | 后果 | 正确思路 |
| --- | --- | --- |
| 以为一次 recv 就是一条消息 | 半条误处理、连续消息丢失 | 根据协议累计并循环解析 |
| 用局部变量保存解析进度，返回后丢失 | 下一轮不知道已经读到正文 | 状态放进连接上下文 |
| 多个连接共享一份输入长度 | A 的半条与 B 混合 | 每连接独立数组与计数 |
| 刚看到头就相信长度 | 越界、超大内存、溢出 | 先完整头、再解码、再限制 |
| 对网络字节使用 strlen 或 `%s` | 遇到 `\0` 截断或读越界 | 用明确的实际长度 |
| 处理一条后清空所有输入 | 下一条消息尾部丢失 | 只消费处理过的部分 |
| send 返回正数就清空队列 | 响应缺尾巴 | 只推进实际发送长度 |
| 部分发送后又从数组开头发 | 客户端收到重复字节 | 从 `out_begin` 续发 |
| 暂时不可写时 while 原地重试 | CPU 空转，其他人得不到处理 | 回到等待，保留写关注 |
| 永远把所有连接加到写集合 | 无输出也不断被唤醒 | 有待发数据才关注可写 |
| 队列满了丢输入，却不约定协议错误 | 请求和响应无声消失 | 有限队列、背压或明确拒绝 |
| 恢复写入后不处理已有完整输入 | 没新读事件就停住 | 空间恢复后调用解析函数 |

### 11.3 关闭与计时错误

| 错误做法 | 后果 | 正确思路 |
| --- | --- | --- |
| 把 recv 的 0 当作“暂时没数据” | 不断读取 EOF，空转 | 进入收尾或清理 |
| EOF 一律马上丢弃全部输出 | 半关闭客户端收不到完整响应 | 明确输入是否完整，必要时 DRAINING |
| 只标记槽位空闲，不关 Socket | 句柄和内核资源泄漏 | 统一关闭函数 |
| 关闭后继续用句柄发送 | 操作无效，甚至碰到复用的新连接 | 每个动作后检查生命周期 |
| 删掉 Linux 的 SIGPIPE 处理 | 对断开连接发送可能终止服务端 | 忽略信号或采用适当的发送标志 |
| 把 select 返回 0 当全部连接超时 | 正常连接被误关 | 检查每连接自己的时间 |
| 用系统日历时间计算期限 | 校时后出现误超时或永不超时 | 使用单调时钟 |
| 每来 1 字节都延长消息期限 | 慢速发送者可以长期占用 | 为整条消息设置固定组装期限 |

### 11.4 推荐排查顺序

1. 确认服务端是否监听、客户端是否采用相同协议。
2. 看具体连接编号与底层调用结果，别只写“通信失败”。
3. 追踪 `life`、`parser`、`in_len`、`body_need`。
4. 追踪 `out_begin`、`out_end` 与实际发送字节数。
5. 检查读/写关注条件是否与状态一致。
6. 检查关闭原因和期限，确认是否有统一清理日志。

日志不要直接输出无限长正文或敏感业务内容。用长度和编号就足以定位本章的大多数问题。

## 13. 参考答案与最终阶段检查

### 13.1 入门题参考答案

1. 生命周期、解析进度与输出进度是不同维度。前一条已排队，后一条可能还在组装，连接支持双向收发。
2. 只能确定头已满。先解出长度，再判断剩余 3 字节是否足够，不能凭批次数判断。
3. 不改动已用长度和解析状态，返回循环等待。
4. 新 `out_begin = 65`、`out_end = 100`，待发送 35 字节。
5. `send()` 的确认范围是本机网络栈接受字节；对方处理完成要有业务级确认。
6. 消息头截断，本实验记录 `truncated frame at EOF`，立即关闭并归还资源。
7. 字节已经从内核搬进应用内存，新读通知不负责提醒应用内部还有完整消息。
8. 缓慢发送者可以在每次空闲期限前发送一点点；整条消息的固定期限不会被这些字节无限续期。

### 13.2 最终自测场景

闭上文档，用纸写出以下场景的处理路径：

~~~text
客户端 A 发来半个头。
客户端 B 一次发来两个完整请求。
B 的第一轮发送只成功交出 100 字节。
A 后来补齐头，但长度超限。
B 结束发送，仍在等待响应。
~~~

合格解释应该包括：A/B 独立上下文；A 保留 HEADER 进度，非法长度后关闭；B 循环解析两条并按序排队；发送偏移推进 100；观察 EOF 后在完整消息边界进入 DRAINING，输出发空或超时后清理。

## 14. 下一步：本章怎样连接到工程实践

### 14.1 非阻塞 connect 也需要状态

服务端本实验通过 `accept()` 得到已连接 Socket。客户端若使用非阻塞 `connect()`，可能先返回“连接正在进行”，要进入 CONNECTING 状态，等合适的事件后查询 `SO_ERROR` 判断成功或失败，再进入 OPEN。

不能仅凭可写就宣布连接成功，也不能把正在进行的连接误判为断开。具体平台处理留到 [[TCP客户端]] 与 [[超时、断线与异常]]。

### 14.2 耗时业务与线程池

Socket 非阻塞，不代表数据库、磁盘访问或长计算也不阻塞。一个慢业务函数仍能拖住整个循环。

线程池是预先准备一组工作线程，让它们做耗时工作。通常由事件循环拥有连接和队列，工作线程只接收请求数据，完成后把结果交回；同时检查连接编号/代次是否仍有效，并决定是否需要按请求顺序重排结果。

跨线程队列需要同步；工作结果需要唤醒等待中的事件循环。这些细节不能只靠一个新的状态枚举解决，参考 [[线程与进程模型]]。

### 14.3 优雅停机与优雅关闭

优雅停机可按下面顺序设计：停止接受新连接 → 停止接收新业务 → 已有结果有限时间内发送 → 到总截止时间后统一释放。

本章 DRAINING 处理单个连接收到 EOF 后的收尾。整台服务停机还要协调监听 Socket、业务任务和所有连接；一定保留最终期限，不能无限等待慢客户端。

### 14.4 重连、心跳与连接池

- **心跳**：双方定期交换小消息，帮助发现通信或应用长期无响应；不能等同于任意字节到达。
- **重连**：旧连接失败后建立新连接。不能把旧解析状态和未确认请求无条件搬过去，否则可能造成重复业务。
- **连接池**：把可复用的连接保存起来供之后使用，要定义借出、归还、失效检查和空闲回收规则。

这些都是在本章的上下文、状态、期限和所有权基础上扩展，见 [[05-协议与工程实践/心跳、超时与重连]]。

### 14.5 更复杂的协议与 I/O 接口

HTTP、TLS 或自定义 RPC 会有更多解析与业务阶段，但基本问题不变：保存进度、验证边界、限制排队、明确结束。

epoll、IOCP 等接口改变等待或完成通知机制，不会替应用自动解决消息边界、慢客户端、资源回收和业务确认。
