# 字节、编码与数据边界

## 学习目标

学完本章后，你应该能够：

- 区分位（bit）、字节（byte）、字符（character）和 Unicode 码点。
- 解释“字符串编码成字节、字节解码成字符串”的过程，并定位常见乱码。
- 看懂一段十六进制数据，知道文本和二进制数据在 Socket 中都只是字节。
- 理解 TCP 没有消息边界，能够选择一种 framing（消息分帧）方案。
- 写出不会因为半包、粘包或一次 `send` 未发完而出错的基本收发逻辑。

## 1. 先建立统一的词汇

### 1.1 位、字节与十六进制

**位（bit）**只有 `0` 和 `1` 两种状态，通常写作 `b`；**字节（byte）**是计算机处理数据的基本单位，通常为 8 个位，写作 `B`。

> 1 byte = 8 bits，能表示 `2^8 = 256` 个不同值，即 `0x00` 到 `0xFF`。

网络编程里常用十六进制，因为一个十六进制数字正好对应 4 个 bit，两个十六进制数字对应一个字节。例如：

```text
二进制：  1110 0100  1011 1000  1010 1101
十六进制：   E4        B8        AD
十进制：     228       184       173
```

这里的 `E4 B8 AD` 只是三个字节；它们是否代表汉字，要看双方约定的编码。

在 C 中，`char` 占用 1 个 C 字节，但标准只保证它至少有 8 个 bit。Socket 实践里通常使用 8-bit 字节；需要明确位宽时可使用 `<stdint.h>` 中的 `uint8_t`、`uint32_t` 等固定宽度类型。

### 1.2 字符、码点和字节不是一回事

- **字符**是人看到的抽象符号，例如 `A`、`中`、`🙂`。
- **Unicode 码点（code point）**是 Unicode 为一个抽象字符或符号分配的编号，例如 `A` 是 `U+0041`，`中` 是 `U+4E2D`。
- **编码（encoding）**规定码点如何变成字节。UTF-8、UTF-16、UTF-32 都是 Unicode 编码方式。
- **字节序列**是最终可放进文件或 Socket 的数据，例如 UTF-8 中 `中` 是 `E4 B8 AD`。

同一个字符在不同编码下，字节数可能不同；同一串字节用错误编码解码，也会得到乱码或解码失败。

#### Unicode 码点到底是什么

可以把 Unicode 想成一份世界通用的“字符编号表”。这份表先回答“这个符号是谁”，而不是回答“它在网络上用几个字节发送”。

例如：

| 内容 | Unicode 码点 | 含义 |
| --- | --- | --- |
| `A` | `U+0041` | 拉丁大写字母 A |
| `中` | `U+4E2D` | 汉字“中” |
| `🙂` | `U+1F642` | 一个表情符号 |
| `€` | `U+20AC` | 欧元符号 |

`U+` 表示“这是 Unicode 编号”，后面的十六进制数字才是编号本身。`U+4E2D` 不是网络中直接发送的 4 个字符，也不是固定的 4 个字节；它只是一个抽象编号。

从“人看到的字”到“网络中的数据”需要经过两步：

```text
字符“中”
  -> 查 Unicode 表，得到码点 U+4E2D
  -> 使用 UTF-8 编码，得到字节 E4 B8 AD
  -> Socket 发送这 3 个字节
```

因此要区分三个问题：

1. **字符是什么？** 人类想表达的符号，例如“中”。
2. **码点是多少？** Unicode 中的编号，例如 `U+4E2D`。
3. **编码后有哪些字节？** 发送时真正放进缓冲区的内容，例如 UTF-8 的 `E4 B8 AD`。

码点和编码不是一回事：同一个码点可以用 UTF-8、UTF-16 或 UTF-32 表示；不同编码得到的字节序列和长度可能不同。Socket 只处理最后的字节，不理解 `U+4E2D` 代表汉字。

还要注意，“一个用户看到的字符”有时不一定对应一个码点。例如带组合音标的文字、部分旗帜 emoji 可能由多个码点组合显示。学习 Socket 时，最重要的结论是：协议长度通常按**字节**计算，不按屏幕上看到的字符数计算。

## 2. 编码与解码：文字如何进入网络

### 2.1 两个方向

```text
发送端：字符串 --编码（encode）--> 字节序列 --send--> 网络
接收端：网络 --recv--> 字节序列 --解码（decode）--> 字符串
```

编码和解码必须使用同一种约定。协议文档应明确写出，例如“所有文本字段使用 UTF-8，不带 BOM”。不要把“机器默认编码”当成协议规则，因为不同操作系统、语言运行时或容器的默认值可能不同。

### 2.2 UTF-8 的关键特性

UTF-8 是变长编码：

| Unicode 码点范围         | UTF-8 字节数 | 首字节形式（示意）                             |
| -------------------- | --------: | ------------------------------------- |
| `U+0000`–`U+007F`    |         1 | `0xxxxxxx`                            |
| `U+0080`–`U+07FF`    |         2 | `110xxxxx 10xxxxxx`                   |
| `U+0800`–`U+FFFF`    |         3 | `1110xxxx 10xxxxxx 10xxxxxx`          |
| `U+10000`–`U+10FFFF` |         4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

因此，“字符数”和“字节数”不能混用：字符串 `中A` 有 2 个字符，但 UTF-8 有 4 个字节（`E4 B8 AD 41`）。`recv(fd, buf, 4, 0)` 的 4 是字节数，不是字符数。

UTF-8 的续字节都以 `10` 开头。接收端可以据此判断一个字符预计需要几个字节，但**不要**在网络层按字符切分；网络层应先按协议取得完整字节字段，再交给字符解码器。一个汉字的 3 个字节可能分三次到达。

### 2.3 C 字符串的额外规则：结尾的 `\0`

C 的字符串本质是“以零字节结尾的 `char` 数组”：

```c
char text[] = "ABC";       // 4 个字节：41 42 43 00
size_t n = strlen(text);    // 3，不包含结尾的 00
```

`strlen` 只能用于这种文本字符串，不能用于任意网络数据：二进制数据中间可能恰好有 `0x00`，此时 `strlen` 会提前停止。收发二进制数据必须始终同时保存“指针 + 明确长度”。

```c
uint8_t payload[] = {0x41, 0x00, 0x42};
size_t payload_len = sizeof payload; // 3，不能用 strlen(payload)
```

### 2.4 乱码的排查顺序

看到乱码时按以下顺序检查：

1. 发送端实际使用了什么编码（不要只看源码编辑器显示）。
2. 编码后的字节是否在发送过程中被截断、拼接或改写；先打印十六进制。
3. 接收端是否用同一种编码解码，并按完整字段解码。
4. 是否把 UTF-8 字节误当成 Latin-1/GBK，或把字符数误当作字节数。
5. 文本字段是否包含 BOM、非法 UTF-8 或未声明的规范化形式。

## 3. 网络中的数据：一切最终都是字节

### 3.1 文本协议与二进制协议

HTTP、JSON、简单的行协议属于文本协议，便于人阅读和调试，但需要约定字符编码、转义规则和数字格式。图片、压缩包、序列化结构体等属于二进制数据，不能假设可打印，也不能用字符串函数处理。

无论哪一种，Socket API 看到的都是字节缓冲区：

```c
ssize_t count = recv(fd, buffer, capacity, 0);
// count > 0：收到 count 个字节；count == 0：对端有序关闭；count < 0：出错
```

这行代码可以拆成“调用哪个 Socket、把数据放到哪里、最多放多少、使用什么选项”四个问题：

| 参数 | 含义 | 初学者理解 |
| --- | --- | --- |
| `fd` | 文件描述符（file descriptor） | 操作系统分配给已连接 Socket 的整数句柄，告诉内核从哪个连接读取 |
| `buffer` | 接收缓冲区首地址 | 一块由程序准备好的内存，内核把收到的字节写入这里 |
| `capacity` | 缓冲区最多可写入的字节数 | 防止内核写出数组范围；它是容量，不是一定会收到的数量 |
| `0` | `flags` 标志位 | 这里表示使用默认行为；某些系统可传入额外选项 |

返回值类型 `ssize_t` 是“可以表示负数的字节数类型”：

- `count > 0`：本次实际取到了 `count` 个字节。它可能小于 `capacity`，也可能只是完整消息的一部分。
- `count == 0`：对 TCP 来说，对端已经有序关闭发送方向；当前字节流没有更多数据。
- `count < 0`：读取失败，需要结合 `errno` 判断是被信号中断、暂时没有数据、连接重置还是其他错误。

例如：

```c
char buffer[1024];
ssize_t count = recv(fd, buffer, sizeof buffer, 0);
```

这里 `sizeof buffer` 是 1024，表示“最多写入 1024 个字节”，不是“本次一定收到 1024 个字节”。如果本次只到达 5 个字节，`recv` 可能立即返回 5。`buffer` 也不会自动补上字符串结尾的 `\\0`；如果要把收到的内容当 C 字符串使用，必须确认有空间后手动添加，并且只能对文本数据这样做。

`buffer` 中的内容不保证以 `\0` 结尾，也不保证一次正好包含一条业务消息。

### 3.2 字节序（endianness）与网络字节序

多字节整数在内存中的排列有大小端差异。例如数字 `0x12345678`：

```text
大端（big-endian）：    12 34 56 78
小端（little-endian）： 78 56 34 12
```

Internet 协议通常规定使用**网络字节序**，即大端。C 中可用 `htons`/`ntohs`（16 位）和 `htonl`/`ntohl`（32 位）转换。不要直接把 C 结构体强转后发送：结构体可能有填充、对齐、大小端和编译器布局差异。应逐字段序列化，并明确字段长度。

## 4. 数据边界：一条消息在哪里结束

### 4.1 TCP 是字节流，不是消息队列

TCP 保证字节按顺序、可靠地到达，但不保留应用层的 `send` 次数。这里的“`send` 次数”是指：**发送端程序调用 Socket API 中 `send()` 函数的次数**，不是网卡发了几个包，也不是对端必须调用几次 `recv()`。

例如发送端写：

```c
send(fd, "HELLO", 5, 0);  // 第 1 次 send 调用
send(fd, "WORLD", 5, 0);  // 第 2 次 send 调用
```

程序明确做了两次调用，但 TCP 内核只看到需要按顺序发送的 10 个字节。它可能把两次调用的数据合并后发送，也可能因为缓冲区、网络分段等原因拆开。接收端可能看到：

```text
"HEL" + "LOWORLD"       // 半包 + 粘包
"HELLOWORLD"             // 粘在一起
"H" + "ELLO" + "WORLD"  // 多次半包
```

这不是 TCP 出错，而是 TCP 只知道字节流。应用协议必须自行定义 framing（分帧），让接收端知道何时拥有一条完整消息。也就是说，发送端的两次 `send` 只是两次“把字节交给本机内核”的动作，对端看不到这个调用边界。

### 4.2 UDP 的对比

UDP 保留数据报边界：一次 `sendto` 对应一次 `recvfrom`（前提是接收缓冲区足够，且数据报未丢失）。但 UDP 不保证到达、顺序或不重复；缓冲区太小可能导致数据报被截断。因此“有边界”不等于“可靠”。

## 5. 常见分帧方案

### 5.1 固定长度

每条消息恰好 `N` 个字节，例如 32 字节用户名。

- 优点：解析简单、无需转义。
- 缺点：短消息浪费空间，长消息必须截断或另行设计。
- 注意：`N` 是字节数，不是 UTF-8 字符数；多字节字符不能随意从中间截断。

### 5.2 分隔符

用 `\n`、`\r\n` 或特殊字节标记结尾，例如 `PING\n`。

- 优点：调试直观，适合命令和日志。
- 缺点：正文可能包含分隔符，需要转义或禁止；必须限制单条消息最大长度，避免一直等不到分隔符导致内存增长。
- 解析步骤：在累计缓冲区查找分隔符；找不到就继续接收；找到后取出此前数据，保留分隔符之后的剩余字节。

### 5.3 长度前缀（推荐的通用方案）

先发送固定大小的长度字段，再发送指定数量的正文：

```text
+------------+-------------------+
| 4 字节长度 | payload（N 字节） |
+------------+-------------------+
```

例如 `N = 5`，网络字节序长度为 `00 00 00 05`，后面跟 `HELLO`。接收端必须先完整读满 4 字节，再解析 N，检查 `0 <= N <= MAX_FRAME`，最后读满 N 字节。

长度前缀解决的是“在哪里结束”，不是安全校验：长度仍然可能被恶意写成超大值或整数溢出。解析时先用足够宽的无符号类型计算，并设置合理上限。

### 5.4 自描述格式

JSON、CBOR、Protocol Buffers 等格式内置字段结构或长度信息。

- 优点：字段演进、类型表达和工具支持较好。
- 缺点：仍需解决外层分帧；例如 TCP 上的 JSON 通常要再套长度前缀或换行分隔。

## 6. TCP 接收器的正确思路

### 6.1 `send` 和 `recv` 都可能只处理一部分

即使缓冲区空间足够，`send` 也可能只发送前 `k` 个字节；`recv` 也可能只返回当前已经到达的 `k` 个字节。应使用“偏移量 + 剩余长度”循环：

```c
int send_all(int fd, const void *data, size_t length) {
    const uint8_t *p = data;
    size_t sent = 0;
    while (sent < length) {
        ssize_t n = send(fd, p + sent, length - sent, 0);
        if (n > 0) { sent += (size_t)n; continue; }
        if (n < 0 && (errno == EINTR)) continue;
        return -1; // 对端关闭、超时或其他错误
    }
    return 0;
}
```

这段函数的目标是：**尽量把 `data` 指向的 `length` 个字节全部交给 TCP Socket；只要中途没有不可恢复的错误，就一直尝试。** 函数名里的 `all` 指“全部字节”，不是说数据已经被对端业务处理完。

逐行理解如下：

1. `int send_all(int fd, const void *data, size_t length)`：定义一个函数。传入 Socket 描述符 `fd`、数据起始地址 `data` 和要发送的字节数 `length`。返回 `0` 表示这次循环完成，返回 `-1` 表示失败。
2. `const uint8_t *p = data;`：把通用指针转换为“指向字节的指针”。`uint8_t` 表示一个 8 位无符号字节；`const` 表示函数不会修改原数据。
3. `size_t sent = 0;`：记录已经成功交给内核的字节数，开始时一个字节也没有发送。
4. `while (sent < length)`：只要已发送数量小于总长度，就继续发送。
5. `p + sent`：把指针向后移动 `sent` 个字节。例如已经发送 3 个字节，就从第 4 个字节开始继续。
6. `length - sent`：告诉 `send` 本次最多还需要发送多少字节。
7. `ssize_t n = send(...)`：调用一次系统接口。返回正数表示本次实际发送了多少字节；可能小于请求的数量。
8. `if (n > 0) { sent += (size_t)n; continue; }`：本次发送成功，就把 `sent` 增加 `n`，然后回到循环开头继续发送剩余部分。
9. `if (n < 0 && (errno == EINTR)) continue;`：如果调用被信号打断，数据并不一定有问题，直接重新尝试。`errno` 是系统调用失败后提供的错误原因。
10. `return -1;`：如果返回 0、其他负数错误，或发生超时、连接关闭等情况，就停止并报告失败。阻塞 TCP 中，返回 0 通常意味着对端关闭了连接。
11. `return 0;`：循环结束，说明本次调用要求的所有 `length` 个字节都已交给本机内核。

假设要发送 10 个字节，但三次 `send` 分别只接受了 4、3、3 个字节，变量变化如下：

| 循环 | `sent`（开始） | 本次请求 | `send` 返回 `n` | `sent`（结束） |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0 | 10 | 4 | 4 |
| 2 | 4 | 6 | 3 | 7 |
| 3 | 7 | 3 | 3 | 10 |

注意两个边界：

- `send` 返回成功，只表示字节已被本机内核接受，不表示对端程序已经读取或处理。
- 非阻塞 Socket 还要处理 `EAGAIN/EWOULDBLOCK`。这时不能紧密死循环，应保存剩余数据，等下一次“可写”事件再继续。

生产代码还应处理非阻塞 Socket 的 `EAGAIN/EWOULDBLOCK`，并把“尚未发送的部分”保存到连接状态中，交给下一次可写事件处理。

### 6.2 用累计缓冲区解析长度前缀

长度前缀协议假设每条消息都是：

```text
前 4 字节：正文长度 N（网络字节序）
后 N 字节：正文 payload
```

关键难点是：TCP 一次 `recv` 可能只给你半个长度字段，也可能同时给出多条消息。因此不能“每次 `recv` 后立刻把缓冲区当成一条消息”，而要准备一个**累计缓冲区**：新收到的字节先追加进去，解析成功后再移除已经消费的部分。

设缓冲区中已有 `used` 个字节，解析循环可写成：

```text
while true:
    如果 used < 4：继续 recv，等待长度字段
    N = 按网络字节序读取前 4 字节
    如果 N > MAX_FRAME：关闭连接或拒绝该帧
    如果 used < 4 + N：继续 recv，等待完整 payload
    取出 [4, 4+N) 作为一条消息
    删除已取出的字节，剩余字节留给下一条消息
```

逐步解释：

1. `used < 4`：连完整的长度字段都没有收到。先继续 `recv`，不要猜测长度。
2. `N = ...`：当至少有 4 个字节时，按网络字节序把前 4 字节转换成整数。网络字节序通常是大端，不能直接按本机整数布局读取。
3. `N > MAX_FRAME`：长度来自网络，不能盲目信任。先检查上限，防止恶意长度导致巨额内存分配或整数溢出。
4. `used < 4 + N`：长度知道了，但正文还没收齐。继续接收，保留当前已有字节。
5. `取出 [4, 4+N)`：现在才拥有一条完整消息。把这 N 个字节交给业务层；如果是文本，再按约定编码解码。
6. `删除已取出的字节`：如果缓冲区后面还有字节，它们可能属于下一条消息，必须保留下来，不能丢弃。
7. 解析一条后继续循环：一次 `recv` 可能带来两条甚至更多完整消息，所以要不断检查缓冲区。

举一个长度为 5、正文为 `HELLO` 的例子。完整帧是：

```text
00 00 00 05 48 45 4C 4C 4F
```

假设网络分三次到达：

| 到达次数 | 新收到的字节 | 累计缓冲区 | 解析结果 |
| ---: | --- | --- | --- |
| 1 | `00 00` | `00 00` | 少于 4 字节，不知道 N |
| 2 | `00 00 05 48` | `00 00 00 05 48` | 知道 N=5，但只有 1 个正文字节 |
| 3 | `45 4C 4C 4F` | 完整 9 字节 | 取出 `HELLO`，缓冲区变空 |

再假设一次 `recv` 收到了两条连续帧：

```text
00 00 00 05 HELLO 00 00 00 05 WORLD
```

解析第一条后，不能把后面的 `WORLD` 丢掉；应把已消费的 9 字节移走，留下第二个长度字段和正文，然后循环解析第二条。这个“保留剩余字节”的动作正是累计缓冲区的核心。

实现时通常维护三项状态：

```text
buffer：一块可容纳累计数据的内存
used：其中已经写入了多少字节
offset：从哪里开始寻找下一条尚未解析的帧
```

收到数据时追加到 `buffer + used`，解析成功后增加 `offset`；当剩余数据被消费完，可以把 `used` 和 `offset` 归零，或把未消费的尾部移动到缓冲区开头。无论采用哪种实现，都必须保证：不越界、不接受超过最大长度的帧、不丢掉下一条消息的前半部分。

一次 `recv` 可能同时带来半条消息和下一条消息的一部分，所以“解析出一条后继续循环”很重要。不要每次 `recv` 后都假设缓冲区恰好是一条消息。

## 7. 一个可执行的练习

实现一个 TCP 回显协议：

1. 帧格式为 `4 字节大端长度 + UTF-8 正文`。
2. 服务端最多接受 1 MiB 正文；超过上限立即返回错误并关闭连接。
3. 客户端发送 `你好，Socket`，故意把帧拆成多次 `send`。
4. 服务端用多次 `recv` 组装完整帧，原样回显字节；客户端完整收齐后再 UTF-8 解码。
5. 用十六进制输出检查：长度字段应是字节数，而不是中文字数。

测试用例至少包括：空消息、1 字节 ASCII、单个中文字符、4 字节 emoji、连续两帧、长度字段被拆开的情况、非法 UTF-8 和超过最大长度的情况。

## 常见误区

| 误区 | 正确理解 |
| --- | --- |
| 一次 `send` 对应一次 `recv` | TCP 只提供有序字节流，必须自行分帧 |
| `recv` 返回 0 表示“暂时没数据” | 对阻塞 TCP 而言表示对端有序关闭；非阻塞暂时没数据通常是 `EAGAIN` |
| 用 `strlen` 获取网络数据长度 | 网络数据可能是二进制或含 `0x00`，应显式传长度 |
| 中文是 1 个字节 | UTF-8 中常见中文通常是 3 个字节，emoji 常为 4 个字节 |
| 长度字段写入主机内存后直接发送 | 必须规定字段宽度和网络字节序，避免大小端/对齐问题 |
| 收到半个 UTF-8 字符就立即解码 | 先按消息边界收齐字节，再整体解码；流式文本需使用可保存状态的解码器 |
