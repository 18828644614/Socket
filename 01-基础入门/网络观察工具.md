# 网络观察工具

## 学习目标

- [ ] 能区分“观察端口/连接”和“观察实际数据包”两类工具
- [ ] 能使用 Windows 或 Linux 命令定位一个 Socket 对应的进程
- [ ] 能读懂监听、已建立、等待关闭等常见 TCP 状态
- [ ] 能使用 Wireshark 或 tcpdump 验证数据是否真正经过网络协议栈
- [ ] 遇到连接问题时，能够从地址、端口、进程、连接状态和数据包五个角度排查

## 章节

### 查看监听与连接

网络观察的第一步通常不是抓包，而是先确认程序和端口的状态。对于 TCP 服务器，至少需要回答三个问题：

1. 服务器是否真的在指定地址和端口上监听？
2. 客户端是否成功建立了 TCP 连接？
3. 这个端口或连接究竟属于哪个进程？

#### 先理解地址、端口和连接的显示形式

工具经常用下面的形式显示一个端点：

```text
本地地址:本地端口  <->  远端地址:远端端口
```

例如：

```text
127.0.0.1:8080  <->  127.0.0.1:53124
```

- `127.0.0.1:8080`：服务器在本机回环地址的 8080 端口提供服务。
- `127.0.0.1:53124`：客户端临时使用的端口。客户端通常由操作系统自动分配一个临时端口，因此每次连接都可能不同。
- `127.0.0.1`：只能从本机访问。若服务器绑定的是 `0.0.0.0:8080`，通常表示接受本机所有 IPv4 网卡地址上的连接；`[::]:8080` 则表示 IPv6 的类似含义。

“服务器能在本机访问、其他电脑不能访问”时，优先检查绑定地址和防火墙，而不是立刻怀疑 Socket 收发代码。

#### Windows：`netstat` 与 PowerShell

在 Windows 中，可以先使用以下命令：

```powershell
# 查看所有 TCP 监听端口及其进程 ID（PID）
netstat -ano -p tcp

# 只查找 8080 端口
netstat -ano | Select-String ':8080'

# 根据 PID 找到程序
Get-Process -Id <PID>

# PowerShell 方式查看 TCP 连接与监听项
Get-NetTCPConnection -LocalPort 8080

# 查看 UDP 端口的归属
Get-NetUDPEndpoint -LocalPort 8080
```

`netstat -ano` 中最常见的列如下：

| 列 | 含义 |
|---|---|
| Proto | 协议，通常是 TCP 或 UDP |
| Local Address | 本机 IP 地址和端口 |
| Foreign Address | 对端 IP 地址和端口；监听状态通常显示为 `0.0.0.0:0` 或 `*:*` |
| State | TCP 当前状态；UDP 无连接状态，所以通常没有这一列 |
| PID | 拥有该 Socket 的进程 ID |

#### Linux：`ss`、`lsof` 与 `ip`

在 Linux 中优先使用 `ss`；它比旧工具 `netstat` 更常见、速度也更好：

```bash
# 查看所有 TCP 监听端口，并显示进程信息
sudo ss -ltnp

# 查看 8080 端口
sudo ss -ltnp 'sport = :8080'

# 查看当前 TCP 连接
sudo ss -tnp

# 查看 UDP Socket
sudo ss -lunp

# 从“哪个进程打开了哪个网络文件”观察
sudo lsof -nP -iTCP:8080

# 查看本机 IP 地址和网卡状态
ip addr

# 查看路由表，确认默认网关
ip route
```

`sudo` 的作用是让工具显示其他用户进程的信息。没有管理员权限时，端口和连接仍可能看得到，但进程名和 PID 可能不完整。

#### 重要 TCP 状态

TCP 是有连接状态的协议。观察工具显示的状态是操作系统内核对连接生命周期的记录，不是应用层协议的状态。

| 状态 | 简明含义 | 初学阶段的排查提示 |
|---|---|---|
| `LISTEN` | 服务器正在等待新连接 | 没有 `LISTEN` 时，先检查 `bind()`、`listen()` 是否成功以及端口是否被占用 |
| `SYN-SENT` | 客户端已发起连接，正在等服务器响应 | 长时间停留可能是地址错误、服务未启动、防火墙或网络不可达 |
| `SYN-RECEIVED` | 服务器收到连接请求，等待客户端最终确认 | 短暂出现正常；长期存在要考虑握手包被拦截或客户端异常 |
| `ESTABLISHED` | TCP 三次握手完成，可双向传输字节 | 只表示传输通道建立，不表示业务登录或请求已经成功 |
| `FIN-WAIT-1` / `FIN-WAIT-2` | 本端主动关闭，等待对端结束 | 常见于客户端结束连接后的过渡阶段 |
| `CLOSE-WAIT` | 对端已经关闭，本端程序还没关闭自己的 Socket | 若大量长期存在，通常提示程序没有在读到 EOF 后正确 `close()` |
| `TIME-WAIT` | 本端主动关闭后保留一段时间，防止旧报文影响新连接 | 少量存在正常；不要把它当成端口泄漏直接强行清理 |

`TIME-WAIT` 容易被误解。它的存在是 TCP 可靠关闭的一部分：既可以让最后的确认报文有机会重传，也可以避免旧连接的延迟报文混入之后使用相同四元组的新连接。短时间内大量创建、关闭连接时看到它并不代表程序一定出错。

TCP 连接由四元组唯一标识：

```text
(源 IP, 源端口, 目的 IP, 目的端口)
```

所以多个客户端可以同时连接同一个 `服务器IP:8080`，因为它们的源地址或源端口不同。

### 观察数据包

端口和连接状态只能说明“内核认为连接处于什么状态”，不能完整说明“程序实际发送了什么”。当你需要确认握手、重传、RST、DNS 查询或应用数据流向时，需要使用抓包工具。

#### Wireshark：适合初学者的图形化工具

[Wireshark](https://www.wireshark.org/) 可以按时间展示网卡看到的数据包，并解析常见协议字段。开始时建议只做两件事：选择正确网卡，再使用显示过滤器缩小范围。

如果客户端和服务器都运行在 Windows 本机，并通过 `127.0.0.1` 通信，应选择安装 Npcap 后出现的 **Adapter for loopback traffic capture**（回环抓包适配器）。选择普通的 Ethernet 或 Wi-Fi 网卡，可能看不到这部分本机回环流量。

常用显示过滤器：

| 过滤器 | 用途 |
|---|---|
| `tcp.port == 8080` | 显示 TCP 端口为 8080 的报文 |
| `udp.port == 8080` | 显示 UDP 端口为 8080 的报文 |
| `ip.addr == 127.0.0.1` | 显示指定 IPv4 地址相关的报文 |
| `dns` | 只显示 DNS 报文 |
| `http` | 只显示能被解析为 HTTP 的报文 |
| `tcp.flags.reset == 1` | 查找 TCP RST，常用于连接被立即重置的场景 |
| `tcp.analysis.retransmission` | 查找 Wireshark 判断为重传的 TCP 报文 |

筛选时需要先区分两种概念：

- **捕获过滤器**：抓包开始前使用，决定哪些数据包被保存，语法接近 `tcp port 8080`。
- **显示过滤器**：抓包后使用，决定界面显示哪些已捕获的数据，语法如 `tcp.port == 8080`。

这两者语法不同。初学阶段推荐先不设置捕获过滤器，开始抓包后再用显示过滤器；这样即使写错过滤器，也不至于丢失关键数据。

一次正常 TCP 连接，在 Wireshark 中通常可以按顺序看到：

```text
客户端 -> 服务器  SYN
服务器 -> 客户端  SYN, ACK
客户端 -> 服务器  ACK
客户端 -> 服务器  应用数据（可能分多段）
服务器 -> 客户端  ACK / 应用数据
... 
双方交换 FIN、ACK 关闭连接
```

不要把 Wireshark 中每一行都当作“应用程序发送的一条消息”。对 TCP 来说，一条应用消息可能被拆分到多个 TCP 段；多个很小的应用写入也可能合并在一个 TCP 段中。这正是后续 [[消息边界与拆包]] 章节要解决的问题。

#### tcpdump：适合 Linux 终端与服务器环境

`tcpdump` 可以在没有图形界面的 Linux 机器上抓包。常用命令如下：

```bash
# 查看网卡名称
ip link

# 在 eth0 上观察 TCP 8080 端口，-n 表示不进行名称解析
sudo tcpdump -i eth0 -n 'tcp port 8080'

# 观察回环接口上的本地 Socket 通信
sudo tcpdump -i lo -n 'tcp port 8080'

# 保存为 pcap 文件，之后用 Wireshark 打开分析
sudo tcpdump -i eth0 -n -w socket-8080.pcap 'tcp port 8080'

# 读取已保存文件
tcpdump -n -r socket-8080.pcap
```

`-n` 很重要：它关闭 IP 到域名、端口到服务名的解析，避免工具为了显示友好名称而额外发起 DNS 查询，也让输出更接近原始地址和端口。

抓包文件可能包含账号、Cookie、请求内容或内网地址。练习时只在自己的测试环境抓包，保存和分享前先确认不包含敏感信息。HTTPS 的有效负载已经加密，但域名、IP、端口和通信时序等元数据仍可能可见。

#### 常用辅助观察命令

| 目标 | Windows | Linux | 说明 |
|---|---|---|---|
| 验证 IP 可达性 | `ping <IP>` | `ping <IP>` | 使用 ICMP；成功不代表 TCP 端口一定可访问 |
| 检查路由路径 | `tracert <域名或IP>` | `traceroute <域名或IP>` | 观察到达目标时经过的路由跳数；某些设备会屏蔽探测 |
| 查询 DNS | `nslookup <域名>` | `dig <域名>` 或 `nslookup <域名>` | 确认域名能否解析及解析结果 |
| 测试 TCP 端口 | `Test-NetConnection <主机> -Port 8080` | `nc -vz <主机> 8080` | 验证到指定 TCP 端口的连接是否可建立 |
| 观察本机地址 | `ipconfig` | `ip addr` | 确认本机网卡与 IP 地址 |
| 观察路由表 | `route print` | `ip route` | 确认默认网关和到目标网段的下一跳 |

这些工具各自验证的范围不同。例如 `ping` 成功，只能说明 ICMP 探测得到响应；服务器的 TCP 8080 端口仍可能未监听、被防火墙拦截，或只绑定在 `127.0.0.1`。

### 从现象到工具的排查顺序

遇到“客户端连不上服务器”时，建议按由近到远、由低成本到高成本的顺序排查：

1. **确认参数**：主机名/IP、端口、TCP/UDP 是否与服务端一致。
2. **确认服务端监听**：用 `netstat`、`Get-NetTCPConnection` 或 `ss` 查看目标端口是否为 `LISTEN`。
3. **确认绑定地址**：如果只绑定 `127.0.0.1`，外部机器无法连接；需要按需求绑定本机网卡地址或通配地址。
4. **确认进程归属**：通过 PID 找到程序，避免误连到另一个占用相同端口的服务。
5. **确认路径与防火墙**：使用 `ping`、`tracert`/`traceroute`、端口测试工具。注意它们并不能单独证明全部链路正常。
6. **抓包确认事实**：客户端是否发送 SYN，服务器是否收到 SYN，服务器是否回应 SYN-ACK，或者是否出现 RST、重传、ICMP 错误。
7. **再检查应用层**：只有 TCP `ESTABLISHED` 后仍无业务响应时，才进一步检查协议格式、编码、消息边界和业务逻辑。

这个顺序的价值在于避免盲目修改代码。抓包是最接近事实的手段，但在抓包前先用端口和连接状态缩小问题范围，通常会更快。
