# TCP与UDP概念

## 学习目标

学完本章后，你应该能够：

- 说清 TCP 和 UDP 分别解决什么问题。
- 理解“面向连接”和“无连接”不是“有没有网线”的意思。
- 解释 TCP 的可靠性、顺序、流量控制和拥塞控制。
- 理解 TCP 是字节流、UDP 是数据报，以及这对编程的影响。
- 根据业务需求初步选择 TCP 或 UDP。
- 识别“TCP 一定更快”“UDP 一定不可靠”等常见误解。

## 1. TCP 和 UDP 在协议栈中的位置

TCP 和 UDP 都是**传输层协议**，位于 IP 之上、应用协议之下：

```text
应用层：HTTP、DNS、聊天协议、游戏协议
              ↓ 使用
传输层：TCP 或 UDP（端口、进程间交付）
              ↓ 使用
网络层：IP（跨网络寻找主机）
              ↓ 使用
链路层：以太网、Wi-Fi（相邻设备之间传输）
```

IP 主要负责“把数据送到哪台主机”，但不负责把数据交给主机上的哪个程序，也不保证数据一定到达。传输层通过**端口**把数据交给具体进程，并提供不同的传输能力：

| 协议 | 提供的抽象 | 默认提供的能力 |
| --- | --- | --- |
| TCP | 一条连接上的字节流 | 可靠、有序、去重、双向传输 |
| UDP | 一个个独立数据报 | 端口寻址、尽力交付、保留数据报边界 |

“默认提供”很重要：TCP 的能力由内核协议栈实现；UDP 没有提供的确认、重传、排序等能力，如果业务需要，就要由应用协议自行设计。

## 2. 先用生活例子建立直觉

可以把 TCP 想象成**打电话**：

1. 先拨号并确认对方接通。
2. 通话期间双方知道这是一段持续的会话。
3. 说话内容按顺序传递；没有确认的信息需要重说。
4. 任意一方挂断后，这段会话结束。

可以把 UDP 想象成**寄出一张张明信片**：

1. 写好一张明信片，直接写上地址寄出。
2. 不必先建立持续会话。
3. 明信片可能丢失、晚到或顺序改变。
4. 每张明信片是独立的，收件人知道它是一张完整的数据报。

这个比喻只用于建立直觉。实际网络中，TCP 的“重说”由协议栈根据确认和超时完成，并不是应用再次调用一次 `send()`。

## 3. TCP：面向连接的可靠字节流

### 3.1 “面向连接”是什么意思

TCP 通信开始前，双方要先建立一条逻辑连接。连接由四项共同标识：

```text
(源 IP, 源端口, 目的 IP, 目的端口)
```

服务器通常先 `bind()` 和 `listen()`，客户端调用 `connect()`。连接建立后，服务器通过 `accept()` 得到一个专门服务该客户端的已连接 Socket。

```text
客户端                         服务器
socket()                       socket() -> bind() -> listen()
connect()  ---- 三次握手 ---->  accept()
send/recv() <--- 字节流 ----->  send/recv()
close()      ---- 关闭 ----->  close()
```

这里的“连接”是双方内核中维护的一组状态，不是一条永久占用的物理线路。数据仍会经过共享的网卡、路由器和链路；连接只是让双方能够跟踪序号、确认、窗口和关闭状态。

### 3.2 三次握手解决什么问题

建立 TCP 连接时通常会发生三次握手：

```text
客户端                                      服务器
  | -------- SYN（我想建立连接） ----------> |
  | <----- SYN + ACK（我收到了，也同意） --- |
  | -------- ACK（我确认收到了） ----------> |
  |              连接建立                    |
```

三次握手不是为了完成业务，主要用于：

- 确认双方的发送和接收方向都可达。
- 交换初始序号，使后续字节能够编号和确认。
- 协商部分 TCP 参数，例如最大报文段大小。

握手成功只说明 TCP 通道建立，不代表登录成功、请求格式正确或数据库操作成功。应用仍需发送业务数据并等待业务响应。

### 3.3 TCP 的可靠性从哪里来

TCP 的可靠性不是“网络永远不出错”，而是通过一组机制把丢失、乱序和重复尽量隐藏起来：

| 机制 | 作用 | 初学者应记住什么 |
| --- | --- | --- |
| 序号（Sequence Number） | 给字节流中的数据编号 | 接收端能发现缺少或重复的数据 |
| 确认（ACK） | 告诉发送端已收到哪些数据 | 发送端据此判断是否需要重传 |
| 重传 | 超时或发现丢失后再次发送 | 可靠性会带来等待和额外流量 |
| 校验和 | 检查数据是否损坏 | 损坏的数据通常被丢弃，等待重传 |
| 接收排序 | 暂存先到的后续数据 | 应用看到的是有序字节流 |
| 去重 | 丢弃重复到达的数据 | 应用通常不会收到同一 TCP 字节两次 |

#### ACK 不等于业务成功

ACK 只表示 TCP 层已经收到并确认了字节，不表示服务器程序已经执行完业务：

```text
send() 返回成功
  -> 本机内核接受数据
  -> TCP 发送并得到确认
  -> 服务器内核收到数据
  -> 服务器进程读取数据
  -> 服务器执行业务
  -> 服务器返回应用层的“成功”或“失败”
```

因此，转账、下单等业务不能只看 `send()` 或连接状态，必须设计明确的应用层响应；发生超时后还要防止盲目重试导致重复操作。

### 3.4 TCP 的“流”是什么意思

TCP 不保留发送端每次 `send()` 的边界。发送端执行：

```text
send("ABC", 3)
send("DEF", 3)
```

接收端可能得到：

```text
recv -> "A"
recv -> "BCDE"
recv -> "F"
```

也可能一次得到 `"ABCDEF"`。这不是数据错乱，而是 TCP 只保证字节顺序，不知道 `ABC` 和 `DEF` 是否是两条业务消息。

所以 TCP 应用协议必须自行定义消息边界：

- 固定长度：每条消息都是 32 字节。
- 分隔符：每条消息以 `\n` 结束。
- 长度前缀：先发送 4 字节长度，再发送正文。

详细的半包、粘包和分帧处理见 [[字节、编码与数据边界]] 和 [[02-TCP Socket/消息边界与拆包]]。

### 3.5 流量控制与拥塞控制

这两个概念都和“发送不要太快”有关，但保护对象不同。

#### 流量控制：保护接收方

接收方可能处理得慢、内存有限。如果发送方不断发送，接收方的 Socket 接收缓冲区会被填满。TCP 使用接收窗口告诉发送方：

```text
接收方：我目前还能接收 N 字节，请不要超过这个量。
发送方：根据窗口限制发送，等你腾出空间后再继续。
```

可以把它理解为“水管末端的水桶容量”。流量控制防止**发送方把接收方压垮**。

#### 拥塞控制：保护网络

即使接收方很快，网络路径上的路由器和链路也可能拥堵。TCP 会根据丢包、延迟等信号调整发送速度，避免大量数据挤爆网络。拥塞控制防止**发送方把网络路径压垮**。

```text
流量控制：关注接收方还能处理多少
拥塞控制：关注网络路径还能承载多少
```

实际发送量会同时受接收窗口和拥塞窗口限制。初学阶段不必记具体算法，但要知道：TCP 的可靠和稳定需要付出控制、等待与重传的代价，网络变差时吞吐量可能下降。

### 3.6 TCP 如何关闭

TCP 是全双工的，两个方向可以分别关闭。一方可以表示“我的数据发完了”，但仍继续接收对方剩余的数据，这叫**半关闭**。

当 `recv()` 返回 `0` 时，通常表示对端已经有序关闭其发送方向，当前字节流到达末尾；它不是“暂时没有数据”，也不是收到了一条空业务消息。异常断线、超时和复位的处理会在 [[02-TCP Socket/超时、断线与异常]] 继续学习。

## 4. UDP：无连接的数据报

### 4.1 “无连接”是什么意思

UDP 发送数据报前通常不需要像 TCP 那样完成握手，也不要求双方维护一条有序字节流。发送方可以直接指定目标地址：

```text
发送方：socket() -> sendto(目标 IP、目标端口、一个数据报)
接收方：socket() -> bind(本地端口) -> recvfrom()
```

无连接不等于“完全没有状态”。操作系统仍维护端口、路由和缓冲区等信息，只是 UDP 不建立 TCP 那种连接状态，也不为每个数据报提供确认和重传。

部分系统允许对 UDP Socket 调用 `connect()`，但它通常只是设置默认对端、简化收发并过滤其他来源，不会产生 TCP 三次握手，也不会让 UDP 自动变可靠。

### 4.2 UDP 保留数据报边界

如果发送方两次发送：

```text
sendto("ABC", 3)
sendto("DEF", 3)
```

接收方正常情况下会收到两个独立数据报：

```text
recvfrom() -> "ABC"
recvfrom() -> "DEF"
```

但每个数据报仍可能：

- 丢失；
- 重复；
- 乱序到达；
- 因校验失败被丢弃；
- 因接收缓冲区太小而被截断，具体表现取决于系统 API。

因此，“UDP 有消息边界”与“UDP 可靠”是两件不同的事。

### 4.3 UDP 为什么常被认为延迟低

UDP 没有 TCP 的连接握手、有序等待和自动重传。因此在允许少量丢失、业务愿意自己控制可靠性的场景中，它可以减少某些等待。

但是 UDP 并不自动保证更低延迟：

- 网络拥堵仍会造成排队和丢包。
- 应用层加入重传、排序和拥塞控制后，也会产生延迟。
- 大数据报可能发生 IP 分片；任一分片丢失都可能使整个数据报无法使用。
- 防火墙和 NAT 设备可能更快清理 UDP 映射。

更准确的结论是：UDP 提供的传输层约束更少，应用可以更灵活地权衡延迟、可靠性和实现复杂度。

### 4.4 UDP 数据报不要盲目做大

理论上的 UDP 长度上限很大，但真实网络存在 MTU（最大传输单元）。数据报过大可能被 IP 分片，或者在不允许分片时发送失败。分片越多，任何一个分片丢失导致整份数据无法重组的概率越高。

初学阶段先遵循两条原则：

1. 不要因为理论上能发送很大数据报，就把整个文件塞进一个 UDP 数据报。
2. 如果业务要跨复杂网络稳定运行，应根据协议和路径选择保守大小，并设计分片、编号、重组和超时策略。

## 5. TCP 与 UDP 核心对比

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 通信方式 | 面向连接 | 无连接 |
| 数据单位 | 字节流 | 数据报 |
| 消息边界 | 不保留，需应用层分帧 | 保留一次发送的数据报边界 |
| 到达保证 | 尽力保证可靠、有序、去重 | 不保证到达、顺序或不重复 |
| 丢包处理 | 内核自动确认和重传 | 通常由应用决定是否处理 |
| 流量控制 | 有 | 无统一的 UDP 级流量控制 |
| 拥塞控制 | 有成熟机制 | 需由应用协议采用或自行设计 |
| 通信方向 | 全双工 | 可以双向收发 |
| 开销 | 状态和控制信息较多 | 协议头较小、状态较少 |
| 常见用途 | Web、文件、数据库、SSH、可靠 RPC | DNS、实时音视频、在线游戏、广播/组播 |

## 6. 如何选择 TCP 还是 UDP

先问三个问题：

1. 丢失一条消息，业务能否接受？
2. 消息顺序是否必须严格保持？
3. 是否真的需要自己控制重传、排序、拥塞和超时策略？

```text
数据必须完整且按顺序到达？
  ├─ 是：优先考虑 TCP
  └─ 否：继续判断

更在意实时性，偶尔丢失比等待旧数据更好？
  ├─ 是：可以考虑 UDP
  └─ 否：TCP 通常更省心
```

### 6.1 适合 TCP 的场景

- 网页请求和 API 调用：响应内容不能随意缺字节。
- 文件传输：文件必须完整，顺序通常也很重要。
- 数据库连接、SSH：命令和结果需要可靠传输。
- 订单、支付、账户操作：必须明确处理成功、失败和重试。

### 6.2 适合 UDP 的场景

- DNS 简单查询：请求和响应通常较短，超时后可以重新查询。
- 实时音视频：晚到的数据价值很低，等待重传可能造成卡顿。
- 在线游戏状态更新：旧位置晚到时可能已经没有意义。
- 广播和组播：一个发送方希望把数据发给多个接收方。

“实时音视频使用 UDP”不表示它完全没有可靠性。很多现代协议会在 UDP 之上实现选择性重传、序号、加密和拥塞控制；区别在于这些能力由应用协议控制，而不是直接交给 TCP。

## 7. 两个选型示例

### 7.1 聊天消息

| 需求 | 判断 |
| --- | --- |
| 每个字都不能丢 | 需要可靠传输 |
| 消息顺序不能乱 | 需要有序交付 |
| 可以接受重传等待 | TCP 通常合适 |
| 需要知道一条消息在哪里结束 | TCP 上增加长度前缀或分隔符 |

### 7.2 游戏中的玩家坐标

| 需求 | 判断 |
| --- | --- |
| 下一次坐标可以覆盖上一次 | 少量丢包可以接受 |
| 旧坐标晚到反而有害 | 不应为旧数据长时间等待重传 |
| 希望降低等待 | 可以考虑 UDP |
| 仍需限速、排序或校验 | 在应用协议中补充机制 |

## 8. 常见误区

| 误区 | 正确认识 |
| --- | --- |
| TCP 是物理专线 | TCP 是内核维护的逻辑连接，底层仍经过共享网络 |
| UDP 无连接所以不能双向通信 | UDP 可以双向收发，只是没有 TCP 式连接状态 |
| TCP 一次 `send` 对应一次 `recv` | TCP 是字节流，应用必须处理消息边界 |
| UDP 一定比 TCP 快 | UDP 机制较少，但网络质量和应用设计更重要 |
| TCP 不会发生数据丢失 | TCP 会自动重传，但连接仍可能超时或中断 |
| UDP 完全不能用于重要业务 | 可以补充可靠机制，但复杂度由应用承担 |
| 连接成功就代表请求成功 | 连接成功只代表传输层建立，仍需应用响应 |
| TCP 有消息边界 | TCP 只有连续字节，业务消息边界由应用协议定义 |

## 9. 实践

### 9.1 观察 TCP 连接

1. 在本机启动一个 TCP 服务。
2. 使用客户端连接它，观察 `LISTEN` 和 `ESTABLISHED` 状态。
3. 记录服务端监听端口与客户端临时端口。
4. 关闭客户端，观察连接状态变化。

可结合 [[网络观察工具]] 中的 `netstat`、`ss` 或 Wireshark 练习。

### 9.2 体验 TCP 没有消息边界

设计一个 TCP 回显程序：客户端连续发送两条文本，服务端打印每次 `recv()` 返回的字节数。观察一次读取可能得到半条、一条或多条消息。然后加入换行分隔符或 4 字节长度前缀，使服务端能正确解析消息。

### 9.3 体验 UDP 数据报

1. UDP 客户端连续发送带递增序号的数据报。
2. 服务端打印每次 `recvfrom()` 得到的序号、来源和长度。
3. 思考：如果业务不能接受丢失或乱序，需要增加哪些字段与状态？

不要在未经授权的网络上大量发包或压力测试；练习应限制在本机或明确授权的实验环境。
