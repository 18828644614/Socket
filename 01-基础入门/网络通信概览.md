# 网络通信概览

## 学习目标

- [ ] 理解网络通信的本质是两个或多个进程交换数据
- [ ] 能区分主机、进程、客户端、服务器和网络设备的职责
- [ ] 理解 IP 地址、端口、协议在通信中分别解决什么问题
- [ ] 能按顺序描述一次请求从客户端到服务器再返回的过程
- [ ] 知道 Socket 是应用程序使用操作系统网络能力的接口
- [ ] 初步建立“连接成功不等于业务成功”的排错意识

## 章节

### 网络中的角色

#### 网络通信究竟是什么

从程序员的角度看，网络通信就是：**一个进程把一组字节交给操作系统，操作系统通过网络把它们送到另一个进程。**

这里有三个容易忽略的重点：

1. 真正通信的是**进程**，不只是两台电脑。一个主机可以同时运行浏览器、聊天软件、Web 服务器等许多联网程序。
2. 应用程序通常不直接控制网卡，而是通过 Socket API 请求操作系统完成通信。
3. 网络传输的基本内容是字节。文字、图片、JSON、音频等都必须先编码成字节，接收端再按约定解释。

一次完整通信通常需要回答以下问题：

| 问题 | 对应概念 |
|---|---|
| 与哪台主机通信？ | IP 地址或可解析为 IP 的域名 |
| 与主机上的哪个程序通信？ | 传输层协议和端口 |
| 数据怎样到达目标网络？ | 路由和网关 |
| 数据怎样可靠或快速地传输？ | TCP 或 UDP 等传输协议 |
| 字节具体代表什么？ | HTTP、自定义消息格式等应用层协议 |

后续学习的多数概念，都是在回答表中的某一个问题。

#### 主机与进程

- **主机（host）**：连接到网络并参与通信的设备，例如电脑、手机或服务器。虚拟机和容器在网络视角下也可能表现为独立主机或独立网络环境。
- **进程（process）**：正在运行的程序实例。Socket 通常由进程创建和使用。
- **操作系统内核**：管理 Socket、TCP/UDP、IP、路由表、网卡驱动和收发缓冲区。应用调用 `send()` 并不意味着数据已经到达对端，只表示它尝试把数据交给内核。

“给一台服务器发送数据”这种说法在入门阶段可以使用，但更准确的描述是：客户端进程通过一个传输协议，向某个 IP 地址和端口所代表的服务端进程发送数据。

#### 客户端与服务器

- **客户端（client）**：通常主动发起通信，请求某项服务。例如浏览器主动连接 Web 服务器。
- **服务器（server）**：通常绑定一个相对固定的地址和端口，等待客户端请求，并返回结果。

客户端和服务器描述的是一次通信中的角色，不一定代表设备类型。同一台电脑可以同时运行客户端和服务器；同一个程序也可能在不同场景下既是客户端又是服务器。

```text
客户端进程                                   服务器进程
临时端口 53124                               固定端口 8080
192.168.1.20:53124  --------------------->   192.168.1.10:8080
                     请求
192.168.1.20:53124  <---------------------   192.168.1.10:8080
                     响应
```

服务器使用固定或约定好的端口，是为了让客户端知道去哪里寻找服务。客户端的本地端口通常由操作系统临时分配。多个客户端可以同时连接同一个服务器端口，因为每条 TCP 连接由以下四项共同区分：

```text
(源 IP, 源端口, 目的 IP, 目的端口)
```

例如两个客户端即使都连接 `192.168.1.10:8080`，它们的源 IP 或源端口通常不同，所以操作系统能把返回数据交给正确的 Socket。

#### 其他常见角色

- **DNS 服务器**：把域名解析为 IP 地址。域名便于人类使用，真正进行 IP 通信时仍需要目标 IP。
- **交换机**：主要在局域网中转发链路层帧，让同一网络中的设备互通。
- **路由器/网关**：连接不同网络，根据目的 IP 和路由表把数据包转发到下一跳。
- **防火墙**：根据地址、端口、协议、连接状态等规则允许或阻止流量。
- **代理和负载均衡器**：位于客户端与真实服务之间，代替客户端转发请求，或把请求分配给多台服务器。

因此，客户端看到的对端 IP 不一定就是最终处理业务的那台机器。真实系统中，数据可能先经过家庭路由器、运营商网络、防火墙、负载均衡器，再到达应用服务器。

#### 通信模式不只有“请求一次、响应一次”

最容易理解的是请求-响应模式，但网络程序还有其他模式：

| 模式 | 特点 | 例子 |
|---|---|---|
| 请求-响应 | 客户端请求，服务器处理后响应 | HTTP 接口、简单 RPC |
| 长连接双向通信 | 连接保持较长时间，双方都能发送数据 | 聊天、游戏、WebSocket |
| 发布-订阅 | 发布者发送消息，多个订阅者接收 | 消息系统、事件通知 |
| 点对点 | 节点之间可直接通信，角色可能变化 | 部分文件传输和实时通信系统 |

TCP 连接一旦建立就是**全双工**的，也就是双方都可以独立发送和接收。把 TCP 程序写成请求-响应，只是应用层协议选择了这种交互规则，并不是 TCP 强制规定的。

### 一次通信的过程

下面以客户端通过 TCP 访问服务器为例，先看程序员眼中的简化流程，再展开操作系统和网络中实际发生的事情。

#### 程序员看到的流程

```text
TCP 服务器                         TCP 客户端
socket()                           socket()
bind()
listen()
                                  connect()
accept()   <--- TCP 连接建立 --->
recv()     <------ 请求 ---------- send()
send()     ------- 响应 ---------> recv()
close()                            close()
```

服务器通常先创建 Socket，将它绑定到本地地址和端口，再开始监听。客户端创建 Socket 后主动连接服务器。连接建立后，双方通过发送和接收函数交换字节，最后关闭连接。

`accept()` 容易让初学者困惑：监听 Socket 只负责等待新连接；每当接受一个客户端连接时，`accept()` 会返回一个新的“已连接 Socket”，用于与这个客户端收发数据。监听 Socket 仍然保留，可以继续接受其他客户端。

```text
监听 Socket：0.0.0.0:8080
   |
   +-- 已连接 Socket A：服务器:8080 <-> 客户端A:53124
   +-- 已连接 Socket B：服务器:8080 <-> 客户端B:53125
   +-- 继续等待新的客户端
```

#### 第一步：确定目标

客户端至少需要知道：

- 目标主机名或 IP 地址
- 目标端口
- 使用 TCP 还是 UDP

如果使用域名，系统会先进行 DNS 查询，得到一个或多个 IP 地址。DNS 解析成功只代表“找到了可能的目标地址”，不表示该地址上的服务一定运行，也不表示目标端口可以访问。

#### 第二步：操作系统选择源地址和路由

客户端调用 `connect()` 时，操作系统会查询路由表，决定：

- 使用哪块网卡
- 使用哪个本地 IP 作为源地址
- 下一跳是目标主机本身，还是默认网关
- 为客户端分配哪个临时端口

如果客户端和服务器在同一台主机并使用 `127.0.0.1`，流量通常通过回环接口在内核中完成，不会离开这台机器。使用本地回环测试成功，只能证明本机程序之间能够通信，不能直接证明局域网或互联网路径正常。

#### 第三步：建立 TCP 连接

TCP 客户端与服务器通过三次握手建立连接：

```text
客户端                         服务器
   | -------- SYN -----------> |
   | <----- SYN + ACK -------- |
   | -------- ACK -----------> |
   |       连接已建立           |
```

可以把它理解成双方确认两件事：对方能够收到自己的数据，自己也能够收到对方的数据；同时双方还会交换后续可靠传输需要的初始序号等信息。

三次握手成功后，TCP 状态通常变为 `ESTABLISHED`。这只说明传输通道建立成功，不代表：

- 客户端发送的业务数据格式正确
- 服务器已经读取或处理数据
- 数据库操作已经成功
- 服务器一定会返回符合预期的响应

这些属于应用层，需要应用协议和业务代码继续保证。

#### 第四步：发送数据

假设客户端调用：

```text
send(socket, "hello", 5)
```

从概念上看，会发生以下过程：

1. 应用程序把 `hello` 的 5 个字节交给本机内核的 Socket 发送缓冲区。
2. TCP 根据实际情况把字节组织成一个或多个 TCP 段，添加端口、序号等控制信息。
3. IP 添加源 IP、目的 IP 等信息，并根据路由决定下一跳。
4. 网卡和链路层把数据发送到当前网络中的下一台设备。
5. 数据可能经过多个路由器，最终到达服务器。
6. 服务器内核检查协议头、处理排序与确认，把有效字节放入接收 Socket 的缓冲区。
7. 服务器进程调用 `recv()`，从接收缓冲区取走字节。

这里最重要的认识是：**`send()` 成功通常只表示数据已被本机内核接受，并不等于对端应用已经处理。**

同样，数据到达服务器网卡也不等于服务器程序已经读取。中间还有内核协议处理和 Socket 接收缓冲区。要确认业务是否完成，通常需要服务器返回应用层响应。

#### 第五步：服务器处理并响应

服务器从已连接 Socket 读取字节，按照双方约定的应用层协议解析数据，执行业务逻辑，再发送响应。

例如双方约定一行文本是一条消息：

```text
客户端发送：TIME\n
服务器响应：2026-08-25 14:30:00\n
```

换行符是这里的消息边界。TCP 本身只提供连续字节流，不知道 `TIME\n` 是一条完整命令。一次 `send()` 的内容可能被对端多次 `recv()` 才读完，也可能与下一次发送的内容一起被某次 `recv()` 读出。因此，应用协议必须规定如何判断一条消息结束，详见 [[消息边界与拆包]]。

#### 第六步：关闭连接

通信完成后，任意一方都可以发起 TCP 关闭。TCP 支持半关闭：一方可以表示“我不再发送”，但仍继续接收对方剩余的数据。因此，关闭并不总是一个瞬间完成的动作，而是双方分别结束发送方向的过程。

对于接收方，`recv()` 返回 `0` 通常表示对端已经有序关闭发送方向，当前字节流到达末尾。它不是“收到一个长度为 0 的业务消息”。程序应结束读取并按协议决定是否关闭自己的 Socket。

#### 从域名到响应的完整视图

访问一个基于 TCP 的远程服务时，可以用下面这条主线记忆：

```text
输入域名与端口
  -> DNS 获得目标 IP
  -> 路由表选择网卡、源 IP 和下一跳
  -> TCP 三次握手建立连接
  -> 应用把字节写入 Socket
  -> 内核进行 TCP/IP 封装并通过网络发送
  -> 对端内核把字节交给服务器 Socket
  -> 服务器解析协议、执行业务、发送响应
  -> 客户端接收并解析响应
  -> 一方发起关闭，双方释放连接资源
```

如果使用 HTTPS，在 TCP 建立之后、HTTP 请求发送之前，通常还会进行 TLS 握手。更完整的协议分层关系见 [[分层模型与常见协议]]。

#### UDP 流程有什么不同

UDP 通常不进行三次握手。发送方可以把一个数据报直接发往目标 IP 和端口，接收方需要提前绑定端口并等待数据报。

```text
UDP 接收方                       UDP 发送方
socket()                         socket()
bind()
recvfrom() <---- 一个数据报 ----- sendto()
```

这不表示 UDP 一定比 TCP “更好”或“总是更快”。UDP 不提供 TCP 的确认、重传、有序交付和流量控制；如果业务需要这些能力，就必须接受数据可能丢失、重复、乱序，或在应用层自行处理。详细对比见 [[TCP与UDP概念]]。

### 通信中的几个关键边界

#### 主机边界

本机进程之间通过回环地址通信，和跨机器通信使用相同或相近的 Socket 接口，但经过的真实网络路径不同。本机成功不代表防火墙、路由和外部绑定地址都正确。

#### 内核与应用边界

发送缓冲区和接收缓冲区位于内核中。应用程序与内核之间的数据交接、内核与网络之间的数据交接、远端内核与远端应用之间的数据交接，是三个不同阶段。理解这个边界可以避免把“写入成功”“网络到达”和“业务处理成功”混为一谈。

#### 传输层与应用层边界

TCP 负责可靠传输字节，但不理解登录、订单或聊天消息。应用程序必须自己规定编码、长度、消息类型、错误响应和版本等规则。

#### 网络错误与业务错误

| 现象 | 更可能属于哪一类 |
|---|---|
| 域名无法解析 | DNS 或网络配置问题 |
| 连接超时 | 路由、防火墙、服务未响应等网络问题 |
| 连接被拒绝 | 主机可达，但目标端口未监听或被明确拒绝 |
| 已连接但一直没有响应 | 应用协议、业务处理、死锁、双方都在等待等问题 |
| 收到错误码或错误消息 | 通信大概率已完成，服务器报告了应用层失败 |

排查时先判断失败发生在哪个边界，会比直接反复修改 `send()` 或 `recv()` 更有效。具体工具见 [[网络观察工具]]。
