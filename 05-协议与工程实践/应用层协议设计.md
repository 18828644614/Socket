# 应用层协议设计

> 本章面向“刚学 Socket，还不知道协议到底要设计什么”的读者。你不需要先背 HTTP、RPC 或某个序列化库；我们会从“两个程序怎样约定说话”开始，逐步写出一份小协议，并让它在 Windows 和 Linux 上跑起来。

## 0. 先看学习地图：要学什么、按什么顺序

### 0.1 学完本章后，你应该能做到

- 用自己的话解释“应用层协议”是什么，以及它和 TCP、Socket 的分工。
- 在设计协议前列出通信双方、消息、字段、边界、顺序、错误和版本规则。
- 读懂请求、响应、状态码、请求编号、幂等性等常见术语。
- 为 TCP 选择分隔符、固定长度或长度前缀等消息边界方案。
- 设计一份小型文本协议，并写出清楚的协议表格和示例。
- 在 Windows 和 Linux 上分别编译、启动并手工测试同一份协议的服务端。
- 识别半包、粘包、错误码混乱、版本不兼容、输入未限制等常见问题。
- 知道什么时候继续使用文本协议，什么时候考虑二进制格式、TLS、认证或成熟协议。

### 0.2 推荐学习顺序

| 阶段 | 学习范围 | 建议时间 | 通过标准 |
| --- | --- | ---: | --- |
| A. 补齐地基 | TCP 字节流、Socket 收发、编码、字节序 | 30～60 分钟 | 能解释一次 `send` 为什么不一定对应一次 `recv` |
| B. 认识协议 | 应用层职责、角色、消息和状态 | 30 分钟 | 能画出客户端与服务端的对话顺序 |
| C. 设计步骤 | 需求、消息目录、字段、边界、错误、版本 | 45～60 分钟 | 能写出一页协议草案 |
| D. 贯穿示例 | `MiniCalc/1` 的完整规范 | 30～45 分钟 | 能根据规范预测每条响应 |
| E. 动手运行 | Windows Winsock 与 Linux POSIX 服务端 | 60～90 分钟 | 能用两个终端完成握手、计算和退出 |
| F. 工程实践 | 兼容性、安全、超时、日志、测试和演进 | 45～60 分钟 | 能找出协议草案中的风险 |
| G. 巩固检查 | 练习题、答案和阶段清单 | 30～45 分钟 | 不看答案完成基本改造题 |

第一遍建议只要求自己掌握 A～E。安全、性能和二进制协议先建立地图，再按后续章节深入。

### 0.3 前置知识

如果下面某一项不熟，不必停下来背定义，先打开对应章节做快速回顾：

1. [[IP地址与端口]]：程序怎样找到另一台机器上的服务。
2. [[TCP与UDP概念]]：本章示例使用 TCP；TCP 提供有序字节流，但不提供应用消息边界。
3. [[Socket基础]]：Socket 是程序使用网络通信功能的端点。
4. [[发送与接收数据]]：理解 `send`、`recv` 的返回值和部分读写。
5. [[字节、编码与数据边界]]：理解字节、UTF-8、网络字节序和长度单位。
6. [[消息边界与拆包]]：理解分隔符、定长和长度前缀。

还需要一点 C 语言基础：变量、数组、指针、函数、字符串、`if`/`while`、编译器命令。不会指针也可以先运行代码，但要在阅读代码时把“缓冲区是一块内存”这个概念补上。

### 0.4 术语小抄

| 术语 | 新手解释 |
| --- | --- |
| 应用层 | 最接近业务的一层，例如登录、聊天、下单、计算。 |
| 协议 | 通信双方都遵守的格式和规则，像一份“对话说明书”。 |
| 消息 | 协议中的一条完整对话单位，例如一个请求或一个响应。 |
| 字段 | 消息中的一部分数据，例如版本号、用户编号、金额。 |
| 请求 | 客户端希望服务端执行的操作。 |
| 响应 | 服务端对请求的结果或错误说明。 |
| 分帧 | 从连续字节中找出一条条完整消息。 |
| 状态码/错误码 | 用固定代码表达结果，便于程序判断。 |
| 兼容性 | 新旧版本在一起工作时，是否仍能正确理解消息。 |
| 幂等 | 同一个请求重复执行，最终效果与执行一次相同。 |
| 序列化 | 把内存中的数据转换成可传输的字节或文本。 |

## 1. 应用层协议到底解决什么问题

### 1.1 TCP 只负责“把字节送过去”

可以把 TCP 想成可靠的水管：它尽量保证字节按顺序到达，但它不知道这些字节是在表达“登录”“加法”还是“退出”。

```text
业务程序：  “请把 2 和 3 相加”
      ↓ 序列化
网络字节：  41 44 44 20 32 20 37 20 35 0A ...
      ↓ TCP
对方程序：  收到字节，再按协议解析成一条 ADD 请求
```

TCP 不会告诉接收方：

- 发送方调用了几次 `send()`；
- 哪些字节是一条业务消息；
- `37` 是数字、文本还是某个字段；
- 收到错误时应该返回什么；
- 连接建立后必须先认证还是先发数据。

这些都属于应用层协议的工作。

### 1.2 一个协议像一份“对话说明书”

至少要回答这些问题：

1. 谁是客户端，谁是服务端？
2. 使用 TCP、UDP 还是其他传输方式？
3. 一条消息从哪里开始，到哪里结束？
4. 消息有哪些类型？
5. 每个字段是什么类型、多少字节、使用什么编码？
6. 消息的先后顺序是什么？
7. 成功、失败、超时和断开如何表达？
8. 如何让请求和响应对应起来？
9. 新版本增加字段后，旧客户端怎么办？
10. 收到恶意或异常输入时，资源和连接如何保护？

如果只写“客户端发 JSON，服务端返回 JSON”，那只是选了一个表示格式，还没有完成协议设计。

### 1.3 协议、格式和实现的区别

| 层次 | 例子 | 解决的问题 |
| --- | --- | --- |
| 协议语义 | `ADD` 表示加法；`ERR` 表示失败 | 双方对行为的理解一致 |
| 消息格式 | `ADD 2 7 5\n` | 字节如何排列、字段如何分隔 |
| 传输方式 | TCP 连接、端口 19091 | 字节怎样到达对方 |
| 程序实现 | C、Python、Go 的服务端 | 由哪个程序执行这些规则 |

JSON、Protobuf、HTTP 都可以作为工具，但工具不会自动替你决定业务语义、状态顺序和错误处理。

## 2. 设计前必须补齐的基础

### 2.1 TCP 是字节流：一次 `send` 不等于一次消息

发送端可能写：

```c
send(sock, "PING 1\n", 7, 0);
send(sock, "PING 2\n", 7, 0);
```

接收端可能读到：

```text
第一次 recv："PING"
第二次 recv：" 1\nPING 2\n"
```

也可能一次读到两条，也可能一条被拆成多次。接收程序必须根据协议规定的边界，维护累计缓冲区并逐条解析。详细练习见 [[消息边界与拆包]]。

本章的 MiniCalc 协议使用换行符 `\n` 作为一条消息的结束标记。服务端读到换行之前，都只是在积累字节。

### 2.2 长度、字符和字节不是一回事

Socket 的长度参数通常是**字节数**。UTF-8 中一个中文字符通常占 3 个字节，一个常见 emoji 可能占 4 个字节。因此协议要明确：

- 文本字段使用什么编码，例如 UTF-8；
- 长度按字节算还是按字符算；
- 是否允许换行、零字节和控制字符；
- 非法编码如何处理。

MiniCalc 为了让第一次实验简单，只允许 ASCII 命令和十进制整数。它没有偷偷假设“机器默认编码”。

### 2.3 发送和接收都可能只完成一部分

`recv()` 返回正数只表示本次拿到了这些字节，可能还不是完整消息；`send()` 返回正数也只表示本次把这些字节交给了本机内核，可能还要继续发送剩余部分。生产程序通常需要 `send_all` 或保存待发送队列。

### 2.4 连接状态是协议的一部分

同一条消息在不同阶段可能含义不同。例如：

```text
连接建立
  ↓
必须先发送 HELLO 1
  ↓
才能发送 PING / ADD / QUIT
  ↓
收到 QUIT 后回复 BYE，再关闭连接
```

如果服务端允许客户端在握手前直接发送 `ADD`，协议就会出现不清楚的状态。状态机不一定要画得很复杂，但必须明确“现在允许什么”。

## 3. 一套可重复的协议设计流程

下面的顺序适合第一次设计自己的协议。每一步都产出一小段文档，不要一开始就写解析代码。

### 第 1 步：写目标和边界

先写一句话：协议为谁解决什么问题？再写明确不解决什么问题。

本章示例的目标是：

> 在一条 TCP 连接上，客户端向服务端发送简单命令；服务端完成握手、心跳、整数加法，并返回可判断的结果。

它暂时不做：用户认证、加密、并发多客户端、文件传输、复杂表达式和持久化。边界越清楚，第一版越容易验证。

### 第 2 步：列出角色和消息目录

| 角色 | 消息 | 方向 | 目的 |
| --- | --- | --- | --- |
| 客户端 | `HELLO` | 客户端 → 服务端 | 声明协议版本 |
| 服务端 | `OK ... HELLO` | 服务端 → 客户端 | 接受版本 |
| 客户端 | `PING` | 客户端 → 服务端 | 检查连接仍可用 |
| 客户端 | `ADD` | 客户端 → 服务端 | 请求两个整数相加 |
| 服务端 | `OK ...` | 服务端 → 客户端 | 返回成功结果 |
| 服务端 | `ERR ...` | 服务端 → 客户端 | 返回机器可判断的错误 |
| 客户端 | `QUIT` | 客户端 → 服务端 | 请求结束会话 |

### 第 3 步：选择消息边界

常见选项如下：

| 方案 | 示例 | 优点 | 风险 |
| --- | --- | --- | --- |
| 定长 | 每条固定 32 字节 | 解析简单 | 短消息浪费空间，长度难扩展 |
| 分隔符 | 每行以 `\n` 结束 | 人能直接观察，适合命令 | 内容含分隔符时要转义；必须限制最大长度 |
| 长度前缀 | `[4 字节长度][正文]` | 可承载任意字节，效率好 | 长度字段也会半包，需检查上限 |

入门实验优先选分隔符；文件、二进制数据和高性能服务通常会考虑长度前缀。选择理由要写进协议文档，而不是只写“大家都这么做”。

### 第 4 步：规定字段和编码

每个字段至少写清楚：名字、位置、类型、范围、是否必填、非法时怎么办。

例如 `ADD`：

| 字段 | 类型 | 范围 | 说明 |
| --- | --- | --- | --- |
| 操作名 | ASCII 单词 | 固定为 `ADD` | 区分消息类型 |
| `request_id` | 十进制整数 | 0～2147483647 | 对应响应；客户端在连接内递增 |
| `a`、`b` | 十进制有符号整数 | -2147483648～2147483647 | 本例的两个操作数 |
| 结束符 | 一个 `\n` | 必须存在 | 标记消息结束 |

### 第 5 步：规定顺序和状态

用“允许/禁止”的句子写出来：

- 建立 TCP 连接后，客户端必须先发送 `HELLO 1`。
- 握手成功前，其他命令都返回 `ERR 0 VERSION_REQUIRED`。
- 握手成功后，可以发送多个 `PING` 或 `ADD`。
- 每个请求都必须带一个 `request_id`；响应复制这个编号。
- `QUIT` 得到 `BYE` 后，服务端关闭连接。

### 第 6 步：规定错误

错误要让程序能判断，不能只返回一句模糊的“出错了”。建议同时提供：

- 稳定的错误类别，例如 `BAD_REQUEST`；
- 可读的调试信息（生产协议可另设 message 字段）；
- 发生错误后的动作：忽略本条、要求重试、还是关闭连接。

本例使用短错误码，避免第一次实践引入空格转义问题。

### 第 7 步：考虑兼容和演进

协议第一版就要留下版本位置。常见策略有：

- `HELLO 1`：握手时选择版本；
- 新增字段放在末尾，旧端忽略未知字段；
- 不改变已有字段含义；
- 无法安全理解时返回明确错误，而不是猜测。

“把版本号写进文件名”不等于完成版本设计；还要说明协商失败和升级顺序。

### 第 8 步：写可观察、可测试的例子

协议文档至少应有：正常对话、错误对话、边界输入、连接关闭行为。别人应该能只看示例就用 Ncat、nc 或脚本复现问题。

## 4. 贯穿示例：MiniCalc/1 协议规范

### 4.1 协议目标

MiniCalc/1 是一个教学协议：客户端通过 TCP 连接向服务端发送行文本，服务端完成握手、心跳和整数加法。默认监听 `127.0.0.1:19091`，只用于本机学习。

### 4.2 传输和编码规则

- 传输：TCP。
- 地址：示例只绑定 `127.0.0.1`，避免直接暴露到局域网。
- 编码：命令、编号和数字使用 ASCII；每条消息以一个换行字节 `\n` 结束。
- Windows 客户端发送 `\r\n` 时，服务端允许并忽略 `\r`。
- 一行最长 1023 个有效字节；超过限制返回 `LINE_TOO_LONG`，继续读到换行以恢复边界。
- 数字是十进制文本，不允许小数、十六进制或空字符串。

### 4.3 消息格式

```text
HELLO <version>\n
PING <request_id>\n
ADD <request_id> <a> <b>\n
QUIT <request_id>\n
```

响应格式：

```text
OK <request_id> <result> [value]\n
ERR <request_id> <error_code>\n
```

其中方括号表示可选文字，不是要原样输入的括号。

### 4.4 消息示例

| 发送 | 含义 | 预期响应 |
| --- | --- | --- |
| `HELLO 1` | 请求使用版本 1 | `OK 0 HELLO 1` |
| `PING 7` | 心跳/连通性检查 | `OK 7 PONG` |
| `ADD 8 2 3` | 计算 2 + 3 | `OK 8 RESULT 5` |
| `QUIT 9` | 结束会话 | `OK 9 BYE`，随后关闭 |
| 握手前的 `PING 7` | 状态不允许 | `ERR 0 VERSION_REQUIRED` |
| `HELLO 2` | 服务端不支持的版本 | `ERR 0 UNSUPPORTED_VERSION` |
| `ADD x 2 3` | 请求编号不是整数 | `ERR 0 BAD_REQUEST` |
| `WHAT 1` | 未知操作 | `ERR 1 UNKNOWN_COMMAND` |

### 4.5 为什么要有 `request_id`

如果客户端连续发送多个请求，响应可能因为实现方式或未来的异步处理而不按原顺序到达。复制 `request_id` 可以让客户端知道“这个响应对应哪一个请求”。本例服务端现在按顺序处理，但从第一版就保留这个字段，便于以后扩展。

编号只在当前连接内有意义；服务端不把它当作数据库主键，也不因为编号跳跃就报错。生产协议还要写清楚重复编号是否允许，以及重试后是否可能重复执行。

### 4.6 成功、错误和连接关闭

- `OK`：请求格式正确并完成了操作。
- `ERR`：请求没有完成；错误码是程序应依赖的稳定部分。
- 收到 `QUIT` 后先发送 `OK <id> BYE`，再关闭连接。
- 对端直接关闭连接时，服务端结束本次会话；不能把 EOF 当成一条正常请求。
- 对于无法恢复的协议错误，生产服务可以关闭连接；教学服务只报告错误并继续，便于观察。

## 5. 逐步理解服务端代码会做什么

无论 Windows 还是 Linux，处理循环都遵循同一条路线：

```text
创建 Socket
  → 绑定 127.0.0.1:19091
  → 监听
  → accept 接受一个客户端
  → 读取到换行，得到一条完整行
  → 判断当前状态是否允许该消息
  → 解析字段并校验范围
  → 生成 OK 或 ERR 响应
  → send_all 确保响应字节全部交给内核
  → 回到读取下一条消息
```

注意三件事：

1. `recv_line` 负责**分帧**，它不能把没有换行的半条消息交给业务层。
2. 解析函数负责**语法和范围校验**，不能把网络传来的字符串直接当可信整数。
3. 主循环负责**状态和动作**，例如握手前拒绝 `ADD`、收到 `QUIT` 后退出。

代码为了让初学者看清协议，故意只处理一个客户端。多客户端版本应把连接状态保存到每个连接对象中，再配合 [[I-O多路复用]] 或线程模型。

## 6. Windows 示例：Winsock MiniCalc 服务端

### 6.1 保存代码

将下面内容保存为 `minicalc_server_win.c`。它使用 Winsock 2，服务端只监听本机回环地址。

```c
#define _CRT_SECURE_NO_WARNINGS
#include <winsock2.h>
#include <ws2tcpip.h>
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define PORT 19091
#define MAX_LINE 1024

static int send_all(SOCKET sock, const char *data, int length) {
    int sent = 0;
    while (sent < length) {
        int n = send(sock, data + sent, length - sent, 0);
        if (n <= 0) {
            return -1;
        }
        sent += n;
    }
    return 0;
}

/* 返回：正数=有效行长度，0=对端关闭，-1=网络错误，-2=行太长 */
static int recv_line(SOCKET sock, char *buffer, int capacity) {
    int used = 0;
    int too_long = 0;

    for (;;) {
        char ch;
        int n = recv(sock, &ch, 1, 0);
        if (n == 1) {
            if (ch == '\n') {
                break;
            }
            if (ch == '\r') {
                continue;
            }
            if (used + 1 < capacity) {
                buffer[used++] = ch;
            } else {
                too_long = 1;
            }
        } else if (n == 0) {
            if (used == 0 && !too_long) {
                return 0;
            }
            break;
        } else {
            return -1;
        }
    }

    buffer[used] = '\0';
    return too_long ? -2 : used;
}

static int parse_i32(const char *text, long *value) {
    char *end = NULL;
    long parsed;

    errno = 0;
    parsed = strtol(text, &end, 10);
    if (errno == ERANGE || text[0] == '\0' || *end != '\0') {
        return 0;
    }
    if (parsed < -2147483647L - 1 || parsed > 2147483647L) {
        return 0;
    }
    *value = parsed;
    return 1;
}

static int send_error(SOCKET client, long id, const char *code) {
    char response[128];
    int length = snprintf(response, sizeof response,
                          "ERR %ld %s\n", id, code);
    return (length < 0 || length >= (int)sizeof response) ? -1
                                                            : send_all(client, response, length);
}

int main(void) {
    WSADATA wsa;
    SOCKET listener = INVALID_SOCKET;
    SOCKET client = INVALID_SOCKET;
    struct sockaddr_in address;
    int hello_done = 0;

    if (WSAStartup(MAKEWORD(2, 2), &wsa) != 0) {
        fprintf(stderr, "WSAStartup failed: %d\n", WSAGetLastError());
        return 1;
    }

    listener = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listener == INVALID_SOCKET) {
        fprintf(stderr, "socket failed: %d\n", WSAGetLastError());
        WSACleanup();
        return 1;
    }

    memset(&address, 0, sizeof address);
    address.sin_family = AF_INET;
    address.sin_port = htons(PORT);
    address.sin_addr.s_addr = inet_addr("127.0.0.1");
    if (address.sin_addr.s_addr == INADDR_NONE) {
        fprintf(stderr, "inet_addr failed\n");
        closesocket(listener);
        WSACleanup();
        return 1;
    }

    if (bind(listener, (struct sockaddr *)&address, sizeof address) == SOCKET_ERROR ||
        listen(listener, 8) == SOCKET_ERROR) {
        fprintf(stderr, "bind/listen failed: %d\n", WSAGetLastError());
        closesocket(listener);
        WSACleanup();
        return 1;
    }

    printf("MiniCalc/1 listening on 127.0.0.1:%d\n", PORT);
    client = accept(listener, NULL, NULL);
    if (client == INVALID_SOCKET) {
        fprintf(stderr, "accept failed: %d\n", WSAGetLastError());
        closesocket(listener);
        WSACleanup();
        return 1;
    }

    for (;;) {
        char line[MAX_LINE];
        int line_length = recv_line(client, line, (int)sizeof line);
        if (line_length == 0) {
            puts("client closed the connection");
            break;
        }
        if (line_length == -1) {
            fprintf(stderr, "recv failed: %d\n", WSAGetLastError());
            break;
        }
        if (line_length == -2) {
            send_error(client, 0, "LINE_TOO_LONG");
            continue;
        }

        if (strncmp(line, "HELLO ", 6) == 0) {
            long version;
            char extra[32];
            int fields = sscanf(line + 6, "%ld %31s", &version, extra);
            if (fields != 1) {
                send_error(client, 0, "BAD_REQUEST");
            } else if (version != 1) {
                send_error(client, 0, "UNSUPPORTED_VERSION");
            } else {
                hello_done = 1;
                if (send_all(client, "OK 0 HELLO 1\n", (int)strlen("OK 0 HELLO 1\n")) < 0) {
                    break;
                }
            }
            continue;
        }

        if (!hello_done) {
            send_error(client, 0, "VERSION_REQUIRED");
            continue;
        }

        {
            char operation[16];
            char id_text[32];
            char arg1[64];
            char arg2[64];
            char extra[64];
            int fields = sscanf(line, "%15s %31s %63s %63s %63s",
                                operation, id_text, arg1, arg2, extra);
            long id;

            if (fields < 2 || fields >= 5 || !parse_i32(id_text, &id)) {
                send_error(client, 0, "BAD_REQUEST");
                continue;
            }

            if (strcmp(operation, "PING") == 0) {
                if (fields != 2) {
                    send_error(client, id, "BAD_REQUEST");
                } else {
                    char response[128];
                    int length = snprintf(response, sizeof response,
                                          "OK %ld PONG\n", id);
                    if (length < 0 || length >= (int)sizeof response || send_all(client, response, length) < 0) {
                        break;
                    }
                }
            } else if (strcmp(operation, "ADD") == 0) {
                long a;
                long b;
                long long result;
                char response[128];

                if (fields != 4 || !parse_i32(arg1, &a) || !parse_i32(arg2, &b)) {
                    send_error(client, id, "BAD_REQUEST");
                    continue;
                }
                result = (long long)a + (long long)b;
                if (result < -2147483648LL || result > 2147483647LL) {
                    send_error(client, id, "NUMBER_OVERFLOW");
                    continue;
                }
                {
                    int length = snprintf(response, sizeof response,
                                          "OK %ld RESULT %ld\n", id, (long)result);
                    if (length < 0 || length >= (int)sizeof response || send_all(client, response, length) < 0) {
                        break;
                    }
                }
            } else if (strcmp(operation, "QUIT") == 0) {
                if (fields != 2) {
                    send_error(client, id, "BAD_REQUEST");
                } else {
                    char response[128];
                    int length = snprintf(response, sizeof response,
                                          "OK %ld BYE\n", id);
                    if (length >= 0 && length < (int)sizeof response) {
                        send_all(client, response, length);
                    }
                    break;
                }
            } else {
                send_error(client, id, "UNKNOWN_COMMAND");
            }
        }
    }

    closesocket(client);
    closesocket(listener);
    WSACleanup();
    return 0;
}
```

```c
static int send_all(int fd, const char *data, size_t length) {
    size_t sent = 0;
    while (sent < length) {
        ssize_t n = send(fd, data + sent, length - sent, 0);
        if (n > 0) {
            sent += (size_t)n;
        } else if (n < 0 && errno == EINTR) {
            continue;
        } else {
            return -1;
        }
    }
    return 0;
}

/* 返回：正数=有效行长度，0=对端关闭，-1=网络错误，-2=行太长 */
static int recv_line(int fd, char *buffer, size_t capacity) {
    size_t used = 0;
    int too_long = 0;

    for (;;) {
        char ch;
        ssize_t n = recv(fd, &ch, 1, 0);
        if (n == 1) {
            if (ch == '\n') {
                break;
            }
            if (ch == '\r') {
                continue;
            }
            if (used + 1 < capacity) {
                buffer[used++] = ch;
            } else {
                too_long = 1;
            }
        } else if (n == 0) {
            if (used == 0 && !too_long) {
                return 0;
            }
            break;
        } else if (errno == EINTR) {
            continue;
        } else {
            return -1;
        }
    }

    buffer[used] = '\0';
    return too_long ? -2 : (int)used;
}

static int parse_i32(const char *text, long *value) {
    char *end = NULL;
    long parsed;

    errno = 0;
    parsed = strtol(text, &end, 10);

        return 0;
    }
    if (parsed < -2147483647L - 1 || parsed > 2147483647L) {
        return 0;
    }
    *value = parsed;
    return 1;
}
```

## 9. 常见错误和排查顺序

| 现象 | 常见原因 | 处理方法 |
| --- | --- | --- |
| `bind/listen failed` 或地址已在使用 | 旧服务端仍占用 19091 | 关闭旧进程，或同时修改代码和客户端端口 |
| Windows 找不到 `winsock2.h` | 没有 MinGW-w64 或 Visual Studio SDK | 使用对应开发者命令行，检查编译器安装 |
| Windows 出现 `undefined reference` | 忘记链接 Winsock 库 | GCC 命令末尾加 `-lws2_32`；MSVC 加 `ws2_32.lib` |
| Linux 找不到 `arpa/inet.h` | 正在 Windows 原生编译 Linux 代码 | 用 Linux、虚拟机或 WSL 编译 Linux 文件 |
| 客户端输入后没有响应 | 没有按 Enter，或连错端口 | 行协议要以换行结束，核对地址和端口 |
| 一发送 `PING` 就收到版本错误 | 忘了先发送 `HELLO 1` | 按协议状态先握手 |
| 每次 `recv` 被当成一条完整消息 | 把 TCP 当成消息队列 | 使用分隔符或长度前缀解析；见 [[消息边界与拆包]] |
| 服务端接受超长输入后解析错位 | 超长行没有读到换行就继续解析 | 拒绝后继续丢弃到换行，恢复边界 |
| 把 `ERR` 的文字当唯一判断依据 | 文案可能改变或被本地化 | 客户端依赖稳定错误码 |
| 中文变乱码 | 两端编码不同，或按字符数计算长度 | 明确 UTF-8，按字节计算；见 [[字节、编码与数据边界]] |
| 认为 `send` 返回成功就等于业务完成 | `send` 只表示本机接受了字节 | 需要响应、确认或业务状态才能判断完成 |
| 版本升级后旧客户端异常 | 改变了已有字段含义或顺序 | 保留旧语义，新增版本/能力协商和兼容规则 |
| 服务端收到恶意大数字后崩溃 | 直接转换、没有范围检查 | 使用有界转换，先检查错误和溢出 |
| 监听了 `0.0.0.0` 后局域网可访问 | 绑定了所有网卡 | 学习阶段使用 `127.0.0.1`；对外服务需认证和 TLS |

推荐排查顺序：先确认运行的是正确平台版本，再确认编译成功；然后确认服务端监听，客户端连到了同一个地址和端口；最后逐条检查发送的字节、换行和错误码。

## 10. 工程中还要继续学习的知识点

### 10.1 文本协议和二进制协议

文本协议便于抓包、日志和手工测试；二进制协议通常更紧凑、解析更严格。两者都需要外层分帧。JSON 也不是“自动有边界”：在 TCP 上发送 JSON 时，仍要使用换行、长度前缀或其他规则告诉接收端一条 JSON 在哪里结束。

### 10.2 重试、幂等和重复请求

网络超时后，客户端可能不知道服务端是否已经执行成功，于是再次发送同一个请求。设计支付、创建订单等操作时，必须说明：

- 请求是否可以安全重试；
- `request_id` 是否作为幂等键；
- 服务端是否保存已处理请求的结果；
- 重复请求返回原结果还是报错。

`PING` 和本章的 `ADD` 没有外部副作用，适合入门；“创建资源”通常需要更严谨的幂等设计。

### 10.3 超时、心跳和取消

应用层要区分：连接建立超时、等待响应超时、空闲连接超时和业务执行超时。心跳只能帮助发现连接是否仍有响应，不能替代业务确认。可以继续阅读 [[心跳、超时与重连]]。

### 10.4 安全和资源限制

网络输入是不可信的。真实协议至少要限制：单条消息大小、请求数量、并发连接数、解析耗时、认证失败次数和错误日志频率。需要认证或机密性时使用 TLS，而不是自己发明“加密字段”。详见 [[安全与输入校验]]。

### 10.5 可观察性

协议实现应记录 request_id、消息类型、耗时、结果类别和关闭原因，但不要把密码、令牌等敏感内容写进日志。协议出现问题时，十六进制转储和原始收发日志往往比猜测更有用。

14. 选做：把服务端改成同时处理多个客户端。每个连接必须独立保存 `hello_done`、接收缓冲区和待发送数据；可参考 [[I-O多路复用]] 和 [[状态机与连接管理]]。

### 11.3 参考答案要点

1. TCP 只提供有序字节流，不保留发送方的 `send` 调用边界；应用协议要自己定义换行或长度字段。
2. 握手确认双方使用同一版本，避免后续字段被错误解释。
3. 它把响应和请求对应起来；本例只在一条连接内递增，不是全局数据库 ID。
4. 程序依赖稳定代码，开发者和日志需要可读信息；两者职责不同。
5. 不能。它只说明本机把字节交给了 Socket 内核；业务完成需要响应或其他确认。
6. JSON 描述内容格式，不自动告诉接收端 JSON 在字节流中的结束位置。
7. 不能。还要规定未知字段、字段含义、版本协商、必填字段和无法理解时的行为。
8. 防止恶意或意外输入让缓冲区无限增长、占用内存或拖慢解析。

## 12. 阶段检查清单

### 阶段 A：基础

- [ ] 我能说出 TCP 是字节流，不保留 `send` 次数。
- [ ] 我知道 `recv()` 返回 0 和“暂时没数据”不是一回事。
- [ ] 我知道协议长度通常按字节计算。
- [ ] 我能解释分隔符、固定长度和长度前缀的差别。

### 阶段 B：协议建模

- [ ] 我能列出协议的客户端、服务端和消息方向。
- [ ] 我能画出握手、请求、响应、错误和关闭顺序。
- [ ] 我能为每个字段写出类型、范围、编码和必填规则。
- [ ] 我知道状态规则必须写出来，不能只藏在代码的 `if` 中。

### 阶段 C：MiniCalc 实验

- [ ] 我能在 Windows 或 Linux 编译对应版本。
- [ ] 我能用 Ncat 或 nc 完成 `HELLO`、`PING`、`ADD`、`QUIT`。
- [ ] 我能复现 `VERSION_REQUIRED`、`BAD_REQUEST` 和 `UNKNOWN_COMMAND`。
- [ ] 我能解释服务端为什么要先读到换行再解析。
- [ ] 我能解释 `request_id` 如何出现在响应中。

- [ ] 我知道错误码比可读文案更适合作为程序判断依据。
