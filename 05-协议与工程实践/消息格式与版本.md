# 消息格式与版本

> 面向第一次接触“序列化、二进制协议、版本兼容”的读者。先看学习路线，再按顺序学概念，最后复制代码运行。第一次不用背住全部术语，能解释例子、改动例子并验证结果，比记定义更重要。
>
> 前一章 [[应用层协议设计]] 解决“双方要约定哪些对话规则”；本章继续解决“字段怎样变成字节、如何安全读回来、格式升级时旧程序怎么办”。前章 MiniCalc 是换行文本协议，本章另建 MF/1.0 教学协议，二者不能混用。

## 0. 先规划学习范围和顺序

### 0.1 学完后应该能做到什么

你的最终作品是一份别人能照着实现的消息规范，以及能验证它的程序。你应该能够：

- 区分业务数据、序列化后的正文、外层消息帧和 TCP 字节流。
- 比较文本与二进制格式，知道 JSON、TLV、Protobuf 各解决什么问题。
- 写清字段类型、编码、字节序、长度、必填性、默认值和非法值处理。
- 看懂十六进制消息，算出每个字段的位置。
- 运行不会把“一次接收”当成“一条消息”的服务端。
- 拒绝错误长度、未知版本、截断消息，区分可继续与必须断开的错误。
- 解释新旧兼容，设计逐步升级、观察和回退的方法。

### 0.2 推荐学习路线

| 阶段 | 学习内容 | 本次产出 | 通过标准 | 建议时间 |
| --- | --- | --- | --- | --- |
| A：补齐地基 | 第 1 节：字节、编码、TCP、C 缓冲区 | 术语小抄 | 能算中文的 UTF-8 字节数 | 30～45 分钟 |
| B：选正文格式 | 第 2～3 节：文本、JSON、二进制、Schema | 字段表 | 能说明缺失与零的区别 | 45～60 分钟 |
| C：设计外层消息 | 第 4～5 节：帧头、长度、字节序、校验 | 手算一条完整帧 | 能找到正文起点 | 45～60 分钟 |
| D：让代码工作 | 第 6～9 节：读代码、分平台运行、测试客户端 | 实验记录 | 中文、空正文、连续帧都通过 | 60～120 分钟 |
| E：版本演进 | 第 10 节：兼容、协商、升级顺序 | 兼容矩阵 | 能判断字段修改是否破坏旧端 | 45～60 分钟 |

### 0.3 学习范围的轻重

**现在必须掌握**：UTF-8 字节数、固定宽度整数、大端、长度上限、部分收发、JSON 基本规则、字段校验、新旧兼容、异常测试。

**现在理解用途即可**：TLV、Protobuf、CRC、MAC、TLS、能力协商、灰度发布。正文会解释这些词。

**以后按需要深入**：手写序列化库、位级压缩、压缩算法、自定义浮点编码、数字签名算法、零拷贝和高性能非阻塞解析器。第一次不需要把这些全部实现。

## 1. 前置知识：从“数据”到“网络字节”

### 1.1 先补齐哪些基础

| 知识 | 本章用途 | 回顾入口 |
| --- | --- | --- |
| IP、端口、客户端和服务端 | 找到正在监听的程序 | [[IP地址与端口]]、[[Socket基础]] |
| TCP 有序字节流 | 理解为何自己找消息边界 | [[TCP与UDP概念]]、[[消息边界与拆包]] |
| `send`、`recv` 返回值 | 处理部分读写和断开 | [[发送与接收数据]] |
| 字节和编码 | 算长度、传中文 | [[字节、编码与数据边界]] |
| C 数组、指针、循环、函数 | 阅读服务端 | [[C语言网络编程基础]] |

`127.0.0.1` 是本机回环地址，连接它就是连接同一台电脑。本章用 TCP 端口 `19092`，与前章 `19091` 分开。两个终端是两个操作窗口，不是两台电脑。

### 1.2 字节、字符、编码是什么

- **位（bit）**：一个 0 或 1。
- **字节（byte）**：通常由 8 位组成；本章按 8 位字节设计，取值 0～255。
- **字符**：人理解的文字，例如 `A`、`中`。
- **编码**：文字对应成字节的规则，本章文本选 UTF-8。
- **十六进制**：用 `0～9、A～F` 表示数字。`0x10` 是十进制 16；两个十六进制数字能表示一个字节。

```text
文本       UTF-8 字节（十六进制）        字节数
A          41                            1
中         E4 B8 AD                      3
你好       E4 BD A0 E5 A5 BD              6
```

网络长度通常按**字节数**计算。Python 的 `len("你好")` 为 2，而 `len("你好".encode("utf-8"))` 为 6。先编码，再计算发送长度。

“文本格式”也会变成字节。例如数字 300 写成文本是 `33 30 30`，按 16 位无符号大端整数编码则是 `01 2C`。差别是双方如何解释这些字节。

### 1.3 序列化、反序列化与分帧

**序列化**：把程序中的数据转成可保存、传输的表示。**反序列化**：按规则还原数据。**分帧**：从连续字节中找出一条完整消息。

```text
业务对象：{name: "小明", age: 18}
    ↓ JSON 序列化，再 UTF-8 编码
正文 payload：JSON 字节
    ↓ 加上记录正文长度的帧头
消息帧 frame：[帧头][正文]
    ↓ TCP 传输，可能任意拆分或合并
接收端：读满帧头 → 检查长度 → 读满正文 → 解码 → JSON 解析 → 业务校验
```

**帧头（header）**像信封，记录版本、类型、编号、长度；**正文（body/payload）**像信的内容。本章的“帧”是应用层消息帧，不是以太网帧。

JSON 能表达字段，但不会替你规定 TCP 消息边界。`{"x":1}{"x":2}` 可以被专门约定成对象流，不过普通 JSON 文档解析器通常不把它当一个合法文档。新手优先使用明确长度前缀，或规则清楚的逐行 JSON。

### 1.4 C 字符串不等于网络数据

C 字符串用 `\0`（零字节）结束。网络正文可以包含零字节：

```text
41 00 42 0A   →   A、零字节、B、换行，共 4 字节
```

`strlen()` 只能得到 1；`%s` 还可能越界读取，因为网络缓冲区不保证存在结束符。正确做法是保存“数据地址 + 字节长度”。

确实要转成 C 字符串时，另分配 `N+1` 字节、复制 N 字节并在末尾补 `\0`，同时明确内部是否允许零字节。二进制正文应直接按长度处理。

### 1.5 固定宽度整数与字节序

`uint32_t` 是 32 位无符号整数，范围 0～4294967295，线上占 4 字节。`int`、`long` 的宽度可能随平台变化，不适合直接作为跨平台格式规范。

**大端**指高位字节在前；**小端**指低位字节在前：

```text
数字 0x01020304
大端：01 02 03 04
小端：04 03 02 01
```

本章多字节整数统一大端，即网络字节序。可用 `htons/htonl`、`ntohs/ntohl` 转换 16/32 位整数，也可逐字节移位读写。已经逐字节写成大端时，不要再调用一次 `htonl`。

一字节字段没有多字节顺序问题；JSON 数字文本也不需要逐个使用这些转换函数。

## 2. 文本格式：先把内容写清楚

### 2.1 简单分隔文本

```text
CHAT|7|小明|你好\n
```

马上会遇到问题：昵称有 `|` 怎么办？正文有换行怎么办？空昵称允许吗？`7` 是编号还是版本？必须规定分隔、转义、字段数和编码，不能只靠 `split('|')` 猜测。

**转义**是用特殊写法表示有特殊含义的内容。例如约定反斜杠与字母 n 这两个字节 `\n` 表示正文中的换行，真正换行表示消息结束；还要规定反斜杠本身如何表示，避免歧义。

### 2.2 JSON：带名字的字段

JSON 是文本数据格式，支持对象、数组、字符串、数字、布尔值 `true/false` 和空值 `null`。

```json
{
  "request_id": 7,
  "op": "chat.send",
  "text": "你好",
  "urgent": false
}
```

这里是一个对象；`op` 是字段名，`"chat.send"` 是字符串值，`false` 是布尔值。JSON 不支持注释、末尾多余逗号、单引号字符串。

字段顺序通常不应承载业务含义。需要有顺序的一组数据时用数组。`"7"` 是字符串，`7` 是数字，不能不加约定地互换。

### 2.3 能解析不等于合法请求

```text
{"age":18,}          → 语法错误
{"age":"eighteen"}   → 语法正确，类型不符
{"age":-1}           → 数字，但不符合年龄范围
{}                  → 必填字段缺失
{"age":null}         → 明确给了空值，不一定等于缺失
```

解析后还要检查字段类型、必填项、范围、字符串字节数、数组数量和嵌套深度。

重复字段名也要有规则：不同库可能保留首个、末个或报错。协议宜明确拒绝重复键，并选择支持相应检测的解析方式，避免不同处理层读出不同值。

### 2.4 数字、金额与时间的坑

| 问题 | 原因 | 建议 |
| --- | --- | --- |
| 金额用浮点数 | 某些十进制小数无法用二进制浮点精确表示 | 用整数分，或有明确精度的十进制字符串 |
| 超大 ID 用 JSON 数字 | JavaScript 常见 `Number` 不能精确表达所有超过 `2^53-1` 的整数 | 大 ID 用十进制字符串，或限制到双方精确范围 |
| 时间写 `2026/10/15 12:00` | 时区和格式不明确 | 约定 UTC Unix 毫秒，或带时区的标准日期字符串 |
| 缺失字段自动变 0 | “未提供”与“确实为零”可能不同 | 每个可选字段定义缺失语义 |

**Unix 时间戳**是从约定起点累计的时间值。一定明确秒或毫秒，否则会差 1000 倍。UTC 可以理解为双方统一使用的时间基准，避免本地时区歧义。

### 2.5 Python 格式小实验

可在 Python 交互环境逐行运行。Windows 使用 `python` 或 `py -3` 进入，Linux 使用 `python3` 进入；输入 `exit()` 退出。

```python
import json

obj = {"op": "chat.send", "text": "你好", "urgent": False}
text = json.dumps(obj, ensure_ascii=False, separators=(",", ":"), allow_nan=False)
body = text.encode("utf-8")
print(text)
print("字符数:", len(text), "字节数:", len(body))
decoded = json.loads(body.decode("utf-8"))
print(decoded["text"])
```

`ensure_ascii=False` 保留可读中文；否则可能输出 `\u4f60` 等转义，也是合法 JSON，但字节数不同。`separators` 去掉多余空格；`allow_nan=False` 避免生成标准 JSON 不支持的 NaN、Infinity。接收端若要拒绝这些值，还需配置自己的解析规则。

这里只演示转换，不代表完成了业务校验。C 项目应选成熟 JSON 库、检查解析错误、释放对象，不要用 `strstr`、`sscanf` 或正则表达式代替通用 JSON 解析器。

## 3. 二进制格式与字段规范

### 3.1 二进制格式是什么

二进制格式按位置、长度或字段标签解释字节。年龄 18 若编码为一字节整数，就是十六进制 `12`；若编码为文本，就是 `31 38`。

| 比较项 | JSON 等文本 | 二进制格式 |
| --- | --- | --- |
| 观察 | 通常能直接阅读 | 常需十六进制工具、解码器 |
| 大小 | 字段名、数字文本有开销 | 固定宽度或紧凑编码可能更小 |
| 演进 | 按字段名扩展，需未知字段策略 | 取决于布局，TLV 等更易扩展 |
| 实现 | 成熟库降低语法处理难度 | 手写容易出现字节序、越界、对齐错误 |
| 性能 | 取决于数据与库 | 不保证一定快，应测量 |

二进制不自动提供压缩、保密或认证。抓包仍能看见字节；保密需要 TLS 等机制。

### 3.2 固定布局

```text
偏移 0：type，1 字节
偏移 1～4：request_id，4 字节大端
偏移 5～8：body_length，4 字节大端
偏移 9 开始：正文
```

如果在偏移 1 插入新字段，旧程序后续字段都会读错。版本演进必须考虑外层布局是否稳定，不能只在结构体中间加一行。

### 3.3 为什么不能直接发送 C 结构体

```c
/* 反例：本机内存布局不等于网络规范。 */
struct Message {
    unsigned char type;
    unsigned int length;
    char *text;
};
```

不要直接把 `&message` 与 `sizeof(message)` 交给 `send`：

1. 编译器可能在字段之间插入**填充字节**，以满足对齐要求。
2. 本机整数的字节序不一定符合协议。
3. 类型宽度可能不同。
4. 指针是本进程地址，对方不能靠它读取文字。
5. 未初始化的填充字节可能带出不该发送的内存内容。

`#pragma pack` 只影响部分布局问题，不能解决其他问题。应逐字段编码到字节数组。

### 3.4 TLV：带标签和长度的字段

TLV 是 **Type/Tag（类型或编号）+ Length（长度）+ Value（值）**。假设标签 1 字节、长度 2 字节大端：

```text
01 00 03 42 6F 62
│  │     └─ 值：Bob，3 字节
│  └─ 长度：3
└─ 标签：1 表示昵称
```

旧端遇到未知可选标签时，可以按长度跳过，但前提是规范允许忽略其含义。跳过前仍须检查长度未超过当前正文边界。

TLV 也要规定标签能否重复、顺序、最大数量、嵌套限制与未知必需字段行为。影响安全或操作含义的新字段不能随意忽略。

### 3.5 成熟格式先认识用途

- **Protobuf（Protocol Buffers）**：常用 `.proto` 文件定义字段，再生成读写代码。字段编号应稳定，删除的编号要保留，不可复用给另一含义。能跳过未知字段有助兼容，但不保证业务一定兼容。
- **MessagePack、CBOR**：用二进制表达整数、字符串、数组、映射等结构，适合需要紧凑表示的数据。
- 这些工具不会替你设计 TCP 分帧、请求编号、认证、升级顺序或业务校验。

第一次可以选“成熟正文格式 + 明确外层长度”。只有需求和测量结果支持时，再增加复杂度。

### 3.6 每个字段都要有说明书

**Schema（模式或结构约定）**可以先是一张表：

| 字段 | 类型与表示 | 必填/默认值 | 范围与非法处理 |
| --- | --- | --- | --- |
| `user_id` | 十进制字符串 | 必填 | 1～20 个 ASCII 数字，不接受负号 |
| `text` | UTF-8 字符串 | 必填 | 编码后 1～1024 字节，非法编码拒绝 |
| `urgent` | 布尔值 | 可选，缺失为 false | 拒绝 null、字符串 "false" |
| `sent_at_ms` | 非负整数 | 可选，缺失为未知 | UTC Unix 毫秒，约定双方可表达范围 |

还要规定额外字段、重复键、空字符串、`null`、缺失字段与超限处理。**默认值也是协议，改变默认值可能改变旧消息的含义。**

## 4. 长度与校验

### 4.1 长度包括什么

```text
方案 A：length = 正文字节数；整帧 = 固定帧头大小 + length
方案 B：length = 整帧字节数；正文 = length - 帧头大小
```

两者都能用，但不能混用。本章采用 A：不包括帧头和 C 字符串结束符，按序列化、编码后的字节数计算。

以后加入压缩时，要分别规定压缩后线上长度与解压后大小上限，不能只限制压缩数据。

### 4.2 能表达大长度，不等于允许大长度

32 位无符号长度最大为 4294967295；本章仅允许 0～1024。1 KiB = 1024 字节，1 GiB = 1024³ 字节。

```text
读满帧头 → 检查标识、版本、标志 → 解析无符号长度
        → 先比较上限 → 合法才收正文 → 收满才处理业务
```

不要先 `malloc(length)` 再检查。计算 `header_size + length` 也要防整数溢出。本例先限制到 1024，后续转 `int` 与小范围计算才安全。生产系统还需限制连接总内存、并发数量、正文读取时间。

### 4.3 长度、CRC、认证、加密分别解决什么

| 目标 | 方法 | 不能保证的事情 |
| --- | --- | --- |
| 字节够不够完整消息 | 长度、读满循环、截断检测 | 不能证明内容未被篡改 |
| 格式和业务是否合法 | 类型、范围、必填项校验 | 不能证明发送者身份 |
| 检测偶发损坏 | 校验和、CRC | 攻击者可以同步重算校验值 |
| 验证持有密钥的一方发出且未改动 | MAC，例如 HMAC | 单独使用通常不保密 |
| 保护传输机密性与完整性 | 正确配置并验证对端身份的 TLS | 不能代替业务输入校验、权限检查 |

CRC 是“循环冗余校验”，可以理解为从数据算出一段用于查错的值。MAC 是消息认证码，不是这里的网卡地址。TLS 是常用安全传输协议。

TCP 有传输差错检测与重传，但不等于业务合法或应用级防篡改。普通无密钥哈希如 SHA-256 也不能直接证明身份。

MF/1.0 没有 CRC 字段：长度与读满负责截断检测，规则检查负责判断帧头是否合法。以后加 CRC，要约定算法、覆盖范围、存放位置、计算时机、字节序及升级方式，不能偷偷在旧正文后加 4 字节。

### 4.4 EOF 与半条消息

EOF 是 End Of File 的缩写，这里表示对端有序结束发送，不是暂时没数据。

| 情况 | 本例动作 |
| --- | --- |
| 新帧开始前，`recv` 返回 0 | 会话结束 |
| 帧头只读一部分就 EOF | `truncated header`，关闭 |
| 正文未读满就 EOF | `truncated body`，关闭 |
| 超时或不可恢复网络错误 | 记录错误，关闭 |
| 正文长度为 0 | 合法空正文，立即处理 |

不能把半条消息当成功结果。错帧头后不盲目搜索下一个 `MF`：正文也可能包含该字节序列。

## 5. 贯穿实验：MF/1.0 完整规范

### 5.1 小目标

MF 是本章自定义教学名字，表示 Message Frame。客户端发送一帧，服务端原样回显正文。采用**固定二进制帧头 + 任意字节正文**。

服务端不解释正文。中文由客户端编码为 UTF-8；零字节、换行也允许。改成“UTF-8 JSON 业务”时，必须在收满之后新增严格解码、解析和 Schema 校验。

### 5.2 固定 16 字节帧头

**偏移**从 0 开始，表示该字段之前经过的字节数。偏移 12 即第 13 字节。

| 偏移 | 字节数 | 字段 | 约定 |
| ---: | ---: | --- | --- |
| 0～1 | 2 | `magic` 魔数/标识 | 固定 `4D 46`，ASCII `MF` |
| 2 | 1 | `major` 主版本 | 1 |
| 3 | 1 | `minor` 次版本 | 0 |
| 4 | 1 | `type` 类型 | 1 请求、2 成功响应、255 错误响应 |
| 5 | 1 | `flags` 标志 | 必须 0 |
| 6～7 | 2 | `reserved` 保留字段 | 必须 0 |
| 8～11 | 4 | `request_id` 编号 | 无符号 32 位大端，响应复制 |
| 12～15 | 4 | `body_length` 正文长度 | 无符号 32 位大端，0～1024 |
| 16 开始 | N | `body` 正文 | 恰好 N 字节，不自动加 `\0` |

魔数帮助发现错误格式，不提供认证。保留字段现在不可使用，不能随意填值；未来使用须明确升级规则。

### 5.3 类型、错误与连接规则

- TCP，监听 `127.0.0.1:19092`，同一连接允许多帧，依次处理。
- 请求 `type=1`，成功响应 `type=2`，相同编号、相同正文。
- 编号范围 0～4294967295。本例不检测重复，也不提供去重保证。正式实现要避免尚未完成的请求编号冲突。
- 其他请求类型：先收完整条合法长度正文，再返回 `type=255`、ASCII 正文 `BAD_TYPE`，继续接收下一帧。
- 魔数、主/次版本、标志、保留字段、长度错误：直接关闭，不承诺回错误帧。
- 半帧 EOF、超时、不可恢复收发错误：关闭当前连接。
- 演示仅接受 1.0，严格拒绝 1.1、2.0，没有握手协商。第 10 节是后续设计，不代表本例已实现。

### 5.4 手算一帧

请求编号 7，正文 `你好`：

```text
4D 46 | 01 | 00 | 01 | 00 | 00 00 | 00 00 00 07 | 00 00 00 06 | E4 BD A0 E5 A5 BD
 MF   major minor type flags reserved request_id   body_length     UTF-8 body
```

正文 6 字节，帧头 16 字节，共 22。响应只把类型 `01` 改为 `02`。

正文 `Hi`、编号 1：

```text
4D 46 01 00 01 00 00 00 00 00 00 01 00 00 00 02 48 69
```

共 18 字节。空正文只有 16 字节头，长度为 `00 00 00 00`。

- [ ] 能算帧头、正文起点、整帧长度。
- [ ] 能解释长度 0 与 `recv` 返回 0 的区别。
- [ ] 能区分回错误帧和直接断开两类情况。
- [ ] 不把校验值误认为认证和加密。

## 6. 读代码之前：六个小任务

Windows 与 Linux 的协议逻辑相同，平台代码分开，每份 C 代码可独立编译。

| 函数 | 职责 | 阅读重点 |
| --- | --- | --- |
| `get_u32/put_u32` | 大端整数读写 | 先转无符号 32 位再移位 |
| `recv_exact` | 读满指定字节 | 用 `used` 保存进度，区分两种 EOF |
| `send_all` | 完整交给本机 Socket | 用 `sent` 保存进度，成功不代表业务处理完成 |
| `reply` | 构造帧头、发送正文 | 未显式列出的数组元素初始化为零 |
| `serve` | 检查、接收、处理 | 先查长度，收满再处理 |
| `main` | 监听、接受、关闭 | 每个连接结束后继续等待下一个 |

### 6.1 大端读写怎么理解

`p[0] << 24` 是将首字节放到 32 位整数最左边 8 位。四个字节移到各自位置，再用按位或 `|` 合起来。

`h + 12` 是数组第 13 字节的地址，不是字段值加 12。`put_u32(h + 12, length)` 将长度写进偏移 12～15。

### 6.2 为什么读满能处理连续帧

读帧头时每次最多请求还缺的帧头字节，读正文时最多请求还缺的正文字节，因此不多取下一帧。即使两帧一起到达，下一帧仍留在 Socket 接收缓冲区，供下一轮读取。

另一种方式是一次读一大块到应用缓冲区，再拆多帧、保留尾部。两种方式都要保存进度。当前阻塞实现不能直接照搬到非阻塞 Socket；非阻塞时需保存状态、等待下一次可读事件，见 [[状态机与连接管理]]。

### 6.3 实现边界与平台差异

- 阻塞、串行服务端，一次只处理一个连接，不是并发服务。
- 固定 1024 字节正文数组，长度通过检查才写入。
- 收发设置约 5 秒等待超时；这不是整帧的 5 秒绝对期限。持续缓慢补字节可能拖长会话，生产系统还需整帧截止时间。
- Windows：`WSAStartup` 初始化，`SOCKET` 表示 Socket，`closesocket` 关闭，`WSAGetLastError` 取错误。
- Linux：Socket 用整数文件描述符表示，`close` 关闭，`errno` 取错误；`EINTR` 表示被信号打断，可以重试。
- Linux 使用 `MSG_NOSIGNAL`，避免写入已关闭连接时被 `SIGPIPE` 终止进程。这是 Linux 示例，不保证所有 Unix 系统相同。
- 使用 `Ctrl+C` 停止服务。示例未另写退出信号处理器。

## 7. Windows 示例：Winsock 服务端

### 7.1 保存代码

需要 MinGW-w64 GCC，或 Visual Studio 的 C/C++ 编译工具，二选一。编辑器不等于编译器。保存下面完整代码为 UTF-8 的 `mf_server_win.c`。

```c
/* mf_server_win.c: Windows / Winsock 2 */
#include <winsock2.h>
#include <ws2tcpip.h>
#include <stdint.h>
#include <stdio.h>

typedef SOCKET socket_t;

static void report_error(const char *where) {
    fprintf(stderr, "%s: WSA error %d\n", where, WSAGetLastError());
}

static int set_timeouts(socket_t s) {
    DWORD ms = 5000;
    return setsockopt(s, SOL_SOCKET, SO_RCVTIMEO,
                      (const char *)&ms, sizeof(ms)) == 0
        && setsockopt(s, SOL_SOCKET, SO_SNDTIMEO,
                      (const char *)&ms, sizeof(ms)) == 0;
}

#define PORT 19092
#define HEADER_SIZE 16
#define MAX_BODY 1024

/* 所有整数按“大端”逐字节读写，不传输 C 结构体。 */
static uint32_t get_u32(const unsigned char *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] << 8) | (uint32_t)p[3];
}

static void put_u32(unsigned char *p, uint32_t v) {
    p[0] = (unsigned char)(v >> 24);
    p[1] = (unsigned char)(v >> 16);
    p[2] = (unsigned char)(v >> 8);
    p[3] = (unsigned char)v;
}

/* 返回 1=读满，0=一个字节未读就 EOF，-2=中途 EOF，-1=错误。 */
static int recv_exact(socket_t s, unsigned char *buf, int length) {
    int used = 0;
    while (used < length) {
        int n = recv(s, (char *)buf + used, length - used, 0);
        if (n > 0) { used += n; continue; }
        if (n == 0) return used == 0 ? 0 : -2;

        return -1;
    }
    return 1; /* length 为 0 时也成功，不调用 recv。 */
}

static int send_all(socket_t s, const unsigned char *buf, int length) {
    int sent = 0;
    while (sent < length) {
        int n = send(s, (const char *)buf + sent, length - sent, 0);
        if (n > 0) { sent += n; continue; }

        return 0;
    }
    return 1;
}

static int reply(socket_t s, unsigned char type, uint32_t id,
                 const unsigned char *body, uint32_t length) {
    unsigned char h[HEADER_SIZE] = {'M', 'F', 1, 0, 0};
    h[4] = type;
    put_u32(h + 8, id);
    put_u32(h + 12, length);
    return send_all(s, h, HEADER_SIZE)
        && send_all(s, body, (int)length);
}

static void serve(socket_t s) {
    unsigned char h[HEADER_SIZE], body[MAX_BODY];
    if (!set_timeouts(s)) {
        report_error("setsockopt timeout");
        return;
    }
    for (;;) {
        uint32_t id, length;
        int rc = recv_exact(s, h, HEADER_SIZE);
        if (rc == 0) { puts("peer closed between frames"); return; }
        if (rc == -2) { puts("truncated header"); return; }
        if (rc < 0) { report_error("recv header / timeout"); return; }

        if (h[0] != 'M' || h[1] != 'F') {
            puts("bad magic; close"); return;
        }
        if (h[2] != 1 || h[3] != 0) {
            puts("unsupported version; close"); return;
        }
        if (h[5] != 0 || h[6] != 0 || h[7] != 0) {
            puts("unsupported flags/reserved; close"); return;
        }
        id = get_u32(h + 8);
        length = get_u32(h + 12);
        if (length > MAX_BODY) {
            puts("body too large; close before reading body"); return;
        }
        rc = recv_exact(s, body, (int)length);
        if (rc != 1) {
            if (rc == -1) report_error("recv body / timeout");
            else puts("truncated body");
            return;
        }

        printf("request id=%lu type=%u bytes=%lu\n",
               (unsigned long)id, (unsigned)h[4], (unsigned long)length);
        if (h[4] == 1) {
            if (!reply(s, 2, id, body, length)) {
                report_error("send response / timeout"); return;
            }
        } else {
            const unsigned char error[] = "BAD_TYPE";
            if (!reply(s, 255, id, error, (uint32_t)(sizeof(error) - 1))) {
                report_error("send error / timeout"); return;
            }
        }
    }
}

int main(void) {
    WSADATA data;
    SOCKET listener = INVALID_SOCKET;
    struct sockaddr_in addr = {0};
    int rc = WSAStartup(MAKEWORD(2, 2), &data);
    if (rc != 0) {
        fprintf(stderr, "WSAStartup: %d\n", rc);
        return 1;
    }
    setvbuf(stdout, NULL, _IONBF, 0);
    listener = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listener == INVALID_SOCKET) { report_error("socket"); goto done; }
    addr.sin_family = AF_INET;
    addr.sin_port = htons(PORT);
    addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (bind(listener, (const struct sockaddr *)&addr, sizeof(addr)) == SOCKET_ERROR) {
        report_error("bind"); goto done;
    }
    if (listen(listener, SOMAXCONN) == SOCKET_ERROR) {
        report_error("listen"); goto done;
    }
    printf("MF/1.0 listening on 127.0.0.1:%d\n", PORT);
    for (;;) {
        SOCKET client = accept(listener, NULL, NULL);
        if (client == INVALID_SOCKET) { report_error("accept"); break; }
        serve(client);
        closesocket(client);
    }
done:
    if (listener != INVALID_SOCKET) closesocket(listener);
    WSACleanup();
    return 1; /* 正常教学运行由 Ctrl+C 结束。 */
}
```

## 8. Linux 示例：POSIX Socket 服务端

### 8.1 保存代码

其他发行版使用自己的包管理器。保存下面完整代码为 UTF-8 的 `mf_server_linux.c`，不依赖 Windows 版文件。

```c
/* mf_server_linux.c: Linux / POSIX Socket */
#include <arpa/inet.h>
#include <errno.h>
#include <netinet/in.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/socket.h>
#include <sys/time.h>
#include <unistd.h>

typedef int socket_t;

static void report_error(const char *where) {
    perror(where);
}

static int set_timeouts(socket_t s) {
    struct timeval tv = {5, 0};
    return setsockopt(s, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv)) == 0
        && setsockopt(s, SOL_SOCKET, SO_SNDTIMEO, &tv, sizeof(tv)) == 0;
}

#define PORT 19092
#define HEADER_SIZE 16
#define MAX_BODY 1024

/* 所有整数按“大端”逐字节读写，不传输 C 结构体。 */
static uint32_t get_u32(const unsigned char *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] << 8) | (uint32_t)p[3];
}

static void put_u32(unsigned char *p, uint32_t v) {
    p[0] = (unsigned char)(v >> 24);
    p[1] = (unsigned char)(v >> 16);
    p[2] = (unsigned char)(v >> 8);
    p[3] = (unsigned char)v;
}

/* 返回 1=读满，0=一个字节未读就 EOF，-2=中途 EOF，-1=错误。 */
static int recv_exact(socket_t s, unsigned char *buf, int length) {
    int used = 0;
    while (used < length) {
        int n = (int)recv(s, buf + used, (size_t)(length - used), 0);
        if (n > 0) { used += n; continue; }
        if (n == 0) return used == 0 ? 0 : -2;
        if (errno == EINTR) continue;
        return -1;
    }
    return 1; /* length 为 0 时也成功，不调用 recv。 */
}

static int send_all(socket_t s, const unsigned char *buf, int length) {
    int sent = 0;
    while (sent < length) {
        int n = (int)send(s, buf + sent, (size_t)(length - sent), MSG_NOSIGNAL);
        if (n > 0) { sent += n; continue; }
        if (n < 0 && errno == EINTR) continue;
        return 0;
    }
    return 1;
}

static int reply(socket_t s, unsigned char type, uint32_t id,
                 const unsigned char *body, uint32_t length) {
    unsigned char h[HEADER_SIZE] = {'M', 'F', 1, 0, 0};
    h[4] = type;
    put_u32(h + 8, id);
    put_u32(h + 12, length);
    return send_all(s, h, HEADER_SIZE)
        && send_all(s, body, (int)length);
}

static void serve(socket_t s) {
    unsigned char h[HEADER_SIZE], body[MAX_BODY];
    if (!set_timeouts(s)) {
        report_error("setsockopt timeout");
        return;
    }
    for (;;) {
        uint32_t id, length;
        int rc = recv_exact(s, h, HEADER_SIZE);
        if (rc == 0) { puts("peer closed between frames"); return; }
        if (rc == -2) { puts("truncated header"); return; }
        if (rc < 0) { report_error("recv header / timeout"); return; }

        if (h[0] != 'M' || h[1] != 'F') {
            puts("bad magic; close"); return;
        }
        if (h[2] != 1 || h[3] != 0) {
            puts("unsupported version; close"); return;
        }
        if (h[5] != 0 || h[6] != 0 || h[7] != 0) {
            puts("unsupported flags/reserved; close"); return;
        }
        id = get_u32(h + 8);
        length = get_u32(h + 12);
        if (length > MAX_BODY) {
            puts("body too large; close before reading body"); return;
        }
        rc = recv_exact(s, body, (int)length);
        if (rc != 1) {
            if (rc == -1) report_error("recv body / timeout");
            else puts("truncated body");
            return;
        }

        printf("request id=%lu type=%u bytes=%lu\n",
               (unsigned long)id, (unsigned)h[4], (unsigned long)length);
        if (h[4] == 1) {
            if (!reply(s, 2, id, body, length)) {
                report_error("send response / timeout"); return;
            }
        } else {
            const unsigned char error[] = "BAD_TYPE";
            if (!reply(s, 255, id, error, (uint32_t)(sizeof(error) - 1))) {
                report_error("send error / timeout"); return;
            }
        }
    }
}

int main(void) {
    int listener, enabled = 1;
    struct sockaddr_in addr = {0};
    setvbuf(stdout, NULL, _IONBF, 0);
    listener = socket(AF_INET, SOCK_STREAM, 0);
    if (listener < 0) { report_error("socket"); return 1; }
    if (setsockopt(listener, SOL_SOCKET, SO_REUSEADDR,
                   &enabled, sizeof(enabled)) < 0) {
        report_error("setsockopt reuseaddr"); goto done;
    }
    addr.sin_family = AF_INET;
    addr.sin_port = htons(PORT);
    addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (bind(listener, (const struct sockaddr *)&addr, sizeof(addr)) < 0) {
        report_error("bind"); goto done;
    }
    if (listen(listener, SOMAXCONN) < 0) {
        report_error("listen"); goto done;
    }
    printf("MF/1.0 listening on 127.0.0.1:%d\n", PORT);
    for (;;) {
        int client = accept(listener, NULL, NULL);
        if (client < 0) {
            if (errno == EINTR) continue;
            report_error("accept"); break;
        }
        serve(client);
        close(client);
    }
done:
    close(listener);
    return 1; /* 正常教学运行由 Ctrl+C 结束。 */
}
```

## 9. 客户端、运行方法与分步骤观察

### 9.1 保存测试客户端

C 服务端展示字节处理，Python 标准库方便构造错误帧。无需第三方包。以下纯 Python 代码在两个平台相同；两平台的 C 代码和运行命令分别给出。

保存为 `mf_client.py`，不要命名为 `socket.py` 或 `struct.py`，否则会遮蔽同名标准库。

```python
import argparse
import socket
import struct

HEADER = struct.Struct("!2sBBBBHII")  # 恰好 16 字节；! 表示大端、无对齐填充
MAX_BODY = 1024


def frame(body, request_id=1, kind=1, major=1, minor=0,
          magic=b"MF", flags=0, reserved=0, declared=None):
    length = len(body) if declared is None else declared
    return HEADER.pack(magic, major, minor, kind, flags, reserved,
                       request_id, length) + body


def recv_exact(sock, length):
    data = bytearray()
    while len(data) < length:
        part = sock.recv(length - len(data))
        if not part:
            raise EOFError(f"need {length} bytes, received {len(data)}")
        data.extend(part)
    return bytes(data)


def receive(sock):
    magic, major, minor, kind, flags, reserved, rid, size = HEADER.unpack(
        recv_exact(sock, HEADER.size))
    if (magic, major, minor, flags, reserved) != (b"MF", 1, 0, 0, 0):
        raise ValueError("invalid response header")
    if size > MAX_BODY or kind not in (2, 255):
        raise ValueError("invalid response length/type")
    return kind, rid, recv_exact(sock, size)


def expect(sock, expected):
    actual = receive(sock)
    if actual != expected:
        raise AssertionError((actual, expected))
    kind, rid, body = actual
    print(f"OK type={kind} id={rid} bytes={len(body)} preview={body[:24]!r}")


def check_closed(sock):
    try:
        data = sock.recv(1)
    except ConnectionResetError:
        data = b""  # 拒收未读正文时，系统也可能复位连接。
    if data != b"":
        raise AssertionError(f"expected close, got {data!r}")
    print("OK rejected/closed")


def run(host, port, case):
    with socket.create_connection((host, port), timeout=8) as sock:
        sock.settimeout(8)
        if case == "demo":
            body = "你好，Socket".encode("utf-8")
            packet = frame(body, 1)
            print("header:", packet[:16].hex(" "))
            # 多次写入；不保证实际 TCP 包或对端 recv 的切分方式。
            for part in (packet[:1], packet[1:7], packet[7:18], packet[18:]):
                sock.sendall(part)
            expect(sock, (2, 1, body))
            sock.sendall(frame(b"", 2) + frame(b"A\x00B\n", 3))
            expect(sock, (2, 2, b""))
            expect(sock, (2, 3, b"A\x00B\n"))
            sock.sendall(frame(b"x" * MAX_BODY, 4))
            expect(sock, (2, 4, b"x" * MAX_BODY))
        elif case == "unknown":
            sock.sendall(frame(b"?", 5, kind=99) + frame(b"ok", 6))
            expect(sock, (255, 5, b"BAD_TYPE"))
            expect(sock, (2, 6, b"ok"))
        elif case == "truncated":
            sock.sendall(frame(b"ab", declared=5))
            sock.shutdown(socket.SHUT_WR)  # 告诉对方：不会再补足剩余字节。
            check_closed(sock)
        elif case == "partial-header":
            sock.sendall(frame(b"")[:7])
            sock.shutdown(socket.SHUT_WR)
            check_closed(sock)
        else:
            packets = {
                "bad-magic": frame(b"", magic=b"XX"),
                "bad-major": frame(b"", major=2),
                "bad-minor": frame(b"", minor=1),
                "bad-flags": frame(b"", flags=1),
                "bad-reserved": frame(b"", reserved=1),
                "oversize": frame(b"", declared=MAX_BODY + 1),
            }
            sock.sendall(packets[case])
            check_closed(sock)


if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--host", default="127.0.0.1")
    parser.add_argument("--port", type=int, default=19092)
    parser.add_argument("--case", default="demo", choices=[
        "demo", "unknown", "truncated", "partial-header", "bad-magic",
        "bad-major", "bad-minor", "bad-flags", "bad-reserved", "oversize"])
    args = parser.parse_args()
    run(args.host, args.port, args.case)
```

### 9.2 先理解几处 Python 写法

- `b"MF"` 是字节，`"你好"` 是字符串，`.encode("utf-8")` 才将字符串变为字节。
- `pack` 将字段编码，`unpack` 按同一规则读回。
- `!2sBBBBHII`：`!` 表示大端且无本机对齐填充；`2s` 占 2 字节，四个 `B` 各 1 字节，`H` 占 2 字节，两个 `I` 各 4 字节，合计 16。
- `packet[1:7]` 取偏移 1～6，不包含右边界。
- `sendall` 处理部分发送，但接收仍须循环。
- `with` 让代码块结束时关闭 Socket；`expect` 比较完整类型、编号、正文，符合预期才输出 OK。
- `declared` 用来构造错误测试：让声明长度与真实正文不同，正常业务不应这么做。
- 客户端超时 8 秒，比服务端等待时间稍长；超时会抛异常，不会被当成成功拒绝。

### 9.5 第一步：看正文与字节数

`demo` 的输出应类似：

```text
header: 4d 46 01 00 01 00 00 00 00 00 00 01 00 00 00 0f
OK type=2 id=1 bytes=15 preview=...
OK type=2 id=2 bytes=0 preview=b''
OK type=2 id=3 bytes=4 preview=b'A\x00B\n'
OK type=2 id=4 bytes=1024 preview=...
```

第一条正文是 `你好，Socket`：两个汉字和中文逗号共 9 字节，加上 6 个 ASCII 字母，共 15 字节，所以长度为 `00 00 00 0F`。

`preview` 中中文显示为 `\xe4` 等转义是字节表示法，不是传输乱码。客户端比较的是完整字节，不只是预览。后面三条分别验证空正文、零字节与换行、上限 1024 字节。

### 9.6 第二步：看拆分写入与连续帧

第一帧拆成四次 `sendall`，第二、三帧合并为一次 `sendall`。服务器应解析出四条独立请求。

**四次写入不保证对方正好执行四次接收。** 系统可能合并本机数据。实验验证结果不依赖发送边界；要确定性覆盖所有接收切分，需要给接收器注入限制每次返回长度的读取函数，见练习。

`sleep`、`TCP_NODELAY` 也不能替代分帧，它们不会让 TCP 自动保存应用消息边界。

### 9.7 第三步：看可恢复错误

`unknown` 连着发送未知类型 99 与正常类型，预期：

```text
OK type=255 id=5 bytes=8 preview=b'BAD_TYPE'
OK type=2 id=6 bytes=2 preview=b'ok'
```

这证明服务端消耗了错误消息的合法正文，再处理下一帧。若没先读完正文，下一轮会把 `?` 误当帧头，导致错位。

### 9.8 第四步：看必须关闭的错误

| `--case` | 实际构造 | 服务端预期 |
| --- | --- | --- |
| `bad-magic` | 标识改成 XX | `bad magic; close` |
| `bad-major` | 版本 2.0 | `unsupported version; close` |
| `bad-minor` | 版本 1.1 | 同样拒绝，目前仅实现 1.0 |
| `bad-flags` | 标志为 1 | `unsupported flags/reserved; close` |
| `bad-reserved` | 保留字段为 1 | 同样拒绝 |
| `oversize` | 只发送帧头，声明正文 1025 字节 | 不等待正文，立即拒绝 |
| `partial-header` | 只发送 7 字节帧头，再结束发送 | `truncated header` |
| `truncated` | 声明 5 字节正文，只发 2 字节，再结束发送 | `truncated body` |

客户端输出 `OK rejected/closed` 只证明连接被关闭，拒绝原因应同时对照服务端日志。关闭可能表现为 EOF，也可能因未读数据等情况表现为连接复位，都不能当作成功响应。

`shutdown(SHUT_WR)` 表示“不会再发送”，但保留读取方向，使服务端能发现缺少字节；不同于立即关闭整个本地 Socket。

## 10. 版本演进：另一端不一定同时升级

### 10.1 为什么版本号还不够

服务器可能今天升级，用户电脑上的客户端却停在上个月。增加字段、改变单位、改变默认值，都可能使旧端误解消息。

版本号只是标记，还要定义：接受哪些版本、哪些内容可忽略、怎样协商、失败怎样处理、先升级谁、怎样回退。

**软件版本、外层帧版本、正文结构版本**是不同概念。程序从 3.2 升到 3.3，线路格式和行为没变，就不一定改协议版本；正文扩展也不一定需要改变稳定帧头。

### 10.2 两个兼容方向

本章按下面含义讨论，交流时最好同时说清“谁读谁的消息”，避免团队叫法差异：

| 名称 | 含义 | 组合 |
| --- | --- | --- |
| 向后兼容 | 新程序仍能理解旧消息 | 新接收端 ← 旧发送端 |
| 向前兼容 | 旧程序能安全处理新消息 | 旧接收端 ← 新发送端 |

读懂不只是解析成功，也要求含义正确。把超时 500 从秒改成毫秒，双方都能读出整数，但语义已经不兼容。

### 10.3 主版本、次版本是约定，不是魔法

常见约定：

- **主版本 major**：无法按旧规则安全理解的变化。
- **次版本 minor**：在某种兼容策略下新增可选能力。

主版本相同并不自动安全。要有字段可跳过机制、默认值、未知值策略和发送降级规则，才能讨论接受更高次版本。

本例严格接受 1.0。删掉次版本检查，不等于实现了兼容升级。真正支持 1.1 之前，先写清新增内容、旧端行为、请求和响应两方向的影响。

### 10.4 哪些改动危险

以下是 JSON 正文的设计例子，不是当前回显服务已实现的业务：

```json
{"op":"chat.send","text":"你好"}
```

新版本想增加字段：

```json
{"op":"chat.send","text":"你好","urgent":false}
```

| 改动 | 新端读旧消息 | 旧端读新消息 | 判断 |
| --- | --- | --- | --- |
| 新增可选 urgent，缺失默认 false | 有默认值则可处理 | 允许未知字段且可安全忽略时可处理 | 可设计为兼容 |
| 新增必填 token | 旧消息缺失，可能失败 | 旧端不了解新认证要求 | 需专门迁移，不能直接假设兼容 |
| text 改名 content | 新端只认新名会失败 | 旧端找不到 text | 通常破坏兼容，可暂时双读并规定冲突处理 |
| ID 从整数改成字符串 | 类型可能不符 | 类型可能不符 | 新建字段或明确升级 |
| timeout 从秒改成毫秒 | 可解析，但含义错 | 同样含义错 | 破坏语义兼容 |
| 枚举增加一个值 | 新端仍认识旧值 | 旧端不一定认识新值 | 必须规定未知值行为 |
| 已删除字段编号另作他用 | 同一编号被读成不同含义 | 同样危险 | 不应复用 |

**枚举（enum）**是有限选项集合，例如状态只能是 `pending/done/failed`。新增 `cancelled` 后，旧端要明确拒绝、显示未知或安全降级，不能自动触发敏感动作。

有些字段不能安全忽略。例如 `require_confirmation=true` 如果被旧端忽略，导致无需确认就付款，便不是安全的可选扩展。

### 10.5 四种组合都要测试

| 客户端 | 服务端 | 检查 |
| --- | --- | --- |
| 旧 | 旧 | 基线正常 |
| 旧 | 新 | 新服务端接收旧请求，返回旧端可理解的响应 |
| 新 | 旧 | 新客户端降级发送，理解旧响应 |
| 新 | 新 | 新能力生效，旧能力仍正常 |

请求、响应都要测试。新服务端能解析旧请求，却返回旧客户端不认识的结构，仍不算兼容。

本例只有 1.0 实现，`bad-major/bad-minor` 验证的是拒绝行为，没有两版真实程序就不能宣称四组合兼容已通过。

### 10.6 版本协商与能力协商

**协商**是先交换各自支持内容，再选共同可用的规则。假设未来双方已实现一个共同的稳定握手格式：

```text
客户端：协议 1.0、1.1；能力 echo、json-body
服务端：协议 1.0；能力 echo
最终选择：1.0 + echo
```

**能力**是具体功能，例如压缩、某种正文格式，比笼统的“最新版”更明确。

前提是握手本身双方都懂。不能把全新 JSON 握手直接发给只认识二进制 MF/1.0 的旧端，期待它自动协商。没有共同版本或必要能力时应明确失败；安全要求不能为了连通而悄悄降级。

当前示例没有 HELLO 和协商状态。未来添加时要规定消息类型、旧端行为、超时，以及选定版本后每帧是否必须一致。

### 10.7 帧头如何升级

本例正文固定从偏移 16 开始，没有 `header_length`，不能在 1.0 帧头中间随便插字段。可以：

- 保持外层不变，在已经约定好的正文格式中扩展可选字段。
- 为新主版本设计稳定开头、头部长度、扩展区，并实现不同版本的分派读取。
- 使用不同端口或服务入口隔离不兼容版本，保留迁移期。

头部长度本身也需要稳定前缀，解析器必须先知道从哪里读它。增加长度字段并不能让完全不认识新开头的旧端自动理解新格式。

### 10.8 升级与回退步骤

1. 固化当前文档和测试，核对旧端实际行为。
2. 先部署能读新旧请求的服务端，暂时继续给旧客户端返回旧格式。
3. 发布新客户端，只在协商或明确配置确认支持后发送新内容。
4. 小比例启用新功能，观察版本分布、解析失败、拒绝原因和业务结果。这叫“灰度发布”。
5. 验证回退：撤回新版服务端后，新客户端能否降级？新持久化数据能否被旧端读取？
6. 确认旧端迁移完并经过约定支持期，再停用旧协议。

“先升级服务端”不是永远正确的口诀，前提是新服务端同时照顾旧请求与旧响应，必须用矩阵证明。

### 阶段 E 检查

- [ ] 能解释新端读旧消息、旧端读新消息。
- [ ] 不把新增可选字段当成无条件兼容。
- [ ] 知道修改单位、默认值也可能破坏兼容。
- [ ] 知道协商也需要共同格式。
- [ ] 能写升级、观察、回退步骤。

## 11. 常见错误与排查顺序

### 11.1 按层定位

文件是否保存正确 → 工具能否运行 → 编译链接是否成功 → 服务端是否监听 → 客户端是否连对端口 → 帧头是否正确 → 长度是否正确 → 正文是否符合业务。

| 现象 | 常见原因 | 排查办法 |
| --- | --- | --- |
| gcc/cl/python 找不到 | 没安装或启动方式不对 | 先查版本，MSVC 用开发者命令提示符 |
| Windows 链接错含 WSAStartup、__imp_send | 缺 Winsock 库 | GCC 加 `-lws2_32`，MSVC 加 `Ws2_32.lib` |
| Windows 10048 / Linux Address already in use | 端口占用 | 关之前的实验服务，或同时改两端端口 |
| ConnectionRefusedError | 服务端没启动、已退出、端口错 | 看监听提示，核对 `--port` |
| 日志 bad magic | 发了文本或连错服务 | 用本章客户端，检查开头 `4D 46` |
| unsupported version | 主/次版本不支持 | 目前只支持 1.0，不要直接删校验 |
| 长度变成几千万 | 字节序、偏移错或重复转换 | 按字段表逐字节核对 |
| 中文长度不符 | 用了字符数 | 计算编码后字节长度 |
| 含零字节时正文变短 | 使用 strlen 或字符串处理 | 显式传递长度 |
| 等待后超时 | 声明正文比实际长，或某端没继续发 | 核对声明长度与实际字节 |
| 下一帧错位 | 上一帧没读完，或多读后丢弃尾部 | 精确消费、保留剩余数据 |
| 服务端没返回 shell 提示符 | 正在前台监听 | 另开终端运行客户端 |
| Linux Broken pipe | 向已关闭连接写入 | 处理 send 错误；本例用 MSG_NOSIGNAL |
| Python socket 模块缺属性 | 同名 socket.py 遮蔽标准库 | 改文件名，清理由该文件生成的缓存 |

```

```

建议记连接标识、版本、类型、请求编号、声明长度、实际读取进度、拒绝原因。未知类型应单独计数，便于发现版本混用。

正文可能有隐私，不要默认全部打印。二进制用有限长度十六进制预览；文本也要限制日志长度、处理控制字符。继续看 [[日志、监控与调试]]、[[安全与输入校验]]。

| 截断 | 半帧头、半正文 | partial-header、truncated |
| 不支持输入 | 错魔数、版本、标志、保留位、未知类型 | 对应案例覆盖 |
| 错误后继续 | 可恢复错误后正常请求 | unknown 覆盖 |
| 超时 | 空闲、半帧不补、持续慢速发送 | 应另做等待超时与整帧截止时间测试 |
| 业务正文 | 非法 UTF-8、畸形 JSON、类型错、重复键、过深嵌套 | 回显不解析正文，引入 JSON 后新增 |
| 新旧版本 | 四组合、降级、回退 | 当前只有 1.0，升级时新增真实实现测试 |

最大整数长度可用 `frame(b"", declared=0xFFFFFFFF)` 构造：应在帧头阶段拒绝，不分配巨大内存。要让命令行可选，记得同步加入客户端选项列表。

**模糊测试（fuzzing）**是自动生成、变异大量输入，查找崩溃、越界、长时间占用等问题。可进一步使用编译器内存检查工具测试 C 解析器，不必第一遍就搭完整工具链。

## 13. 练习题与参考答案

### 13.1 基础题

1. 正文 `中A`、编号 9，正文和整帧分别多少字节？
2. `00 00 01 00` 按大端、小端分别是什么数字？
3. 为什么长度为 0 合法，而 recv 返回 0 可能表示会话结束？
4. `{"urgent":false}`、`{"urgent":"false"}`、`{}` 为什么不同？
5. 正文从 UTF-8 换成另一编码，只改文档不改双方约定，可以吗？
6. 新增 JSON 字段为什么不一定兼容？举两个反例。

### 13.2 动手题

7. 给 demo 增加 1 字节正文，核对类型、编号、正文。
8. 加最大整数长度异常案例，拒绝后再连接发正常请求。
9. 新增 type=3 PING、type=4 PONG，正文必须为空；非空返回稳定错误码。先改规范，再改两端、测试，说明旧端会怎样处理。
10. 新增 UTF-8 JSON 正文消息类型，选 C JSON 库，定义字段表，补非法编码、畸形 JSON、重复键、类型错误、超限测试。不要改变原 type=1 回显语义。
11. 正文上限改成 4096，要同步哪些地方？对端仍只接受 1024 时怎么处理？

### 13.3 设计与进阶题

12. 设计聊天正文 1.0→1.1：新增可选 client_message_id，定义缺失语义、四组合与回退步骤。
13. 给 TLV 设计未知可选字段和未知必需字段的区分与处理。
14. 给 recv_exact 做可替换读取接口，确定性测试每次只读 1 字节、任意位置截断、连续两帧。
15. 加整帧 5 秒绝对截止时间。为什么每次 recv 超时 5 秒不够？研究单调时钟，不用会被校时改变的墙上时间。

### 13.4 参考答案与提示

1. 正文 4 字节，整帧 20 字节；帧头末 8 字节为 `00 00 00 09 00 00 00 04`。
2. 大端 256，小端 65536。字节相同，解释规则不同。
3. 前者是协议字段，后者是系统调用结果。零长度正文不用 recv，本例读满函数直接成功。
4. 分别是布尔值、字符串、缺失字段，只有 Schema 明确规则后才能决定行为。
5. 不可默默改变。即使长度相同，也可能解码失败或读成错误文本，需双方明确约定、迁移。
6. 旧端可能拒绝未知键；新字段可能要求不能忽略的新行为，例如强制确认或权限限制。
7. 用 `frame(b"A", 新编号)`，预期类型 2、相同编号、长度 1。
8. 上限判断应发生在读正文和分配前，关闭后主循环重新 accept。
9. 旧端按当前规则回 BAD_TYPE，不代表支持 PING。新客户端要识别不支持，降级或提示，不能把错误当 PONG。
10. 读满 → 严格 UTF-8 → 完整 JSON 解析 → Schema 校验 → 业务，各层独立报错。
11. 服务端数组、上限、客户端限制、文档、边界测试、并发内存预算；可协商较小上限，或继续限制 1024。
12. 缺失 ID 可以定义为“没有客户端去重标识”。单有 ID 不等于实现去重，还需记录、并发处理和过期规则。
13. 可定义标签范围或必需标记，但必须预先写入规范；只能安全忽略的内容才能跳过。
14. 用包装读取函数控制块大小，结果不得依赖操作系统碰巧怎样交付字节；也测错误与中途 EOF。
15. 帧开始记录单调时钟截止点，每次等待用剩余时间；不能每补一小块就重置整帧 5 秒。
