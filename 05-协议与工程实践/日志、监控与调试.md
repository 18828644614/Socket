# 日志、监控与调试

> 本章从“程序出问题时，我该看哪里”开始，沿用知识库的 **C 语言 + TCP Socket** 路线。你不需要提前会看日志、统计图或抓包，也不需要先搭建监控平台。
>
> 学习路线：**补齐前置知识 → 设计日志 → 理解指标 → 学会排查 → 分平台运行实验 → 用工具验证 → 故障复盘与练习**。Windows 和 Linux 服务端源码分别提供；先选择自己正在使用的平台完成一遍，再比较差异。

## 0. 学习规划：先知道要学什么、按什么顺序学

### 0.1 这一章解决什么问题

假设你写好了一个 Socket 服务器，接下来会碰到这些问题：

- 客户端说“连不上”，你怎么知道服务端是否启动、是否监听正确端口？
- 客户端说“卡住了”，你怎么区分没发数据、没带消息结束符、处理太慢、回包失败？
- 一天发生了十万次请求，你怎么知道失败比例和通常耗时？
- 程序偶尔出错，你怎么留下足够信息，让明天的自己也能重现？
- 加了很多 `printf()` 以后程序反而变慢，应该保留哪些、关闭哪些？

本章的最终目标是：**拿到一个故障现象，能用时间、连接、请求、返回值和工具输出组成证据链，而不是靠猜。**

### 0.2 完整学习范围和推荐顺序

建议分 8～10 次学习，每次 45～90 分钟。下面的时间只是安排建议；卡住时回到前置知识，不必赶进度。

| 阶段 | 学习内容 | 对应章节 | 完成标志 |
| --- | --- | --- | --- |
| A：认识现场 | 进程、端口、TCP、消息边界、返回值、两种时钟 | 第 1 节 | 能画出一次请求经过的步骤 |
| B：留下记录 | 日志级别、事件、字段、连接编号、错误码、安全记录 | 第 2～3 节 | 能解释一行日志的每个字段 |
| C：观察整体 | 计数器、当前值、速率、错误率、延迟分布、告警 | 第 4 节 | 能算出一分钟的吞吐与失败率 |
| D：形成方法 | 假设、复现、分层排查、证据边界 | 第 5 节 | 能选择下一条有用命令 |

| I：巩固迁移 | 练习、参考答案、阶段检查、后续路线 | 第 14～16 节 | 独立完成综合排错实验 |

**现在必须掌握：**正确检查返回值；及时保存系统错误码；给连接和请求编号；明确日志时间与耗时；统计连接数、结果数和延迟；能查端口、读基本 TCP 抓包；能复现至少三类故障。

**本章需要理解，但不要求立刻搭建：**日志集中收集、Prometheus、Grafana、OpenTelemetry、分布式追踪、直方图。先用本地文件和小程序弄懂这些工具要处理什么信息。

**以后再深入：**大规模高并发压测、采样算法、复杂追踪平台、操作系统内核追踪、eBPF。它们不是学会本章的前提。

先尝试回答：

1. 服务器正在运行，是否一定已经成功监听？——不一定，`bind()` 或 `listen()` 可能失败。
2. `send()` 返回 7，是否证明对方已经处理请求？——不能，只能说明本机接受了这 7 个字节用于发送。

## 1. 前置知识：把排错时会碰到的词讲清楚

### 1.1 进程、PID、端点和连接

**程序**是磁盘上的可执行文件；启动后的一个运行实例叫**进程**。操作系统给它一个进程编号，叫 **PID（Process ID）**。同一个可执行文件启动两次，是两个进程，PID 不同。

**端点**可以先理解成 `IP 地址:端口`。例如 `127.0.0.1:9090`。其中 `127.0.0.1` 是回环地址，只能用于本机通信。

TCP 连接通常用以下四个值区分，简称**四元组**：

```text
客户端IP:客户端端口 <-> 服务端IP:服务端端口
127.0.0.1:53124    <-> 127.0.0.1:9090
```

客户端临时端口可能每次变化。只记“9090 出问题”，无法区分十个客户端中的哪一个出问题。

**监听 Socket**等待新连接；`accept()` 返回的**已连接 Socket**负责与某个客户端通信。Linux 常用整数文件描述符表示 Socket；Windows 使用 `SOCKET`。这些值释放后可能被复用，不能当作永久唯一编号。

### 1.2 一次请求经过哪些步骤

```text
客户端：创建 Socket → connect 建立连接 → send 发送请求
                                       ↓
服务端：监听 → accept 接入 → recv 收集字节 → 分帧 → 校验 → 处理业务
                                                            ↓
客户端：读取响应 ← 网络传输 ← 服务端 send 响应 → 关闭或继续复用连接
```

**分帧**是把连续字节切成一条条应用消息；**校验**是检查消息是否符合约定；**业务处理**是实际完成请求，例如查询数据。

一个慢请求可能慢在任何一步。因此只写“request failed”不够，还需要知道卡在哪个阶段。

### 1.3 返回值、错误码和“暂时没有”

| 情况 | Linux | Windows | 应怎样理解 |
| --- | --- | --- | --- |
| 接收成功 | `recv()` 返回正数 | 同左 | 本次收到这么多个字节，不一定是一条完整消息 |
| 输入结束 | `recv()` 返回 `0` | 同左 | 对端有序结束发送方向，称为 EOF |
| 操作失败 | 通常返回 `-1`，读取 `errno` | 通常返回 `SOCKET_ERROR`，读取 `WSAGetLastError()` | 保存具体错误，结合操作和阶段判断 |
| 非阻塞暂时不可读/写 | `EAGAIN` / `EWOULDBLOCK` | `WSAEWOULDBLOCK` | 等待就绪后重试，不应每次都记成严重故障 |
| 调用被中断 | `EINTR` | 某些调用可能有 `WSAEINTR` | 按调用规则处理；本章等待和读写会重试 |

**阻塞**表示调用可能停在里面等待；**非阻塞**表示当前做不了就尽快返回。`select()` 用来等待“现在值得尝试读/写”的通知，这叫**就绪**。就绪不保证接下来能读到一整条消息，也可能读到 EOF。

TCP 支持只关闭一个方向，即**半关闭**。`recv()==0` 不代表本端再也不能发送。本章协议简单规定“一条请求、一条响应、关闭连接”，对缺失请求的 EOF 直接清理。

### 1.4 C 语言最少需要懂什么

- `char line[64]` 是能存 64 个字节的数组；必须防止越界。
- `int n = recv(...)` 的 `n` 是实际字节数。网络输入未必带 C 字符串结束符 `\0`。
- `\n` 是一个换行字节；本章用它标记消息结束。`\r\n` 是两个字节，与单独 `\n` 的协议约定不同。
- `size_t` 常用于容量或长度；Linux `recv()` 返回 `ssize_t`，Windows 返回 `int`。本章每次接收 1 字节，所以 Linux 的结果转成 `int` 不会丢失有效范围。
- `static` 全局变量在程序运行期间保留；示例用它保存累计指标。
- `unsigned long long` 用作非负的较大计数值；`%llu` 是对应的 `printf()` 格式。Windows 的 `SOCKET` 不应直接用 `%d` 打印。
- 示例没有线程，因此无需先学锁。如果以后加入多线程，计数器和日志写入必须重新考虑同步。

### 1.5 两种时间：记录“几点”与计算“多久”

**墙上时钟**回答“现在几点”，可能被人工修改或系统校时调整。日志时间适合采用 UTC，例如 `2026-10-15T06:00:00.123Z`，`Z` 表示 UTC；北京时间要加 8 小时。

**单调时钟**用于计算时间间隔，不随手动修改日期而向后跳。Windows 示例使用 `GetTickCount64()`，Linux 使用 `clock_gettime(CLOCK_MONOTONIC, ...)`。

```text
日志关联：2026-10-15T06:00:00.123Z
计算耗时：单调结束值 - 单调开始值 = duration_ms
```

多台机器即使都用 UTC，也可能有时钟偏差。需要校时，还要靠请求编号关联，不能仅凭两台机器的时间戳断定精确先后。跨机器相减也不适合直接当作精确网络耗时。

**本节小练习：**为什么不能用“Socket 的整数值 + 当前系统时间差”独立解决所有关联和计时问题？提示：句柄可能复用，墙上时钟可能调整。

## 2. 核心地图：日志、指标、追踪和调试分别做什么

可以把服务器想成一家餐厅：

| 手段 | 通俗理解 | 能回答的问题 | 不能单独证明的事 |
| --- | --- | --- | --- |
| 日志（log） | 某张订单的过程记录 | 哪个请求、在哪一步、因为什么失败？ | 没有记录就不能推断“肯定没发生” |
| 指标（metric） | 每分钟订单数、排队人数 | 故障是否普遍、从什么时候开始变慢？ | 通常不能定位到某个具体请求 |
| 追踪（trace） | 同一订单在多个厨房的流转 | 一个请求跨多个服务时，时间花在哪里？ | 没有埋点或传播编号的部分仍看不到 |
| 抓包 | 观察运输途中经过的包裹 | 是否握手、是否有数据、是否重传或复位？ | TCP ACK 不代表业务处理完成 |
| 调试器 | 暂停某位厨师，查看正在做什么 | 当前执行到哪一行、变量是什么？ | 暂停会改变时序，可能制造超时 |
| 系统调用观察 | 观察程序向操作系统提出的请求 | 卡在 `recv`、等待就绪，还是写文件？ | 看不到所有业务函数内部逻辑 |

**可观测性**可以先理解成“通过外部留下的信息，判断程序内部发生了什么”。它不是“工具装得越多越好”，而是你是否能回答问题。

本章先把日志和指标做好，再借助抓包与调试器交叉验证。**监控**是持续收集并判断状态；**告警**是在满足规则时提醒人处理。仅仅有一个日志文件，还不等于已经有了监控。

## 3. 日志：让每条记录都有可解释的含义

### 3.1 应记录哪些事件

先覆盖程序的关键边界，再按需要增加细节：

1. **启动**：程序版本、运行模式、监听地址和端口；配置不能包含密码。
2. **启动失败**：失败操作、地址端口、系统错误码，随后怎样退出。
3. **连接接入**：连接编号、对端地址、PID。
4. **请求阶段**：收到完整消息、校验结果、请求编号、消息长度。
5. **请求结果**：成功、非法输入、读超时、写失败、业务失败、耗时。
6. **连接清理**：关闭原因、连接持续时间，资源是否释放。

下面的教学程序固定监听 `127.0.0.1:9090`，不重复打印端点，也省略版本与对端地址，重点实现编号、错误码和结果指标。迁移到多主机环境时，应补上 `service`、`version`、本地和对端地址、阶段等字段。

不要默认每次 `recv()` 都打 INFO。高并发下逐字节日志会放大磁盘、CPU 和延迟开销。把大量细节放到可开关的 DEBUG，更适合需要时排查。

### 3.2 日志级别不是“越严重越好”

| 级别 | 含义 | 本章示例 |
| --- | --- | --- |
| DEBUG | 临时排查的细节 | 缓冲区剩余字节、每次读写数量；本章默认不输出 |
| INFO | 重要但正常的生命周期事件 | 开始监听、请求通过校验、连接关闭 |
| WARN | 需要关注，但服务通常还能工作 | 非法消息、请求超时 |
| ERROR | 某项操作失败，需要保留原因 | `bind()`、`recv()` 或 `send()` 的真实系统错误 |

正常 EOF 通常不是 ERROR；非阻塞“暂时不可用”更不应该刷屏。超时也不必一律 ERROR：测试客户端主动不发消息，与所有正常客户端都无法得到响应，是不同的影响程度。

级别是团队约定，不是操作系统自动给出的结论。连接关闭事件即使是 INFO，也能通过 `result=timeout` 表示本次以超时结束；前面的超时事件已写 WARN。

### 3.3 日志字段：从一句话升级成可以筛选的记录

```text
ts=2026-10-15T06:00:00.123Z pid=4200 level=INFO event=request_received conn_id=3 request_id=17 duration_ms=-1 code=0 result=valid
```

这是**格式示意，时间和编号不是实测值**。字段含义：

| 字段 | 含义 | 约定 |
| --- | --- | --- |
| `ts` | 事件发生时间 | UTC，带毫秒 |
| `pid` | 本次进程编号 | 进程重启会变化，但 PID 以后也可能复用 |
| `level` | 级别 | INFO、WARN、ERROR 等 |
| `event` | 稳定的事件名称 | 例如 `request_received`，不要把自由文本当事件名 |
| `conn_id` | 进程内连接编号 | 每次 `accept` 后递增；`0` 表示不属于特定连接 |
| `request_id` | 应用请求编号 | 本章从 `PING` 中解析；`0` 表示尚未解析出合法编号或此事件无编号 |
| `duration_ms` | 已定义区间的耗时 | 单位毫秒；`-1` 表示该事件不统计耗时 |
| `code` | 立即保存的系统错误码 | `0` 表示本行没有系统错误码，不代表业务成功 |
| `result` | 阶段结果或结束原因 | 例如 `valid`、`timeout`、`local_send_complete` |

这里采用 `键=值` 格式，是一种**结构化日志**：字段固定，便于程序解析。它不是 JSON；本章所有值均无空格，才能简单按空格拆分。若允许任意文本，需要转义和更严格的格式，实际项目常使用成熟 JSON 日志库。

**请求编号**关联一次应用请求；**连接编号**关联一条 TCP 连接。长连接可以有多个请求，断线重连后也可能重试同一个逻辑请求，两者不能互相代替。

本章请求编号由客户端给出，可能重复，也不能拿来鉴权。生产环境通常还需要实例编号、进程启动标识、服务端生成的追踪编号，区分重启、重试和多台机器。文件描述符与 PID 都有复用可能。

### 3.4 系统错误码必须立即保存：Windows 与 Linux 分开看

下面是**局部示意，不是独立程序**。完整可运行代码在第 7、8 节。

**Windows / Winsock：**

```c
int n = recv(s, buffer, capacity, 0);
if (n == SOCKET_ERROR) {
    int saved = WSAGetLastError();  /* 紧跟失败调用，先保存 */
    /* 之后即使日志函数调用其他 API，也使用 saved */
    fprintf(stderr, "event=recv_failed code=%d\n", saved);
}
```

**Linux：**

```c
ssize_t n = recv(fd, buffer, capacity, 0);
if (n == -1) {
    int saved = errno;             /* 紧跟失败调用，先保存 */
    fprintf(stderr, "event=recv_failed code=%d message=%s\n",
            saved, strerror(saved));
}
```

不要在成功返回后读取“上一次错误码”解释本次结果：错误状态不会因为每次成功调用都自动归零。也不要先 `close()`、写复杂日志，再去取错误码。

`WSAStartup()` 是特殊例子：它直接返回错误编号，失败时应使用返回值。Windows 普通 Win32 API 可能要求 `GetLastError()`，但这里的 Winsock 操作使用 `WSAGetLastError()`。

常见错误名供查阅，不要求背数字：

| 场景 | Windows | Linux | 首先检查 |
| --- | --- | --- | --- |
| 绑定冲突 | `WSAEADDRINUSE`，常见 10048 | `EADDRINUSE`，数值依系统而异 | 已有监听进程、绑定参数、重启后的端口状态 |
| 连接被拒绝 | `WSAECONNREFUSED`，常见 10061 | `ECONNREFUSED` | 地址端口是否正确、有无监听，是否有主动拒绝 |
| 连接被复位 | `WSAECONNRESET`，常见 10054 | `ECONNRESET` | 对端异常关闭或网络路径中的复位；结合抓包 |
| 已关闭连接上发送失败 | 可能是复位或其他关闭相关错误 | 可能 `EPIPE` / `ECONNRESET` | 对端是否已经关闭；Linux 还需处理 SIGPIPE |
| 资源不够 | 不同资源对应不同错误 | 例如 `EMFILE` / `ENFILE` | 本进程/系统句柄上限、资源泄漏 |

同样的网络故障在不同系统、不同时间点不一定得到相同错误。**本章自己计算的等待超时记录 `result=timeout code=0`，它不等于系统返回了 `ETIMEDOUT`。**

### 3.5 记录数据时，先考虑长度、安全和可读性

以下写法危险：

```c
/* 错误示意，切勿复制到服务器中 */
printf(buffer);                    /* 网络输入可能被当成格式串 */
printf("body=%s\n", buffer);       /* 可能没有结尾 \0，也可能越界读取 */
```

正确思路是记录**事件、长度、校验结果和必要的脱敏摘要**，不是把所有内容原样倒出来。

- 密码、访问令牌、Cookie、身份证号等不进入普通日志。
- 文本中的换行、回车和控制字符应转义，防止输入伪造额外日志行，这叫**日志注入**。
- 二进制数据可以在本地排错时截取少量字节转十六进制，同时标明原始长度和是否截断。十六进制只是另一种表示，**不是脱敏或加密**。
- 只记录前 64 字节也可能包含完整口令，截断不等于安全。
- 不要为了日志对整个巨大报文反复编码，观察代码也会消耗资源。

本章服务端不打印输入原文，只输出固定事件名和经过数字校验的请求编号，避免把这类风险带进实验。

**阶段 B 小检查：**能否仅凭 `conn_id=3` 找到跨重启的唯一连接？不能。能否把 `code=0` 当作成功条件？不能，必须结合事件和结果。

## 4. 监控指标：从一条记录看到整体情况

### 4.1 三种最常用的指标类型

**计数器（Counter）**：累计发生多少次，例如进程启动以来接受了 100 条连接。通常只增加，进程重启会从零开始。

**当前值（Gauge）**：当前是多少，例如现在有 8 条活动连接、日志队列里积压 20 条记录。可以增加也可以减少。

**直方图（Histogram）**：把耗时按区间统计，例如 `≤10ms`、`≤50ms`、`≤100ms`。它帮助看见“少数特别慢”的请求。不同系统的桶可能是独立区间，也可能累计计数；Prometheus 经典直方图的桶是累计计数，不能把这些桶再直接相加。

### 4.2 Socket 服务至少应观察什么

| 方面 | 初学先关注 | 出问题时意味着什么 |
| --- | --- | --- |
| 流量 | 每秒接入数、完成数、收发字节数 | 业务突然无流量，或流量超过处理能力 |
| 结果 | 成功、非法输入、超时、读写错误、提前 EOF | 区分客户端格式问题和服务端/链路问题 |
| 延迟 | 客户端总耗时、服务端处理耗时、P95/P99 | 慢在哪个区间、是否只有一部分请求很慢 |
| 资源 | 当前连接、CPU、内存、句柄/文件描述符 | 是否接近容量限制，是否有泄漏 |
| 积压 | 待处理请求、发送队列、线程池队列 | 请求来得比处理得快，出现排队 |

本章示例实现结果、连接、字节和简单耗时统计；CPU、内存、队列与延迟分布需要在后续项目继续补充。

### 4.3 速率和比例必须有时间窗口与分母

在某 60 秒窗口内：

```text
completed_total：开始时 100，结束时 220
failed_total：   开始时   5，结束时  11

完成速率 = (220 - 100) / 60 = 2 次/秒
失败率   = (11 - 5) / (220 - 100) = 5%
```

**吞吐量**表示单位时间完成多少工作。这里统计“完成”，与“接入”不同；请求可能还在排队或处理中。系统稳定且时间窗口足够长时两者才更容易接近。

计算时先回答：

1. 分母是连接、完整请求、业务请求，还是已完成尝试？
2. “失败”包含用户非法输入吗？超时算在哪类？
3. 时间窗口内是否发生重启、指标清零？若出现负差值，不能直接算负速率。
4. 分母为零时应显示“无样本”，不要算除零，也不要当成服务健康。

本章每条连接最多处理一条请求，所以用关闭连接数统计尝试结果很方便。真实长连接服务不能直接把“连接数”当作“请求数”。

### 4.4 平均值、P95 和 P99

10 个耗时样本：9 个是 `1ms`，1 个是 `901ms`，平均值为 `91ms`。平均值既不能代表大多数请求的 `1ms`，也掩盖了一个很慢的请求。

**P95**可先理解为“按耗时从小到大排序后，大约 95% 的样本不超过的数值”；P99 对应 99%。它们描述尾部延迟，不是成功率。

本章练习采用**最近秩法**：第 `ceil(p × N)` 个样本，`ceil` 表示向上取整。例如 20 个样本的 P95 取排序后第 19 个。其他工具的插值算法可能得到不同值，少量样本也不适合稳定判断 P99。

生产中通常使用分桶直方图近似统计。不能把两台服务器的 P95 直接取平均当作整体 P95；需要合并底层样本或兼容的桶再计算。

### 4.5 耗时起止点必须写清楚

```text
客户端总耗时：发起连接前 → 收齐并验证响应/得到失败
服务端连接耗时：accept 返回后 → 本次清理完成
业务处理耗时：完整请求通过校验后 → 业务处理结束
```

它们不是同一件事。客户端可能还包含建连和服务端接入前的排队；服务端连接耗时可能包含等待客户端发送完整请求。

本章 `connection_closed.duration_ms` 采用第二种口径。`latency_*` 只汇总服务端判定 `ok` 的连接耗时，因此不能拿它代表所有失败请求或客户端体验。

### 4.6 标签、维度和高基数

监控工具通常允许用 `result=timeout`、`service=echo` 等标签拆分指标。**基数**可以理解成“标签组合有多少种”。

把每个 `request_id`、`conn_id`、用户 ID 或完整 URL 当作指标标签，会产生大量不同时间序列，消耗内存与存储。通常把这些明细放日志里，指标只保留数量有限、稳定的分类，例如协议、操作名、结果类型。

### 4.7 健康检查和告警的入门原则

- “进程还在”不等于“端口监听”，更不等于“业务能完成”。
- TCP 端口探测只验证建连；应用探测应发送合法请求并校验响应和编号。
- “最近 1 分钟失败率超过阈值，且样本数足够，持续一段时间”通常比“出现一次失败就报警”更有价值。阈值取决于业务目标，不能照抄一个百分比。
- `active_connections=0` 可能是没有用户，也可能是入口坏了；需要流量、探测、监听等证据。
- 指标长时间没有上报要单独检测。“没有数据”不能画成“0 次失败”。
- TCP 探针连接后立即断开，会进入本章的 `peer_eof_total`，不能因此直接宣称有业务故障。

## 5. 调试方法：每一步都让不确定范围变小

### 5.1 先明确现象，再提出可验证的假设

“网络坏了”太宽泛。换成：

```text
现象：10:05，本机客户端连接 127.0.0.1:9090 成功，5 秒内没有完整响应。
假设 A：请求没带换行，服务端还在等完整消息。
假设 B：消息完整，但处理函数很慢。
假设 C：服务端已发送，客户端在等待错误的消息格式。
```

下一步应分别找 `request_received`、服务端耗时、客户端实际发送字节和抓包，而不是一次修改端口、缓冲区、超时、协议四个参数。

### 5.2 推荐排查顺序

1. **参数与环境**：正确的可执行文件、版本、模式、地址、端口、平台？
2. **进程和监听**：PID 是否存在，目标端口由谁监听？启动是否报错？
3. **连接建立**：拒绝、等待超时，还是已建立？在建连阶段就失败时，先查监听和路径。
4. **字节与分帧**：有没有发送、有没有收到、长度和结束符是否符合协议？
5. **处理与响应**：是否通过校验，是否卡在业务函数，是否只发送了部分响应？
6. **关闭与清理**：EOF、RST、超时、主动关闭分别由谁触发？有没有释放资源？
7. **扩大观察**：补抓包、系统调用、调试器、CPU/内存证据，验证剩余假设。

UDP 没有 TCP 的连接握手和 EOF 语义。排查 UDP 时改为观察绑定端口、目标地址、数据报和丢包；不要照搬 `ESTABLISHED` 或 TCP RST 的判断。

### 5.3 每类证据都有边界

- `connect()` 成功：TCP 连接建立，不代表应用协议通过。
- `send()` 返回正数：本机网络栈接收了字节，不代表远端程序已读取。
- 抓包看见 ACK：远端 TCP 层确认相应序号，不代表远端业务成功。
- 服务端写 `response_sent`：服务端本地完成发送循环，仍不证明客户端读到了响应。
- 客户端收齐正确 `PONG`：本次实验协议成功，不证明数据库、登录等未测试的功能也健康。
- 没看到某行日志：还要排除日志级别、缓冲、丢失、进程错误和时间范围问题。

### 5.4 如何做一个可复现的实验

先保留正常基线，再一次只改变一个条件。固定程序版本、协议、地址端口、客户端参数；记录预期和实际结果。连续重复几次，区分稳定规律与偶发现象。

本章通过客户端控制发送内容与时序，不需要关闭系统防火墙，也不需要向外部服务发请求。只在自己的回环测试环境操作。

## 6. 实验设计：一个能够解释自己的 PING/PONG 服务

### 6.1 实验协议与边界

```text
请求：PING 17\n
响应：PONG 17\n
```

- TCP，IPv4，服务端固定绑定 `127.0.0.1:9090`。
- 请求必须为大写 `PING`、一个空格、1～9 位十进制数字、一个 LF。编号值为 `1..999999999`；允许前导零，响应按数字规范化输出。
- `PING 0\n`、`PING -1\n`、`PING 1\r\n`、`HELLO 1\n`、嵌入 `\0` 都是非法输入。
- 一条连接只处理第一条请求，发送一次响应后关闭。它不是多请求长连接服务器。
- 收集一行共享 **3 秒读取期限**；不会每收到一个字节就重新计时。
- 最多读取 64 字节；64 字节还没有换行时拒绝。合法请求最多 15 字节，容量上限并不代表任意 64 字节都合法。
- 写响应另有 **3 秒写入期限**；它从处理完成后开始，所以本程序**没有实现覆盖收取、处理、发送的统一端到端期限**。
- `slow` 模式在完整请求通过校验后等待约 1200ms，模拟业务慢。

**教学取舍：**服务端一次处理一个连接，逐字节收取一行，方便看清分帧与超时。它没有并发、持久会话、TLS、鉴权、自动重连、周期采集器、优雅退出或完整日志库，也不用于性能压测。前一个客户端迟迟不发完整请求，后一个客户端可能在接入队列中等待；`listen(..., 8)` 的 8 是请求的积压队列长度参数，不是“最多 8 个业务并发”。

### 6.2 本章指标的精确定义

| 输出字段 | 本程序中的含义 |
| --- | --- |
| `accepted_total` | `accept()` 成功返回的累计连接数 |
| `active_connections` | 已接入且尚未清理的当前连接数；串行示例通常是 0 或 1 |
| `closed_total` | 已完成清理与结果归类的连接数 |
| `ok_total` | 收到合法请求，并完成本地响应发送循环 |
| `invalid_total` | 格式非法或输入过长 |
| `timeout_total` | 本程序设置的读取或写入期限到期 |
| `io_error_total` | 设置非阻塞、等待或读写遇到不能继续的错误，或描述符超出 `select` 能力 |
| `peer_eof_total` | 尚未收到完整请求时，读到了对端 EOF |
| `frames_total` | 找到第一条 LF 结尾帧的累计数量，包括格式非法帧 |
| `rx_bytes_total` | `recv()` 实际成功返回的字节总数 |
| `tx_bytes_total` | `send()` 实际成功返回的字节总数 |
| `latency_count` | `ok` 连接的样本数 |
| `latency_sum_ms` / `latency_max_ms` | 这些样本的耗时总和 / 进程启动以来最大值 |

注意：

- 五种结束结果互斥，每次关闭只增加其中一种。
- 每次打印快照时，应满足 `accepted_total = active_connections + closed_total`。
- `closed_total = ok_total + invalid_total + timeout_total + io_error_total + peer_eof_total`。
- 应用收发字节不是抓包总字节：不含 TCP/IP 头、ACK、重传；服务端未读取的额外输入也不计入 `rx_bytes_total`。
- 所有累计值只在本次进程内有效，重启会归零。
- 只在接入和关闭时输出 `event=metrics` 快照，不是每秒输出。阻塞等待 `accept()` 时没有新日志是正常的；生产监控通常还需独立的周期采集和实例存活检测。

例如，一次正常 `PING 1\n` 的请求/响应各 7 字节。一次单独的新进程实验结束后应该有 `accepted_total=1`、`closed_total=1`、`ok_total=1`、`frames_total=1`、`rx_bytes_total=7`、`tx_bytes_total=7`、`active_connections=0`。

### 6.3 先按功能阅读代码

| 函数或部分 | 作用 | 阅读重点 |
| --- | --- | --- |
| 平台辅助函数 | 错误、关闭、时间、非阻塞、初始化 | Windows/Linux 哪里不同 |
| `event()` | 输出一行固定字段日志 | 不拼接原始网络输入 |
| `metrics()` | 输出指标快照 | 累计值与当前值分开 |
| `wait_ready()` | 在同一个截止时刻前等待 | 每次重建 `fd_set` 和剩余时间 |
| `parse_request()` | 严格检查长度、关键字、数字、LF | 不依赖输入以 `\0` 结尾 |
| `serve()` | 收齐一行、校验、处理、完整发送 | 暂时不可用与真实错误分开 |
| `main()` | 创建监听、接入、统一清理、归类统计 | 每个成功接入最终都走清理路径 |

## 7. Windows 完整服务端：`observe_windows.c`

适用于 Windows 原生 MinGW-w64 GCC，在 PowerShell 启动。不是 WSL 的 Linux 程序。需要 `winsock2.h` 和链接库 `ws2_32`。

`GetTickCount64()` 是本例的单调计时来源；`GetSystemTime()` 只用于打印 UTC 时间。Windows 的 `select()` 忽略第一个参数，因此传 `0`。

下面是**一个完整源文件**，不要与 Linux 版本拼在一起。

```c
#define _WIN32_WINNT 0x0600
#define WIN32_LEAN_AND_MEAN
#include <winsock2.h>
#include <ws2tcpip.h>
#include <windows.h>
#include <stdio.h>
#include <string.h>

typedef SOCKET sock_t;
typedef unsigned long long u64;
#define BAD_SOCKET INVALID_SOCKET
static int last_error(void) { return WSAGetLastError(); }
static int again(int e) { return e == WSAEWOULDBLOCK; }
static int interrupted(int e) { return e == WSAEINTR; }
static void close_sock(sock_t s) { closesocket(s); }
static u64 now_ms(void) { return (u64)GetTickCount64(); }
static void delay_ms(void) { Sleep(1200); }
static int nonblock(sock_t s) {
    u_long on = 1;
    return ioctlsocket(s, FIONBIO, &on);
}
static void utc_stamp(char *buf, size_t cap) {
    SYSTEMTIME t;
    GetSystemTime(&t);
    snprintf(buf, cap, "%04u-%02u-%02uT%02u:%02u:%02u.%03uZ",
        (unsigned)t.wYear, (unsigned)t.wMonth, (unsigned)t.wDay,
        (unsigned)t.wHour, (unsigned)t.wMinute, (unsigned)t.wSecond,
        (unsigned)t.wMilliseconds);
}
static unsigned long process_id(void) { return GetCurrentProcessId(); }
static int net_start(void) {
    WSADATA data;
    return WSAStartup(MAKEWORD(2, 2), &data);
}
static void net_stop(void) { WSACleanup(); }
static int wait_call(sock_t s, int writing, fd_set *set, struct timeval *tv) {
    (void)s;
    return select(0, writing ? NULL : set, writing ? set : NULL, NULL, tv);
}

/* All event/result strings are constants; never log raw network input. */
static void event(const char *level, const char *name, u64 cid, u64 rid,
                  long long duration, int code, const char *result) {
    char ts[40];
    utc_stamp(ts, sizeof ts);
    printf("ts=%s pid=%lu level=%s event=%s conn_id=%llu request_id=%llu "
           "duration_ms=%lld code=%d result=%s\n",
           ts, process_id(), level, name, cid, rid, duration, code, result);
}

enum { OK, INVALID, TIMEOUT, IO_ERROR, PEER_EOF, OUTCOME_COUNT };
static const char *outcomes[] = {"ok", "invalid", "timeout", "io_error", "peer_eof"};
static struct {
    u64 accepted, active, closed, outcomes[OUTCOME_COUNT];
    u64 frames, rx, tx, latency_count, latency_sum, latency_max;
} m;

static void metrics(void) {
    char ts[40];
    utc_stamp(ts, sizeof ts);
    printf("ts=%s pid=%lu level=INFO event=metrics "
           "accepted_total=%llu active_connections=%llu closed_total=%llu "
           "ok_total=%llu invalid_total=%llu timeout_total=%llu "
           "io_error_total=%llu peer_eof_total=%llu frames_total=%llu "
           "rx_bytes_total=%llu tx_bytes_total=%llu "
           "latency_count=%llu latency_sum_ms=%llu latency_max_ms=%llu\n",
           ts, process_id(), m.accepted, m.active, m.closed,
           m.outcomes[OK], m.outcomes[INVALID], m.outcomes[TIMEOUT],
           m.outcomes[IO_ERROR], m.outcomes[PEER_EOF], m.frames, m.rx, m.tx,
           m.latency_count, m.latency_sum, m.latency_max);
}

/* 1 = ready, 0 = deadline reached, -1 = system error; save error immediately. */
static int wait_ready(sock_t s, int writing, u64 deadline, int *err) {
    for (;;) {
        u64 now = now_ms();
        if (now >= deadline) return 0;
        u64 left = deadline - now;
        struct timeval tv;
        tv.tv_sec = (long)(left / 1000);
        tv.tv_usec = (long)((left % 1000) * 1000);
        fd_set set;
        FD_ZERO(&set);
        FD_SET(s, &set);
        int n = wait_call(s, writing, &set, &tv);
        if (n > 0) return 1;
        if (n == 0) return 0;
        int e = last_error();
        if (interrupted(e)) continue;
        *err = e;
        return -1;
    }
}

/* Only: PING + one space + 1..9 digits + LF. IDs must be 1..999999999. */
static int parse_request(const char *line, int n, u64 *rid) {
    if (n < 7 || n > 15 || memcmp(line, "PING ", 5) != 0 || line[n-1] != '\n')
        return 0;
    u64 id = 0;
    for (int i = 5; i < n - 1; ++i) {
        if (line[i] < '0' || line[i] > '9') return 0;
        id = id * 10 + (unsigned)(line[i] - '0');
    }
    if (id == 0) return 0;
    *rid = id;
    return 1;
}

static int serve(sock_t s, u64 cid, int slow) {
    char line[64];
    int used = 0, err = 0;
    u64 rid = 0, read_deadline = now_ms() + 3000;
    for (;;) {
        int ready = wait_ready(s, 0, read_deadline, &err);
        if (ready <= 0) {
            event(ready == 0 ? "WARN" : "ERROR", "read_wait_end", cid, 0, -1,
                  err, ready == 0 ? "timeout" : "select_failed");
            return ready == 0 ? TIMEOUT : IO_ERROR;
        }
        /* One byte per recv keeps this teaching parser small; not for throughput. */
        int n = (int)recv(s, line + used, 1, 0);
        if (n < 0) {
            int e = last_error();
            if (again(e) || interrupted(e)) continue;
            event("ERROR", "recv_failed", cid, 0, -1, e, "io_error");
            return IO_ERROR;
        }
        if (n == 0) {
            event("INFO", "peer_eof", cid, 0, -1, 0,
                  used ? "incomplete_frame" : "no_frame");
            return PEER_EOF;
        }
        m.rx += (u64)n;
        used += n;
        if (line[used - 1] == '\n') break;
        if (used == (int)sizeof line) {
            event("WARN", "frame_too_long", cid, 0, -1, 0, "invalid");
            return INVALID;
        }
    }
    ++m.frames;
    if (!parse_request(line, used, &rid)) {
        event("WARN", "request_rejected", cid, 0, -1, 0, "invalid");
        return INVALID;
    }
    event("INFO", "request_received", cid, rid, -1, 0, "valid");
    if (slow) delay_ms();
    char reply[32];
    int len = snprintf(reply, sizeof reply, "PONG %llu\n", rid);
    int sent = 0;
    u64 write_deadline = now_ms() + 3000;
    while (sent < len) {
        err = 0;
        int ready = wait_ready(s, 1, write_deadline, &err);
        if (ready <= 0) {
            event(ready == 0 ? "WARN" : "ERROR", "write_wait_end", cid, rid, -1,
                  err, ready == 0 ? "timeout" : "select_failed");
            return ready == 0 ? TIMEOUT : IO_ERROR;
        }
        int n = send(s, reply + sent, len - sent, 0);
        if (n < 0) {
            int e = last_error();
            if (again(e) || interrupted(e)) continue;
            event("ERROR", "send_failed", cid, rid, -1, e, "io_error");
            return IO_ERROR;
        }
        if (n == 0) {
            event("ERROR", "send_failed", cid, rid, -1, 0, "zero_write");
            return IO_ERROR;
        }
        sent += n;
        m.tx += (u64)n;
    }
    event("INFO", "response_sent", cid, rid, -1, 0, "local_send_complete");
    return OK;
}

int main(int argc, char **argv) {
    if (argc > 2 || (argc == 2 && strcmp(argv[1], "slow") != 0)) {
        fprintf(stderr, "usage: %s [slow]\n", argv[0]);
        return 2;
    }
    setvbuf(stdout, NULL, _IONBF, 0); /* Flush each line even with file redirection. */
    int e = net_start();
    if (e != 0) { event("ERROR", "network_init_failed", 0, 0, -1, e, "exit"); return 1; }
    sock_t listener = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listener == BAD_SOCKET) {
        e = last_error();
        event("ERROR", "socket_failed", 0, 0, -1, e, "exit");
        net_stop(); return 1;
    }
    struct sockaddr_in addr;
    memset(&addr, 0, sizeof addr);
    addr.sin_family = AF_INET;
    addr.sin_port = htons(9090);
    addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (bind(listener, (struct sockaddr *)&addr, sizeof addr) < 0) {
        e = last_error();
        event("ERROR", "bind_failed", 0, 0, -1, e, "exit");
        close_sock(listener); net_stop(); return 1;
    }
    if (listen(listener, 8) < 0) {
        e = last_error();
        event("ERROR", "listen_failed", 0, 0, -1, e, "exit");
        close_sock(listener); net_stop(); return 1;
    }
    event("INFO", "listening", 0, 0, -1, 0, argc == 2 ? "slow" : "normal");
    u64 next_id = 0;
    int exit_code = 0;
    for (;;) {
        sock_t s = accept(listener, NULL, NULL);
        if (s == BAD_SOCKET) {
            e = last_error();
            if (interrupted(e)) continue;
            event("ERROR", "accept_failed", 0, 0, -1, e, "exit");
            exit_code = 1; break; /* Avoid spinning forever on resource exhaustion. */
        }
        u64 cid = ++next_id, started = now_ms();
        ++m.accepted; ++m.active;
        event("INFO", "connection_opened", cid, 0, -1, 0, "accepted");
        metrics();
        int outcome;
        if (nonblock(s) < 0) {
            e = last_error();
            event("ERROR", "nonblock_failed", cid, 0, -1, e, "io_error");
            outcome = IO_ERROR;
        } else {
            outcome = serve(s, cid, argc == 2);
        }
        close_sock(s);
        --m.active; ++m.closed; ++m.outcomes[outcome];
        u64 elapsed = now_ms() - started;
        if (outcome == OK) {
            ++m.latency_count; m.latency_sum += elapsed;
            if (elapsed > m.latency_max) m.latency_max = elapsed;
        }
        event("INFO", "connection_closed", cid, 0, (long long)elapsed, 0, outcomes[outcome]);
        metrics();
    }
    close_sock(listener);
    net_stop();
    return exit_code;
}
```

## 8. Linux 完整服务端：`observe_linux.c`

适用于 Linux 或 WSL 内的 Linux，使用 GCC 与 POSIX 接口。`MSG_NOSIGNAL` 是这里使用的 Linux 选项，避免发送到已关闭连接时被 SIGPIPE 信号直接终止；错误会以返回值和 `errno` 交给程序处理。它不代表可以忽略发送失败。

Linux 的 `select()` 第一个参数是“要检查的最大文件描述符 + 1”；`FD_SET` 无法安全容纳大于等于 `FD_SETSIZE` 的描述符，因此代码显式拒绝这种情况。Windows 的 `fd_set` 组织不同，本例每次只放一个 Socket，不能照搬 Linux 的数值上限判断。

下面是另一份**完整源文件**。

```c
#define _POSIX_C_SOURCE 200809L
#include <sys/types.h>
#include <sys/socket.h>
#include <sys/select.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
#include <fcntl.h>
#include <errno.h>
#include <time.h>
#include <stdio.h>
#include <string.h>

typedef int sock_t;
typedef unsigned long long u64;
#define BAD_SOCKET (-1)
static int last_error(void) { return errno; }
static int again(int e) { return e == EAGAIN || e == EWOULDBLOCK; }
static int interrupted(int e) { return e == EINTR; }
static void close_sock(sock_t s) { close(s); }
static u64 now_ms(void) {
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return (u64)t.tv_sec * 1000 + (u64)t.tv_nsec / 1000000;
}
static void delay_ms(void) {
    struct timespec t = {1, 200000000L};
    while (nanosleep(&t, &t) < 0 && errno == EINTR) { }
}
static int nonblock(sock_t s) {
    int flags = fcntl(s, F_GETFL, 0);
    return flags < 0 ? -1 : fcntl(s, F_SETFL, flags | O_NONBLOCK);
}
static void utc_stamp(char *buf, size_t cap) {
    struct timespec t;
    struct tm tm;
    clock_gettime(CLOCK_REALTIME, &t);
    gmtime_r(&t.tv_sec, &tm);
    strftime(buf, cap, "%Y-%m-%dT%H:%M:%S", &tm);
    size_t n = strlen(buf);
    snprintf(buf + n, cap - n, ".%03ldZ", t.tv_nsec / 1000000);
}
static unsigned long process_id(void) { return (unsigned long)getpid(); }
static int net_start(void) { return 0; }
static void net_stop(void) { }
static int wait_call(sock_t s, int writing, fd_set *set, struct timeval *tv) {
    return select(s + 1, writing ? NULL : set, writing ? set : NULL, NULL, tv);
}

/* All event/result strings are constants; never log raw network input. */
static void event(const char *level, const char *name, u64 cid, u64 rid,
                  long long duration, int code, const char *result) {
    char ts[40];
    utc_stamp(ts, sizeof ts);
    printf("ts=%s pid=%lu level=%s event=%s conn_id=%llu request_id=%llu "
           "duration_ms=%lld code=%d result=%s\n",
           ts, process_id(), level, name, cid, rid, duration, code, result);
}

enum { OK, INVALID, TIMEOUT, IO_ERROR, PEER_EOF, OUTCOME_COUNT };
static const char *outcomes[] = {"ok", "invalid", "timeout", "io_error", "peer_eof"};
static struct {
    u64 accepted, active, closed, outcomes[OUTCOME_COUNT];
    u64 frames, rx, tx, latency_count, latency_sum, latency_max;
} m;

static void metrics(void) {
    char ts[40];
    utc_stamp(ts, sizeof ts);
    printf("ts=%s pid=%lu level=INFO event=metrics "
           "accepted_total=%llu active_connections=%llu closed_total=%llu "
           "ok_total=%llu invalid_total=%llu timeout_total=%llu "
           "io_error_total=%llu peer_eof_total=%llu frames_total=%llu "
           "rx_bytes_total=%llu tx_bytes_total=%llu "
           "latency_count=%llu latency_sum_ms=%llu latency_max_ms=%llu\n",
           ts, process_id(), m.accepted, m.active, m.closed,
           m.outcomes[OK], m.outcomes[INVALID], m.outcomes[TIMEOUT],
           m.outcomes[IO_ERROR], m.outcomes[PEER_EOF], m.frames, m.rx, m.tx,
           m.latency_count, m.latency_sum, m.latency_max);
}

/* 1 = ready, 0 = deadline reached, -1 = system error; save error immediately. */
static int wait_ready(sock_t s, int writing, u64 deadline, int *err) {
    for (;;) {
        u64 now = now_ms();
        if (now >= deadline) return 0;
        u64 left = deadline - now;
        struct timeval tv;
        tv.tv_sec = (long)(left / 1000);
        tv.tv_usec = (long)((left % 1000) * 1000);
        fd_set set;
        FD_ZERO(&set);
        FD_SET(s, &set);
        int n = wait_call(s, writing, &set, &tv);
        if (n > 0) return 1;
        if (n == 0) return 0;
        int e = last_error();
        if (interrupted(e)) continue;
        *err = e;
        return -1;
    }
}

/* Only: PING + one space + 1..9 digits + LF. IDs must be 1..999999999. */
static int parse_request(const char *line, int n, u64 *rid) {
    if (n < 7 || n > 15 || memcmp(line, "PING ", 5) != 0 || line[n-1] != '\n')
        return 0;
    u64 id = 0;
    for (int i = 5; i < n - 1; ++i) {
        if (line[i] < '0' || line[i] > '9') return 0;
        id = id * 10 + (unsigned)(line[i] - '0');
    }
    if (id == 0) return 0;
    *rid = id;
    return 1;
}

static int serve(sock_t s, u64 cid, int slow) {
    char line[64];
    int used = 0, err = 0;
    u64 rid = 0, read_deadline = now_ms() + 3000;
    for (;;) {
        int ready = wait_ready(s, 0, read_deadline, &err);
        if (ready <= 0) {
            event(ready == 0 ? "WARN" : "ERROR", "read_wait_end", cid, 0, -1,
                  err, ready == 0 ? "timeout" : "select_failed");
            return ready == 0 ? TIMEOUT : IO_ERROR;
        }
        /* One byte per recv keeps this teaching parser small; not for throughput. */
        int n = (int)recv(s, line + used, 1, 0);
        if (n < 0) {
            int e = last_error();
            if (again(e) || interrupted(e)) continue;
            event("ERROR", "recv_failed", cid, 0, -1, e, "io_error");
            return IO_ERROR;
        }
        if (n == 0) {
            event("INFO", "peer_eof", cid, 0, -1, 0,
                  used ? "incomplete_frame" : "no_frame");
            return PEER_EOF;
        }
        m.rx += (u64)n;
        used += n;
        if (line[used - 1] == '\n') break;
        if (used == (int)sizeof line) {
            event("WARN", "frame_too_long", cid, 0, -1, 0, "invalid");
            return INVALID;
        }
    }
    ++m.frames;
    if (!parse_request(line, used, &rid)) {
        event("WARN", "request_rejected", cid, 0, -1, 0, "invalid");
        return INVALID;
    }
    event("INFO", "request_received", cid, rid, -1, 0, "valid");
    if (slow) delay_ms();
    char reply[32];
    int len = snprintf(reply, sizeof reply, "PONG %llu\n", rid);
    int sent = 0;
    u64 write_deadline = now_ms() + 3000;
    while (sent < len) {
        err = 0;
        int ready = wait_ready(s, 1, write_deadline, &err);
        if (ready <= 0) {
            event(ready == 0 ? "WARN" : "ERROR", "write_wait_end", cid, rid, -1,
                  err, ready == 0 ? "timeout" : "select_failed");
            return ready == 0 ? TIMEOUT : IO_ERROR;
        }
        int n = (int)send(s, reply + sent, (size_t)(len - sent), MSG_NOSIGNAL);
        if (n < 0) {
            int e = last_error();
            if (again(e) || interrupted(e)) continue;
            event("ERROR", "send_failed", cid, rid, -1, e, "io_error");
            return IO_ERROR;
        }
        if (n == 0) {
            event("ERROR", "send_failed", cid, rid, -1, 0, "zero_write");
            return IO_ERROR;
        }
        sent += n;
        m.tx += (u64)n;
    }
    event("INFO", "response_sent", cid, rid, -1, 0, "local_send_complete");
    return OK;
}

int main(int argc, char **argv) {
    if (argc > 2 || (argc == 2 && strcmp(argv[1], "slow") != 0)) {
        fprintf(stderr, "usage: %s [slow]\n", argv[0]);
        return 2;
    }
    setvbuf(stdout, NULL, _IONBF, 0); /* Flush each line even with file redirection. */
    int e = net_start();
    if (e != 0) { event("ERROR", "network_init_failed", 0, 0, -1, e, "exit"); return 1; }
    sock_t listener = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (listener == BAD_SOCKET) {
        e = last_error();
        event("ERROR", "socket_failed", 0, 0, -1, e, "exit");
        net_stop(); return 1;
    }
    struct sockaddr_in addr;
    memset(&addr, 0, sizeof addr);
    addr.sin_family = AF_INET;
    addr.sin_port = htons(9090);
    addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    if (bind(listener, (struct sockaddr *)&addr, sizeof addr) < 0) {
        e = last_error();
        event("ERROR", "bind_failed", 0, 0, -1, e, "exit");
        close_sock(listener); net_stop(); return 1;
    }
    if (listen(listener, 8) < 0) {
        e = last_error();
        event("ERROR", "listen_failed", 0, 0, -1, e, "exit");
        close_sock(listener); net_stop(); return 1;
    }
    event("INFO", "listening", 0, 0, -1, 0, argc == 2 ? "slow" : "normal");
    u64 next_id = 0;
    int exit_code = 0;
    for (;;) {
        sock_t s = accept(listener, NULL, NULL);
        if (s == BAD_SOCKET) {
            e = last_error();
            if (interrupted(e)) continue;
            event("ERROR", "accept_failed", 0, 0, -1, e, "exit");
            exit_code = 1; break; /* Avoid spinning forever on resource exhaustion. */
        }
        u64 cid = ++next_id, started = now_ms();
        ++m.accepted; ++m.active;
        event("INFO", "connection_opened", cid, 0, -1, 0, "accepted");
        metrics();
        int outcome;
        /* POSIX FD_SET cannot represent descriptors >= FD_SETSIZE. */
        if (s >= FD_SETSIZE) {
            event("ERROR", "fd_limit", cid, 0, -1, 0, "io_error");
            outcome = IO_ERROR;
        } else
        if (nonblock(s) < 0) {
            e = last_error();
            event("ERROR", "nonblock_failed", cid, 0, -1, e, "io_error");
            outcome = IO_ERROR;
        } else {
            outcome = serve(s, cid, argc == 2);
        }
        close_sock(s);
        --m.active; ++m.closed; ++m.outcomes[outcome];
        u64 elapsed = now_ms() - started;
        if (outcome == OK) {
            ++m.latency_count; m.latency_sum += elapsed;
            if (elapsed > m.latency_max) m.latency_max = elapsed;
        }
        event("INFO", "connection_closed", cid, 0, (long long)elapsed, 0, outcomes[outcome]);
        metrics();
    }
    close_sock(listener);
    net_stop();
    return exit_code;
}
```

## 9. 测试客户端、编译和第一轮运行

### 9.1 共用测试客户端：`probe.py`

服务端练习仍使用 C；客户端用 Python 标准库，目的是方便精确控制输入和延迟，不需要安装第三方包。**这一文件在 Windows 和 Linux 都可用**，不含平台专属 Socket API；两端运行命令在下面分开给出。

其中 `socket` 是网络库，`argparse` 解析命令行参数，`time.monotonic()` 计算总耗时。`bytes` 表示字节序列，`b"..."` 是它的字面写法；`repr()` 将换行等显示为 `\n`，方便确认实际内容。

客户端设置的总期限覆盖发起连接、发送和接收，接收循环不会每个字节重新获得一整段时间。示例中固定的测试休眠会增加调度误差，因此它是实验用超时检查，不是硬实时保证。客户端错误会打印 `client_error`，脚本为教学统一以正常退出结束；自动化测试需检查输出或自行补充失败退出码。

```python
import argparse
import socket
import time

p = argparse.ArgumentParser(description="Local PING/PONG test client")
p.add_argument("mode", choices=["normal", "split", "invalid", "no-newline", "eof", "long", "drip", "two"])
p.add_argument("--id", type=int, default=1)
p.add_argument("--timeout", type=float, default=5.0)
p.add_argument("--port", type=int, default=9090)
a = p.parse_args()
if not (1 <= a.id <= 999999999) or a.timeout <= 0 or not (1 <= a.port <= 65535):
    p.error("id=1..999999999, timeout>0, port=1..65535")

started = time.monotonic()
try:
    with socket.create_connection(("127.0.0.1", a.port), timeout=a.timeout) as s:
        # One deadline covers connect + send + receive. Do not refresh it per byte.
        deadline = started + a.timeout

        def remaining():
            left = deadline - time.monotonic()
            if left <= 0:
                raise TimeoutError("client total deadline exceeded")
            s.settimeout(left)

        request = f"PING {a.id}\n".encode("ascii")
        expected = f"PONG {a.id}\n".encode("ascii")
        if a.mode == "split":
            remaining()
            s.sendall(request[:2])
            time.sleep(0.2)
            remaining()
            s.sendall(request[2:])
        elif a.mode == "drip":
            for byte in request:
                remaining()
                s.sendall(bytes([byte]))
                time.sleep(0.6)
        elif a.mode == "eof":
            s.shutdown(socket.SHUT_WR)  # End our sending direction, still read.
        else:
            data = {
                "invalid": b"HELLO 1\n",
                "no-newline": request[:-1],
                "long": b"X" * 64,
                "two": request + b"PING 2\n",
            }.get(a.mode, request)
            remaining()
            s.sendall(data)

        response = bytearray()
        while not response.endswith(b"\n"):
            remaining()
            part = s.recv(1)
            if not part:
                print("peer_eof: no complete reply", repr(bytes(response)))
                break
            response.extend(part)
            if len(response) > 64:
                raise ValueError("reply too long")
        else:
            if bytes(response) != expected:
                raise ValueError(f"unexpected reply: {bytes(response)!r}")
            print("ok:", repr(bytes(response)))
except (OSError, ValueError) as exc:
    print(f"client_error: {type(exc).__name__}: {exc}")
finally:
    print(f"client_elapsed_ms={(time.monotonic() - started) * 1000:.1f}")
```

```bash
cd ~/socket-labs/observability
python3 ./probe.py normal --id 17
```

预期结果与 Windows 相同。`Ctrl+C` 停止服务端。需要保存日志时，先结束旧实例，再在终端 A 启动：

```bash
./observe_linux > server-linux.log 2>&1
```

**终端 C：**

```bash
tail -n 30 -f server-linux.log
```

本例没有设置端口复用选项，目的是避免把平台差异藏起来。如果停止后立即重启遇到 `EADDRINUSE`，先查有无旧进程与 TCP 状态；必要时等旧连接状态消退再重试。不要一上来就杀掉所有进程。生产服务的快速重启与端口复用设计可继续看 [[Socket选项与内核参数]]。

### 9.4 正常日志应如何阅读

以下省略时间等公共字段，仅显示顺序，**不是新的日志格式**：

```text
event=listening result=normal
event=connection_opened conn_id=1
event=metrics accepted_total=1 active_connections=1 closed_total=0 ...
event=request_received conn_id=1 request_id=17 result=valid
event=response_sent conn_id=1 request_id=17 result=local_send_complete
event=connection_closed conn_id=1 duration_ms=... result=ok
event=metrics accepted_total=1 active_connections=0 closed_total=1 ok_total=1 ...
```

按 `conn_id=1` 把过程连起来，再看请求编号。`connection_closed` 没有保留请求编号，使用 `request_id=0`；这是本章函数边界的简化，不表示前面的请求编号无效。

`duration_ms` 是整数毫秒，小请求可能显示 `0`，表示不足本例计时分辨率或落在同一毫秒刻度，不表示绝对没有耗时。客户端通过 `repr()` 把收到的换行显示为 `\n`，便于检查协议。

## 10. 故障实验：先预测，再运行，再对照日志

### 10.1 第一组实验的目标

保持服务端为普通模式。每次只运行一条客户端命令，等它结束，再观察该连接的日志和最新指标。

| 模式 | 改变了什么 | 服务端关键事件/结果 | 应学会什么 |
| --- | --- | --- | --- |
| `normal` | 合法请求 | `request_received` → `response_sent` → `ok` | 建立正常基线 |
| `split` | 先发 `PI`，约 200ms 后发剩余内容 | 仍为 `ok` | 多次发送仍组成同一条消息 |
| `invalid` | 发 `HELLO 1\n` | `request_rejected`，`invalid` | 完整消息不等于合法消息 |
| `no-newline` | 发 `PING 1` 后保持连接 | 约 3 秒后 `read_wait_end result=timeout` | 缺少分隔符会一直等到期限 |
| `eof` | 不发请求，半关闭发送方向 | `peer_eof result=no_frame` | EOF 与等待超时不同 |
| `long` | 发 64 个 `X`，没有 LF | `frame_too_long`，`invalid` | 长度限制先保护缓冲区 |
| `drip` | 每隔约 600ms 发 1 字节 | 通常在完整行到达前读取超时 | 总读取期限不会被一点点输入无限延长 |
| `two` | 一次发送两行 `PING` | 只处理第一行，得到一次 `ok` | 协议规定与 TCP 收包方式是两回事 |

`split` 保证有两次应用发送，不保证网卡上一定出现两个 TCP 段。测试环境和网络栈可能合并或拆分它们。`two` 也不用于验证多请求长连接：本服务端明确只处理第一条，客户端收到第一条响应就结束。

### 10.2 Windows：逐条运行

终端 A 保持 `.\observe_windows.exe` 运行；下面在同目录的终端 B 执行：

```powershell
python .\probe.py normal
python .\probe.py split
python .\probe.py invalid
python .\probe.py no-newline
python .\probe.py eof
python .\probe.py long
python .\probe.py drip
python .\probe.py two
```

### 10.3 Linux：逐条运行

终端 A 保持 `./observe_linux` 运行；下面在同目录的终端 B 执行：

```bash
python3 ./probe.py normal
python3 ./probe.py split
python3 ./probe.py invalid
python3 ./probe.py no-newline
python3 ./probe.py eof
python3 ./probe.py long
python3 ./probe.py drip
python3 ./probe.py two
```

### 10.4 如何判断第一组实验是否通过

如果从全新普通模式进程开始，**只做以上八次连接，没有端口探测、其他客户端或调试器介入**，等待每次清理完成，预计累计结果为：

```text
accepted_total=8
active_connections=0
closed_total=8
ok_total=3
invalid_total=2
timeout_total=2
io_error_total=0
peer_eof_total=1
frames_total=4
latency_count=3
```

原因：`normal`、`split`、`two` 成功；`invalid` 与 `long` 非法；`no-newline` 与 `drip` 超时；`eof` 提前结束。只有前三次成功和 `invalid` 收到了首条 LF 完整帧，所以 `frames_total=4`。精确耗时、句柄、PID 和收取到的慢速字节数不要写死。

如果结果不符，先用 `conn_id` 找到多出的连接。`Test-NetConnection`、`nc -z`、健康探针都可能真实接入并改变统计。

对 `invalid`、`long`、`no-newline` 等模式，本客户端常显示 `peer_eof: no complete reply`，也可能看到连接复位等系统错误。**客户端看到 EOF，不代表服务端归类为 `peer_eof`**：可能是服务端先因超时关闭了连接。以服务端自身读到了什么、如何结束为分类依据。

### 10.5 第二组：慢服务端与客户端超时

先停止普通模式服务端，再以 `slow` 模式启动。两端分别使用自己的运行环境；Windows 原生服务端配 Windows 客户端、WSL 服务端配 WSL 客户端更容易避免网络边界混淆。

**Windows，终端 A：**

```powershell
.\observe_windows.exe slow
```

**Windows，终端 B：**

```powershell
python .\probe.py normal --id 21
python .\probe.py normal --id 22 --timeout 0.2
```

**Linux，终端 A：**

```bash
./observe_linux slow
```

**Linux，终端 B：**

```bash
python3 ./probe.py normal --id 21
python3 ./probe.py normal --id 22 --timeout 0.2
```

第一条通常约 1.2 秒后成功；第二条客户端约 0.2 秒到期，服务端可能还在睡眠。**等待服务端完成这一连接后再看结果**。

服务端稍后 `send()` 可能成功，也可能失败：本机接受写入时，不一定已经知道对方的关闭状态。因此可能出现“客户端超时，服务端却是 `ok`”，也可能出现 `send_failed`。这不是日志矛盾，而是观察点和成功口径不同。

不要为了让数字“好看”就把客户端超时改成无限等待。正确做法是明确客户端总预算，测量排队、处理与传输时间，再决定优化或调整预算。

### 10.6 第三组：未监听端口与重复启动

**未监听端口：**先用第 11 节的命令确认 9092 没有服务，再测试。


**重复启动：**保持一份服务端运行，再在另一终端启动同一服务端。

Windows：

```powershell

```

Linux：

```bash
./observe_linux
```

第二份应报告 `bind_failed` 并退出。第一份继续服务。应查询端口归属后有针对性地停止自己启动的旧实例，避免因为看到端口占用就结束无关进程。

## 11. 用工具交叉验证：端口、数据包、断点和系统调用

### 11.1 Windows：确认监听、PID 和连接

以下在 PowerShell 执行，无匹配项时可能提示未找到对象，先检查服务端是否已经启动。

```powershell
# 监听的端口由哪个进程持有？
Get-NetTCPConnection -State Listen -LocalPort 9090 |
    Select-Object LocalAddress,LocalPort,State,OwningProcess

# 根据查询结果自动列出对应进程
Get-NetTCPConnection -State Listen -LocalPort 9090 |
    ForEach-Object { Get-Process -Id $_.OwningProcess }

# 查看这个端口的所有 TCP 状态
Get-NetTCPConnection -LocalPort 9090 |
    Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,State,OwningProcess

# 传统命令；文本搜索可能连相近端口一起匹配，需核对列
netstat -ano -p tcp | Select-String ':9090'

# 建立一次 TCP 端口探测连接，会改变实验指标
Test-NetConnection -ComputerName 127.0.0.1 -Port 9090
```

普通正常请求很快关闭，未必来得及看到 `Established`。可在另一终端运行 `no-newline`，在 3 秒内查询；不要因为“查询时没看见”就断言连接从未建立。

### 11.2 Linux：确认监听、PID 和连接

在 Bash 执行。`sudo` 主要用于查看其他用户的进程信息；自己的端口状态通常也可不加它查看。

```bash
# -l 监听，-t TCP，-n 数字地址端口，-p 进程
sudo ss -ltnp 'sport = :9090'

# 查看 9090 相关连接状态
ss -tnp '( sport = :9090 or dport = :9090 )'

# 如已安装 lsof，可从进程打开的网络资源角度查看
sudo lsof -nP -iTCP:9090

# 可选：nc 属于额外工具，不一定已经安装；它只检查 TCP 建连
nc -vz 127.0.0.1 9090
```

`nc -vz` 建连后关闭，也可能给本章服务端增加一次 `peer_eof_total`。端口探测不是“只读数据库查询”，它会实际影响服务端行为。

### 11.3 学会读几种 TCP 状态

| 状态 | 入门解释 | 本章排查动作 |
| --- | --- | --- |
| `LISTEN` | 等待别人连接 | 核对地址、端口和进程 |
| `SYN-SENT` | 发起握手，还没完成 | 检查目标、路径、过滤策略 |
| `ESTABLISHED` | 握手完成 | 再查完整请求、处理与响应 |
| `CLOSE-WAIT` | 已收到对端结束发送，本端还没关闭 | 少量短暂存在正常；大量长期存在要检查清理路径 |
| `TIME-WAIT` | 主动关闭后的保护等待状态 | 不等于进程泄漏；结合连接创建速率判断 |

不要为了“去掉 TIME-WAIT”随意修改内核参数。先弄清连接生命周期，见 [[连接生命周期]] 和 [[Socket选项与内核参数]]。

### 11.4 Windows：Wireshark 抓一次本机请求

需要安装 Wireshark 和适当的 Npcap 抓包支持。操作顺序：

1. 选择回环接口，通常显示为 **Adapter for loopback traffic capture** 或类似名称。不是普通 Wi-Fi/Ethernet 接口。
2. 开始抓包，再运行 `python .\probe.py normal --id 31`。
3. 停止抓包，在**显示过滤器**中输入 `tcp.port == 9090`。
4. 找到一次握手和应用数据，右键该连接的包，选择 **Follow → TCP Stream**。
5. 检查重组流是否包含 `PING 31` 和 `PONG 31`，并核对消息末尾 LF。可使用十六进制视图确认 `0a`。
6. 从某个包打开对应流后，可用 `tcp.stream eq N` 聚焦这次连接，`N` 用界面中实际的流编号替换。

常用显示过滤器：

```text
tcp.port == 9090
tcp.port == 9090 && tcp.len > 0
tcp.port == 9090 && tcp.flags.reset == 1
tcp.port == 9090 && tcp.analysis.retransmission
```

它们分别筛选端口、携带 TCP 有效负载、复位、分析为重传的数据包。复位不等于“必然是黑客”，重传也不是业务重复提交的同义词。

### 11.5 Linux：tcpdump 抓回环并保存

**终端 C，先启动抓包：**

```bash
sudo tcpdump -i lo -nn -s 0 -w pingpong.pcap 'tcp port 9090'
```

**终端 B，运行客户端：**

```bash
python3 ./probe.py normal --id 31
```

终端 C 按 `Ctrl+C` 结束并保存文件。随后读取：

```bash
tcpdump -nn -tttt -r pingpong.pcap
tcpdump -nn -A -r pingpong.pcap 'tcp port 9090'
```

参数：`-i lo` 指定回环接口；`-nn` 不把地址、端口转换成名字；`-s 0` 请求捕获完整包；`-w` 写文件；`-r` 读文件；`-A` 显示可打印内容，适合本章明文小协议。Wireshark 的重组流视图通常更便于阅读完整应用对话。

`'tcp port 9090'` 是**捕获过滤器**，与 Wireshark 显示过滤器 `tcp.port == 9090` 不是同一语法。抓错接口或捕获时漏掉的数据，事后调整显示过滤器也找不回来。

### 11.6 抓包最常见的误读

- **TCP 段 ≠ 应用消息。**一条消息可跨多段；一段也可带多条消息。
- **看见发出 ≠ 对端进程收到。**单侧抓包只能说明这个观察点看到了什么；必要时在两端同时捕获。
- **ACK ≠ 业务成功。**应结合应用响应和编号。
- **FIN 与 RST 不同。**FIN 表示结束发送方向；RST 是连接复位。应用退出、未读数据、系统策略等都会影响实际关闭方式，不能只凭一个标志断言根因。
- **重传标记是分析结果。**抓包丢包、重复捕获、网卡分段/校验和卸载都可能影响显示；本机抓包的校验和提示不一定是真实链路损坏。
- **TLS 会加密应用内容。**看不到明文不等于没传数据；不要为了调试就把真实服务的加密关掉。
- **抓包也包含敏感信息。**本章只抓本机明文测试数据，分享前仍应检查文件内容、权限和保存期限。

### 11.7 Windows：用 GDB 看 C 变量和调用栈

需要 MinGW-w64 发行环境中的 GDB。先停止独立运行的服务端，避免调试器里的新实例绑定失败。已用 `-g -O0` 编译。

**PowerShell：**

```powershell
gdb .\observe_windows.exe
```

**进入 GDB 提示符后逐条输入：**

```text
break parse_request
run
```

**另一个 PowerShell：**

```powershell
python .\probe.py normal --id 41 --timeout 30
```

断点停住后回到 GDB，输入：

```text
bt
print n
x/8bx line
next
continue
```

`bt` 查看调用栈，即函数之间的调用关系；`print n` 看当前帧长度；`x/8bx line` 以十六进制显示 8 个字节。`PING 41\n` 正好是 8 字节，最后应为 `0x0a`。`next` 执行下一行；`continue` 继续运行。实验结束后在服务端等待状态按 `Ctrl+C`，输入 `quit`，按提示退出调试会话。

不要依赖调试器显示 `%s` 形式的输入缓冲区；它未必有 `\0`。查看已知长度的字节更可靠。

### 11.8 Linux：用 GDB 看同一位置

同样先停止旧服务端，再在 Bash 执行：

```bash
gdb ./observe_linux
```

**GDB 内：**

```text
break parse_request
run
```

**另一终端：**

```bash
python3 ./probe.py normal --id 41 --timeout 30
```

**断点停下后，在 GDB 内：**

```text
bt
print n
x/8bx line
next
continue
```

两平台的断点操作类似，但 Socket 类型、系统错误码和底层调用不同。**断点会暂停整个本例进程，却不会暂停另一个进程的超时计时。**即使用 30 秒客户端预算，也应尽快查看并继续；如果在服务端读取期限内暂停太久，也会影响服务端后续超时判断。正常性能数据与断点实验必须分开记录。

进阶练习：在 `serve` 内等待或发送前设断点，验证暂停如何制造超时。多线程进程中调试器是否暂停全部线程取决于调试设置，要另外学习。

### 11.9 Linux：用 strace 看程序与操作系统的交互

**系统调用**可以理解成程序请操作系统帮忙做事，例如接收连接、收数据、等待事件。Linux 下的 `strace` 能记录这些调用。停止旧实例后执行：

```bash
strace -tt -T -o syscalls.log \
  -e trace=network,read,write,close,select,pselect6,clock_nanosleep \
  ./observe_linux
```

在另一终端运行：

```bash
python3 ./probe.py no-newline
```

完成后停止服务端，查看：

```bash
tail -n 60 syscalls.log
```

`-tt` 显示时间；`-T` 显示调用耗时；`-o` 写文件；`-e trace=...` 限定调用范围。库函数可能映射成其他系统调用：C 的 `recv()` 常显示为 `recvfrom`，`select()` 可能显示为 `pselect6`；看到名称不同不等于代码没执行。

观察顺序应接近：`accept` 返回 → 读取若干字节 → 继续等待 → 等待返回超时 → `close` 关闭。也可用更简洁的完整记录方式：

```bash
strace -tt -T -o syscalls-all.log ./observe_linux
```

完整记录还会包含加载库、输出日志等无关细节，文件更大。`strace` 会改变时序并可能输出数据内容，应只在受控实验里使用，不能把它的运行耗时直接当成未观测时的基准性能。

Windows 没有原生 Linux `strace` 这套调用接口；WSL 的 `strace` 用于 WSL 内的 Linux 进程。Windows 入门先用日志、GDB、端口工具和 Wireshark；以后再按需求学习 Visual Studio 调试器、ETW 等平台工具。

## 12. 日志与监控的工程实践

### 12.1 为什么重定向后“日志不见了”

标准输出是程序默认向外输出文字的通道，标准错误通常用于错误提示。C 标准库会**缓冲**输出：先留在内存，之后再批量写出，重定向到文件时尤其容易看到延后出现。

本章使用：

```c
setvbuf(stdout, NULL, _IONBF, 0);
```

这行在首次输出前关闭标准输出的 C 库缓冲，便于实验实时看到日志。也可以对关键事件 `fflush(stdout)`，但每条都刷新会增加开销。

**刷新到操作系统不等于断电后一定还在磁盘上。**文件系统也有缓存，应用崩溃、强制结束、磁盘满和采集故障都可能造成丢失。需要持久性保证时，必须专门设计并测试，不是多写一个 `fflush()` 就够了。

### 12.2 Windows：按连接、结果和指标查询

在保存了 `server-windows.log` 的 PowerShell 中：

```powershell
# 查一个连接。边界匹配避免把 conn_id=1 误匹配为 10、11。
Select-String -Path .\server-windows.log -Pattern '(^| )conn_id=1( |$)'

# 查警告、错误
Select-String -Path .\server-windows.log -Pattern 'level=(WARN|ERROR)( |$)'

# 查看最近一条指标快照
Select-String -Path .\server-windows.log -Pattern 'event=metrics( |$)' |
    Select-Object -Last 1

# 根据最终归类统计结果，避免同一失败的多条事件被重复计数
Get-Content .\server-windows.log |
    Where-Object { $_ -match 'event=connection_closed( |$)' } |
    ForEach-Object {
        if ($_ -match '(?:^| )result=([^ ]+)') { $Matches[1] }
    } |
    Group-Object |
    Select-Object Name,Count
```

**不要统计日志中出现 `timeout` 这个词的行数当作超时次数。**一条超时连接可能同时有等待事件、关闭事件、指标快照，按行数会重复或遗漏。应读取明确计数器，或每连接唯一的最终结果事件。

### 12.3 Linux：按连接、结果和指标查询

```bash
# 用空格/行边界避免编号前缀误匹配
grep -E '(^| )conn_id=1( |$)' server-linux.log

grep -E 'level=(WARN|ERROR)( |$)' server-linux.log

grep -E 'event=metrics( |$)' server-linux.log | tail -n 1

# 按最终关闭事件统计结果
awk '
  /event=connection_closed( |$)/ {
    for (i = 1; i <= NF; i++) {
      if ($i ~ /^result=/) {
        split($i, a, "="); count[a[2]]++
      }
    }
  }
  END { for (k in count) print k, count[k] }
' server-linux.log
```

`grep` 过滤文本，`awk` 逐行处理字段。这里只因为日志值不带空格，才可以如此解析；任意 JSON 或包含转义的日志不应简单按空格拆分。

### 12.4 日志文件不能无限增长

**轮转**表示在文件达到某个时间或大小后，切换到新文件，并按保留策略删除或归档旧文件。

入门时就应知道：

- 设置单文件大小、保留天数、总容量和磁盘空间告警。
- DEBUG 默认关闭或限时开启；重复错误可限速或汇总，但要明确记录被压缩/丢弃的数量。
- 多线程日志可能交错，计数器也可能数据竞争；不能把本例直接复制成无锁并发版本。
- 同步写盘会拖慢请求；异步日志通过队列减少等待，但要定义队列满时阻塞、丢弃还是降级，并观察丢弃数。
- 不要在程序还持有输出句柄时简单改名就认为它会自动写新文件。Linux 进程可能继续写旧 inode；Windows 文件共享规则也可能阻止操作。
- 本章通过 Shell 重定向，程序本身没有重开日志文件的能力。可由服务管理器或采集器负责日志生命周期；要使用 `logrotate` 等工具，还需匹配应用重开文件的方式。`copytruncate` 存在复制与截断间丢失日志的窗口，不能宣称无损。
- 日志写入失败时应有备用错误路径与告警，避免“记录错误又产生错误”的递归刷屏。

### 12.5 从本地快照到监控平台

理解本章之后，再学习下面的工作分工：

```text
应用代码记录事件 → 标准输出/文件 → 日志采集器 → 可检索日志存储
应用暴露指标   → 周期采集/上报 → 时序数据库 → 图表与告警规则
```

**时序数据库**专门保存“某指标在某时刻的数值”。Prometheus 常用来周期拉取指标；Grafana 常用来展示图表；OpenTelemetry 提供遥测数据的标准化采集与传播方式。它们不是本章 C 程序中已经包含的功能。

第一个仪表盘只需几张图：完成速率、按原因拆分的失败率、活动连接、延迟分布、CPU/内存、指标上报存活。先验证口径，再追求漂亮图表。

**服务目标（SLO）**可理解成“希望达到的可用性或延迟目标”，例如某类请求在规定窗口内有多少比例能按时正确完成。告警应与用户影响关联，并包含程序、实例、窗口、阈值、当前值和排查入口。不要把教学示例的 `ok_total` 直接当成业务可用性指标。

### 12.6 追踪的最小理解：同一请求跨服务怎样串起来

假设客户端请求 A 服务，A 又调用 B 服务：

```text
trace_id=T1
  span=A处理：40ms
    span=B调用：30ms
```

**trace** 是整个请求过程；**span** 是其中一段操作记录，通常有开始、结束、状态和父子关系。`trace_id` 串联全程，`span_id` 区分各段。

如果 A 的日志有编号、B 的日志没有接收和传播同一个追踪上下文，就无法自动关联。日志可加入追踪编号帮助从指标跳转到具体请求，但不要把每个追踪编号作为监控指标标签。跨服务总耗时也不能把父 span 与子 span 直接相加，子操作已经包含在父操作的时间区间里。

本章单服务的 `conn_id + request_id` 是理解关联的起点，不是完整的分布式追踪实现。请求重试与幂等性继续看 [[心跳、超时与重连]] 和 [[简易RPC项目]]。

## 13. 常见错误与故障排查手册

### 13.1 常见现象对照

| 现象或错误做法 | 常见原因 | 如何验证与处理 |
| --- | --- | --- |
| `gcc`、`python` 找不到 | 未安装或 PATH 未配置 | 先完成环境章节；Windows 可检查 `Get-Command gcc,python`，Linux 用 `command -v gcc python3` |
| 找不到 `winsock2.h` | 编译器不是 Windows 原生工具链 | Windows 用 MinGW-w64；Linux 复制 Linux 版本 |
| `undefined reference to WSAStartup` | 忘记链接 Winsock | 使用完整 Windows 命令并保留末尾 `-lws2_32` |
| Linux 出现 `WSAGetLastError` 相关错误 | 混用了两平台源码 | 分别保存完整源文件，不混拼 |
| 启动后只显示 `listening` | 正在正常等待连接 | 运行客户端；不要把没有流量当卡死 |
| `bind_failed` | 端口被占用，或重启遇到旧状态 | 查监听进程、核对参数、处理自己启动的旧实例 |
| 客户端连接被拒绝 | 未监听、地址端口错误、主动拒绝 | 对照客户端参数和目标机监听，必要时抓握手包 |
| 连接成功却无响应 | 缺少 LF、非法输入、处理慢、客户端解析错误 | 先看 `request_received` 是否出现，再沿时间线定位 |
| 明明发了数据却 `frames_total` 不增 | 没有完整 LF，或超长先被拒绝 | 检查实际字节与边界，不以“发送次数”算帧 |
| 正常响应耗时显示 `0` | 毫秒级计时下不足一个刻度 | 不是无耗时；用慢模式或更高分辨率时钟练习 |
| 所有失败都 `code=0` | 没记录系统错误，或本来就是应用超时/格式错误 | 检查立即保存错误码的位置，并结合 `event/result` |
| 日志显示成功，客户端超时 | 成功定义不同、客户端已放弃 | 核对总预算与本地发送完成语义，不强行合并结论 |
| 抓不到本机包 | 选错接口或起抓太晚 | 回环选 Npcap loopback / Linux `lo`，先抓再请求 |
| 抓包行数比请求数多 | 握手、ACK、关闭、拆分与重传 | 按流重组，不按数据包数量算请求 |
| 统计的超时次数翻倍 | 按包含关键词的日志行计数 | 读取 `timeout_total` 或唯一关闭结果 |
| `active_connections` 一直涨 | 清理/计数路径遗漏，或连接真的滞留 | 对照接入与关闭事件、句柄数、当前连接，不只看一个指标 |
| `TIME-WAIT` 比较多 | 频繁建立并关闭连接 | 不一定泄漏；查长期趋势、资源上限与业务连接策略 |
| 开启 DEBUG 后延迟飙升 | 输出频繁、格式化或写盘太慢 | 比较关闭/开启日志的受控基线，设计限量与异步策略 |
| 调试时客户端总超时 | 断点暂停造成的时序变化 | 把断点实验和正常运行分开，不据此直接判网络故障 |
| 重启后速率出现负数 | 累计指标清零 | 按实例和启动周期识别重置，不能直接作差 |

### 13.2 一张能照着执行的排查清单

假设收到“客户端没有得到 PONG”的报告：

1. 记录完整客户端命令、发生时间和时区、错误类型、请求编号。先区分“建连失败”和“连接成功但等待响应失败”。
2. 在服务端核对启动日志、PID、监听地址端口；确认不是运行旧可执行文件。
3. 用端口工具验证监听归属。需要探测时，记录探测会额外产生连接。
4. 在日志中找对应连接。没有接入记录时，查目标环境、抓包、日志过滤与进程；不要直接归因业务解析。
5. 有接入但没有 `request_received`：查读取超时、EOF、非法输入、缺少 LF、超长帧。
6. 有合法请求但迟迟没有 `response_sent`：查慢模式、处理函数、写等待与发送错误。必要时用断点或系统调用观察。
7. 有 `response_sent` 但客户端失败：查客户端预算、收包逻辑、响应编号和消息边界；必要时看两端抓包。
8. 核对最终归类与计数器，保存关键证据、最小复现和恢复方式。修复后重跑正常基线和原故障用例。

**停止猜测的标准：**每个结论都能指出支持它的日志、返回值、时间区间或数据包。暂时没有证据的说法保留为“假设”，不要写成根因。

### 13.3 最小复盘格式

```text
问题：什么用户动作触发了什么可见失败？
影响：哪些请求、多少比例、持续多久？
时间线：统一注明时区，列出关键事件和编号。
事实：日志、指标、抓包各观察到了什么？
根因：哪条证据链排除了其他解释？
恢复：做了什么，如何确认恢复？
修复：代码或配置怎样避免再次出现？
验证：重现用例、正常用例是否都通过？
剩余问题：尚未验证的假设和后续负责人/动作。
```

## 14. 练习题：从会看日志到独立排错

先做题，再打开后面的参考思路。练习代码只在实验目录修改，保留原始版本方便对比。

### 14.1 基础概念题

1. `pid`、Socket 句柄、`conn_id`、`request_id` 分别解决什么问题？它们跨重启是否一定唯一？
2. 为什么 `recv()` 返回 `0` 与非阻塞 `EAGAIN` 不能放进同一个“重试”分支？
3. 为什么应先保存 `errno`/`WSAGetLastError()`，再记录详细日志？
4. UTC 时间和单调时钟分别用于什么？为什么客户端和服务端时间不能随便相减？
5. `send()` 完整发送、TCP ACK、业务成功分别能证明到哪一层？
6. 为什么不应把完整用户输入直接作为日志格式字符串，或直接当 `%s` 打印？
7. 为什么日志事件与指标都需要明确口径？“错误日志有 20 行”为什么不等于“20 次请求失败”？
8. 为什么 `request_id` 通常适合放日志，不适合做每条指标的标签？

### 14.2 数值题

1. 30 秒窗口内 `closed_total` 从 200 变到 350，`timeout_total` 从 4 变到 10。完成速率和超时占比各是多少？忽略重启，分母采用已关闭连接。
2. 一次快照中 `accepted_total=12`、`closed_total=10`，活动连接应该是多少？若实际记录为 5，你会怀疑什么？
3. 耗时排序为 `[2, 3, 3, 4, 4, 5, 6, 7, 8, 200]`，用最近秩法计算平均值、P95；平均值能完整描述体验吗？
4. 一次新进程的 `PING 17\n` 正常实验，应分别增加多少应用接收字节、发送字节、完整帧、成功数？
5. 两个采样点间发生重启，累计完成数从 1000 变成 30，能否直接算出吞吐？还需要什么信息？

### 14.3 必做操作题

1. 选择 Windows 或 Linux，完成编译与普通请求；截取同一 `conn_id` 的日志，解释每行。
2. 运行 `split`，证明“应用层一次发送”和“完整消息”不是同一概念。不要用 TCP 段数量作为唯一证据。
3. 运行 `no-newline`，记录客户端现象、服务端超时、持续时间和最终结果。
4. 运行 `eof`，与上题比较。写清“是谁读到 EOF”，不要混淆客户端与服务端。
5. 从全新进程执行八项实验，用指标检查两个守恒关系，并解释 `frames_total` 为什么是 4。
6. 以 `slow` 模式运行，把客户端预算改成 0.2 秒；记录两端结果并解释为什么可能不同。
7. 用端口工具找到 PID；用 Wireshark 或 tcpdump 保存一次自己的回环实验。
8. 在 `parse_request` 设断点，观察 `PING 41\n` 的 8 个字节，核对最后一个是 `0x0a`。

### 14.4 小改造题

1. **补齐日志上下文：**在接入时记录对端地址端口，并在启动时打印本地监听地址、端口、程序版本。用 `accept()` 的地址参数或 `getpeername()` 获取端点；Windows/Linux 地址长度参数类型不同，分别查看平台文档。
2. **拆开延迟：**记录“等完整帧”“业务处理”“发送响应”三个耗时，说明它们与连接总耗时、客户端总耗时的关系。
3. **统计失败样本：**保留现有成功延迟指标，再按有限结果类型统计失败连接耗时。明确样本数，避免把成功/失败混成一个不解释的平均值。
4. **增加 DEBUG 开关：**通过启动参数决定是否输出每次读写的字节数；不要输出原始口令或任意输入，比较开启前后的影响。
5. **严格 CRLF 策略：**如果决定支持 `\r\n`，明确协议、解析和长度检查要如何一起变化，并增加测试，不能仅“忽略所有回车”。
6. **统一最终结果：**让 `connection_closed` 在有合法请求编号时保留它。先设计返回结构，避免为了日志引入不安全的全局“当前请求编号”。

- 定位问题后给出最小复现、恢复步骤、再次运行的验证结果。

<summary>参考答案与思路（做完再展开）</summary>

**基础题要点：**

1. PID 对应进程；Socket 句柄对应操作系统资源；连接编号关联一次连接；请求编号关联一次应用请求。PID、句柄可能复用，本章自增编号只在进程内有效，客户端请求编号也可能重复。
2. EOF 表示发送方向结束，重试读取通常仍是 EOF；暂时不可用表示以后可能有数据，应该等就绪。把 EOF 无限重试会忙循环或资源滞留。
3. 后续调用可能影响错误状态，保存原始错误码才能解释原失败点。成功调用后不能用陈旧错误码判断失败。
4. UTC 便于事件时间关联；单调时钟适合计算本机间隔。多机有时钟偏差，且网络与排队的观察区间也不同。
5. 本地网络栈接受字节、远端 TCP 栈确认字节、应用完成业务，是三种不同证据。
6. 格式串注入、无结束符越界读取、控制字符伪造日志、敏感数据泄露，都可能发生。
7. 同一失败可以有多条日志；应统计唯一结果或定义清楚的计数器。指标没有窗口和分母也无法解释。
8. 请求编号组合过多，容易制造大量时间序列；日志更适合保存明细。

**数值题：**

1. `(350-200)/30=5` 次/秒；`(10-4)/(350-200)=4%`。
2. 应为 2。若为 5，检查是否漏减、重复加、跨实例混读、采样非一致，或并发统计没有同步。本例单线程快照应一致。
3. 总和 242，平均 `24.2ms`；最近秩 `ceil(0.95×10)=10`，P95 为 `200ms`。平均值不能同时代表多数短请求和少数长尾，小样本 P95 本身也不稳定。
4. `PING 17\n` 与 `PONG 17\n` 各 8 字节；接收/发送各 +8，帧 +1，成功 +1，关闭 +1。
5. 不能直接作差。需要启动标识、重启时刻和更细采样，或使用能识别计数器重置的监控方法；仅凭两个值无法恢复重启前窗口内遗漏的完成数。

**操作题判定：**

- `split` 最终仍匹配正确 `PONG`；说明服务端按 LF 收齐，而不是按 `recv()` 次数判定请求。
- 缺 LF 时服务端归类为读取超时；客户端可能因服务端关闭看到 EOF，并不矛盾。
- 提前半关闭时服务端很快读到 EOF，通常不必等 3 秒。
- 八项实验守恒值见第 10.4 节。若夹杂探针或其他请求，应先剔清额外连接再比较。
- 慢模式下客户端先放弃，服务端本地发送可能成功；“两端结果不一致”应解释观察边界，不应删除任何一端的日志。
- 端口证据证明监听归属；抓包证明观察点上的 TCP 交互；断点证明某时刻的代码与变量，它们互相补充。
